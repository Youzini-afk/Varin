### D-291 · 2026-09-19 · research profile / AI4S

类型：默认值调整

背景：原 research profile 草案把文献、PDF、引用、notebook 和 `paper/claim/citation/experiment` 节点放在产品中心，并采用分钟级、人在环、带检查点的半自主研究。这会把科研做成资料和记录管理，忽略问题发现、综合思考、快速实践和并行探索。用户明确提出由强模型做问题发现与综合、较强模型做实验设计、快速模型做实现和监查，并通过子线程形成研究集群。

决定：

1. Piarium AI4S 的产品中心是“异构模型科研集群”：一条首席研究主线持续推进整体问题，多个 Thread 代表独立研究分支，Run 冻结当次模型、工具、权限、范围、输入和工作状态。
2. 模型按能力路由而非固定型号或永久职业：`frontier-reasoning` 负责问题发现和综合，`deep-design` 负责深读与实验设计，`high-throughput-execution` / `fast-exploration` 负责实现、批量分析和局部变体，`critical-review` 与 `scientific-writing` 按影响和缺口触发。分支可动态升级、降级和换模型；快速模型也可以参与假设和反例生成。
3. 研究循环是动态分叉、低成本区分、真实执行、事件触发综合和下一轮重分配。Host 调度器负责模型/CPU/GPU/数据资源，首席模型负责科学方向和投入优先级；普通批处理、进程监控和日志整理不启动 Agent。
4. 线程树只表示执行责任、生命周期和资源归属。研究发现通过引用和定向消息跨分支复用，不再建设一套与 Thread 树平行的强制研究图。分支交接由 Host 自动生成新发现、影响、依据、替代解释和下一步，不要求用户填写表单。
5. 证据、版本、运行、产物和可复现信息是集群的内部事实基础，不是用户的前置流程。研究状态是可重建视图；来源、运行结果和文件修订保留原始权威。证据表、实验协议、Research Diff 和文章结构按需生成。
6. 写作线从研究中途参与，持续发现主张缺口并回流新的检索或实验任务。首个纵切选择开放的计算研究问题，验证“并行问题发现 → 实验设计 → 快速执行 → 强模型综合 → 下一轮”的研究推进闭环；论文复现只是一个场景，不定义整个 Profile。
7. 通用内核只提供研究动作、分支、调度、来源、运行和产物接缝；领域 Profile 通过材料连接器、工具、模拟器、指标、验证器和写作模板扩展。第一阶段从代码、数据和计算实验开始，不预建全领域数据库、实验室系统、自有基础模型或第二套 Agent runtime。

原因：科学价值来自减少未知和形成可行动的新理解，而不是记录数量。把强模型固定为主管、快模型固定为工人会浪费模型能力；把所有实验一次性展开会制造重复和资源浪费；把严谨性放在用户流程前面会形成科研管理表单。现有 Thread/Run、WorkingState、检索、上下文、权限和 Rust kernel 已经提供了实现集群的基础，不应再造平行生命周期。

考虑过的替代：

- 固定“强模型思考 → 中模型设计 → 快模型执行”的流水线：不采用，研究分支需要按结果动态升级，快速模型也能提供局部假设和反例。
- 先建设论文/证据/实验数据库和完整科研工作流：不采用，结构应从实际研究循环中自动生成，避免把研究者变成记录维护者。
- 一次性展开假设×方法×条件的完整矩阵：不采用，先用低成本区分行动动态分配资源，保留独特但早期信号弱的路线。
- 为科研再建一个 Agent runtime、工作图或存储后端：不采用，复用 Pi、Thread/Run、Host 和 Rust kernel；研究关系通过引用和现有结果交付表达。
- 普通运行也持续唤醒模型监查：不采用，进程事件和指标由程序处理，异常、冲突和关键结果才触发模型。

影响：新增 [research-cluster-design.md](../design/research-cluster-design.md)；更新 `agent-harness.md` 的 research profile、`agent-harness-plan.md` 的后续领域顺序、`roadmap.md` 的 research 条目与 `status.md` 的未接线说明。后续实现使用现有 `dispatch` / `send` / `wait` / `read_thread` / WorkingState / Rust kernel 接缝；本条不宣称任何生产代码已接线。

状态：已接受设计；待实施。

### D-297 · 2026-09-19 · 工作台 UIUX 与 Agent 工作侧重独立

类型：产品交互与执行配置边界

背景：D-291 的 research Profile 同时被用于描述研究行为和界面，实施计划没有明确入口与切换语义。
讨论中曾提出把科研与 Agent/IDE 作为绑定执行行为的互斥模式、为左侧增加独立“研究”入口，或由项目选择科研界面。
这些形式会把 UIUX 与任务混在一起，使切入 IDE、浏览项目或打开对话改变研究环境。用户明确要求：在现有 Agent/IDE
切换区域增加整体工作台入口，播放既有切换动画；项目和对话另行选择影响提示词与工具组织的工作侧重，未来办公同样适用。

决定：

1. **工作台 UIUX 与工作侧重有不同身份。** Workbench Profile 管理完整 Shell、导航、布局、操作与动画；
   Agent Profile 的用户可见名称为“工作侧重”，管理提示词、默认激活能力、工具组织、上下文和协作方式。
   不再用未限定的 research Profile 同时指代两者。
2. **入口位于现有 Agent/IDE 切换区域。** 科研与未来办公复用现有工作台、贡献点、Transition Scene 与选择事务，
   不放进项目选择菜单，不另建研究中心或平行会话库。用户主动切换整套 UIUX；打开项目/对话、改变侧重不自动切 Shell。
   7A 调整当前 workspace 优先的所选 Profile 解析，项目仍可保留面板/编辑器布局，不能覆盖当前工作台。
3. **新对话捕获默认，已有对话独立。** 对话显式选择优先，其次是创建时的项目默认，最后沿用现有通用/编程默认。
   工作台类型不参与解析；项目默认改变不回写已有对话。对话显示当前侧重及待应用选择，允许手动覆盖。
4. **配置切换与执行生命周期分开。** 对话侧重变更从下一轮用户请求沿 Run/worker 安全切点应用；在途 Run 与已派发分支
   保持冻结配置，新配置失败保留原配置。切 UIUX 不应用 Agent 配置、不调用模型、不派发任务；切侧重不删除成果或隐式取消分支。
5. **跨组合保持可用。** IDE 是完整开发环境，能够继续科研任务；科研工作台能够处理普通编程对话，办公工作台与侧重
   后续沿同一边界发展。工具调用不以科研 Shell 挂载为前置，研究界面只消费实际 Thread/Run/Artifact，不为填充面板生成任务。
6. **复用既有权威。** 工作台、项目设置、会话配置、Run、Documents、编辑器、进程和对象各守原责任；研究主线在切换后
   继续使用同一身份和成果。7A 交付独立入口、基础科研工作台与根主线，7B–7E 逐步接入分支、实验、综合和写作视图，
   不以办公完整实现或新的通用 Profile 框架为前置。

原因：科研同时需要讨论、检索、计算、编码和写作。让用户选择适合当前操作的 UIUX，并另行指定 Agent 工作方式，
才能在同一项目和同一任务中使用这些能力；界面导航不应成为修改执行配置的隐式动作。

影响：[research-cluster-design.md](../design/research-cluster-design.md) 第 10 节；[agent-harness.md](../design/agent-harness.md)
第 10 节；[agent-harness-plan.md](../plan/agent-harness-plan.md) 阶段 7；[composable-workbench.md](../design/composable-workbench.md)
选择语义；architecture、roadmap、status 与决策索引。D-291 正文保留；本条补齐其产品形态与独立绑定。

状态：设计已在 D-298 的 7A 中实现；异构能力路由、调度、实验和写作仍按 7B–7F 继续实施。

### D-298 · 2026-09-19 · AI4S 7A：独立工作台与真实研究主线

类型：产品入口与执行身份

决定：

1. 增加第一方 `piarium.research` Shell，复用已有 Profile 切换事务、动画和共享窗口/导航/资源框架。
   删除 workspace Profile selection 的持久字段与写者，项目只保留布局。科研展示从既有 Thread 投影读取主线与分支，
   不从原生 Pi session 的 fork 关系猜测科研分支，不为展示而创建任务。
2. 工作侧重使用独立的 `code`/`research` 执行配置。项目条目保存新对话默认，broker 的 session metadata 保存
   创建时捕获的来源及 selected/active/generation。运行中只修改待应用选择；新 Run 启动前 stage worker、提交
   durable metadata 再发布，失败保留原 active。当前 Run 的 steer/followUp 属于同一次执行，保持其冻结侧重。
3. 科研主线直接使用用户当前 Pi 会话与模型。实际 agent_start 附着一个 `purpose: research-root` Thread 与新 Run，
   实际 settle 写报告和原文引用；不会额外启动主模型会话。普通分支仍使用原 ThreadRuntime 和原生 Pi 子会话。
4. Run/session binding 显式区分 `attached-root` 与 `spawned-child`。主线结束解绑不留子会话 tombstone，lost 不自动
   作为子任务重启，删除 Thread 不删其附着的用户会话；主会话删除仍沿其自己的 broker 生命周期处理。
   用户在主线运行中或结束后均能以 user 身份操作其研究分支。
5. 本阶段保持现有模型选择和工具授权。异构 capability 路由、研究更新与调度、实验/产物组织、综合写作和质量验证
   按 7B–7F 实施。通用侧重仍可使用已有工具；科研侧重不扩大权限，不限制在科研 Shell 内执行。

持久格式：Thread catalog 使用 schema 10，session-binding 索引使用 schema 2；不引入旧内部格式迁移或双写。
原生 Pi JSONL、用户工作区文件与项目资产不改写。工作台选择与 session work focus 各守既有权威。

状态：7A 已实现并接线；本地验证与未实测边界见 [status](../status.md)。7B–7F 未宣称交付。

### D-299 · 2026-09-19 · AI4S 7B 第一段：能力路由与冻结分支

类型：研究分支执行配置

决定：

1. `thread.dispatch` 可声明 `investigation`、`experimental-design`、`fast-exploration` 或
   `high-throughput-execution`。每种能力有独立模型槽位、工具集合、系统提示片段和默认资源请求；
   用户可在 dispatch 时补充 CPU/GPU/network/long-running 请求。
2. 能力槽位未配置时，dispatch 返回 `unavailable`，不静默使用主模型。能力分支只能从科研工作侧重的主线派出，
   工具仍受父 Run 冻结 allowlist 约束。分支的 `research` manifest 进入 Thread/Run durable projection，资源请求暂时只冻结记录，
   不在本段偷偷实现调度器。
3. 能力分支沿既有 WorkingState/Thread/Run 和 Pi 子会话执行；隔离执行能力使用 isolated WorkingState，
   调查/设计/快速探索默认只读。7B 后续再接动态模型升级、同 Thread 新 Run、资源等待和结果交接。

原因：先让不同能力真正进入已有 Thread/Run 生命周期，才能在同一权限、工作状态和恢复边界内观察并行研究；
预先建设一套独立的研究调度平台会把能力声明和实际执行再次分离。

状态：7B 第一段已实现并接线；完整 7B 及 7C–7F 仍为后续阶段。

### D-300 · 2026-09-19 · 实验执行、远程资源与通用多 Agent 自然交流

类型：设计修订，待实施

背景：7D 仅以本地 batch adapter 描述科研执行，没有回答远端监督、断连恢复、资源争用、机器选择和模型如何渐进使用。
7E 又以结构化 ResearchUpdate 和 Host 事件分类触发强模型综合，容易把交流变成填表，并频繁消耗强模型。
用户要求完善真实实验现场管理，同时强化整个 Harness 的父子/同伴交流；集群现状由程序从已有输出形成，不让 Agent 另行发布近况。

决定：

1. **实验规格、attempt、后端作业、资源分配与产物分开。** Agent Run 可管理多个实验尝试，模型等待不停止计算。
   Host 负责编排与授权，持久记录复用 Rust typed catalog，实际进程由既有 Rust 核心监督。提交固定代码/输入/环境/参数，
   使用稳定身份恢复；重试、检查点恢复和新配置重跑保留各自来历。
2. **7D 覆盖本机、受管远程与首个原生集群后端。** SSH 用于接入、部署/隧道和排查，远端受管组件或已有 Host 持续监督作业。
   原生集群首先接 Slurm，allocation/队列/抢占以其事实为准；Kubernetes/Ray 按实际需求后续接入。
   普通 SSH 命令能力如实显示，不以连接存活冒充作业权威；不另建 TS 进程服务或第二套 Agent runtime。
3. **资源工具呈现容量、分配、用量、来源与新鲜度。** CPU/GPU、显存、数据位置和外部作业分别考虑。
   同一目标的资源由唯一管理方确认，跨根共享事实；暂时低利用率不等于可分配，断连后先对账再释放/重派。
   共享机器不能假称对外部进程有独占保证，用户/部署已有公平性与优先级继续生效，不凭猜测增加配额或抢占。
4. **资源协调 Agent 可选。** 主线或普通协调 Thread 可讨论研究优先级、机器和费用取舍，实际动作仍走相同资源/权限工具。
   系统不依赖常驻管理模型；普通作业、日志、指标、参数矩阵与排队由程序处理，不为每个 seed 派 Agent。
5. **实验工具渐进披露。** 初始只暴露启动、查看、等待、控制与资源概览，详细配置、日志、指标和产物按 job/attempt 展开。
   远端操作绑定实际目标与路径；暂停/恢复/检查点/扩容按真实后端能力提供。取消请求、停止事实、连接状态与收集失败分开，
   不重复启动响应丢失的作业，不因等待超时释放仍运行的资源，大产物保留责任可追溯。
6. **7E 是通用协作增强。** 沿现有 `send` / `wait` / `threads` / `read_thread` 支持父子和授权同组分支直接交流，
   Thread 树继续管理责任与生命周期。消息自由表达，不要求 finding/impact/alternativeExplanations/nextActions 或研究分类。
   Host 保留耐久身份、幂等、关联与授权；发消息不授予对方全文、文件或控制权限。
7. **发送可选择等待。** 目标交互为 `send(to, message, wait=0)`，0 立即回执，正值表示最多等待的秒数；
   回复到达即返回，超时不取消消息/对方工作，后续用同一回执等待或读取。不等待仍允许目标处理问题。
   正常答复沿实际收件上下文关联，多问题时可用简短引用，不拿任意新输出匹配答复。
   等待让出模型名额且不锁住收件；归档/删除状态不隐式复活，重连不重复执行，系统不自动回复确认形成循环。
8. **持续现状由程序摘取原文。** 表只保留线程、任务、状态、进展；任务/状态来自真实记录，进展取该 Agent 最后一段已完成的可见输出，
   约 20 个可见字符加省略号。这是预览默认，不是内容限制；不读隐藏推理，不要求状态工具/定期汇报，不调用总结模型。
   新消息和新结果归入同一进展列并标记来源。摘录绑定 Thread/Run、原文 entry/block、修订与时间，可逐层展开到显示时的原文。
9. **现状贯穿工作过程。** 从已有输出事件维护投影，在实际模型请求前给初始短表或变化行，覆盖工具续接与等待返回，
   不只在初始化注入。Zone 2 追加变化并保留旧前缀；仅准备不确认观察，UI/Agent 游标独立，压缩/fresh 按原文收据补必要状态。
   大团队可按关系和关注范围渐进展开，不能固定截断后假装全貌。查看线程不会唤醒它。
10. **研究判断由交流推动。** Host 不把产物、异常或冲突事件机械映射为强模型调用。用户/Agent 的明确消息或已建立等待驱动续接，
    Agent 读取材料后决定是否综合、复核、派发下一步。研究备忘录和文章按需产生，不维护强制 ResearchBoard 或 writing-gap 交接协议。

原因：科研需要大量并行行动，也需要模型自由地互相讨论和改变方向。把真实执行交给程序、把含义交给模型、
把现状变成已有文字的可展开入口，既减少额外调用和注意力消耗，也保留灵活的研究推进能力。

考虑过的替代：要求每个 Agent 定期发布近况，会打断原任务；用独立模型总结所有线程，会增加成本与延迟；
Host 根据事件类别自动叫首席，会混淆运行事实与科学价值；只包装本机 bash，再补远程资源，会留下不一致的生命周期。
这些均不作为默认方案。资源协调 Thread 仍可按具体任务需要派发，不禁止有实际用途的协作方式。

影响：本条部分取代 D-291 的强制交接格式、共同维护研究板及自动事件综合设计；D-285 的已交付消息账本与生命周期保留，
其公开 inform/request 选择将按本条的自然交流/可选等待目标改造。旧条目正文不改，当前代码未随本决策改动。

### D-301 · 2026-09-19 · 7G：环境增量留史与每请求完整团队快照

类型：设计修订 / 后续阶段

决定：在当前 D-300 执行任务完成后，验收时一并提出并接续实施独立 7G；传统 Zone 2 按每请求前检查的环境增量留史，
每个授权 Agent 的完整当前线程短表作为当次请求的临时尾部，固定协作说明放在稳定系统提示。

原因：持续现状用于让各 Agent 知道彼此在推进什么并自然发起交流，并非子向主汇报。仅推完成/失败通知或要求主动查询，
会失去这种持续感知。逐段追加所有进展又会使历史膨胀；原地改写历史表会破坏后面的前缀缓存。尾部临时完整快照能保住
不断增长的真实历史前缀，代价是每次处理一张短表；不能将缓存命中等同于不占上下文或附页零成本。

具体契约：

1. **一处实际请求前准备。** 初次输入、工具续接、等待恢复、消息唤醒和压缩/fresh 都经过同一准备边界。
   原 `before_agent_start` 环境入口扩展并消除重复；状态变化本身不发起模型调用。
2. **环境事实增量留史。** 用户编辑/终端、新诊断、Git/计划修改、新知识指针和实质消息/结果沿原有来源与交付权威，
   未送达内容在完整历史/工具结果后追加，送达后保留为可重放消息。无变化不加空块，不重写旧事实，不每次全量召回知识。
3. **团队快照每请求完整提供。** 表在环境增量之后，只属于当次请求；无变化也保留，旧表不写入后续对话历史。
   完整指当前授权/所选范围，范围和未展开入口明确；不只给变化行并假定模型拥有已从输入消失的基线。
4. **通用协作语义保持。** 每个有授权的线程均可消费，父子和同组线程可以相互交流；不要求主线转发。
   四列、最后一段已完成可见输出、约 20 字预览和原文引用沿 D-300，不添加定期汇报、隐藏推理读取或总结模型。
5. **角色与权限分开。** 稳定系统提示说明协作用途和查看/通信入口；动态材料默认映射为来源明确的 `user` 内容。
   内部区分真人消息、Host 观察、团队快照和定向消息；摘录不会因此得到用户/系统权限。不伪造 assistant 或工具调用结果，
   遵守 provider 工具配对和允许的续接位置。真实工具仍返回正常工具结果。
6. **前缀和容量诚实。** 历史固定、仅增长，快照在增长后的末尾生成；实际请求预算包含快照与待追加环境事实。
   检查 provider 序列化前缀和真实用量，不能用内部字符串或局部 mock 宣称实际缓存收益。位置效应不是统一的注意力定律，
   通过简短表、明确来源与真实工作观察判断是否影响任务，不添加机械注意力评分或每轮任务重述。
7. **不同交付语义。** 环境事件只在实际送入模型后确认，准备/过滤/失败不算已读，重试不重复追加；快照不依赖已读游标。
   压缩/fresh 后环境基线按原文收据恢复，表重新读当前事实，不能伪造快照 Pi entry/保留收据。UI 和各 Agent 观察独立，
   普通状态不在两个通道重复，消息/结果正文不被表中短标记消费。空团队与查询失败分别表达。

考虑过的替代：把旧表从中间移动/替换会破坏后续缓存；把所有状态追加进历史会累积大量旧表；临时尾部只发 delta 会丢基线；
只发完成/失败通知或只让主 Agent 了解全局会改变协作需求；动态 system/developer 或伪造 assistant/tool 会混淆资料来源。
这些不作为最终方案。环境增量与短表的作用不同，不要求它们采用同一种保留方式。

影响：部分取代 D-300 第 9 项“首次短表/后续变化行”的后续目标；D-300 其余通信、原文投影、实验执行与资源设计保持。
同步 Harness 8.1.1/9.3.7、科研集群设计 7.4、plan 7.8/7G、architecture、roadmap、status 与决策索引。
当前执行任务仍按已收到的 prompt 完成；验收先核对原交付，再下达 7G，不用后加要求倒推原任务失败，不把在途代码当作交付证据。

状态：设计已接受 / 排在当前执行任务之后 / 尚未实施和验收。本次只改文档，无运行时或缓存收益验证结论。

### D-303 · 2026-09-20 · D-300 本机实验与协作纵切验收返工

类型：验收纠正 / 生产实现修复

决定：保留已交付代码，在实际生产链修复实验规格身份、固定输入、资源预留、恢复与产物消费，以及新 Run/消息/原文的身份问题。
不能以辅助队列测试或报告中的测试总数代替行为验收；完整 7D/7F 仍按原计划定义，7G/7H 是之后的独立任务。

原因：原交付遗漏了会改变结果的反例，包括排序参数导致规格串用、spec 复用绕过资源请求、多个工作区重复预留同一机器、
排队实验读取 live 目录/输出相互污染、后台状态不确定时错误终结、日志/产物未完整交付、SSE 发错通道、跨会话刷新覆盖，
以及 capability 升级只改声明未改执行现场、同 session 的旧 Run 原文漂移。已有全套通过并不能排除这些缺陷。

权威保持：Pi 管模型/session，Host 管任务授权和编排，Rust 管 immutable input、对象引用、机器承诺记录和进程/文件。
资源事实在 Host 的私有 catalog 域跨工作区共享，访问与控制仍按实际任务关系；不增加 TS 数据库、第二进程系统或 OS 隔离承诺。
普通来源 locator、已固定正文、真正收集的 Artifact 分别表达。大日志/产物经既有对象与分页能力，不用新硬上限掩盖正文丢失。

消息的原始 continuation 意愿与运行时实际 mode 分开保留；工作现场变化沿真实新 Run 准备，幂等身份不由随后变化的 manifest 重算。
原文依照选定 Run 的真实边界读取，缺失为 unavailable，不扩回完整对话。现状摘录源于最新可见原段落并标注实际 Run，
授权关系和实际送达决定展示/游标，不让不可见行被确认。原 D-300 delta 交付与 D-301 的后续完整临时表仍明确分期。

边界：本次修复以本机执行和公开工具/HTTP/UI 消费者为验收对象；登记非本机目标或模拟 backend 不是远程/Slurm 实现。
真实模型科研质量、完整桌面重启、跨平台恢复、批量矩阵和大数据复用成本分别保留缺项，不能统一改称“仅未实测”。
具体实现与验证由 status 和所属模块文档记录，不另留临时验收文档。

### D-304 · 2026-09-20 · 7I 受管远程、自然生长实验与运维线程

类型：设计收口 / 实施范围调整

决定：在 D-301 / 7G 与 D-302 / 7H 后追加 7I，接续受管远程、多机器执行、材料复用和轻量批量操作。
管理 Agent 定位为按规模引入的运维线程；Slurm 等原生集群暂不接入。研究矩阵描述自然生长的研究关系，不建设独立矩阵产品。

原因：当前需要让现有研究线程可靠地操作远端现场。专用矩阵表和固定管理组织会限制自然探索，原生集群适配尚无真实使用需求。
规模小时工作线程可自行处理环境；规模增大后，一个或多个分管运维线程可负责机器、环境和数据问题，必要时再协调。

具体设计：

1. 远端执行组件复用 Rust 进程/文件/对象核心或已有 Piarium Host；现有连接管理负责 SSH、凭据和接入。
   Host 保存研究意图与目标引用，目标保存实际作业和确认分配。跨连接共用稳定机器身份；不复制本地 grant 或建设第二套 Agent loop。
2. 远端已接收作业不依赖桌面连接。未派发的跨机器工作由可见的协调 Host 持有；需要无人值守持续推进时使用常驻远程 Host，
   不静默复制队列或假称关闭本地协调者后仍会继续全局派发。失联、退出、取消与收集分别处理。
3. 实验随讨论与结果自然追加。单次执行直接可用；多个既有实验可一起提交、等待、取消、补跑或查看，按项保存实际结果与来源。
   普通脚本/配置可表达参数重复；可选组仅引用已有实验，不强制维度表、搜索语言、科学流程或每个 seed 一个模型会话。
4. 代码、数据、环境分别同步和复用，可写工作与输出独立。程序记录来源和明确的数值结果，Agent 判断科学意义与可比关系。
5. 运维 Thread 复用任务派发、自然语言通信、7G 现状和既有远端工具，可持续分管或临时排障；不限定数量、层级或模型。
   程序负责采样与实际资源确认，运维判断并执行授权处置，不逐心跳调用模型，也不因角色名称获得整机权限。
6. 交付看代码职责、生产通路、实际功能及状态逻辑；具体疑点按需验证。未做完整真机/付费模型/平台对照不是单独阻断项，
   实际未实现功能仍明确记录。Slurm 不作为当前欠账或门禁；没有用户部署需求时不为其添加配置和框架。

影响：部分调整 D-300 的原生集群交付、参数矩阵和资源协调 Agent 描述；D-303 本机验收事实保留。
设计第 5.1/6/11/13 节、plan 7.6/7.7/7D/7F/7I、Harness research 概述、status、architecture、roadmap 与索引同步。
状态：设计已接受 / 7G → 7H → 7I 排序 / 尚未实施。本次只有文档变更，不宣称新增远程或批量执行能力。

### D-305 · 2026-09-20 · 7G/7H/7I 生产收口

类型：生产实现 / 定向验收

决定：D-301、D-302、D-304 的三段生产链已接通。每次 Agent 模型请求在容量判断前附加新环境事实和完整临时团队表；
Pi 工具按权限确认后的真实资源冲突调度，后台命令主动交回并把终态送入同一上下文入口；实验可在本机和受管远程 Host 上按稳定目标、
固定材料、确认资源和独立工作目录运行，并由目标 Rust kernel 持久监督。多项提交/取消、单项补跑和远端普通 shell 进入公开工具、HTTP 与 UI。

实现边界：环境事实实际送达后才写 Pi 历史和推进收据，团队表不留史；同资源工具只建立顺序，不传播前序失败。
远端 client principal、Host 身份、协调者和执行目录分别保存；对象按内容复用，GPU 以当前 inventory 的 UUID 与可用显存确认，
目标绑定覆盖用户同名环境变量。显式目标不重选，隐式目标只从当前可确认的连接机器中稳定选择并写入 attempt。

普通运维继续复用 Thread、消息、团队现状和同一套工具，不新增管理 Agent runtime。远端已有数据或环境可由授权工具在目标上准备并由命令显式引用，
当前没有一等 dataset/environment snapshot registry；这不能被 `env` 字段冒充。Slurm、参数矩阵 DSL、固定组织层级仍不在当前范围。
真实外部 SSH 主机、跨平台远端、长时桌面断开和付费模型协作质量尚未实测，不改变已接通生产职责的事实。
