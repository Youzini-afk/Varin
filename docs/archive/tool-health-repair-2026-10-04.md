## 后续：写入与计划更新的等待链路

同日继续处理用户反馈的长期超时与写入过慢，确认并移除以下同步开销：

- `write` / `edit` 已提交后还等待 LSP 绑定、启动及诊断；默认诊断等待 5 秒，绑定阶段另在其前。`apply_patch` 逐文件等待诊断。现在提交确认直接返回，诊断继续由显式工具及已有语言观察提供。
- 权威知识库每次计划、事件和记忆修改都执行全库 `flush()`，重写与该小修改无关的符号数据。用户现有最大主文件约 245 MB，另有正文约 230 MB、属性索引约 198 MB、文本索引约 149 MB；这里只读了文件大小，没有打开实际数据库。
- 改用数据库现有的 full 模式 WAL（预写日志）确认用户状态写入，快照在原有 30 秒期限及关闭时整理。符号图的同步回调保留原来的 normal 模式，在退出时恢复 full，避免增加后台建图的逐次同步成本。依据是 [TriviumDB v0.8.8 原生 WAL 实现](https://github.com/YoKONCy/TriviumDB/blob/v0.8.8/src/storage/wal.rs)，未修改依赖或改用其他数据库。
- 停止加载、维护没有生产读者的全文/关键词索引；记忆读的是载荷和派生向量，符号检索读属性、ngram 索引与图关系。既有正文都还保存在载荷里。
- 派生语义索引与计划/记忆拆成两个按需启动的存储进程。同一进程的 IPC 批次按完成的存储组返回，已完成结果不再等批次中后面的数据库。

## 第二轮复检后的修复

依据 `artifacts/2026-10-04-varin-tool-health-recheck-773b7d8c.md` 和同一 Pi 会话的工具结果，继续检查材料、计划响应和默认桌面选择。原报告未修改。

### 已确认并修复

- 普通会话的快照没有 Thread 身份，内核却把缺省 `threadId` 序列化成 JSON null；TS 依契约用 `!== undefined` 判断，因而把自己的材料当作外部线程材料拒读。之前原生测试只使用带 Thread 的身份，遗漏了普通会话。修正 Rust 记录返回的可选字段语义，现有存储无需迁移。
- 先给原生测试加入普通会话，得到与报告相同的空读取；修复后，真实内核上的 HTML 获取→快照重读、PDF 概览→文本与查找→PNG 渲染、跨线程拒绝/明确共享、内核重启后重读均通过。
- 网页及 PDF 读取不再把底层异常转换成 snapshot-missing。元数据、正文/原始文件引用和长度异常给出具体错误；真正缺失、已释放及无权读取仍返回不可用。
- Host 原先忽略 `harness.respond` 返回的 `accepted:false`，误提交观察游标。现在拒收算投递失败，未送达观察可以再次提供。这修复超时后的状态丢失风险，不是最初 30 秒等待的确定根因。
- Windows 同名进程先选有可见、非零面积窗口的实例，默认窗口也优先有效窗口。保留明确指定 PID/句柄的行为。使用实际 PowerShell 函数和合成窗口清单验证，未操作桌面。

### 修复

- 删除每个候选值一次复合索引查询、每个文件一次全局 link 索引查询的匹配方式。
  一轮只读取一次已确认连接的集合，文件关联沿该文件自己的边读取并做集合匹配。
- 全工作区解析不再是一个不可穿插的存储 RPC。内部协议升为 3，分为创建解析任务、
  逐文件执行、释放任务。每个文件仍以原生事务发布，文件之间释放 IPC 队列。
  前台计划、观察读取及其他请求可以在解析结束前完成。
- 只有连接事实或带候选的文件代次变化才使解析过期；笔记、计划和普通符号文件的
  修改不会反复触发全库候选计算。解析中途发生相关写入时更新捕获集合并重新核对，
  不用旧文件载荷覆盖新代次，也会撤回失去连接来源的关联。
- 关闭存储等待已接纳的分步任务；任务状态在成功、失败后及关闭时释放。旧的整轮
  RPC 不保留为兼容入口。没有更换数据库、迁移格式、新增解析数量上限或延长工具超时。
