## 判断

实现已经接通了相当多的设计能力，来源、回执、扩展组合和领域生命周期的职责划分值得保留。
但阶段组件通过并不等于产品整合通过。本次 Windows 实际 HTTP/内核 IPC 验收发现了普通错误断开整个内核、
工具回执竞态、通知破坏历史游标、停止状态误报等问题，已直接修复。

**两份设计仍不能整体标为验收完成。** Windows 只读目录触发快照失效的问题已定位但尚未修复；
managed-source 的已知能力缺口、正式安装/真机和性能证据也仍在。

## 已修复的问题

| 问题及影响 | 修改 |
| --- | --- |
| 错误响应写死协议版本 1，当前协议为 27。一次普通失败就被 Host 当成坏帧，断开整个内核连接 | 错误帧使用统一协议常量；真实传输验证错误/取消之后仍可继续请求 |
| Host 先发回执、再发工具结果，但内核异步持久化尚未完成。成功的 `computer_observe` 被改成 `unknown`，Run 随之失败 | ToolBridge 等待该调用自己的持久回执 ACK；其他调用独立完成，取消和迟到回执仍归原调用 |
| Computer 控制事实正文被操作者和主线程共用，正文 ID 不等于各自历史记录 ID。下一轮消费通知后使用错误 head，停在 `execution-recovery` | 历史投影使用外层记录 ID，来源字段保留原事实 ID；同一正文仍可共用 |
| Stop 同时保存取消通知和物理释放，更新同一桌面记录产生 CAS 冲突，已释放输入仍显示“取消未确认” | 物理标记复用现有字段合并写入，并持续核对原输入者；仅重试明确的 `record-revision-conflict`，存储失败仍保留未确认状态 |
| 多个桌面按顺序清理；一个未返回的释放阻止后来桌面的清理。脚本恢复还会阻止新环境打开 | 清理按原执行/分配分别保留在途任务；共同部分只列举和安排工作。新脚本等待旧环境名单捕获，不等待其全部排空 |
| 部分新增 Router 在直接调用测试中正常，真实 HTTP 请求体却没有 JSON parser | 补齐 agent profiles、Bot memory、Computer、Runtime 和 managed-execution POST；二进制 PUT 保持原处理 |
| 配置的 Worker/Retrieval 预设被父线程当前可见工具名单再次否决，可写私有子任务也受影响 | 使用已解析的预设/来源/工作模式选择，再核对冻结的能力版本与真实声明；Host 扩展/MCP 仍绑定父线程原实现 |
| Rust 的 Windows 命名空间路径与 Host 普通盘符路径被判成不同来源；文件观察也因此拒绝 | 比较原 Host/root ID 与规范路径身份；仍核对实际目录和重定向 |
| TypeScript 服务收到命名空间形式 cwd 后，跨文件定义退化成 import 别名；返回 URI 也可能被误判越界 | 语言进程使用普通平台路径，视图键使用路径身份；URI 映射统一盘符/UNC 表示，实际定义仍要求落到目标文件 |
| Windows 持久重命名直接调用 Win32，长目录下 stdin 等回执无法落盘，已执行交互变成未知 | 在 Win32 边界构造长路径形式，保留原原子替换与刷盘语义 |
| 丢失回执后的文件写入恢复，用未解析资源合同比较已解析合同，拒绝恢复真实原操作 | 恢复使用同一资源规划入口解析合同；只核对原 journal，不重新写文件 |
| 一个 Surface 准备失败时，通用清理可能销毁仍被整组更新持有的 Host candidate | 清理前核对当前 Catalog、待应用组和实际实例，组内其他成员可继续准备 |

文件根注册结果补上真实协议类型，来源工具绑定也从 `unknown` 改为生成类型，删除消费端重复猜测字段的代码。
没有新增全局并发限制、猜测超时、通用重试层或内部旧格式兼容分支。

## 验证

环境为 Windows x64、Node 24、当前源码构建的 debug kernel（版本身份 `0.9.25`）。
模型端使用本地 HTTP 协议夹具，Computer 使用受控驱动；没有付费模型调用或真实桌面输入。

- 实际 Host/内核 IPC：子线程 39 项；MCP authority 9 项；文件恢复 1 项；内核传输 5 项；
  真实 TypeScript 语言服务 1 项。Computer 的完整 HTTP → 扩展 broker → 内核 → 受控驱动链路 1 项，
  包含 Stop、控制事实送达、后继 Run、自然收尾及重开历史。
- Rust/Host 跨语言组合：managed source 7 项；持久脚本 6 项，包括真实 Node/guardian、嵌套工具、
  同步死循环取消、迟到回执、独立 Thread 进程及 typed media。
- Computer 与脚本生命周期 57 项；Computer 服务、ToolBridge、HTTP parser、URI 映射 128 项；
  扩展更新组与 scoped composition 24 项。MCP 资源消费者 15 项。
- Runtime 的 Computer 控制事实、被动消息、来源继承 15 项。
- Windows kernel 构建、Host 源码/测试类型检查、扩展 Host 构建、所改 TypeScript lint、
  协议生成一致性和文档链接检查。

测试夹具也存在漂移：遗漏 composition、使用旧 provider key/纯字符串工具结果、缺少真实控制事件接线、
未持有已准备的扩展，以及在 Windows 调用 `/bin/sh`。本次按当前协议修订，并保留了副作用、停止证明、
子任务授权与原回执检查。它们与上表产品错误分别判断。

## 仍未通过或未覆盖

### Windows 静态目录捕获

`source-picker-review.native.test.ts` 的目录列表/检索场景仍可能在 source preparation 阶段失败：
`Documents capture: watch-sequence-changed`。独立 Node 样本确认：新建目录首次被枚举/读取时会出现
`change src`，目录 atime 变化，mtime/ctime/mode 未变。捕获代码没有修改源文件。

[libuv 的 Windows watcher](https://github.com/libuv/libuv/blob/v1.x/src/win/fs-event.c)
确实订阅 `FILE_NOTIFY_CHANGE_LAST_ACCESS`，而 Node `fs.watch` 回调没有提供具体变化原因。
当前 Documents 将目录事件计入捕获变更游标，所以读取本身可以使稳定捕获失败。

这应在 Windows 文件观察边界解决。不能直接忽略全部目录 `change`：目录权限也属于当前快照状态。
本次保留原两次状态读取、目录集合核对和变更检查，没有用延时、自动重试或放松一致性来掩盖失败。

  项目 MCP/定时任务消费者仍有明确缺口，详见对应领域记录。
- 本次没有证明正式安装包、实际 Windows GUI 输入/焦点、多虚拟机、真实双机网络、真实模型质量与长期恢复行为。
- 没有做吞吐、延迟、内存和大仓冷启动测量，不能据这些正确性检查宣称“性能已达到设计目标”。
- 本次检查重点是新增能力之间的调用、取消、持久化和恢复边界；没有把 1138 个变动文件全部逐行审查。

建议继续沿现有职责划分补齐上述交付面，并优先完成 Windows watcher 的真实变更过滤。
