# 运行时整合验收

日期：2026-10-11。审阅基线：`bf73791b7b977c5438cfed13425f78cd0da581db`，
分支：`implementation/native-agent-runtime`。本文同时记录本次修复，不能用此前分层测试的通过数代替这里的结论。

## 判断

整体方向符合[运行时设计](../design/agent-runtime-design.md)和[扩展设计](../design/runtime-extensibility-design.md)：
Catalog 维护运行事实，正文存入内容对象；耗时读取在 worker 执行；策略通过同一执行器提交工具图；
子任务、消息、接续与研究作业复用原有输入和执行身份。没有发现需要推翻这套基本结构的证据。

但审阅基线不能通过整体交付验收。实际 Windows Host → IPC → Rust → 本地模拟 provider 的链路发现了
编译失败、普通消息不能续聊、子任务准备失败、授权不能重建以及合法并发使内核退出等问题。
这些不是单个工具的错误，主要来自跨模块合同漂移。本次已修复下列确认问题。

两份设计仍未全部实现，也还不能宣称性能目标达成或具备默认切换条件。
默认运行时切换、Pi 删除和用户资产迁移继续遵循现有交付分工。

## 已修复的确认问题

| 问题及影响 | 本次处理 | 主要位置 |
| --- | --- | --- |
| Windows 路径重叠检查移动了后续仍需借用的 `PathBuf`，内核无法编译 | 改为借用 | `storage/recovery.rs` |
| 控制请求和响应走不同通道时，两端记账不同；合法状态查询与取消并发会触发 admission window exceeded 并断开内核 | 请求额度按协议声明的响应通道归属，与 Host 一致；没有扩大窗口 | `runtime.rs`、transport acceptance |
| Host 发送合法的 `operationId`，内核第二份手写 grant 字段名单却拒绝它 | 保留生成协议的参数校验，删除重复字段名单 | `runtime.rs` |
| 输入受理与启动装配的工具目录不同，新增 family/message/follow-up 工具使冻结身份校验失败 | 两处和 child capability discovery 使用同一组所属模块的 schema | `run_tools.rs`、`agent_inputs.rs`、`run_assembly.rs` |
| 继承来源时，Runtime 又维护了一份旧工具名单，普通续聊和无工作区消息被拒绝 | Runtime 校验来源选择；具体工具由原工具入口校验，继承仍复用已接受的目录 | `catalog_submission.rs` |
| HTTP 接口的旧名单拒绝 source preparer 自己返回的 process write/resize | HTTP 只检查名称形状，具体名称交给原协议和工具声明解析 | `thread-routes.ts` |
| child handoff 是获取新授权的 Host 请求，却被 Host 客户端要求先持有工具授权 | 明确使用 Host 通道，Rust 继续核对原已接受的 handoff | `kernel-client.ts` |
| 只需 branch 元数据的查询默认携带文件条目，既多读数据又违反固定父快照的读取范围 | 元数据查询显式 `includeEntries:false`，文件读取继续使用固定 pin | `storage-adapter.ts` |
| 关闭或撤销后重新使用确定的 grant ID，重启恢复重复碰到已撤销授权 | 活跃缓存仍复用；新授权生命周期创建新 ID，原撤销不失效 | `storage-adapter.ts` |
| Rust 与 Node 对 Windows 路径的命名空间表示不同，实时来源和可写子任务结果被误判为环境变化 | 两侧比较规范路径身份，保留 Host/workspace/root ID 与重定向检查 | `live-source.ts`、`source-launch.ts`、`storage/file_resources.rs` |
| 安装唯一策略插件会隐式影响未选择它的任务，子任务可能重新执行父编排 | 默认使用内置循环；明确路由或注册表选择才替换策略；恢复继续绑定原 artifact | `agent-policy.ts` |
| 目录无权限位在 Rust 为 null，在 Host 为缺省，正确的结果被判为与固定根不一致 | 协议声明真实 nullable 输出，Host 统一可选权限位表示；不改变存储格式 | protocol、`journal-files.ts`、`storage-adapter.ts` |
| Host 工作态的临时内容对象未转交恢复记录写入方，脏缓冲整合在 file CAS 失败 | 使用已有 owner 转交接口，在原工作区内从 Host storage/recovery maintenance 转给恢复写入方；受限 Run 不获得该通道 | `kernel-recovery-store.ts`、`storage/objects.rs` |
| 已结束接续项继续占据活动区，工具说明和卡片反复解释内部机制 | 已结束项默认收进历史；保留状态、操作和可展开证据，说明按用途与参数分配 | `ThreadFollowups.tsx`、`followup_tools.rs` |

位置省略的 Rust 目录均为 `kernel/crates/varin-kernel/src/`；Host 目录为
`packages/web/application-host/lib/kernel/`。本次没有增加总工具并发上限、重试层或旧格式兼容分支。

## 实现方式的评价

**值得保留的部分**

- 调用受理、执行终态、效果证据和真正停止分开。取消等待不会被伪装成取消目标作业；
  重启后根据原回执续接，不重新执行已经提交的记忆写入或派生第二个子任务。
- 策略、普通扩展工具和子任务保留具体 artifact/configuration 身份。当前路由变化可以准备后续选择，
  不替换一个未结束交换正在使用的实现。
- 大正文离开 Catalog 的短事务，文件读取保留真实 reader 生命周期直到 worker 结束。
  GC 保活关系与授权分开；本次没有发现新增持久字段漏入内容根集合的确认问题。
- follow-up/calendar 通过原输入受理和 Run 启动路径交付，研究作业停止与产物收集是不同事实。

**仍需继续收敛的部分**

- 工具名单、参数字段和身份比较曾在多个入口重复维护，这是本次多数整合失败的共同原因。
  已移除实际出错的副本；后续能力应使用所属模块的声明与现有绑定，不再在 HTTP、装配和 Runtime 分别补名字。
- 一些实现文件和历史台账过于庞大，压缩成一行的 schema/测试使审查困难。此次只整理涉及的说明和边界，
  没有把大规模格式重排混入行为修复。
- 现有配置预设仍可能包含 Pi 工具名，在新目录中显示不可用。普通默认 dispatch 已可运行，
  但预设配置与产品设置的完整适配不能据此算完成；不应靠工具别名兼容掩盖它。
- 通用 preparation failure 和 HTTP 错误投影仍偏粗，跨层排障困难。需要由所属失败类型提供短而可操作的状态，
  不能把调用栈、请求正文或重复的内部职责解释塞进模型结果和默认界面。

## 验证及其含义

使用当前源码构建的 Windows x64 debug kernel，身份 `0.9.25`；Host 测试直接连接该二进制，
provider 是本地 HTTP 协议夹具。没有调用付费模型或操作用户桌面。

本次复用了现有验证入口，覆盖真实子任务准备、私有可写工作区、主子消息、等待与重启、
策略图和记忆回执恢复、实时来源、工作态结果与整合恢复、并发控制及大正文通道。
五个实际内核集成测试文件最终 **78 项全部通过**：`child-dispatch-review`、`policy-graph-review`、
`live-source-review`、`storage-adapter`、`kernel-transport.acceptance`（均为 `.native.test.ts`）。另已执行：

- Runtime follow-up 与策略控制的三个现有测试文件：62 项通过。
- 共享 blob reader 的实际 Rust worker 场景：6 项通过，包括取消排空、GC 保活和固定来源消费者。
- 扩展工具、正文读取、研究作业及产物续接等 Host 组件：44 项通过。
- 策略选择、SDK 协作示例和已授权存储上下文：19 项通过。
- 会话、消息、Goal 界面相关行为验证：67 项通过；另有 UI 类型检查。
- Windows Rust all-targets 检查、Host 源码及测试类型检查、所改 TS/TSX lint、协议生成一致性检查。

原测试中的旧域版本数字、Python 外部依赖、缺省/null 比较、错误的策略作用域和同步启动假设已按现合同修正。
分支整合恢复使用明确的 executor-stopped 证据；没有把“重试 merge”直接当成旧执行已停止。
这些测试修订与产品修复分开判断，不能把所有最初失败都称为产品缺陷。

## 未完成与未验证

完整能力尚有 Computer Use/人工交接与远端执行、Web/材料/PDF/学术/Bot、MCP resources/prompts/Tasks、
持久脚本，以及来源、检索、上下文、provider 的剩余接线。日志条件和指标条件仍未因 reader 改进而自动具备。
范围见[实施台账](../plan/agent-runtime-implementation.md)和此前各领域记录。

这次没有完成安装包点击流程、跨平台图形会话、真实远端/虚拟机、付费模型质量、长期负载与性能测量。
Windows 的一个临时目录捕获样本曾收到目录失效通知，导致稳定性校验拒绝；已追踪到 `fs.watch` 通知，
未发现捕获代码主动写目录，尚不能判明外部通知来源。没有为此放松快照一致性检查或添加猜测性的重试。

因此，本次结论是：**基本架构可以继续推进，确认的整合问题已修复；两设计整体交付仍不能标为完成。**
