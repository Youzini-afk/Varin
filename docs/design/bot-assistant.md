# Varin Bot：长期总助手、连续上下文与记忆

状态：2026-10-30 已接入原生运行、事项关联、任务复用、选择性背景交接、跨项目来源、日程与记忆链路。当前机制与合同见 [长期总助手](../bot.md)、[协作](../collaboration.md)和[记忆模块](../../packages/web/application-host/lib/memory/DOCUMENTATION.md)。本文保留已确认的产品设计依据，不再列入活动提案。

## 1. 产品目标与已确定的方向

用户主要面对一个长期总助手。Bot 承担原先由用户承担的协调工作：理解交流、安排适合的执行者、跟进事情、联系前后信息，并在有必要时回来沟通。用户可以随时进入工作台查看执行现场、直接与 Agent 交流、调整或停止工作，然后回到 Bot 继续交谈。

Bot 以沟通和统筹为主，保留直接处理小事的基础能力。它能判断、讨论和组织材料，也能直接读一段内容、查询状态、调整安排或完成简短操作。需要连续探索、深入设计、反复试验和大量执行的工作适合交给现有 Agent。具体如何参与由模型结合实际任务决定，不用固定流程或狭窄工具白名单强制分流。

设计的成功标准是：用户交代事情后仍能自由交谈，中途介入后各方能接上变化，隔一段时间回来仍然能延续已有理解，同时保有对所有实际工作的可见性与控制。

| 议题 | 本轮决定 |
| --- | --- |
| 日常入口 | 围绕一个长期总助手组织体验；保留现有多个 Bot 的数据与访问能力，不引入必须组建团队的前置步骤 |
| 执行分工 | 复用现有 Agent 预设、临时派发、外部 Harness 和协作工具；不另建 Bot 执行器 |
| 任务复用 | 对相关工作优先考虑已有执行者；支持原对话继续、带相关背景另开工作和独立新建，由实际需要选择 |
| 提示词 | 表达目的、角色和实际能力；不把产品验收清单写成模型每轮必须遵循的流程 |
| 后台回报 | 结果送达、模型处理和面向用户的通知分别成立；子任务完成不自动逐条通知用户 |
| 上下文 | 稳定前缀、真实对话、可回读摘要与相关增量材料结合；按原生请求边界更新 |
| 压缩 | 提前准备、原子发布、保留新增尾部和原始引用；失败保留原有效上下文 |
| 记忆 | 自由正文、来源与修订、可选关联；主动保存和后台增量整理共用原写入者 |
| 任务事实 | 从原任务和资源所有者读取；记忆保存理解与经历，不充当实时任务状态 |
| 用户介入 | 原工作台操作继续生效；重要变化回到 Bot，关联原事项和来源 |
| 性能 | 按新增内容处理，避免每轮枚举全部历史、重新生成用户画像或引入固定模型判断链 |

本稿覆盖产品语义、运行衔接、上下文、记忆、工作台交互原则与实施安排。具体视觉稿、外部消息平台接入、多 Bot 群聊以及向其他 Harness 暴露 Varin 的 MCP/CLI 能力另行设计。本轮保留现有入口和能力，不要求用户先配置这些扩展功能。

## 2. 提示词与机制的边界

设计文档可以列出需要正确处理的情况；模型提示词不必逐条复述这些情况。两者面向不同对象。

- 模型判断什么有意义、是否直接处理、如何协作、记什么、怎样整理和什么时候沟通。
- 系统保证原始记录可回读、任务与消息正确归属、实际结果不会被状态投影改写，以及持久化、取消和权限的既有语义。
- 工具说明表达真实输入、输出与能力边界。机器可解析的引用和写入操作可以有结构，正文的组织不受固定语义栏目限制。
- 不要求每轮判断固定分类，不强制先计划再派发，不固定压缩摘要或记忆正文的章节，不要求任务都经过审查 Agent。
- 任务复用是模型可选择的能力，不要求每次交办先搜索、打分和审批；不新增专用的复用决策模型。

以下是表达方向的中文草案，实施时与现有系统提示组合、去重，不把示例扩展成工作流程。

**总助手职责：**

> 你是与用户长期合作的助手。通过交流理解用户，运用可用能力帮助他们处理事情。你可以直接工作，也可以与其他 Agent 协作；根据当前需要决定如何参与、组织工作和与用户沟通。

实际具有任务续接与历史读取能力时，可补充：

> 你可以继续与已有 Agent 合作，利用其相关工作背景，也可以按需要创建新的工作。

**上下文延续：**

> 这份记录将帮助你在原始对话不再完整可见时继续交谈和工作。请保留能让后续理解与行动保持连续的信息，结合这段对话判断内容的意义、关联和详略。原始记录可以按引用回读。

**长期记忆：**

> 记忆帮助未来的交流与工作延续已有理解。结合实际经历，判断什么值得留下，以及怎样表达才保有它的意义和适用背景。

实际指令来源与权限沿现有系统处理。引用材料、工具输出和模型推断保留其来源身份；正文中出现“以后必须……”不使外部资料获得用户指令的身份。用户在档案里明确设置的合作指令属于配置，自动整理形成的理解属于可修正的记忆。

## 3. 当前基础与本轮缺口

### 3.1 可复用的实现

- Bot 档案由 Catalog typed record 保存，每个 Bot 有稳定入口 Thread、家目录、模型选择、指令和生命周期状态。
- Catalog 通过入口绑定与子任务关系确定 Bot 归属；界面模式不决定执行身份。
- 原生协作已有派发、报告、等待、消息、代码交换与外部执行适配。
- 现有 send 的 request 可以沿旧 Agent 对话接续，inform 只等待其下次正常处理；threads 可查询当前和历史成员。续接可用 sourceAgent 调整隔离来源；dispatch 的 inheritContext 继承派发方当时的背景。文件来源选择与背景继承是不同能力，不把 sourceAgent 当成继承该 Agent 对话。
- 暂停先关闭执行闸门，再停止相关 Run、等待实际执行者排空、处理专属电脑；恢复沿原身份续接。
- Bot 使用独立的 MemoryService/KnowledgeStore 路径，已有来源、修订、遗忘、后台整理及可选语义召回；普通 Agent 的轻量笔记保持原职责。
- 原生上下文已有后台准备、容量核验、候选摘要、保留原文和 checkpoint 发布机制。
- 日程由原生 Calendar 执行；Host 负责配置资产和准备，已有时间区与错过执行策略。

## 4. 助手、事项与执行的关系

### 4.1 长期身份与每次交办

Bot 是长期合作对象；事项是需要延续理解的一件事；Thread、Run、派发和产物是已有的交流与执行记录。

事项可以从简单关联开始：一段目标描述、相关交流与任务的引用，后续根据需要补充理解。随口问答不自动创建正式事项，也不要求先填计划、完成条件或分类。已有计划和 Goal 有实际用途时继续使用，不为了进入 Bot 模式自动创建 Goal 或预算。

同一事项可以经过多次执行，也可能跨项目、跨日程、跨时间延续。一次执行完成只改变执行状态。Bot 对“事情已经完成”的判断可以作为带来源的说明保存；执行仍未结束、尚有待处理问题等事实由原所有者呈现，不被该说明覆盖。

事项关联依附现有 Catalog 的 Thread、branch、派发和计划引用；补充必要的关联记录，不建第二套任务数据库。描述性概述可以由 Bot 更新，运行状态由原记录投影。工作目录和导航项目分别解析，不能靠事项名称或界面分组授予文件权限。

用户可以把已存在的普通会话或项目交给 Bot 跟进。这增加一条明确的跟进关系，不改变原会话的身份、模型、来源或所有者。跟进、读历史、发送消息、改变工作分别使用现有对应操作；“跟进”不隐式给出所有控制权限。

默认工作入口指向选定的总助手。现有其他 Bot 保留，用户需要独立长期职责时仍可访问和创建；不自动将其合并到一份记忆，也不把每个临时执行者变为长期 Bot。

复用 Agent 是延续已有工作理解。Thread 保留稳定身份、头像、历史和相关记忆；每次新的交办保留自己的原始请求、事项关联、执行和回报。改名不重写旧交办的用途，某一轮失败也不使之前的成果失效。需要多轮执行的一次交办可以引用多个原执行，但不新建独立的状态权威。

同一执行者可以先后参与相关事项；同时开展的独立任务需要分别跟踪。不能用 Thread 当前显示的名称或最新 Run 代替所有交办的结果。当前谁请求了什么、结果应该回到哪里，按该次交办确定。

### 4.2 三种延续方式

| 方式 | 语义 | 保留与更新 |
| --- | --- | --- |
| 原对话继续 | 在已有 Agent 的目标分支上交付新的工作 | 保留有效历史与摘要，追加本次要求和尚未收到的变化；每次交办独立结算 |
| 带相关背景另开工作 | 新执行身份利用已有工作的相关理解，适合新方向或并行探索 | 选取现有报告、记忆、原文或必要交接材料，固定来源引用；新上下文不自动复制全部旧对话 |
| 独立新建 | 从本次任务需要的材料开始 | 可以引用事实和成果；不默认继承原执行者的推导、结论或未决假设 |

选择依据是工作的关系、上下文价值、当前状态和用户意图。时间间隔、名称相似度、历史长度或缓存命中率都不单独决定复用。用户可以明确要求“让之前的继续”“沿用调查但重新考虑方案”或“独立看看”。总助手在普通任务判断中选择相应能力，不执行固定的复用流程。

原对话继续沿现有消息/续接机制；另开工作沿 dispatch 和原始材料引用。需要扩展的是从指定相关工作选取背景的交接能力，不能把现有 inheritContext 的含义悄悄改为“任意旧 Agent 历史”，也不能用文件来源参数混代。具体工具合同围绕实际动作扩展，不要求每次提交一个复杂的复用策略对象。

### 4.3 发现适合的既有工作

当前事项直接关联已参与的 Agent、交办与成果；查找其他工作时复用 threads/read_thread/报告读取入口，按访问范围分页搜索。当前上下文只带相关成员和原引用，不持续注入所有历史成员。

发现结果优先给出原交办、最近实际结果、成果位置、项目/来源与当前忙闲状态。短说明可来自已有交办和报告，正文按需展开。无合适摘要时不必先调用模型整理全部成员才能返回目录。名称用于识别，不作为能力或权限证明。

已有工具的任务家族范围不应因为总助手搜索而被隐式放宽。对明确纳入跟进的普通会话，沿第 4.1 节的关系和真实访问权限查找，保留原身份。目录不可用、目标已删除与没有相关工作分别返回；不能找不到原任务就静默新建一个同名替代者。

### 4.4 再次接手与过时信息

续接材料以本次交办为入口，附带相关事项中该执行者尚未收到的变化：用户的新要求、明确修正、必要的新结果，以及当前实际来源与之前来源的关系。系统按原消息、事件和 revision 记录投递位置，避免每次复制全部主对话。

变化材料说明来源和先后关系，不要求模型按固定栏目回答。新近不自动等于更正确：实时文件事实以本次实际读取为依据，用户决定以原身份和适用范围解释，历史观察继续保留当时的语境。失败尝试也可能有价值，不因其旧或失败而自动删除。

旧假设已被明确替换时，提供纠正及依据；旧上下文过于分散或方向发生明显变化时，可以用第 8 节的原压缩机制重新整理有效理解，或选择带背景另开工作。不能仅在旧历史末尾堆叠大量“忽略之前”声明来代替上下文整理。整理后的工作背景保留原文入口和来源版本，原始历史不被改写。

### 4.5 运行中的交办与回报

当前工作的补充或纠正可进入原运行的合法输入边界；新的独立工作需要明确顺序交办或另开并行执行。顺序交办沿持久输入队列等待前一工作边界，不伪装成当前目标的插入消息。用户明确改变当前目标时使用原调整/停止机制，已经发生的操作按原回执结算。

接受交办、开始执行和完成结果分别可观察；排队的请求可以按自己的身份取消，不能因此取消同一 Agent 的其他交办。Bot 是否等待回报由实际需要决定，不因为复用默认同步阻塞主对话。

结果关联本次请求者、目标分支、事项和实际 execution。若原系统只按最初父任务回报，需要扩展为按本次交办路由；历史父子关系仍保留。重试、重启、用户直接发送消息与 Bot 发起接续共用原幂等和准入机制，不能造成同一工作重复启动或回报串到另一轮。

### 4.6 能力与外部执行者

复用保留已选执行者和用户配置，不按“更适合”自动换模型或提供商。每次新执行按原准备机制解析实际绑定并展示变化；已受理的请求仍使用自身冻结的配置。缺少本次所需能力时返回真实情况，由总助手选择其他执行者或用户明确调整。

外部 Harness 的续接依赖其真实原生会话与适配器能力。能够 resume 时继续原会话；无法定向整理其内部上下文时，可以使用带相关背景的新会话，不能声称已经清掉外部会话中的旧理解。会话失效、能力不支持或资源不可用都不静默退回全新会话。新的交接材料遵守原权限和第 11 节的遗忘要求。

## 5. 持续交谈、后台处理与用户介入

### 5.1 主对话的响应性

主对话保持原生对话与请求边界，复用现有 steering、队列和工具后台执行能力。输入可持续受理；新的用户消息可以在实际支持的下一模型步骤边界进入。多条输入保留原顺序及其身份，不由 UI 伪装成另一个并发主 Run。

Bot 派发长任务后可以结束当前回合，后台工作独立继续。直接调用支持后台运行的工具时，保存实际操作引用并释放前台等待。等待中的用户输入应使用原 Wait/队列恢复机制，不必须等子任务全部结束才处理。

用户到达时，尚未开始的后台整理与可合并回报让出下一个前台处理机会；已开始的模型请求和工具依原语义结束、续接或取消。不能以“保持可交谈”为由丢掉已发生的工具效果或重新派发同一操作。CPU、文件扫描和记忆索引工作不能占用对话事件循环或 Catalog 长事务。

没有新事件、用户消息或日程时，Bot 可以空闲。长期存在不等于模型持续运行；Host 退出后由既有持久记录恢复，没有执行 Host 时界面明确显示不可执行状态。

### 5.2 回报的持久送达

子任务的结果仍属于原任务。发布终态报告后，原 Catalog 保存送往本次交办请求者的触发关系，包含真实结果引用和所属事项。首次派发使用原派发关系；复用时使用该次接续关系，不一律回到最初父任务。准备期失败、取消、部分结果与成功同样能送达，并保持原语义。

Bot 正在处理时，回报作为待处理增量保留；空闲时，可以触发新的处理回合。复用现有 ingress、队列、原生接续和执行闸门，不在 Host 另开常驻轮询 Agent。对已注册 Wait 的同一结果与主动回报使用一致的消费身份，避免双重处理。

入队、被某次请求看到、成功处理分别有原记录依据。失败或重启后从已保存的位置继续，复用已经发生的工具结果；不通过“再跑整个回合”制造重复副作用。实现时使用 Catalog 事务串起触发与消费关系，ContentStore 保留正文与来源。

可在一个处理边界取出已到达的多项变化，不引入为了凑批而强制等待的固定窗口。进度文本和百分比主要更新投影，不逐条触发模型。报告、明确问题、用户介入以及已登记关注条件等有语义的变化可以触发处理。多层协作的结果先回到本次交办的直接请求者，防止每一层把同一结果重复送到总助手。

### 5.3 处理结果与对用户说话

一次后台处理可以更新理解、继续协作、请求信息或给用户发消息，也可以没有面向用户的回复。运行时需要能记录“已处理但没有用户消息”的合法结果，不生成空聊天气泡或伪造最终答复。

模型根据内容和用户要求决定如何沟通。系统只保证可区分内部处理记录与真正发给用户的消息，并提供查看工作详情的入口。用户指定的汇报节奏作为实际要求保留；不把每个完成事件固定改写成一条汇报。

系统通知跟随实际用户可见消息和既有待处理问题/权限规则，遵守用户通知设置。单个子 Agent 完成不另发一遍通知；已有通知和未读状态按原消息身份去重。Bot 不能代替用户批准需要人工决定的权限请求。

### 5.4 用户直接进入工作台

用户可以查看任务历史、向子 Agent 发消息、修改文件、处理权限、调整或停止工作。所有动作沿原工作台与执行 owner 生效，不通过 Bot 转译一遍。

影响该事项的用户消息、明确方向变化、取消和新的结果，作为带原来源的更新送回 Bot。输入焦点切换、滚动和普通进度不形成记忆事件。Bot 读取时能分清用户原话、子 Agent 报告和系统状态。

Bot 已准备的请求不会被原地改写；新的决定在后续合法边界进入。准备提交的调度操作仍检查实际任务状态和原 revision，避免用户已经取消而旧计划继续创建工作。对正在执行的外部操作遵循其真实可打断能力，界面展示尚未停止或结果未知。

用户直接续接旧 Agent 与 Bot 同时准备交办时，原分支准入决定实际顺序并返回可见结果。Bot 不依据此前的“空闲”快照覆盖用户刚开始的工作；待交办请求保持自身身份，可排队、撤回或改选执行者。用户在此轮作出的纠正也进入之后相关续接的增量背景。

## 6. 跨项目、日程与暂停

Bot 家目录承载自己的文件，不限制所有任务只能在家目录执行。跨项目派发复用已登记来源目录与来源准备，使用真实项目、resource owner 和 Host 身份；省略目标时沿已确定的来源。项目访问、信任、工具权限和外部来源准入继续由原系统判断，不新增第二份默认拒绝一切的 Bot 项目白名单。

用户可主动指定 Bot 经常跟进的项目，作为默认发现与上下文关联；这份偏好不构成额外访问授权。对普通会话的跟进关系与跨项目派发分别保留，不能把已存在的会话改造成 Bot 子任务。

Bot 日程、定时提醒与条件接续复用 Calendar 和 follow-up。日程目标可以是 Bot 入口或已有真实工作，定义保持可见、可编辑；Bot 家目录是否适合作为现有 loop 资产命名空间在实施时核对，不新增第二个计时器。错过触发继续使用现有 skip / coalesce_once 语义。

“暂停 Bot”延续现有生命周期操作：关闭新执行入口，处理范围内的真实执行及专属电脑，等原所有者给出停止状态。退出视图、归档消息、关闭通知不等于暂停。暂停期间回报仍能保存，恢复后读取最新状态与取消记录，不机械重启所有旧计划。

本轮不新增强制用量预算、轮数上限或统一超时。沿用用户已配置的预算和模型容量，显示真实使用量；辅助整理使用现有用途模型选择与实际可用绑定，不强制引入决策模型或自动改选其他渠道。

### 6.1 对话复用与执行来源分别准备

保留原对话并不要求复用旧文件状态；复用某份成果也不要求继承原执行者的判断。来源、上下文和实际能力分别准备，再在本次执行准入时确定组合，失败不留下已偷偷切换的目标。

Shared 继续使用所选实际来源，必要的文件事实重新读取；隔离工作延续原逻辑分支，明确更新基础时复用 sourceAgent/三方合并，保留本人的修改及真实冲突。新开的并行工作按本次 workMode 选择来源，不因为复用了背景就暗中共享旧 Agent 的可写隔离目录。

结束的工作保留必要历史、成果和版本引用，进程、终端与挂载按原资源生命周期处理，不为了“熟悉情况”永久驻留。再次执行时按需恢复实际环境。已有修改、未结算操作和仍存活的引用由原 owner 持有；不以清理空闲 Agent 的名义丢弃这些资产，也不新增完整目录备份缓存。

## 7. 上下文组织与缓存

### 7.1 逻辑构成

下表描述系统装配职责，不是要求模型填写的摘要模板。

| 材料 | 职责与生命周期 |
| --- | --- |
| 稳定基础 | 身份、工具合同、明确配置的合作指令；一个已准备请求中固定 |
| 连续交流 | 当前 checkpoint、保留原文和近期真实消息；按历史顺序延续 |
| 工作概况 | 相关事项及原任务的当前事实，提供深入读取入口；随实际变化追加 |
| 本次相关材料 | 触发事件、召回记忆、需要的报告与资料片段；带原身份和版本 |

工作概况既能让 Bot 意识到其他事情仍在进行，也避免复制所有执行现场。具体报告正文可以按需展开或续读。关联事项的短说明引用原目标与最近交流，不要求每个事项生成标准化长摘要。

### 7.2 稳定前缀与增量投递

使用现有 RequestSnapshot 固定一次请求的真实输入。工具顺序、相同内容的序列化和已接受 checkpoint 保持稳定；不每轮重排所有记忆或在最前面插入更新时间。

新用户消息、任务结果、状态变化和召回材料在可接受的后部追加，记录已投递的身份与 revision。同一条材料不因相似度排序变化重复进入上下文。用户切换话题时，检索可以改变，已发送的历史不因此被反复重写。

工作概况在新 checkpoint 中可以合并成简洁现状，后续仍按增量更新。关联项目、当前事项、触发来源是确定性信息，直接从原记录取得；不增加一个每轮都要调用的“上下文规划模型”。

少量经常有用的长期理解可以进入固定的记忆背景快照，正文仍标为记忆材料，并保留版本与来源；不会因此提升为系统指令。是否继续保留由使用需要和压缩整理决定，不按访问次数自动固化成永久用户画像。

记忆修订附上明确替换关系，后续请求能识别哪段理解已变更。新配置只在合法准备边界生效。实际权限撤销与明确遗忘优先于缓存复用；缓存只优化相同前缀，不能作为继续发送被禁止内容的依据。

### 7.3 本次检索依据

用户消息触发时，使用近期交流、明确引用和相关事项；后台回报触发时，使用原任务目标、事项关联与结果，而不是取另一话题最后一句用户消息。显式搜索工具以模型提供的查询为准，不擅自改写为自动召回的窄范围。

关联材料与语义候选分开取得再合并。请求预算按实际模型分词器、可用窗口、生成预留和实际序列化输入核算，不给所有模型写死同一条数或字符数。材料过长时提供可读片段、范围及继续读取入口；不能截断后当作完整结果。

### 7.4 读取成本

最新触发、最近交流和未处理变化沿原游标读取。历史中的大正文在需要时读取。Bot 打开或准备下一请求不应每次扫描所有分支、全部事项或记忆。

缓存可保存按来源 revision 得到的投影，底层原记录仍是权威；恢复后由原游标与内容身份追平。不得引入持久维护的第二套聊天历史作为读取捷径。

### 7.5 复用上下文与选择性背景交接

原对话继续时，利用其有效 checkpoint、近期真实历史和工作记忆，追加第 4.4 节的变化即可；不为每次续接强制重新生成整段背景。一次已经结束的 Run 与下一轮请求分别保存，不重放旧工具输出制造“重新熟悉”的假步骤。

带背景另开工作时，优先使用已有合适报告、当前有效记忆和精确原文引用。需要重新整理时，由模型按本次需要组织材料，不套固定交接清单；原执行者忙碌时可以读取已持久化资料，不为生成交接而强制打断它。新任务读取固定的材料版本，后续变化通过明确消息或再次读取取得。

历史中的建议、推断、用户原话和当前执行事实保留区别。独立复核可以只取得必要原材料和成果，旧结论按需要读取；不能在“独立新建”中自动继承全部历史判断。新任务仍使用自己的系统指令、模型与工具，引用旧上下文不授予旧角色的权限。

复用的收益来自减少重复理解与探索；已有历史也消耗输入容量。缓存命中由实际 provider 决定，不把旧对话视为永远免费。正常压缩和选择性背景交接帮助控制成本；不设“超过若干轮/若干天就必须换新 Agent”的规则。

## 8. 无感压缩与长期连续性

无感有两层目标：减少用户等待，且压缩后仍能接上交流。使用现有准备线和替换线，不重设另一套 Bot 专用比例或把预留空间误当成独立窗口。

准备阶段固定历史 head 和关联材料版本，在后台生成候选。期间主对话、子任务和记忆整理继续运行。发布时安装该固定范围的摘要与保留原文，完整接上范围之后的新消息和变化。

摘要正文由模型判断内容与详略。系统提供清晰的来源引用、实际预算和可保留原文能力，不强制“目标/承诺/未完成事项”等栏目。模型需要具体原话、数字或推导时，可以保留相应原文或按引用回读。

旧摘要可以帮助续写，但原始历史始终有可查询入口，避免只能层层总结旧总结。源记录已删除或不可用时明确返回其状态，不凭摘要编造原话。

候选过期、失败或超过容量时，不覆盖原 checkpoint。接近容量而候选仍未完成时，沿既有等待机制展示真实原因并继续处理；不宣称在任意模型、网络和负载下绝不会等待。重点是准备充分提前、处理不阻塞主线程，正常情况下在需要替换前完成。

压缩与记忆整理拥有独立进度。压缩不等待长期记忆提炼；后台整理继续从原始记录处理未覆盖范围，不以压缩后的摘要代替从未读取过的来源。记忆在准备期间发生变化时，候选发布保留原版本依据，新的修订在后续增量中接上；遗忘依第 11 节处理。

对复用的任务 Agent，同样可以整理有效上下文而保留稳定 Thread 身份。需要独立或并行工作时才使用新的执行身份，关联原背景来源。压缩不清空原交办和产物关系，另开工作也不把来源任务标成失败、覆盖其报告或自动取消它。

## 9. 记忆的内容、来源与关系

### 9.1 自由正文

记忆是对经历的理解。正文可以是一句话、一段叙述、相互关联的要点或有必要保留的精确原文。长度和组织由材料决定，不强制一个事实一行，不强制人物、情绪、主题或性质分类。

例如“偏好柔和蓝色”可以单独存在；“接受蓝色重点色，但反对让整个界面蒙上偏色，这来自此前默认主题的讨论”也可以作为有背景的一段记忆。后者不能因为包含多个相关判断而被强制切碎。

nature、标签、标题和触发线索可辅助阅读与检索，但不作为能否保存的必填语义分类。结构化响应只约束新增/修订等操作、来源引用及目标身份，不约束正文必须回答哪些问题。

### 9.2 事实依据

现有 MemoryService/KnowledgeStore 保持唯一的记忆写入路径。一个保存结果需要稳定身份、正文、所属范围、修订与可回读的来源关系。事件发生时间与记录时间在有依据时分别保留，不能把今天整理的旧事件显示成今天发生。

来源可以是一个或多个原始消息片段、已确认任务结果、明确材料引用或用户直接编辑。直接编辑本身是一次用户写入，不要求它伪装成历史原句。模型归纳保留支撑它的来源，相关推测保留原有表达性质。

引用存在证明来源可定位，不自动证明模型归纳正确。程序检查身份、引用范围与版本；内容质量通过合理的提炼提示和定向行为样例评估，不能用“字符串恰好匹配”替代语义判断。

模型私有推理不作为记忆来源。公开对话、公开思考或执行材料按其真实角色保存；外部资料中的指令不提升为用户授权。

### 9.3 关联与主题概述

关联可以连接同一事项、补充、修订、原始来源和相关经历。确有意义时才创建语义关系，不要求每条记忆生成一张关系图。用于版本替换与派生依赖的结构关系由系统准确维护；模型提出的语义关系可修正。

围绕项目、人物或主题的概述可由 Bot 主动或后台按需形成，正文仍自由。概述引用底层记忆及其版本，不复制成另一份无法更新的事实。来源变化时标记需要更新，读取时可以直接回到底层有效内容；不用阻塞所有查询等重新概括完成。

概述不成为自己的事实来源，不形成循环派生。一个报告被多个 Agent 转述仍指向原来源，不按转述次数增加可信度。已有补充和 supersede 关系优先扩展，不另建一套图数据库。

### 9.4 与其他内容的关系

实时执行状态从 Catalog、Calendar、文件与进程所有者读取。记忆可保存这次工作后来形成的理解和经验，不能把“上周仍在失败”当作当前状态。

文件、知识材料和产物继续由原系统保存，记忆通过引用关联。检索向量与全文索引是可重建的派生资源，正文和来源不依赖嵌入服务才能读取。

## 10. 记忆写入、补记与修订

### 10.1 三个入口共用一个写入者

用户直接保存/编辑、Bot 主动记忆、后台整理都通过 MemoryService 提交。明确“记住”的请求无需等待后台扫描；保存反馈依据原写入回执。用户预览选中段落的整理结果时，预览本身不写入，沿现有保存/撤销流程提交。

Bot 可以主动保存经历、工作经验、理解或疑问，不需要等用户说出特定关键词。后台整理帮助覆盖主模型未主动保存的内容；不开启后台整理仍保留主动记忆与读取能力。

### 10.2 增量材料与连贯片段

从原生持久事件和历史位置发现新增内容，按 Bot 与来源记录处理进度。跨分支共享的原始消息按原身份去重，覆盖范围与读取 witness 分开。恢复时追平未处理位置，不能反复展开整份 Bot 历史再寻找新内容。

片段选择考虑自然交流边界。整理时可以带入必要的前文和相关既有记忆，支持多来源引用，不以一次请求、固定字符块或单条消息作为不可突破的语义单位。已有来源过长时分批读取，只有实际处理过的范围才能推进覆盖。

输入来源优先为真实交流与有意义的结果引用。工具产生的海量原始日志留在执行记录中，Bot 或整理者需要某段证据时按引用读取。用户在子任务内的纠正作为原始用户材料进入增量队列，不伪装成 Bot 说过的话。

### 10.3 后台处理与提交

后台任务按新增材料触发，可在主对话活跃时合并待处理范围并让出资源；不按固定频率强制调用模型做全库反思。启动恢复和必要的来源对账可以扫描游标/元数据，不能等同于每次重读正文。

使用已配置的记忆整理用途模型，保留现有明确选择、禁用与绑定语义；未设置时沿现有 Bot 模型继承规则。专用决策模型可选，不能成为记忆是否可用的前置条件。实际使用量沿原 MemoryWork 记录。

模型得到新增连贯材料、相关既有记忆及必要引用，决定新增、修订、补充或不保存。空提案表示已读范围没有需要写入的内容；模型失败、长度截断和来源不可用不算空成功。

Catalog 保存原整理任务、请求和执行回执，KnowledgeStore 保存记忆变更及对应整理覆盖。两个存储域通过既有 operation 身份与回执协调；Knowledge 写入和自己的覆盖进度原子提交，Catalog 对写入结果进行确认。不得假定跨库存在一笔事务，也不能在响应丢失后重新生成内容再写一遍。

新的用户编辑与后台候选冲突时，重新读取相关版本再决定如何整理，保留尚未处理范围，不用旧候选覆盖新内容。后台结果已经产生时优先继续完成原提交，不额外调用一次模型制造另一个答案。

### 10.4 修订语义

补充增加背景；修订改变当前理解；不再适用让旧内容退出默认召回；遗忘阻止继续使用指定内容。它们分别保留必要的来源和关系，不依靠删除一行来表示所有变化。

旧方案与新方案可能分别适用于不同情况。时间更新不自动意味着新内容全面否定旧内容，简单的向量相似也不能作为自动合并依据。上下文中“正在考虑改方向”与“已经决定改方向”保留原表达。

修订链帮助查清理解的变化；默认召回返回当前有效内容，主动查历史时可以读取旧版本并明确标示。已被用户遗忘的内容不因为历史模式而重新暴露。

## 11. 遗忘、失效与派生内容

遗忘使用原删除/失效能力，并补齐派生依赖和上下文的传播，不只影响记忆列表。

1. 原记忆变为不可用于后续召回；全文和向量索引按原身份失效。
2. 引用该内容形成的概述、候选整理和相关投影标记失效，重建时排除该来源。
3. 尚未发送的请求在准备边界过滤失效材料；已经注入的上下文在下一请求前移除相关正文。
4. 摘要吸收了该内容时，从允许的来源重新生成受影响部分；无法精确切分时重建受影响 checkpoint，不以继续发送旧内容加一句“忽略”代替遗忘。

已经发送给 provider 的请求按真实在途状态处理；未来请求停止继续传播。用户界面依据实际保存和上下文更新状态反馈，不宣称能够撤回 provider 已接收的内容。

“不再记住这件事”与“删除原始聊天/文件”是独立操作。保留原始记录时，整理覆盖与遗忘标记阻止后台再次从同一来源生成等价记忆；原始对话回读不应自动绕过此次记忆排除继续注入模型。用户明确重新引用、重新授权记住时，再形成新的有效写入。

排除关联原条目及支撑它的具体来源片段，不以词语黑名单删除其他独立经历。来源同时支撑其他有效内容时，只重建受影响的理解，保留其余信息。用户自己查看原始历史与助手主动重新摄入来源分别处理；只是纠正一项推断时使用修订，避免误执行为整段历史遗忘。

只保留维持来源排除、版本引用和未结算操作所必需的记录。不可达派生内容与索引按实际引用回收；不能提前删除仍被有效 checkpoint 或未确认操作引用的记录。回收扩展沿原所有者实施，不另建永久复制全文的“审计账本”。

用户要求永久删除原始数据时，复用对应资产删除能力，处理派生内容与实际保留关系，明确删除范围。不会为了实现遗忘顺手删除项目文件或整个会话。

## 12. 自然召回与主动追溯

### 12.1 选择依据

自然召回围绕本次交流或触发事项选择背景；主动搜索直接响应 Bot 或用户的查询。明确的事项/项目关联先取得，关键词与语义候选再补充，最终按实际上下文预算提供正文与引用。

显式关联不交给可选小模型判断是否“足够相关”后再决定存不存在。显式搜索也不被自动召回的过滤器隐藏。候选排序可考虑语义、名称、时间和来源关系，但不设“每出现一次就提高重要性”的循环强化。

缺少向量运行时或嵌入暂不可用时，文本和关联读取仍可继续，返回真实检索方式及失败原因。不存在相关内容与检索能力不可用分别表示。

### 12.2 可用能力

模型应能自然表达查找、展开、追溯、保存和修改这些动作。优先扩展现有 memory 与历史读取工具；工具返回相关正文、来源和继续读取入口，不默认返回全库目录、全部 schema 或巨型关系图。

查询结果需要说明是全文还是片段。时间查询、相关事项和来源过滤可以作为可选参数，模型不必先填写一组分类才能搜索。进一步回读按原身份和访问范围进行，不能通过记忆引用获得本来不可访问的文件或会话。

### 12.3 使用后如何延续

当前请求实际使用过的记忆投影留在原 RequestSnapshot；后续在正常上下文尾部延续或由成功压缩吸收，避免每步重新检索、删掉、再插入。

召回或反复使用本身不把推测转成事实。模型发现现有记忆与用户当前表达不一致时，可以查来源、讨论或修订；系统提供这些能力，不规定一条必经的冲突裁判流程。

## 13. 记忆范围与 Agent 协作

长期总助手的个人记忆是主要入口。既有 user、bot、session 与项目领域存储继续使用各自真实作用域，不因为产品默认面对一个 Bot 就合并数据库。

派发时按任务需要附带相关理解或引用，沿原来源访问权限读取。子 Agent 可以取得该任务可访问的背景、进一步查询或向 Bot 询问，不自动继承用户全部长期经历。一个记忆属于“这个项目”不代表所有访问该项目的外部 Harness 都应收到它。

子 Agent 新发现随原报告返回，并可成为后台整理材料。长期偏好与概述的更新经过统一 MemoryService 路径，不能因各执行者拥有写文件权限就各自获得用户记忆写入权。保留已有被明确授予的记忆权限，不新增按 Agent 名称硬编码的角色禁令。

外部 Harness 使用现有派发时能够提供的上下文和结果观察。没有能力桥接时不宣称它能直接查询 Varin 记忆；需要的背景可以由主 Bot 提供，后续独立设计 MCP/CLI 接入。

用户把普通会话纳入跟进时，可以同时指定是否纳入长期记忆。短期查阅与持久记住分开表达，不静默导入全工作区的历史或所有 Bot 的私人记忆。

### 13.1 任务连续理解与总助手记忆

总助手主要延续对用户和各事项关系的理解；任务 Agent 延续具体工作的背景、调查与成果。首先复用原历史、报告和有效摘要，不为每个短任务默认创建独立记忆服务、用户画像或后台提炼模型。

确实值得跨轮保留的工作理解，通过已有 MemoryService 保存为与原 Thread、事项或项目关联的内容。正文仍自由，记录当时的来源和适用背景；目标变化时可以修订或退出默认召回。可泛用于项目的经验在有实际依据时纳入对应共享知识，临时排查细节继续留在工作历史。

复用目标不是只按 Bot 全局记忆召回；其当前事项与已有工作关联共同参与检索。带背景另开工作可以引用适用记忆，不复制整库或建立另一条互相漂移的修订链。长期个人偏好继续由总助手的统一记忆路径维护。

任务记忆、背景交接和其后摘要均参与第 11 节的来源依赖。纠正或遗忘发生后，下一轮复用不能重新发送失效版本。任务被删除时，必要成果或记忆按原保留关系处理；失去原始记录的引用明确显示不可用，不能虚构可回溯证据。

## 14. 工作台、记忆管理与交互

本轮确定交互职责，具体布局与动画在实施界面前结合现有工作台设计，不直接套用旧稿的三栏或多 Bot 团队布局。

- 默认打开总助手对话，用户无需先选择角色团队或创建计划。
- 工作概览显示正在跟进的事项与相关执行入口，状态来自原任务。可以看到谁在做、发生了什么、哪里需要介入。
- 点击进入真实子任务聊天或外部会话，保留原文件、终端、权限、恢复与协作面板；返回总助手后延续原位置。
- 原 Agent 再次接到工作时保持身份与头像，展示本轮用途及排队/执行状态。旧交办、名称和报告按原轮次保留；带背景新建显示可打开的来源关系，不伪装成原会话继续。用户可以直接继续、查看原工作或要求独立处理，无需每次选择一组高级复用参数。
- 内部回报使用已有协作记录与可展开消息表现，不把每条后台记录平铺成主聊天消息。
- 主对话的记忆入口能看到当前相关记忆并回溯来源；完整记忆管理支持搜索、编辑、修订历史、归档与遗忘。
- 用户可以直接说“这只针对刚才那次”“我现在不这么想了”“这个印象从哪来”，Bot 通过原工具定位和修改，不要求用户找数据库 ID。
- 记忆管理与档案使用同一份数据和保存逻辑，合并重复编辑器；名称、指令和模型的保存方式保持一致。
- 暂停、继续、删除与失败重试保留真实进度。只关闭视图不触发暂停。
- 移动端默认落在同一总助手，通知定位原消息或事项；按已有 Host 连接状态显示工作能力。

稳定头像、Bot 名称和任务名称复用现有身份映射。视觉细节同时兼顾深浅色、文本换行、长内容收起、可打断动效和键盘访问。未确认的新视觉布局不作为底层实现的依赖。

## 15. 所有权、落地位置与成本控制

| 责任 | 继续使用的所有者 | 本轮扩展 |
| --- | --- | --- |
| Bot、Thread、请求与队列 | Rust Catalog / ContentStore | 事项与交办关联、原任务续接、背景引用、按本次请求回报、用户介入更新 |
| 文件、进程、来源与恢复 | Rust Storage 及原资源所有者 | 复用，不建立 Bot 复制工作区或新文件写入者 |
| 日程与条件接续 | Calendar / follow-up 原机制 | Bot 入口目标、相关事项引用 |
| 记忆正文、修订、覆盖与关联 | MemoryService / KnowledgeStore | 自由多来源内容、派生概述、遗忘传播与增量处理 |
| 记忆模型执行 | 原 MemoryWork / Host 模型绑定 | 处理新增连贯片段，保存实际请求与使用量 |
| 语义索引 | 原派生语义存储 | 按记忆版本失效与增量更新，可重建 |
| 请求上下文与压缩 | 原 ContextPreparation / ContextJob / checkpoint | 实际触发检索、复用时的变化材料、选择性背景交接、增量投影与依赖版本 |
| 工作台和移动端 | application-client / UI | 同一事实的展示与原操作入口 |

不自动选择新渠道、不强制安装嵌入模型、不要求 GPU，不为一般记忆写入预建全量向量索引。已有本地或远端嵌入设置可以用于记忆和知识。检索与背景整理使用实际可用能力及用户选择。

前台读取优先于可延后的后台整理；后台内容准备在存储短事务之外执行。修改范围只失效相关索引和概述，不全库重建。用少量相关既有记忆辅助整理，来源量很大时按实际模型预算分批，避免每段新对话重新输入全部个人历史。

历史成员发现沿现有目录与事项关联查询；不为复用建立另一份 Agent 池、任务状态库或常驻进程池。相关上下文投影按来源版本复用，实际文件环境沿 Storage 生命周期按需恢复。后台记忆更新不得迫使每个休眠或已结束的 Agent 唤醒一次。

本轮不引入固定全局条数、字符、并发、模型循环或超时上限。真实协议边界、上下文容量和已有明确预算继续生效。需要具体保护机制时，依据实现中确认的失败模式处理，不把预防性限制写成产品能力。

内部格式调整遵循仓库现有策略：明确新合同与版本，不自动改写不支持的旧库。可选档案字段缺失时取明确默认值；这不能代替对实质存储变更的评估。用户历史、源文件与外部配置作为资产保留。

## 16. 实施顺序与完成标准

这些阶段是工程依赖顺序，不是 Bot 的工作流程，也不表示只实现第一阶段即可交付完整设计。

### A. 统一触发与原事项关系

在现有协作、ingress 与队列基础上补齐回报持久送达、事项引用、空闲处理、待处理结果合并及用户介入更新。完成合法的静默处理结果与通知分离。核对原 Wait 和外部 Harness 的接续路径，避免重复消费。

统一首次派发、再次交办和用户直接续接的身份与结果路由；补齐当前工作补充、顺序交办和并行另开的语义。复用原 members 查询与来源准备，不先搭建新的 Agent 池。

完成标准：主回合已经结束后仍能处理后台结果；复用每轮可独立追踪并回到本次请求者；用户交谈与工作台介入正常生效；重启后继续原处理；内部动作不会逐条通知用户。

### B. 增量上下文与压缩衔接

调整 bot-memory-owner.ts、bot-history.ts 与原 ContextPreparation，从本次真实触发准备上下文。增加原来源位置读取与投递去重，压缩发布接上新增尾部、任务更新及记忆修订。

接入复用目标的未见变化、有效 checkpoint 和相关工作记忆；提供从指定旧工作选取材料的新任务背景交接，明确区分派发方背景继承、旧工作材料引用和文件来源选择。

完成标准：无变化的基础前缀稳定，普通请求不遍历全部历史；旧 Agent 能收到后来决定的新方向，新任务只继承选择的背景；后台结果不会拿无关最后一句用户消息做检索；候选失败不损失对话。

### C. 开放记忆正文与统一更新

调整 selection-memory.ts、memory-organizer.ts、MemoryService、协议和 UI 消费者，移除强制单事实及必填语义分类，支持多来源叙事、补充和修订。保留原写入回执与来源校验，直接编辑作为独立用户来源。

完成标准：一段有背景的记忆可以完整保存与回读；并发编辑不会被旧整理结果覆盖；主动保存和后台提炼不会重复记下同一原内容。

### D. 召回、概述与遗忘闭环

完善事项关联、文本/语义检索、来源追溯、派生概述和上下文依赖。后台处理按来源游标继续，遗忘影响索引、候选、概述和下一次实际请求。

把任务连续理解与总助手长期记忆接到同一来源机制，确保复用和选择性交接也读取当前有效版本；不为短任务默认启动新的后台提炼循环。

完成标准：隔一段时间能回到原讨论；用户改变理解能生效；遗忘不会被旧摘要或下一次补记重新带回来；没有嵌入模型仍能直接读和搜索。

### E. 产品入口、日程与全链协作

整合总助手入口、工作概览、原工作台介入和记忆管理，统一档案操作，接入 Bot 日程目标与跨项目来源。具体视觉另出针对现有界面的设计。

展示同一 Agent 的历次交办、当前用途和相关新任务的背景来源；支持用户直接续接时与 Bot 的交办协调，核对外部 Harness 真实 resume 能力及来源恢复。

完成标准：从交代事项到执行、介入、回报、记忆及再次继续形成完整链路；普通会话跟进与外部执行保留原身份和能力边界。

各阶段同步更新当前领域文档，避免把提案内容标成已实现。实施结束后将稳定机制并入运行时、协作、检索与工作台文档，本文退出活动设计列表。

## 17. 有判别力的验收情境

验收检查实际行为，不要求模型使用固定措辞、步骤或记忆分类。优先扩展已有对应 owner 的测试，结合少量真实上下文样例检查理解质量，不增加庞大的评测平台作为前置条件。

| 情境 | 需要观察的结果 |
| --- | --- |
| 同时交代发布与论文，随后聊其他话题 | 任务独立推进；主对话可持续受理；回报带回自己的事项背景 |
| 小查询和长调查同时出现 | Bot 可直接处理小查询并使用现有派发能力；不受硬编码动作分类限制 |
| 两份报告先后到达，第一份要求继续取证 | Bot 可以继续协作；不强制每份报告都向用户通知 |
| 子任务完成时主 Bot 已空闲或 Host 刚重启 | 原结果触发一次待处理事项，恢复不重复执行已经发生的操作 |
| 用户进入子任务改了方案，再返回总助手 | Bot 得到带用户来源的变化，后续工作沿新方向；原聊天仍可直接操作 |
| 后台处理时用户发新消息 | 沿合法边界进入；不等待所有子任务结束，也不丢失在途操作回执 |
| 最后一句是“好，继续” | 根据当前事项与前文找到相关记忆，结果不依赖短句自身的相似度 |
| 用户说“这次不用设计稿”，后来要求大改先设计 | 两次表达保留适用背景，不形成永久且互相覆盖的错误偏好 |
| 同一消息被三个 Agent 转述 | 来源仍可追到原处，不变成三份独立证据或三条相同记忆 |
| 需要记住一段有前因后果的经历 | 可保存自由叙事与多处来源，不被单事实分类要求切碎 |
| 压缩期间出现新消息、任务结果和记忆纠正 | 发布后保留全部新增材料及有效修订，仍可按引用查原话 |
| 记忆整理断线或模型返回截断内容 | 原范围仍待处理；有明确失败，不提交空成功或新生成的重复写入 |
| 用户遗忘一个被主题概述和摘要吸收的判断 | 后续请求不继续携带它；相关候选、概述与索引失效，后台不重新提炼 |
| 关闭嵌入服务后查询明确记忆或原话 | 文本与直接引用仍可工作，语义能力状态明确 |
| 用户把已有普通会话交给 Bot 跟进 | 引用原身份，按明确范围读取和控制；不重新创建一个替代任务 |
| 暂停后有结果到达，再恢复 | 结果保存；按最新决定处理，已取消工作不会被旧回报重启 |
| 原 Agent 已完成，上次成果又需要修改 | 保留原身份和有效理解；新交办拥有独立结果，不覆盖旧报告 |
| 用户要求沿用调查但重新考虑方案 | 新工作可以取得相关事实和引用，未选择的旧判断不自动全部继承 |
| 原 Agent 尚在工作，又收到独立请求 | 明确排队或另开并行工作；取消待交办请求不取消当前执行 |
| Bot 准备复用时用户已经直接续接 | 原准入处理实际顺序，Bot 不覆盖新输入或重复启动 |
| 原任务由 A 派发，本轮明确由 B 请求继续 | 本轮结果关联 B 的请求和事项，旧父子关系与旧报告仍准确 |
| 旧对话保留，而文件已由用户或其他 Agent 修改 | 本轮取得当前来源依据；隔离更新保留原修改与冲突，不使用旧文字代替文件事实 |
| 在原独立工作区的背景上另开并行任务 | 背景继承与文件方式分别生效，不暗中共享原可写目录 |
| 已遗忘的记忆曾进入旧 Agent 摘要 | 复用与交接排除失效内容；必要时重建上下文或明确新建，外部会话不假称已清理 |
| 原 Agent 已改名，旧请求的回复晚到 | 按原请求/execution 定位，不靠当前显示名误归属 |
| 原外部会话失效或对应 Harness 不支持所需续接 | 返回实际情况，不能静默新建同名任务冒充继续 |

性能验收围绕长历史但少量新增、许多执行但少量相关事项这两类负载。检查实际读取范围、请求前缀、重复注入和模型调用来源，避免仅凭本机短对话流畅就确认长期成本合理。跨 provider 的缓存命中以其实际返回为准；可先用冻结请求比较验证序列化稳定性。

复用验收增加同一工作多次续接与大量历史成员的情况：发现不拉取所有正文，续接不默认调用模型重新交接，停止的任务不为复用保留常驻执行资源。判断质量关注是否延续有用背景并正确处理变化，不以“新任务越少越好”作为指标。

## 18. 已落地的合同与边界

1. 事项使用原 Catalog 的 bot.matter.updated 事件、revision/CAS 和可重建索引；普通会话的读取、发送和记忆关联分别保存，不改原身份。
2. 终态报告按 execution 与本次 MessageRequest 请求者路由，与 Wait 共用消费记录；空闲事件沿原 ingress 准入。静默完成以实际公开助手输出判断。
3. 增量历史使用冻结 head、afterId 和真实范围覆盖；来源回退时重开当前可达视图，已有来源仍按原身份去重。
4. KnowledgeStore 保留唯一写入者。正文与 nature 解耦，多原文引用与同 store 的确切记忆版本依赖均为可选属性；修订、失效和原回执原子提交。
5. 新遗忘范围使受影响的有效上下文从原引用重建，同时过滤召回依据、模型侧原文读取和背景交接；原 UI 历史保留。已经发出的请求按原在途语义处理。
6. Bot 日程使用家目录和 bot:<id> 资产范围，执行归原 Calendar。用户在原生任务内的发言与受跟进任务结果带来源返回；外部执行保持其适配器的真实观察能力。
7. send.afterCurrent 明确顺序交办；任务复用保留每次 execution。普通会话仅通过当前有效跟进关系接入，不扩大所有家族的默认范围。
8. dispatch.background 固定选择原历史材料，inheritContext 沿原含义，projectId/sourceAgent/sourcePath 选择实际文件来源。外部 Harness 的不支持能力明确返回。

当前机制见 [Bot](../bot.md)、[协作](../collaboration.md)、[运行时](../runtime.md)及源码旁说明。
多 Bot 长期协作、外部消息渠道、跨用户共享记忆及外部 Harness 能力桥接继续作为独立议题。
