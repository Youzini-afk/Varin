# Agent 工作侧重与编程协作设计

状态：设计已讨论，待实施。整理于 2026-10-19；现状核对至 `9b6096630`。

本文整合工作侧重、多 Agent 协作、用途命名、任务复用与收纳、文件交换和提示词的设计。近期先完成编程协作基础，科研与日常／办公的具体能力组合随后展开。实现完成后，将有效说明并入对应模块文档。

## 1. 产品方向与近期范围

Varin 的编程、科研、日常／办公三条线共用 Agent Harness。工作侧重影响常用工具声明、能力发现和协作默认配置；实际权限继续由原有配置和资源所有者负责。

| 工作侧重 | 主要需求 | 能力组织方向 |
| --- | --- | --- |
| 编程 | 理解代码、实现功能、调试与维护 | 文件、代码检索、语言服务、进程与脚本；按需组织实现和独立验证 |
| 科研 | 调查问题、阅读材料、开展实验、分析结果 | 学术检索、网页、PDF、材料集合、数据计算与实验能力 |
| 日常／办公 | 处理资料、文档、表格、演示与日常事务 | 文档处理、预览导出、网页与已连接服务，结合图像和交互内容 |

文件、网页、脚本、图像、交互 HTML 等能力可以服务多种工作。模式调整直接声明与按需披露的侧重，其他已启用且实际可用的能力仍可发现和调用。技能沿用现有注入机制，MCP 沿用自身的发现与调用机制。

工作侧重与工作台布局保持独立。科研实验会涉及代码，办公数据处理也会用到脚本；能力组合应支持这些交叉需求。

近期范围包括：恢复 Agent 之间的代码交换，接通实现与验证角色的协作，统一角色开关、可用能力和提示词。三条线的最终工具清单、科研角色配置及办公文件处理方案后续分别设计。

## 2. 当前实现与待处理问题

### 2.1 模式与能力

当前工作侧重只有 `code` 和 `research`，其中 `code` 在界面显示为“通用”。代码检索、语言服务、进程和脚本等共同常驻，因此默认配置明显偏编程。科研模式额外直接声明 `research_search` 和 `research_decide`；PDF 阅读与材料集合在两种模式下均按需披露。

内置子 Agent 预设只有 `worker` 和 `retrieval`。其默认工具集合由原生能力声明汇总，网页、论文、PDF、Office 等扩展工具没有自动进入这些预设的默认集合。普通派发可以使用父任务已绑定的扩展与 MCP 能力。后续需要让角色配置能够一致地组合这些实际能力。

当前关闭 `worker` 还会将普通派发标为不可用。接入验证角色时，需要理清普通派发与各角色开关的关系，使“只启用验证 Agent”的配置能够正常工作。

四个科研模型角色 `researchInvestigation`、`researchExperimentalDesign`、`researchFastExploration`、`researchHighThroughputExecution` 仍存在于类型和设置目录中，当前源码检索未发现其执行消费者。实验执行、日志与产物已有底层服务，面向 Agent 的 `research_submit` 等工具位于需要单独安装启用的示例扩展。

Office 专用接口当前主要连接 Linux 上的 LibreOffice，支持正文读取与末尾追加、单元格值读写、保存和导出。文档结构与格式、公式与图表、幻灯片内容与布局还需完善。Windows/macOS 未共用此专用桥接。

### 2.2 通信和文件交换

当前 `threads`、`read_thread`、`send` 支持任务家族内的发现、历史读取和直接通信。内置 worker 提示已有读取队友工作、协调接口和告知主代理的要求；普通派发未选该预设时，没有这段角色提示。

跨 Agent 文件交换曾有完整实现。2026-10-06 的提交 [`ae4b8ee11`](https://github.com/Youzini-afk/Varin/commit/ae4b8ee11726242b29c064ccb6832f58f49f942b) 加入 `submit_code`，旧版同时提供 `update` 和 `merge`：

| 旧能力 | 已实现的行为 | 当前缺口 |
| --- | --- | --- |
| `submit_code` | 向队友或父任务提交选定文件改动或精确片段，捕获补丁、尝试应用，并通知双方结果 | 工具与提交编排执行链缺失 |
| `update` | 将父任务的已发布版本纳入正在工作的子任务基线，保留子任务修改并报告冲突 | Agent 入口与上层编排缺失；底层 `rebaseBranch` 仍在 |
| `merge` | 将子任务结果合回父任务文件或编辑器草稿 | 现有结果整合与 UI 入口仍在；Agent 的 `integrate_child` 位于示例扩展 |

2026-10-15 的原生运行时切换提交 [`59df3860f`](https://github.com/Youzini-afk/Varin/commit/59df3860fc94f42b5e8c8c83db95af23bfeaf448) 删除了旧工具及 `code-submission.ts` 编排。当前保留三方合并、结果整合、分支与文件存储基础，需要在原生任务体系中恢复上述用户能力。

### 2.3 命名、续接与展示

当前派发参数包含 `task`、`preset`、`workMode` 和 `tools`，用途名尚无独立参数。子会话标题取任务正文第一行；Catalog 已支持修改 Thread 标题，协作工具尚未提供对应改名入口。任务家族工具返回原生 Thread/branch 身份和原始派发任务；工作概览的子任务行仍以原始 `task` 呈现。

已完成子 Agent 可以通过 `send(kind="request")` 或用户续接启动新一轮，保留原 Thread、对话分支和历史，各轮具有独立执行与成果记录。`inform` 留待下次正常处理。隔离子任务续跑以自己上次保存的成果为文件基础；共享只读任务保留原具体工作区来源。

工作概览把完成、失败和取消的子任务收进默认折叠的“已结束”组，但概览计数仍包含全部子任务。右侧任务家族面板全量列出家族成员，主要在打开或手动刷新时更新。现有全局会话保留设置默认关闭，按更新时间执行归档或删除，与子任务是否完成分别处理。

## 3. 编程协作的职责

主代理负责理解整体目标、关键设计和任务关系，并结合实现与验证证据判断最终交付。它需要亲自参与影响整体结果的判断，也可以直接完成工作。

| 角色 | 职责侧重 |
| --- | --- |
| 主代理 | 推进整体任务，选择分工，处理重要取舍并判断交付 |
| 实现 worker | 完成实现或修复，理解相关依赖，保持设计与协作的一致性 |
| 验证 Agent | 独立判断正确性、完整性和设计质量，自主选择验证方法 |

小任务通常由主代理完成。中型任务优先考虑一个实现 worker，保持实现上下文连贯；更大的任务按实际独立性组织多个执行者。任务规模、依赖和已有进展由主代理判断，这些偏好不形成固定人数或阶段规则。

修复使用实现角色，可以延续已有 worker，也可以建立临时修复线程。主代理负责提供必要目标和背景，各 Agent 可以直接交流、查看相关工作、协调接口与交换改动。角色提示不要求每项发现都汇报主代理。

### 3.1 用途名与稳定短码

派发支持可选的 `name`，由派发方表达用途，例如“上下文统计修复”“文件同步验证”。省略时沿用任务正文生成初始标题的现有方式，无需额外模型调用。用途名复用 Thread 标题这一份可修改数据，具体目标和要求继续放在任务正文中。

模型和 UI 使用“用途名 · 短码”识别 Agent，例如 `上下文统计修复 · A7K2`。用途名可以修改、可以重名；短码稳定定位同一个 Agent。示例长度用于展示，实际短码由 Catalog 分配并保存，在同一 Catalog 内唯一，分配时处理碰撞，已发出的短码保持稳定且不重新分配给其他 Agent。短码跨续接、改名和 Host 重启保留，原生 Thread 身份继续承担底层记录关联。

短码直接用于通信、历史读取、续接、改名和文件交换等协作工具，相关返回值统一提供用途名与短码，普通协作无需反复携带长 Thread ID。调用入口将短码解析到原生身份，后续执行复用原有任务关系、分支与资源绑定。指定历史分支、某轮执行或成果时，沿用相应记录引用；短码负责 Agent 的身份。

续接已有 Agent 时，可以同时提供新用途名和任务内容；省略名称则保留原名。新名称随续接受理生效，避免为一次返工额外调用改名工具。另提供独立的 Agent 改名工具，供主代理、相关队友或 Agent 自身在原有协作范围内调用；UI 同样支持改名。单独改名只更新名称，不启动模型，也不改变角色、模型配置或工作来源。

当前列表显示最新用途名，短码作为次要信息，可复制用于调用。报告、消息、状态表与成果入口采用同样的标识。各轮记录保留当时的任务和名称，既有消息与成果仍按稳定身份关联；改名后可以追溯这名 Agent 以前负责的工作。名称变化通过现有元数据事件刷新 UI 和后续动态状态，不改写系统前缀。

### 3.2 复用选择与历史发现

独立的新任务和一次性检索通常使用新 Agent；相关返工、继续原工作或解释已有判断可以续用原 Agent。组织任务的 Agent 根据任务关联、已有历史和当前文件基础判断。保存已结束任务不持续消耗模型 token；续用时才需要处理它的既有上下文。

结果交付携带用途名、短码和成果引用，便于收到反馈后直接找原负责人。上下文中已无相关引用时，通过 `threads` 查询历史目录；目录返回用途名、短码、简短任务说明、状态、时间和文件来源，详细过程再由 `read_thread` 读取。

`threads` 默认查询当前活跃及有明确待处理事项的任务，历史通过显式范围与分页查询。可按所属任务、工作来源和时间筛选，并利用成果记录中的文件改动关系定位相关执行者。历史查询依赖现有记录与数据库索引，正文按需读取；不在每次请求中展开全家族，也不另设模型来评分复用价值或为每次结束生成摘要。

### 3.3 自动收纳与资源周期

Harness 根据执行、结果投递和实际交接记录处理任务周期，Agent 负责协作判断。完成任务退出活跃展示后，其历史和成果仍可查询及续接。

| 情况 | 模型动态状态表 | 工作概览与右侧任务列表 |
| --- | --- | --- |
| 准备、执行或等待中 | 保留当前任务与进展 | 显示在当前任务中 |
| 执行结束，结果尚待交付或已有交接仍未结束 | 保留具体待处理事项 | 呈现交付或交接进度 |
| 结果已交付且后续事项结束 | 后续请求中退出 | 收进历史，退出活跃计数 |
| 再次收到工作请求 | 原 Agent 重新进入 | 更新当前用途名，保留历次执行入口 |

待处理事项来自已发起的操作和明确等待。仅保留一份代码成果不会使 Agent 永久停在待合并状态；失败和取消也作为结果交付，已有后续请求或交接按各自状态处理。投递判断复用现有回执，模型无需额外确认“已知晓”或逐项整理、归档和删除。

UI 默认展示当前工作，已结束任务通过折叠历史入口分页读取。用户正在查看的报告保持打开，列表变化只更新对应状态；未读标记与模型状态表的退出分别处理。工作概览、右侧面板和模型状态表共用原生事实，通过已有事件更新，不额外建立周期性模型整理或整段历史扫描。

执行资源按原所有者记录的实际使用状态回收；成果保存且执行目录已无人使用时，可释放临时目录。续接可以从保存成果重新准备文件来源。会话、报告和成果按现有用户保留策略管理，生命周期收纳本身不新增固定到期删除规则。历史数量增加时，常规请求仍只投影当前任务；按需查询、文件准备和实际续用承担对应开销。

## 4. 实现与验证解耦

主代理可以把验证交给独立 Agent，让实现继续推进。有验证 Agent 承担这项工作时，实现方可以专注实现与修复，测试编写和运行交由验证方按实际需要处理。

验证可采用实际执行、现有检查、临时复现或有针对性的反例探索。新增自动化测试取决于保护关键行为的价值与维护成本，验证完成以足以支持判断的实际证据为依据。

验证围绕用户可感知的功能及其相关实现组织，可以有重点，也需要关注跨模块关系。实现者的交付说明是参考，验证者独立形成判断。除了行为正确性，还要评估职责归属、状态一致性和维护成本，识别重复权威、复杂兜底及缺乏实际依据的限制。

HACK 的价值在于寻找能暴露实际缺陷的反例。验证工作的目标是改善整体结果，问题数量不作为完成标准。

### 可采用的并行方式

实现形成一段可验证成果后，验证 Agent 开始检查，实现者继续推进后续工作。发现问题时，可以从当前实现分出修复线程，处理后将选定修改交回。若问题影响后续工作的基础，主代理调整相关任务；独立部分可以继续并行。

这是一种可选组织方式。验证可以覆盖多个阶段，也可以针对关键变化启动，时机和范围由任务决定。运行时提供派发、执行、通信、来源交接和代码交换能力，阶段安排由 Agent 自主组织。

## 5. 文件来源、阶段交接与代码交换

### 5.1 保留具体工作来源

每个子任务沿明确的文件来源工作，包括父任务当前选中的具体 worktree。共享来源的只读任务可以读取该目录的变化；隔离执行任务使用对应的独立工作副本。

验证 Agent 需要具备运行程序、构建和操作应用所需的能力。现有只读检索预设不能覆盖这些执行需求。只读代码检查可以复用对应来源；验证会产生文件且实现仍在继续时，需要合适的独立执行目录。复用已有目录和准备结果可以减少重复工作，具体策略由现有来源与执行环境机制承接。

### 5.2 阶段成果交接

主代理应能将某个 worker 的阶段成果交给验证 Agent。Harness 负责固定交接内容并记录实际验证版本，阶段成果可在后续实现继续进行时供验证使用。已有快照和结果记录承担来源关联，模型只需表达要检查谁的哪部分成果。

验证反馈保留所检查的版本。修复线程结合当前实现处理问题，合并后再根据变化判断需要补充哪些验证。报告和文件结果应能关联回实际任务，便于主代理判断整体交付。

模型请求中的动态队友状态、环境观察与摘要接续见 [动态上下文投递与摘要能力恢复](context-delivery-and-compaction.md)。计划继续通过现有工具与结果历史使用，不恢复自动 Zone2 计划增量。

### 5.3 恢复代码交换语义

`submit_code` 保留向队友或父任务提交选定文件改动、精确片段的用途；`update` 恢复将依赖来源的新版本纳入工作副本的能力，并支持从指定队友拉取所需改动。旧版 `update` 的来源固定为目标的直接父任务，本次将来源选择扩展到原有协作范围内的相关任务。完整成果整合复用现有 Integration。

推送与拉取共用一套文件交换执行机制：模型表达来源、接收方和所选改动，Harness 处理补丁捕获、来源版本、请求身份及结果通知。无需为了交接先手工创建 Git commit 或维护一套发布步骤。选定改动应保留接收方已有工作，并支持后续继续提交同一文件的新修改。

无冲突的改动正常应用并通知双方；冲突返回具体受影响内容和实际结果，供 Agent 结合当前实现处理。重复请求沿用原请求身份和结果，已纳入改动沿现有版本与合并关系识别。同步发生在实际交接时，不在每次模型请求前扫描所有工作副本。

实现使用原生 Catalog、Source、WorkingState、Integration 和 Documents 的现有职责。旧代码提供行为参考，合并与写盘继续由当前所有者完成。

### 5.4 续接时的文件基础

续用对话历史与选择文件基础分别表达。续接可以保留上次成果，也可以指定当前集成版本或相关队友的阶段成果；Harness 先准备对应来源，再启动这一轮执行。

采用更新的基础时，通过现有三方合并保留仍需携带的改动，并将实际来源变化作为简短环境事实送入本轮上下文。模型无需计算版本哈希或逐个检查所有队友的工作副本。共享只读任务继续绑定原具体工作区，来源选择始终保留对应 worktree 的身份。

## 6. 开关与提示词组装

角色沿用独立启用配置。Host 根据启用状态、模型选择或继承结果、已准备的能力，得到实际可派发角色。工具目录、角色目录与能力提示使用这份共同结果。

| 实际可用配置 | 主代理得到的协作提示 |
| --- | --- |
| 所有协作角色关闭 | 仅保留主代理基础提示 |
| 实现角色可用 | 可以委派实现或修复 |
| 验证角色可用 | 可以委派独立验证，与主代理自己的实现并行 |
| 实现与验证均可用 | 同时提供两类指引，由主代理选择具体分工 |
| 检索或其他角色可用 | 独立组合相应能力指引 |

提示由共同基础与角色短片段组成。角色关闭或实际不可用时，不注入该角色的可用能力指引。配置界面可以继续显示其关闭或不可用原因。

验证角色可用表示主代理可以选择它。是否派发、由谁实现、由谁验证，通过当次任务正文和协作消息表达。worker 使用稳定的角色提示，不按任务自动切换“自行测试”与“专注实现”两套系统文案，也不为这项分工增加字段或触发规则。

Host 的自动组装复用已有配置与能力准备结果，无需额外模型判断。提示片段与工具声明在既有运行准备边界一次确定；`tool_describe` 的详细说明继续进入工具结果。开关修改用于后续运行，已受理任务沿原配置执行，已有停止入口负责结束任务。

## 7. 提示词定稿

以下为本次讨论确定的中文文案，待实现时接入。角色文案表达目标与职责，具体背景和分工由当次任务提供。

### 主代理基础提示

> 围绕用户目标推进工作，保持对整体设计、任务关系和当前进展的理解。结合实际实现和验证证据，调整工作并判断整体交付。

### 实现角色实际可用时，追加给主代理

> 你可以委派 Agent 完成实现或修复，按任务需要组织协作。

### 验证角色实际可用时，追加给主代理

> 你可以把验证交给独立的 Agent，与实现并行推进。由验证 Agent 承担验证时，可以让实现方专注实现，将测试编写和运行交给验证方按实际需要处理。

### 实现 worker

> 理解分配任务在整体目标中的作用，完成实现或修复，保持与相关工作的协调和设计一致性。根据实际发现调整做法，交付可供后续工作使用的成果。

### 验证 Agent

> 从用户目标和系统整体出发，独立判断实现的正确性、完整性和设计质量，关注相关模块之间的实际行为。自主选择验证方法，依据实际证据形成结论，说明重要发现及其影响。验证以支持判断为度，新增测试和改进建议兼顾实际收益、设计简洁性和维护成本。

### 共同协作提示

> 你可以直接与相关 Agent 交流、查看彼此工作、交换代码改动并协调依赖。

共同提示随实际协作能力提供，其中代码交换文案与恢复后的工具能力一起接入。修复复用 worker 文案；检索角色保留现有机制，其后续调整结合模式能力设计。

## 8. 实施顺序与验证

### 第一阶段：恢复文件交换

在原生任务身份与文件来源上接回选定改动提交、来源更新、结果通知和工具入口，复用现有合并与文件写入机制。对照旧实现核对用户可完成的操作，恢复队友之间以及父子任务之间的交接。

### 第二阶段：接通角色与阶段成果

补齐验证角色，统一原生、扩展和 MCP 能力在子任务配置中的组合方式，接通阶段成果与验证执行目录。按实际可用角色组装第 7 节提示，保留用户已有模型、角色和工具设置。

同时接入用途名、稳定短码、独立改名与带名称的续接；完善按需历史发现、动态状态退出和 UI 收纳，统一工作概览与右侧列表的当前任务计数。续接的文件基础选择与文件交换使用第一阶段的同一机制。

### 第三阶段：核对真实协作结果

用一条真实任务检查“实现继续推进、独立验证发现问题、修复线程交回选定改动、整体整合”的过程。重点核对：

- 验证取得指定成果与正确工作来源，报告能对应所检查版本。
- 文件或片段交接保留接收方已有修改，冲突与应用结果清楚可见。
- 验证能运行实际所需的程序，任务通信和阶段交接能推动后续工作。
- 主代理能够结合合并后的行为与设计作出整体判断。
- 角色开关、可派发能力和提示一致，运行期间前缀保持稳定。
- 用途名在派发、改名和续接后正确呈现；短码跨重启与历史查询保持可调用，名称变化不会断开既有引用。
- 完成任务自动退出当前状态与计数，历史可按需找到并续接；历史数量增加不使常规模型输入携带全量目录。
- 原 Agent 返工可以采用当前文件基础，保留应携带的修改，报告关联实际执行成果。

复用已有检查，按新发现的问题补必要验证与少量有长期价值的回归测试。界面使用现有任务概览、消息和文件结果呈现实际进展，保持运行状态的原有来源。

## 9. 实施时需确定的细节

- 验证角色的内部标识、默认模型继承配置和设置页呈现。
- 阶段来源选择及代码交换的具体参数结构，围绕任务目标保持调用简洁。
- 不同文件来源下执行目录的复用与独立准备策略。
- 编程、科研、日常／办公各自的最终工具声明集合，以及科研与办公能力补齐顺序。

这些细节沿本文件的职责和产品语义落实，涉及重要使用取舍时再讨论。
