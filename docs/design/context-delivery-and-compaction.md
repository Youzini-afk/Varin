# 动态上下文投递与摘要能力恢复

状态：待实施。整理于 2026-10-19。现状核对基于 `a2bbe92fc`，历史对照为 `8aecc4a210913da4eb0d47d9ecdeaf78817bd2f7`。

本文确定原生运行时需要补齐的动态上下文与摘要能力。与 [Agent 工作侧重与编程协作](agent-modes-and-collaboration.md) 配合实施：后者负责角色、分工和代码交换，本文负责模型如何持续了解变化，以及压缩后如何接续工作。

## 1. 恢复范围

| 内容 | 本次决定 |
| --- | --- |
| 动态队友状态表 | 恢复每次模型请求的临时尾部快照 |
| 环境变化 | 保留现有原生事件投递，解除对上下文窗口配置与容量准备的依赖 |
| 摘要的近期背景 | 恢复 S0、A、B 三部分输入，让摘要 Agent 参考主对话将保留的近期内容 |
| 摘要只读查询 | 恢复历史、原始工具输出及任务记录的按需读取 |
| 计划内容、更新与删除 | 不恢复自动 Zone2 增量投递；继续使用现有计划工具、结果历史和 UI |

计划主要由模型自己维护，重复推送会增加上下文负担。该决定只涉及自动投递，现有计划能力继续保留。

系统与项目指令、技能、普通记忆、Bot 知识、附件和原始历史沿现有原生机制工作。此前按用户要求精简的角色身份句与技能说明保持现状。

## 2. 已确认的现状

### 2.1 旧版的两种尾部内容

旧版使用 Zone 0、Zone 1、Zone2 描述不同用途：稳定配置与系统内容、只追加的对话历史、本轮新增事实。

每次模型请求先取得环境增量，再生成完整队友状态表，依次追加到消息尾部。环境增量确认送达后进入历史并参与后续去重；队友状态表仅用于当前请求，下一次重新生成。

状态表的主要字段是 `thread · task · state · progress`，展示任务身份、任务内容、当前状态及真实进展。已结束且没有待处理事项的任务会从表中退出。

### 2.2 原生运行时的接线与缺口

当前 `threads`、`child_status`、`read_thread` 和消息投递仍然可用，默认模型请求缺少自动刷新的队友状态表。`tool_describe(name="dispatch")` 返回的是派发配置，动态队友状态需要单独恢复。

用户编辑、终端命令结束、相关诊断和 Git 状态变化已有原生观察链。Host 将事实提交到 Catalog 输入队列，再由运行时写入历史。若新事实在请求准备提交前入队，运行时会消费输入并重建请求。

当前观察发布位于 `ContextService` 的 `prepare` 查询中。Rust 容量准备在 `context_window_tokens` 缺失时直接返回，导致环境观察也跳过发布。这项依赖需要解除。

旧摘要 Agent 收到已有摘要 S0、待替换历史 A、近期保留内容 B，并可查询原始历史、输出和任务记录。当前默认摘要来源只包含 S0 与 A；B 仍在主对话中保留，但没有交给摘要节点参考。当前摘要启动还会清空工具列表，限制为预先提供材料上的文本生成。

## 3. 请求中的内容安排

恢复后的请求继续保持稳定前缀与增长历史，动态材料放在后部：

| 部分 | 内容与寿命 |
| --- | --- |
| 稳定配置 | 系统指令、工具声明及选定资源，沿已有运行准备边界确定 |
| 有效历史 | 当前摘要、保留资源引用、近期原文、用户输入、工具结果及已投递事件 |
| 本次动态材料 | 新环境事实、现有记忆变化等，分别沿所属机制投递 |
| 最后状态快照 | 当前相关队友的任务、状态和进展，仅供本次请求使用 |

Goal、普通记忆和 Bot 知识保留现有语义。状态表在本次请求其他内容完成组装后追加到消息末尾，使用环境数据的来源标记。

状态表不进入对话分支历史，也不进入后续摘要的历史材料；实际已发送请求仍按现有机制保存精确内容，供检查和恢复。压缩、分支导航或恢复后，下次请求重新获取当前状态。

工具声明和系统提示不携带实时队友状态。这样状态变化只影响请求尾部，同一执行配置下的前缀可以继续复用。

## 4. 环境观察的独立投递

环境事实进入每次普通模型请求的准备流程，与容量估算、自动压缩是否开启以及模型窗口是否已知分开处理。

复用当前用户文件修改、终端、诊断和 Git 观察来源。事件关联真实 Thread、branch、Run 和文件来源，继续使用已有事件身份与投递记录。来源、权限和事件内容由原所有者提供。

正常准备顺序为：取得已经就绪的新观察，沿原输入机制交付，再组装模型请求。沿用现有请求与输入边界处理并发到达的事实。已准备或已发送请求保留原始字节，之后到达的事实在后续边界处理。

投递区分事件已记录、已排队和模型请求实际携带的事实。重试与恢复使用原身份和回执，避免重复投递；压缩继续由现有历史边界和摘要接续承担。

观察准备复用已有订阅、游标和缓存。正常请求只处理新增事实与必要元数据，避免重复扫描项目、深读整段历史或额外调用模型。

## 5. 临时队友状态尾部

### 内容

从原生任务关系和现有执行状态生成当前相关队友的快照。每行包含用途名、稳定短码、简短任务说明、执行状态和已有进展摘要。短码可直接用于协作工具，进展引用原记录，详细工作仍可通过现有历史工具读取。名称变化在后续快照中体现，稳定短码保留原任务关联。

准备、执行、等待中的任务保留在快照中。执行结束后，结果尚待交付或已有交接仍未结束时保留具体事项；结果已交付且后续事项结束后，从下一次快照退出。普通失败和取消沿结果通道交付，单纯保存一份成果不使任务永久停在待整合状态。没有相关任务时省略该段。

结果交付携带用途名、短码和成果引用，投递判断复用现有记录，无需模型额外确认或执行清理。历史目录不自动进入尾部；组织任务的 Agent 可以通过 `threads` 按需分页查询已结束任务，再决定读取历史或续接。续接后同一个 Agent 重新进入当前状态表。

工作概览和右侧任务列表使用同一批事实，自动将结束任务收进历史并退出活跃计数。用户未读状态单独呈现，正在打开的报告保持可读。具体命名、发现、复用及资源周期见 [协作设计](agent-modes-and-collaboration.md)。

角色是否还能接受新派发，与已经存在的任务状态分别表达。角色开关改变后，已有任务的当前状态仍可被相关 Agent 了解。

### 生成与使用

每次准备模型请求时读取最新状态。投影复用现有 Catalog 元数据和状态版本，相同内容可以复用格式化结果。状态表使用简短数据文本，具体任务和协作方式由模型判断。

同一请求保留所使用的状态快照；后续请求替换整张临时表。状态表本身不产生历史消息、任务事件或摘要更新，也不启动新的监控、轮询或模型分析。

此能力与直接消息互补：消息承载交流和具体工作，状态表提供当前整体情况。它不要求 Agent 汇报每项发现，也不改变既有消息的唤起语义。

## 6. 恢复摘要的完整工作材料

### 6.1 S0、A、B 的职责

| 材料 | 用途 |
| --- | --- |
| S0 | 已有摘要，首次压缩时可为空 |
| A | 本次将被新摘要替换的历史 |
| B | 主对话继续保留的近期原文，供摘要 Agent 理解当前工作位置 |

新摘要替换 S0 与 A，B 继续保留在主对话中。摘要 Agent 参考 B 判断哪些背景仍有用，避免重复摘要近期原文。

准备时固定三部分的实际范围、顺序和来源。B 优先提供原文；当所选摘要模型容量需要使用节选时，保留条目身份、缺口说明及继续读取的位置。材料选择依据实际模型容量与已有预算设置。

主任务可以在后台摘要期间继续推进。后续追加的历史保持自己的身份，新摘要按已有边界发布；本次模型实际使用的材料继续保留在请求记录中。

### 6.2 按需只读查询

恢复摘要 Agent 的以下能力：

- 检索和读取本次摘要所对应的原始历史。
- 按条目或输出引用读取原始工具结果，补充预览中省略的内容。
- 读取相关任务、线程、跟进和排程等实际记录，理解未完成工作及其关联。

历史查询沿本次固定的来源，当前任务状态作为带来源的当前观察返回。摘要 Agent 自主决定是否查询以及查询多少；无需在首次输入中展开所有相关记录。

查询复用现有读取所有者与原生工具调用记录，摘要执行继续由现有 ContextJob 和运行时管理。具体工具名称可以适配当前接口，工具说明应清楚表达其读取对象和参数。

### 6.3 摘要角色文案

以下文案用于恢复该角色的用途与材料说明，接入时由实际能力提供对应工具声明：

> 为后续工作生成会话摘要。输入中的 S0 是已有摘要，A 是本次替换的历史，B 是主对话继续保留的近期内容。新摘要替换 S0 和 A；结合 B 理解工作进展，保留继续工作所需的背景。
>
> 保留当前目标、有效要求与授权、修正、决定及原因、有用证据、未完成事项，以及继续工作需要的引用。按需要使用只读查询补充材料，区分用户请求、参考内容、计划和实际结果。返回摘要正文。

该说明不要求固定查询顺序或工具调用次数。摘要质量以能否正确接续实际工作为准。

## 7. 与计划和现有上下文的关系

计划内容及其更新、删除不加入自动环境增量，也不放进队友状态表。模型通过现有计划工具及其结果了解自己维护的计划；计划 UI、存储和手动读取保持现状。

已存在的系统资源、技能引用、记忆快照和后续变更继续由各自所有者维护。恢复动态尾部与摘要查询时，保留现有资源来源与请求投影，避免产生重复正文或另一份可修改状态。

模式和协作角色的提示词按 [协作设计](agent-modes-and-collaboration.md#7-提示词定稿) 接入。实时状态表仅表达事实，角色提示继续表达稳定的职责和可选协作方式。

## 8. 实施顺序与验证

先将环境观察从容量准备中解开，并在最终模型请求中接入临时队友快照。随后补齐摘要 S0/A/B 材料与按需只读查询，沿当前 ContextJob 完成执行和发布。

验证围绕实际发给模型的请求与压缩后的接续结果展开：

| 检查点 | 需要确认的行为 |
| --- | --- |
| 未知模型窗口、关闭自动压缩 | 新环境事实仍正常进入模型输入 |
| 队友状态改变 | 后续请求尾部使用最新状态，稳定前缀与工具声明保持原配置 |
| 命名、结束与续接 | 最新用途名与稳定短码可用；结束任务退出当前快照，历史按需读取，续接后重新出现 |
| 历史与摘要 | 临时状态表不累积进分支历史；环境事实沿已有身份投递 |
| 压缩与恢复 | B 在主对话中保留，同时作为摘要背景；导航或恢复后状态快照重新生成 |
| 摘要查询 | 可以读取所需历史、完整输出和相关记录，查询结果有实际来源 |
| 计划修改 | 计划工具和 UI 正常工作，没有额外的自动计划增量 |

优先复用现有检查与一个能体现摘要接续价值的实际场景，针对发现的重要问题补少量稳定回归。性能核对关注重复扫描、序列化与无变化材料的重复投递。
