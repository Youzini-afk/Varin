# 增量上下文管理：稳定摘要块、原文保留与按需回读

状态：**待讨论**，2026-11-04。基于 Varin `59a9e898b` 的现有上下文管理，以及 billion-context `9dc4c945` 的源码和设计研究。本文保留候选方案供继续讨论，尚未确定实施方向，不作为当前开发或交付要求。现有上下文管理保持原状；当前运行行为见[运行时](../runtime.md)、[检索与上下文](../retrieval.md)和[工作台](../workbench.md)。

待继续讨论：压缩后的要求遗漏与理解连续性、整理及回读带来的总成本和等待，以及是否确有必要引入多块／分层管理。让模型重新阅读并输出相同摘要，本身不会减少重复生成工作；“保留已有摘要”尚不能作为确定的优化方向。

## 1. 候选目标与总体思路

将当前“一份总摘要 + 保留原文 + 后续历史”的上下文，演进为按原历史顺序组织的“多个稳定摘要块 + 有用原文 + 新增历史”。后台准备、替换条件、原文读取、模型配置和原子发布继续使用现有链路。

预期改善三件事：长任务中的早期理解少被反复转述；整理成本更多随新增工作增长；遗漏细节有明确、低成本的原文入口。效果以持续工作的质量、总费用、等待时间和实际资源开销判断，压缩比只是其中一个观察量。

候选思路：

- 在原 Rust Catalog／ContentStore 内实现。摘要块是原历史的派生表示，前端、Host 和知识库不另存一份会话正史。
- 优先整理新增且已经用完的材料，已有摘要通常保持不变；需要时局部合并、修订或重新展开阅读。
- 每个摘要块都能追溯实际来源。来源引用由运行时建立，模型主要负责理解和表达。
- 保留模型选择原文的能力，也允许主 Agent 主动请求整理；自动后台整理继续承担日常工作。
- 准备与替换分开。后台结果完成不立即打断当前模型请求，也不自动让正在执行的工具失去来源。
- 原文、摘要、长期记忆承担不同职责。摘要整理不自动写入 Bot 长期记忆，也不改变用户的遗忘决定。
- 不固定三层摘要、统一增长步长或压缩比例，不增加为了层次而存在的状态机和限制。

原生 Agent、Bot 会话、快速检索和原生子任务均使用同一机制。外部 Harness 继续拥有自己的模型循环；这份设计不通过代理改写它们的请求，也不默认接管其压缩。

## 2. 当前基础与实际缺口

| 现有能力 | 当前行为 | 本次演进 |
| --- | --- | --- |
| 容量准备 | 按模型窗口、预留比例、实际请求估算与可用 usage 判断 | 保留完整请求检查，使用新布局计算候选收益 |
| 后台准备 | 准备线默认在输入预算的 75%，可按准备耗时与增长速度提前 | 保留；先整理合适的局部材料 |
| 替换 | 输入预算不足时使用已完成候选，否则进入持久 context Wait | 保留；发布布局变更而非重写全部摘要 |
| 原文保留 | 整理模型返回 `summary` 与 `retain`；关联消息和工具交换按组保留 | 选择作用于本次目标材料，未触及的原文保持原样 |
| 摘要计算 | 已有分批 fold 和可并行的 source／node-output DAG | 继续执行计算，输出多个可独立发布引用的摘要块 |
| 请求投影 | 当前 checkpoint 的一份摘要、保留原文、边界后的新尾部 | 从不可变上下文布局编译请求 |
| 历史回读 | 历史及工具输出保留原记录，支持分页读取和搜索 | 摘要直接连接来源，增加摘要与原文联合定位 |
| 状态界面 | 准备、待替换、实际等待、成功、失败有不同状态 | 沿用状态，增加块级阅读及替换范围说明 |

当前预留比例默认 10%，按完整窗口计算；输入预算为窗口减预留。准备线与预留／替换线的分母不同，界面仍按完整窗口展示换算后的位置，不在这次改造中悄悄更改用户配置。

决定性实现入口：

- [ContextCheckpoint 与请求组装](../../kernel/crates/varin-runtime/src/catalog_context.rs)：目前发布一份总摘要，再加入 retained items 和后续历史。
- [ContextJob 与摘要计划](../../kernel/crates/varin-runtime/src/context_job.rs)、[任务捕获与发布](../../kernel/crates/varin-runtime/src/catalog_context_jobs.rs)：固定材料、模型配方、执行和提交。
- [原文保留](../../kernel/crates/varin-runtime/src/context_retention.rs)：同一输入、响应和工具交换的保留组。
- [历史读取](../../kernel/crates/varin-runtime/src/catalog_family.rs)、[摘要只读工具](../../kernel/crates/varin-runtime/src/summary_tools.rs)：读取真实历史，当前搜索以正文文本匹配为主。
- [Host 上下文设置](../../packages/web/application-host/lib/kernel/context-settings.ts)、[扩展摘要适配](../../packages/web/application-host/lib/kernel/context-compaction.ts)：配置解析与被冻结的算法选择。

“计算摘要时有 DAG”与“发布多个摘要块”分开处理。不能只把现有摘要拆成几段 Markdown 就宣称完成增量管理。

## 3. 从参考项目吸收的机制

billion-context 将消息区间折成摘要块，再按需要把旧块合成更高层的块，保留消息与块的来源关联。可恢复内容在请求外保存，回读可以作为新的工具结果或文件读取，避免为了查看旧资料重新改写整个前缀。

Varin 吸收以下设计：

1. **以局部材料为整理单位。** 已有摘要可以长期稳定存在，新增历史单独整理。
2. **摘要同时提供回读线索。** 省略长材料时，留下足以判断其用途的内容描述和引用。
3. **将模型判断与运行时执行分开。** 模型决定如何理解、取舍和表达；运行时维护来源、工具配对、发布和资源寿命。
4. **让未变化的表示保持稳定。** 不因后台进度、统计数值或展示排序而改写已进入请求的内容。

参考实现的固定层数、增长阈值、提示词清单、代理适配和消息身份猜测不直接移植。Varin 自己拥有 Thread／branch／history 身份，可以直接建立引用。已有工具结果读取也应继续复用。

增量折叠会减少不必要的前缀变化，但从实际改写点往后的缓存仍可能失效。摘要合并也有再理解和信息损失成本。设计选择按这些实际成本作出，不承诺固定节费倍数或无损摘要。

## 4. 数据组织：原历史、摘要块、上下文布局

### 4.1 原始记录与完整交换单元

原历史继续保存在 Catalog／ContentStore，消息、工具参数与结果、媒体和 typed 附件保持原身份。压缩只改变模型下次看到的投影，不删除聊天记录。

运行时沿现有 retention grouping 建立可整理单元：同一用户输入的组成部分、同一响应中相关的公开内容及工具调用／结果、provider 要求共同保留的内容，按原协议关系处理。未结束的工具交换暂不折叠；已完整结束的更早交换仍可整理。

单元身份直接关联原历史，不使用显示文字、行号或内容相似度代替身份。用户选择半个交换时，运行时给出实际需要一起处理的完整范围，模型及界面看到相同范围。

### 4.2 不可变摘要块

一个摘要块保存三类内容：

| 内容 | 作用 |
| --- | --- |
| 标题与自由摘要正文 | 帮助继续理解工作，也说明可从来源找回什么 |
| 有序的来源单元／来源块引用 | 追溯原文、定位历史、验证分支可见性、传播来源失效 |
| 原生成与发布事实 | 关联 ContextJob、模型请求、当时的来源边界和实际 usage |

摘要正文写入原 ContentStore，Catalog 保存关系与索引。块内容生成后不可原地改写；修订和合并生成新块，新布局替换旧块引用。旧请求继续引用它真正使用过的版本。

“被替换的材料”和“生成时读过的依据”分别记录。实际投递给整理模型的只读参考、记忆版本及 `summary_read` 结果也属于生成依赖，后续遗忘与撤权需要沿它们传播。记录依赖到本次确实使用的节点输入范围，不扩大为整个会话，也不让模型猜测某句话究竟受了哪条参考影响。

合并块引用其直接子块，底层原文沿关系可达。不为每个祖先展开并复制一份全部消息 ID 和正文；需要回读时沿来源范围查询，并对重叠来源去重。

层级由实际关系自然形成，不要求所有摘要同时晋升，也不设置固定三层上限。展示时先给正文和来源，内部层数不用成为用户必须理解的概念。

### 4.3 上下文布局

ContextCheckpoint 保留其原有指令、资源和记忆快照职责，增加一份有序的内容布局。布局中的内容段只分为原文单元引用和摘要块引用；捕获边界后的原始历史仍按原顺序追加。

```text
固定指令与资源
  → 摘要 A
  → 仍需完整保留的原文
  → 摘要 B
  → 最近原文与新输入
```

摘要放在它替代区间的原位置，不把所有新摘要搬到系统提示词或用户最新要求之后。整理多个互不连续的区间时分别替换，中间原文保持位置。

每个原始单元在当前布局中有明确的呈现归属：保留原文，或由摘要代替。摘要的证据来源可以包含仍被保留的原文，但不会因此重复装入同一份原始消息。来源覆盖与实际替换范围分别记录，避免“有引用就算已压缩”的混淆。

从一个区间中保留部分原文时，运行时按实际交换边界排列摘要和原文；若保留项把待替换内容分成几段，结果分别提供这些连续段的摘要。模型使用输入中的短引用标明各段，运行时解析位置和配对，不按字符串自动拆分一份已经生成的总摘要。

### 4.4 分支与复用

分叉可以复用祖先中的不可变块。新分支拥有自己的布局，整理和发布只改变该分支；兄弟分支或正在执行的旧请求保持原版本。

只共享当前分支实际可见的来源。子任务继承到的上下文和文件使用现有派发与附件合同；相同摘要 ID、Thread 名称或内容哈希不授予跨会话读取权限。

## 5. 何时整理、何时替换

沿用现有入口，统一创建 ContextJob：

- **自动准备**：实际容量接近准备线，或既有耗时／增长预测提示需要提前准备。
- **用户整理**：现有 `/` 压缩命令、上下文侧栏的重新生成与提前替换。
- **Agent 主动整理**：主 Agent 判断部分材料已经用完，主动请求折叠或指定仍需保留的引用。

本次不加入每累计固定若干 token 就强制压缩的第二套策略。用户配置、实际模型容量和任务中的主动判断共同决定触发；自动关闭时不产生自动任务，显式请求仍沿手动入口处理。

准备与替换规则：

1. 准备时固定当前有效布局、完整历史边界、目标材料和整理模型配置。
2. 主会话继续使用当前有效布局工作，新消息正常追加。
3. 候选完成后保存为待替换结果。常规后台任务继续等待原替换条件；用户或 Agent 明确要求提前整理时，可在下次请求准备边界应用。
4. 替换前，将候选布局与实际新尾部、指令、资源、工具声明和媒体一起计算，判断完整请求是否可发。
5. 候选可用时原子发布；尚不可用且当前请求仍可发送时继续工作；实际放不下才进入原 context Wait。

候选完成后尾部增长导致仍然放不下，以候选中的有效块为基础，创建具有新固定边界的后续 ContextJob，只补充必要的整理范围。原任务的范围、配方和模型回执保持不变；UI 可将这次继续准备聚合展示。不能每次都从全部历史重新生成总摘要，也不能把失败任务重新挂成同一条“正在准备”无限循环。

没有可进一步缩减的材料、单个必须保留的内容超出真实模型窗口、所选整理模型不可用等情况，返回对应原因及实际需求。原有效上下文保留，不通过静默删消息、媒体或工具结果假装解决。

## 6. 怎样选择整理材料

候选选择先利用原历史元数据，找出已完成、尚未折叠的交换，以及已常驻的摘要块。默认优先处理较早的未折叠增量；年龄和大小用于组织候选，不作为“内容已无用”的证明。

一次整理关注以下材料：

- 实际需要折叠的原文或待合并的摘要。
- 与它相接的必要上下文，以及最新用户要求和近期完整交流，用作理解当前工作与目标变化的只读参考。
- 目标涉及的真实任务／记录引用；需要现状时通过已有只读接口读取，记录观察位置或时间。

不会把全部旧摘要、所有子任务、全套记忆和工具日志作为每次整理的固定输入。也不会只给一段失去上下文的工具输出让整理模型猜用途。

整理模型可以留下仍在使用的原文，可以缩小建议范围，也可以判断本次没有值得折叠的内容。此类结果正常结算；同一材料和同一观察条件下不立即重试。新增完整交换、容量变化或显式新请求再触发下一次判断。

旧摘要合并按相邻或紧密关联的历史范围进行。若某份仍有价值的摘要不在范围内，保持原引用不变。多个主题交错时保留多个块，避免为了合并而将历史关系重新排序。

## 7. 整理模型的输入与提示词

### 7.1 输入分工

继续使用当前 `harness.models.contextCompaction` 的模型、思考强度、温度和可编辑工作指令。

输入明确区分：

1. **本次目标材料**：可以整理的具体单元及块，携稳定引用和估算大小。
2. **只读参考**：帮助理解当前工作，不属于本次替换范围。
3. **继续工作所需的容量信息**：目标是新摘要和保留原文的合计大小；实际完整请求仍由运行时检查。

引用由运行时提供短名称与真实身份映射。模型不需要抄写长 UUID，也不需要自行维护消息索引。短名称只在明确的输入范围中解析，落盘与工具回执使用可重启解析的稳定引用。

### 7.2 默认工作指令方向

保持现有开放写法，建议表达为：

> 整理选定材料，使后续交流与工作能够延续已有理解。结合材料及参考上下文判断什么仍需要原文、什么适合概括，以及怎样表达其中的联系和变化。
>
> 摘要记录这些材料在对应历史位置表达的内容，保留其来源、适用范围和不确定性。对省略的长材料，可以留下有助于日后定位的内容线索；需要核对时使用只读查询。原文仍可通过运行时提供的引用读取。
>
> 在给定的继续工作容量内组织摘要和保留原文。只读参考用于理解，不属于本次替换内容；没有必要改动的部分可以保留。

格式由运行时另行提供：用材料短引用表达待替换的连续段，为每段返回摘要，再列出希望保留的原文引用，允许不折叠。段必须来自本次目标，保留组可以使结果分成几个较小段；来源依赖和插入位置由运行时核验与生成，不要求模型复述元数据。未被有效替换覆盖的材料仍保留原文，不能因为模型漏列就消失。

不强制每个摘要包含目标、决策、TODO、路径、数值等固定栏目；这些内容是否重要由真实材料决定。错误、代码和用户原话需要精确时可保留原文或准确引用，避免将改写后的内容标成逐字引语。

### 7.3 分批与大单元

使用现有摘要执行 DAG 和实际整理模型窗口规划分批。每个独立范围可以并行生成；相互依赖的合并使用明确的前序输出。中间结果不提前成为主对话的有效上下文。

一个完整交换过大时，读取和摘要计算可以分页，最终仍对同一完整交换提交。阅读片段不能变成截断的工具协议；必要时用原 `summary_read output` 继续读取，并明确已读范围。

合并结果可重新读取原文，尤其是来源摘要存在分歧、精确值不清楚或当前问题需要细节时。已有摘要作为派生材料，不能伪装成新用户要求或已核实的工具观察。

## 8. 主 Agent 的主动能力

提供一个轻量的整理请求能力，进入同一个 ContextJob owner。主 Agent 可以交办“整理已经用完的历史”，也可以附上明确范围、希望保留的引用或已有摘要。范围省略时由现有整理计划选择，不要求每次调用前遍历全部历史。

主 Agent 已有合适的摘要时可以提交为候选，复用原校验与发布，不强制再调用另一模型改写。同样，主 Agent 只想交办整理时也无需自己写完摘要。

调用正常返回已受理的任务引用及真实状态，后台继续进行；若执行确实需要等待，沿已有 context Wait 释放运行槽位。工具响应不把“已受理”说成“已完成替换”。任务观察和 UI 使用同一 ContextJob 结果，不新增一套压缩任务账本。

整理能力按现有工具目录披露。主提示只需说明可以整理和回读历史，不要求每轮反思窗口、必须调用某工具或遵循固定步骤。模型不主动使用时，自动准备链路仍然完整。

## 9. 发布、并发与恢复

发布的是对既有布局的明确替换：消耗哪些当前段、产生哪些块和保留段。长文本读取、模型调用、分词与布局编译在短数据库提交段之外进行。

提交核验以下实际关系：原任务是否完成且未取消；来源是否仍可见；被替换的段是否仍是同一版本；新布局的来源、工具交换与附件关系是否完整；实际待发请求是否满足容量要求。

| 准备期间发生的变化 | 处理 |
| --- | --- |
| 同分支追加消息、工具结果或子任务回报 | 保留尾部，重新计算待发请求；旧区间的摘要仍可使用 |
| 用户改变目标 | 新要求保持在尾部；旧摘要表达原历史，不把旧目标重新提升为当前指令 |
| 另一任务整理了不相交的段 | 检查两组目标仍未变化，基于当前布局重新组合并做 CAS 发布；不重复调用模型 |
| 被替换的段已由另一候选处理 | 未发布候选保持其结果和原因，不覆盖新版本；重新规划时可复用仍适用的内容 |
| 分支切换、编辑或恢复历史 | 只向原分支及有效 ancestry 发布；界面当前选中对象不改变归属 |
| 记忆遗忘、来源撤权或来源排除变化 | 原相关候选不得发布；受影响块按第 12 节重建 |
| 主模型／容量改变 | 已受理整理任务仍用冻结配置；新请求按实际模型重新计量，不让旧估算替代新检查 |
| 取消或观察断开 | 取消按原任务执行；关闭面板、断线不等于取消 |

布局 revision 的 CAS 保留。不相交变更的组合必须验证实际输入段与依赖，只把新布局基准移到当前版本；不忽略冲突或靠重试次数掩盖冲突。

一次发布原子提交块引用、布局、原任务回执与事件。调用方丢失响应后读取原回执；已成功生成的结果可以恢复提交，不重新调用付费模型。模型派发效果未知时沿原执行恢复规则处理。

新的 checkpoint 只影响后续 RequestPrepared。已经派发的模型请求、工具参数、运行来源和附件读取继续使用原快照。

## 10. 缓存与实际运行成本

固定块使用固定正文、角色、稳定引用及序列化。块的标题变化也是新修订；UI 的展开状态、阅读次数、相对时间、实时 token 数与进度不进入模型历史正文。

原位置替换使变化从实际被替换的区域开始。靠前的旧块合并会影响较长的后缀，因此先整理新增原文，只有确有容量或理解收益时再合并旧摘要。不能为了“层数整齐”频繁重写前缀。

原文回读通过新的工具结果追加，原块不自动展开回原位置。明确选择让某段原文重新常驻时，作为新的布局变更处理，并计入实际容量。

沿用原 provider 协议适配和来源标识。摘要以派生历史材料呈现，不提升成系统权限，也不伪装成新的用户发言；签名思考、工具配对等 provider 原始单元按既有合同保留。

本地请求编译复用未变化段的投影和分词结果。缓存身份包含实际内容、模型协议／模板和 tokenizer；切换模型时重新计量必要部分，不重新生成全部摘要。

长会话中，请求准备不加载完整历史或递归展开摘要树。当前布局加载当前需要的正文；来源追溯、旧块读取、全文搜索分别按查询取数。共享祖先使用同一不可变对象，内存缓存随实际使用释放。

## 11. 原文回读与历史搜索

### 11.1 统一入口

在现有 `read_thread` 和摘要专用 `summary_read` 的读取能力中接入摘要块。读取可以取得块正文、直接来源、指定历史范围或单个工具输出；大正文沿已有分页协议返回可继续的位置。

来源页默认列直接来源的紧凑描述，真正打开时再读取正文。用户或模型可以沿摘要继续下钻，也可以从命中的原始消息直接读取，不必逐层走完所有祖先。

回读返回原始记录的角色、来源、当时身份与确切版本，作为本次读取的材料。文件附件通过原 typed 引用访问；远端文件不能被转换成当前 Host 的同名路径。

读取不到时说明具体来源已经删除、被排除、无权访问或暂不可用。空结果只描述本次查询范围，不能写成“从未讨论过”。

### 11.2 摘要与原文联合搜索

搜索同时覆盖当前与历史摘要，以及授权可见的原始消息。结果给出命中片段、属于摘要还是原文、所处历史位置和可读取引用；即使一个词没有写入摘要，仍能从原文找到。

在 Catalog 的现有文本范围索引与历史身份上增加可重建的关键词索引。精确短语、错误串和标识符匹配优先，关键词相关度帮助定位，中文和英文都要有可用的切词／子串行为。初始实现不依赖嵌入模型或向量服务。

索引保存检索所需的词项、位置和原文引用，命中片段从原对象读取。现有范围／分页读取语义不变；相关度搜索使用明确的查询类型与游标，不悄悄改变旧搜索的顺序和继续读取规则。

新增原文与摘要按实际新增范围索引，旧历史后台增量补齐。索引进度和查询覆盖范围真实可见；尚未覆盖的历史仍可通过原分页搜索读取，不能因为新索引不完整就返回确定的零命中。首次打开会话、请求准备和切换子任务不等待全库扫描。

查询先固定可见分支／来源范围，命中读取再次经过原 owner。衍生索引不成为权限入口，也不复制一套可独立访问的完整历史正文。候选排序和分页基于固定查询视图，新消息不会让正在续读的页重复或漏项。

### 11.3 回读可发现性

摘要的来源入口常驻且简短；当工具正文被缩减时，结果中直接带原输出引用。引用应说明那里有什么，不只留下不透明 ID。

可以给模型一句“需要精确细节时可读来源”的能力说明。避免每轮重复提醒，也不自动把大量检索结果注入上下文。保持 Agent 自己判断何时需要更多依据。

## 12. Bot 记忆、纠正与遗忘

摘要块记录本会话在对应历史范围发生和理解的内容。长期记忆保存跨会话仍值得使用的知识，继续由 MemoryService／KnowledgeStore 的主动写入、自动提炼与整理维护负责。

上下文整理不顺带创建长期记忆；记忆整理也不接管上下文布局。Bot 的当前事项、任务状态和 incoming 回报仍从各自 owner 投递，不把旧摘要中的“正在执行”当成实时状态。

新消息纠正旧认识时，保留纠正的真实位置。局部摘要可以写明结论如何变化，或在后续合并时表达更新后的理解；不对旧原文进行历史改写。普通事实更新只触及相关块，不要求所有历史摘要重新生成。

遗忘与来源排除沿现有模型侧过滤语义传播：

1. 原 owner 标记被排除的来源范围或记忆版本。
2. 通过摘要的直接依赖关系找到受影响块及其后继。
3. 这些正文退出后续模型投影、模型回读和搜索；从仍允许的原始材料重建受影响范围。
4. 其他块保持稳定，已生成但未发布的相关候选也不得重新带回排除内容。

若块混合了允许与排除材料，在重新整理前使用仍允许的原文投影；容量不足则沿原准备／等待路径处理，不用含排除内容的旧摘要临时顶替。

原始用户聊天按现有资产合同保留，UI 的历史查看权限与模型侧遗忘语义分别遵守原 owner。已经派发给 provider 的请求保持真实事实，遗忘影响后续请求与读取，不伪造撤回已发送的内容。

## 13. 工具结果与媒体的处理

本次复用现有输出可见预算、历史输出读取、材料和附件能力。超长结果的首个可见返回应尽量包含本次操作结果、关键错误或命中概况，以及明确的完整输出入口。

某些结果仍需要完整内容才能判断，如正在定位的错误、重要实验数据或原文核对。是否适合缩减由工具用途和本次需要决定，不统一改成只有路径的占位符，也不新增所有工具都经过摘要模型的调用。

结果缩减发生在首次模型投递时，形成固定表示；之后反复重发使用同一表示。后续折叠可以引用这份结果及原输出，不能把工具日志中未读到的部分表述为已经核实。

图片、PDF、Office、网页快照及文件交接继续保有原 typed 附件关系和材料快照。摘要中的文字描述帮助定位，原图和原文件通过原读取能力取回。媒体费用未知时仍标为未知，不用文本估算冒充完整成本。

## 14. 存储、释放与升级

### 14.1 生命周期

来源引用、块正文与布局使用原 ContentStore 的不可变对象及依赖关系。压缩不会复制一份完整聊天目录；合并也不复制祖先原文。

回收区分以下内容：

| 内容 | 保留与释放依据 |
| --- | --- |
| 原始聊天与附件 | 原会话、分支、派发、材料和读取 owner 的真实引用 |
| 摘要块及来源关系 | 当前／历史布局、派生块、冻结请求、用户可读取的发布历史 |
| 候选和中间结果 | 仍在运行、待发布、可恢复或被后继节点使用；完成结算后释放冗余部分 |
| 搜索索引 | 从来源派生；随来源生命周期删除，可重新构建 |
| 运行时投影和计数缓存 | 当前读者及实际复用；不作为持久历史的额外根 |

保留历史发布结果供用户查看，不把每次预览、未采用候选和摘要模型的全部临时输入永久变成 GC 根。ContextJob 结算且执行者真正结束后，保留必要回执、最终输出与来源，显式释放可重建的准备正文和中间推理。

删除会话沿当前 tombstone、执行结算和引用回收路径，新增摘要关系必须一并参与。仍被其他分支、合法派发或冻结请求使用的内容保留；最后一个真实引用释放后由原 owner 回收。不能仅把块设为 inactive 而一直堆积不可达对象。

### 14.2 现有数据升级

由原 Catalog owner 自动将现有单摘要 checkpoint 转换为新布局中的一个摘要块，加上原 retained items。保留原摘要字节、checkpoint 身份、through 边界、来源权限和既有请求回执，不重跑模型，也不扫描并复制全部正文。

旧摘要只记录到历史边界时，来源按这一已知范围表示，不伪造更细的逐句出处。旧 retained items 的布局顺序首先保持现有请求投影；后续真正进行局部整理时再生成新的位置关系，避免升级当天无故改变模型输入。

已保存的 `RequestPrepared` 正文与 provider 专用内容原样保留，升级不重新序列化已经发送的请求。冻结的旧摘要任务转换为新结构中的等价单段计划，继续其原调用与回执，不能因升级更换摘要算法或重发已派发的请求。

真实持久结构变化与格式标记在原升级事务中提交，随后业务只使用现行表示。派生检索索引单独后台补齐，不作为打开库的前置条件。升级失败保留原数据和明确原因，不要求用户手动修复普通旧版本数据，也不新增永久旧格式执行分支。

## 15. UI 与设置

沿用当前聊天状态行和上下文侧栏，不另建压缩控制台。

- 准备中仍可输入、浏览、调用工具；候选完成显示待替换；只有实际 context Wait 才显示阻塞等待。
- 完成提示说明本次整理的实际范围和结果；尚未测量新请求时显示待计量，不把估算节省当成账单节省。
- “当前摘要”改为按当前布局显示的摘要列表。默认紧凑标题及短预览，展开看完整正文，再点来源进入原消息或输出位置。
- 保留原文在对应位置可见；历史结果展示当时的布局与发布事实，不随当前摘要变动而改变。
- 多个块在同一任务内生成时聚合为一次准备进度，不为每个节点刷一条聊天通知。
- 比例条继续区分系统、用户、助手、普通工具、MCP、摘要及其他成本，保留准备与替换刻度。块的数量不冒充容量。
- 加载、展开、关闭沿已有可打断动效；不预加载全部原文，不因摘要流式增长把用户阅读位置推走。

设置继续使用现有自动整理、后台准备、预留比例、准备线和上下文整理 Agent 配置。原 `keepRecentTokens` 继续按原文额度解释，具体保留位置由模型判断；不新增固定“保留最近 N 条”的规则。

这次不添加摘要层数、块数上限、每层配额和强制压缩周期等用户必须理解的设置。未来确有用户需要再增加明确控制，而不是把内部算法全部铺到设置页。

## 16. 实现落点与交付顺序

| 责任 | 落点 |
| --- | --- |
| 摘要块、布局、来源关系与升级 | `varin-runtime` Catalog、ContextCheckpoint、ContentStore dependencies 与原升级器 |
| 材料选择、模型计算与发布 | ContextJob、context retention、summary tools、context execution 和 budget owner |
| 请求编译与容量 | 原 context projection、request preparation、tokenizer／usage 校准 |
| 历史搜索与块读取 | 原 family history reader，补派生索引和摘要来源读取 |
| 记忆失效传播 | 原 memory exclusion／personalization 与块来源依赖 |
| 配置、扩展与远端 | 原 Application Host；框架无关 API 继续由 application-client 定义 |
| 界面 | 原上下文侧栏、聊天状态行、`/` 压缩入口与历史导航 |

所有依赖当前摘要的消费者一起迁移：标题生成、下一步建议、派发与上下文继承、分支导航、资源／个性化刷新、记忆排除、历史导出和上下文侧栏。它们读取同一个布局接口，并按自身任务选择所需块和近期原文；纯展示可以按序拼接，不能为兼容旧字符串字段再维护一份会不断重写的隐形总摘要。历史导出仍以真实历史为准，摘要视图与完整对话明确区分。

若后续确认采用本方案，可参考以下依赖安排实现；当前不作为施工顺序或交付范围：

1. **统一表示与自动升级。** 旧 checkpoint 可正常打开，新布局能按原顺序编译，原请求恢复与附件可达性保持。
2. **增量准备与发布闭环。** 多块输出、局部 retain、旧块合并、并发追加尾部、候选复用和真实等待完整接通。
3. **回读与来源失效。** 摘要／原文联合定位、分页、分支作用域、遗忘传播、历史结果和资源回收完成。
4. **产品接线。** 主 Agent 主动能力、现有手动入口、上下文侧栏和多端 DTO 使用同一事实。

现有 `varin.context.budget@1` 与 `varin.context.compaction@1` 的职责仍分开：前者决定容量与执行时机，后者产出整理计划。多块结果改变算法合同，需明确升级版本和生成协议；已受理任务使用原冻结语义完成。原单结果计划可以作为新布局的一次整段替换表达，不能把旧扩展输出误当成局部多块计划。

全链路期间不引入另一套 TS 历史写入者、并行摘要数据库或透明代理。外部 Harness 如以后需要接入，应由明确能力协商设计，保持其原执行权威。

## 17. 验收重点

验证围绕真实行为复用原测试，避免为每个字段、每层转发重复造测试。

必须覆盖的行为包括：

- 连续两次局部整理后，未触及块的正文、来源和请求表示稳定；合并后仍可找到原始细节。
- retain、并行工具调用及结果、provider 不透明内容、图片和文件附件组成合法请求。
- 后台准备期间新增用户纠正、工具结果和子任务回报，发布后尾部不丢、不重复，也不重放旧任务。
- 相交与不相交候选、取消、响应丢失、重启、主模型切换均使用原身份和真实回执。
- 分支共享、跨任务已授权来源、遗忘和会话删除后的读取与回收结果正确。
- 旧单摘要数据自动升级后能继续对话；索引未补齐时仍能读取旧历史，查询覆盖如实表达。
- 用户能通过当前侧栏看到准备／待替换／实际等待的区别，打开摘要来源时阅读位置稳定。

质量与成本使用少量有代表性的长任务对照：持续调试与代码修改、含精确数值或引文的科研／办公、跨话题并多次纠正的 Bot 会话。比较现有方案与新方案的任务延续、事实回读、反复探索、总模型费用、缓存读取／创建、等待时间及本地存储和内存。

验证逐步服务实现判断，不建设一套独立评测平台。模拟模型用于确认协议与持久化；真实模型对照用于判断摘要质量和是否值得调整默认策略。没有证据时不宣传固定节费百分比，也不把“没有爆窗”当成内容质量验收。
