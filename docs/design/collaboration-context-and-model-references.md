# 协作上下文、任务查询与模型引用

状态：**设计提案，待实施**。2026-11-11；源码核对基线为 `main@c6a429f05`。本文统一协作信息投递、任务读取和面向模型的引用方式，不代表这些改动已经进入运行时。

本设计接续[长期总助手](bot-assistant.md)中的协作与上下文设计。当前产品行为仍以[协作](../collaboration.md)、[运行时](../runtime.md)和源码为准。

## 1. 目标与已确定的取舍

模型应把注意力用于理解任务、选择对象和决定动作。系统负责把它选中的对象解析到正确的执行、消息、文件版本和资源所有者。

本轮一起处理三个问题：

1. 去掉每次模型请求临时组装的全队状态概览，以原有消息和报告投递延续协作。
2. 任务目录适合发现工作，单项查询适合判断进展，历史读取适合追查依据；返回内容与实际目的相称。
3. 对模型提供简短、稳定、可直接用于后续操作的引用，把内部定位和重复校验信息留在系统中。

提示词继续保持开放。查询时机、是否等待、怎样分工和汇报，由模型结合任务决定。此次不增加“每轮检查任务”的流程，不给压缩模型规定必留栏目，也不增加逐请求运行的上下文规划模型。

明确范围：

- `fix/cache-stable-team-context` 分支中“每次变化追加完整概览”的方案已放弃，**不合并、不作为本案实现基础**。
- #330 连续命中 11,008 tokens 的具体根因尚未证实。本案修正已确认的上下文组装问题；验收不能把结构改进等同于该线上问题已经解决。
- 价格与缓存创建量采集由 [PR #333](https://github.com/Youzini-afk/Varin/pull/333) 独立处理。
- [增量上下文管理](incremental-context-management.md)仍为待讨论方案；本案不引入摘要分块、强制保留清单或新的压缩算法。

## 3. 协作信息怎样进入上下文

### 3.1 使用既有事件与消息，停止逐请求概览

删除 Engine 的逐请求 `teammate_context` 拼接及专用概览读取。界面的工作概览继续从实际任务状态读取，模型通过工具查看需要的信息。

进入模型上下文的协作材料来自实际发生的交流和交付：

- 派发工具结果提供接收者、工作已受理的事实及后续可用引用。
- Agent 主动消息沿既有 `send` 通道送达。
- 结束、失败、取消及准备失败形成原任务的报告通知。
- 提问、权限请求、用户介入和已存在的工作事件沿各自入口送达。

工具启动、文件读取、分支 head 推进、普通运行阶段变化继续用于查询与界面，不自动翻译成一条条模型消息。Agent 仍可自行发送阶段发现和讨论；系统不要求它按固定频率汇报。

### 3.2 送达后固定位置，后续追加

现状与目标的区别：

```text
现状
请求一：历史 H → 临时概览 S1
请求二：历史 H → 助手 A → 工具结果 T → 临时概览 S2

目标
请求一：历史 H → 已送达消息 M
请求二：历史 H → 已送达消息 M → 助手 A → 工具结果 T
请求三：以上历史 → 新到报告 R
```

同一条消息的正文、引用与历史位置在送达后固定。重命名、列表排序或当前状态变化不回写旧消息。修改要求由新消息表达；显式回退、遗忘和上下文压缩仍使用原机制。

模型正在生成时到达的消息进入原输入队列，不修改已经冻结的请求。立即发送与本轮后发送继续遵循当前输入边界；模型可以继续完成当前工具批次，并在相应边界接收新增材料。

### 3.3 补完整报告交付，复用原入口

把现有 Bot 报告交付抽成原委派执行的报告交付能力。每份报告按**这次执行的实际请求者及其接收分支**路由：首次派发回到派发者，复用 Agent 的后续交办回到该次交办者，不一律回给最初父 Agent。

报告通知直接引用原 execution 和原最终输出，不调用辅助模型生成第二份总结。通知给出是谁、哪次工作、结果状态和原答复的可读预览；完整正文和附件可继续读取。长正文遵循已有输出预算与续读机制，不另设固定长度。

运行中的普通 Agent 在后续输入边界收到通知。已经空闲的普通 Agent 沿既有等待、接续或下次输入机制处理；不会仅因移除概览而新增自动启动策略。Bot 的报告驱动接续沿现有规则执行。取消中的父任务保留结果，取消本身不会被报告到达反向撤销。

接续与报告投递是两件事：报告可以已保存、已排队，而接收者暂未运行。既有 UI 可表达这些实际状态，不因报告产生就向用户弹出子任务完成通知。

新通知从原报告发布事件产生。升级首次启动不遍历全部历史执行来补造通知；升级前已受理、升级后才结束的工作仍按其真实结束事件正常交付。

### 3.4 等待、主动回报与读取之间的去重

`wait_child`、自动报告和报告读取引用同一份原报告。已有通知在队列中时，等待完成复用这条通知；已有报告进入本分支历史时，后续等待返回原结果入口，不再附送同一大段正文。后续执行有自己的报告，不被前一次的投递记录吞掉。

送达记录由原历史提交事务建立：原通知进入接收分支，或明确读取原报告的工具结果进入该分支历史，才留下对应交付事实。只在目录中列出任务名称或“已完成”，不记作报告交付。报告通知已交付也不推断模型已理解或用户已知晓。

因此要移除对 `teammates:` 文本及其中 `reportCursor` 的反向解析。`scope=current` 根据实际活动、未结算交接及尚未交付的报告判断，不能继续依赖概览是否出现过。历史 `agent-status` 记录保留原含义，但新流程不再产生这种文本驱动的回执。

### 3.5 压缩、恢复与可查询范围

协作消息、报告和查询结果作为普通历史参加现有压缩，由模型判断如何整理。这里不增加协作专用摘要、不在压缩时强塞全队快照，也不规定必须保留哪些栏目。

后台压缩准备期间到达的新消息沿既有新增尾部保留。重启从原历史和未处理队列恢复，不补播所有旧报告。缺少某项背景时，Agent 可以通过任务查询重新获取。

Varin 查询普通工作台、IDE 会话以及用户创建的任务的能力保持。主动通知遵循实际接收关系；查询能力范围不转换成每轮自动注入范围。Bot 会话不因本案变成可递归检索的普通任务。

## 4. 任务查询：发现、进展与历史

### 4.1 `threads` 是任务目录

目录默认提供名称、Agent 短码、当前状态、足以区分工作的说明和读取入口。列表中的任务说明优先使用现有用途名、标题及已经有的原任务预览；不额外调用模型制作摘要。没有现成预览时先使用名称，完整要求在单项读取中取得，不为了凑一段说明反查每个任务的大正文。普通会话没有派发正文时，不编造一段任务说明。

完整派发正文、来源配置、全部分支与各分支 Run 明细转到单项读取。目录发现阶段不读取这些大正文，不为了返回一页名称扫描全部历史。

保留目前的当前／历史／全部范围，以及名称、工作区、父任务、更新时间、成果路径和分页。默认分页仍使用既有配置，调用者可以按需调整；本案不增加任务数量或可查询范围上限。

“当前”仍包括实际运行、准备、等待和确有未交付事项的任务；运行已经结束、报告待交付可以同时表达。不能因为看过一次目录就将它算成完成交接。

### 4.2 单项概况直接回答“它现在怎么样”

在现有 `read_thread` 中增加概况读取，接受 Agent 短码或现有会话身份。`child_status` 共用这份状态读取能力，再补委派执行自身的信息。

概况提供：当前执行状态、实际等待事项、最近助手消息、正在进行的动作，以及现成报告或成果的入口。没有进行中的动作时显示最近完成的动作；存在多个并行动作时呈现真实并行情况，不随意挑一个代替整体状态。

例如：

```text
检索 Agent [8F2A6C10] · 第 2 次执行 · 运行中
最近消息：两个来源对发布日期的描述不一致，我再核对一下。
正在读取：第二个来源的更新记录
```

文字取自原助手消息；动作取自实际工具调用及其执行记录。子 Agent 不需要额外填写“进度”“阶段总结”，也没有周期性汇报要求。正在准备、等待用户回答或等待某个工具时，展示真实原因，而非仅返回一个模糊的 `running`。

复用快速检索已有的最近消息／动作提取语义，但不照搬其倒序读取大正文的成本。先根据原历史与 Operation 元数据定位必要条目，再读取对应正文；当前请求已有可复用结果时按原身份复用，不建设另一份持续刷新的任务摘要库。

### 4.3 Agent 身份与某次执行分别选择

同一个 Agent 可以被多次交办。每次执行包括准备、多个模型步骤、工具调用、结束和报告；不能把一次工具调用或一次模型请求称为新的交办次数。

```text
8F2A6C10       检索 Agent，稳定不变
8F2A6C10/1     第一次：查找资料
8F2A6C10/2     第二次：核对矛盾来源
```

`child_status` 的新模型接口支持两种选择：

- 选择 Agent：看当前概况；有活跃执行时展示活跃执行，没有时展示最近一次执行及其结束状态。
- 选择执行引用：看该次执行的当前或最终状态。历史执行可以直接指定，不需要同时再传原派发 Operation ID。

一个 Agent 的不同分支存在并行执行时，概况列出它们的短引用和对应工作，不能伪造唯一的“当前一次”。历史执行清单另行按需读取，默认概况不铺开全部接续。

“历史执行”是查旧任务留下的状态与结果，不是查询任意历史时间点的状态快照。原始过程仍通过 `read_thread` 读取。

这里的单项概况也覆盖用户创建、后来被 Bot 复用的普通会话。它们可以只有原 Run 和工作请求，没有子派发记录；通用读取直接使用这些实际记录。`child_*` 继续表达委派操作，不能为了统一查询而给普通会话补造 ChildTask。

### 4.4 观察默认与控制目标

只读概况可以解释为“现在”。等待、停止、报告读取和代码交换则在受理时确定目标：

| 操作 | 目标选择 |
| --- | --- |
| 查看 Agent 进展 | 读取当前概况，返回相应执行引用 |
| 查看某次进展 | 精确执行引用 |
| 等待或停止 | 精确执行；仅给 Agent 且目标唯一时，受理时固定到该执行 |
| 读取报告 | 精确执行或已返回的报告引用；单一原答复直接读取，多段答复保留原顺序并支持续读 |
| 给 Agent 发消息 | 发往选择的会话／分支，沿既有立即／排队语义执行 |
| 交换文件或代码 | 固定所选来源及版本，受理后不跟随下一次接续或新修改漂移 |

同一等待受理后，即使 Agent 已经开始下一项工作，也仍等待原先选中的执行。多个活跃目标需要选择时，返回简短候选及可直接使用的引用，不让模型自行组合内部身份。

已有精确长 ID 的含义保持：旧 `operationId` 仍指原派发，旧 `executionId` 仍指原执行。新模型说明优先使用短引用，不能借“默认看最新”改变旧调用的目标。

### 4.5 历史与原始输出

保留 `read_thread` 的最近记录、范围、搜索、条目、工具输出、媒体及 Run 读取能力。查询一次返回可用内容及明确的续读入口，已定位单项时不要求先重复查目录。

报告默认读取原最终答复，避免“先查状态取 executionId，再取 historyId，最后读报告”的必经链。确实需要某个原始工具结果时，才使用条目或输出选择。读取记录中保留发言者、消息性质和来源，避免把 Agent 报告混成用户新要求。

工具说明表达这些能力即可，不增加“先 threads、再 status、再 read”的强制操作顺序。

## 5. 面向模型的引用规则

### 5.1 引用表达对象，名称帮助理解

保留现有八位 Agent 短码，继续不区分大小写。名称与引用一起显示，例如 `检索 Agent [8F2A6C10]`；改名只影响后续展示，不改变旧引用。

执行采用 `Agent 短码/执行序号`。序号在原 Catalog 接受该次执行时分配，按同一 Agent 单调增加；跨分支也不重复。删除、重启、列表排序和分页都不重新编号。并发受理在原事务中取得不同编号。

编号关联一次原受理工作：委派任务先有 delegated execution，准备完成后创建的 Run 继续使用这个编号；普通会话的新工作绑定原 Run；外部 Harness 的工作绑定原外部交办／turn。恢复同一次工作不再编号，辅助推理也不作为独立任务编号。外部执行不伪造成原生 Run。

其他对象采用简短的类型前缀与稳定编号，例如 `msg:12`、`item:47`、`file:8`、`page:6`、`proc:4`。前缀区分确有不同使用方式的对象，编号由系统分配，不截断 UUID 猜唯一性，也不让模型自己编造别名。

这些是目标表示方式，具体工具字段仍按动作表达。优先让现有 `ref`、目标或标识字段直接接受短引用；像用 `operationId` 实际指代 Agent 的误导入口，在新模型 schema 中改为明确的 Agent／执行选择。后续工具直接接受上游返回的引用，不要求再次兑换。

### 5.2 区分对象身份与固定观察

- Agent、进程、脚本环境等引用指向同一个有生命周期的对象；查询它可以取得新状态。
- 某次执行的引用不会切换到下一次执行。
- 历史条目、报告部分、附件和已保留材料引用指向固定内容。
- 文件读取引用绑定实际来源、路径、读到的版本和文本解释；它不是永远指向该路径最新内容的快捷方式。
- 续读引用固定原查询与读取位置；要刷新最新情况，可以重新查询。

引用本身不携带不断变化的时间戳或状态，也不因每次请求而换号。模型根据名称和返回内容选择对象，系统解析对应的原始身份。

### 5.3 不把所有字符串替换成短码

路径、URL、代码符号、工具名、设置项名以及 DOI 等外部有意义的标识，继续保持原形式。这些内容本身参与模型判断，压成短码会损失信息。

需要收敛的是内部 UUID、重复的父子身份组合、内容哈希和可由原对象推导的校验字段。返回中只保留后续操作确实需要的引用；调试详情与原始回执仍可读取，日常结果不并排堆出两套标识。

## 6. 各类工具如何接入

| 能力 | 模型侧用法 | 系统承担的解析 |
| --- | --- | --- |
| 任务、状态、等待、停止 | Agent 短码或某次执行引用 | 原 Thread、分支、dispatch、execution 和受理目标 |
| 协作消息、回复、排队控制 | 消息短引用，或 Agent 目标与正文 | 原发送／接收关系、reply-to、队列项和投递方式 |
| 历史、报告、原工具输出 | 条目／报告／续读引用 | 原历史位置、内容对象、固定查询与范围 |
| 图片与其他附件 | 原文件或媒体引用 | 来源条目、媒体部分、实际内容对象及已有交付关系 |
| 文件读取与编辑 | 路径，或一次文件读取引用 | 原来源、读取版本、编码、BOM 与换行解释 |
| 进程与脚本 | 进程／脚本环境引用 | 原执行 Host、managed process、环境和等待句柄 |
| 网页、文档、Office、材料集合 | 材料或文件引用及读取／编辑意图 | 原 snapshot、文件版本、提供者和选择范围 |
| 浏览器与桌面操作 | 页面／观察引用及元素或动作 | 原桌面、页面、观察版本和控制时期 |
| 设置与结构化对象更新 | 语义名称或已读取对象引用，加修改内容 | 原 owner、作用域和已观察修订 |
| 日程、接续、转发与后台工作 | 相应对象引用和所需操作 | 原定义、触发对象、Job 和实际执行关系 |

以上能力按原工具 owner 接入统一引用基础。工具之间共享同一对象的引用语义，不各自建立一套私有别名表。

### 6.1 文件：绑定实际读到的版本与格式

一次读取可以返回 `file:8`，并展示路径及可读内容。引用绑定这次观察的来源、路径、读取版本和文本格式。后续编辑选择 `file:8` 与修改内容即可，系统将原 `readVersion`、编码、BOM 和换行信息交给现有文件事务。

如果文件在两次操作之间已被其他人修改，继续执行原版本冲突判断。不能把引用解析成“最新版本”来掩盖冲突。模型可以重新读取路径获取新引用，再判断如何修改。

保留路径操作和明确的目标格式选择：创建文件仍直接给路径与内容；需要转码时显式指定目标编码。系统不因省略格式就改成 UTF-8，也不把某次工具调用中最后读到的文件当成随后所有编辑的默认目标。

读取引用固定观察事实，但不凭空提供旧字节。原 owner 已保留的文件或附件版本可以回读；普通设备文件的旧字节未保留且实际文件已改变时，返回版本变化事实。引用映射不因此额外复制整份文件。

相同路径的新读取版本获得新的观察引用；同一版本的重复读取可复用原引用。不同 Agent 的独立工作区即使路径相同，也对应各自实际来源。

### 6.2 媒体、附件与报告文件

历史读取已经定位到某张图片时，结果给出可直接读取的引用，内部绑定原条目、媒体部分和内容身份。模型不再同时携带 `itemId`、`partIndex`、`expectedContentRef` 和 `anchor` 来证明它选的是刚才那张图。

原文件引用可以被支持该类型的文件读取、文档读取、Office、派发和消息附件选择直接使用。工具通过原描述知道文件名、类型和提供者，避免同一份文件在每个入口重新兑换成另一套标识。

派发或发送时，系统继续沿当前附件链固定内容、建立接收关系并保留原件。同一文件来源、其他 Host、独立工作区等差异由原交付 owner 处理，不要求派发者先调查接收方的文件布局。

嵌入历史中的媒体部分与完整文件有区别时，引用类型表达实际对象；不能把一个截图部分说成其源文档，也不能根据正文中的任意字符串建立附件关系。

### 6.3 续读与分页

读取结果返回可直接使用的 `nextRead`，其中使用简短的续读引用。引用关联原工具、查询条件、读取对象、固定位置以及需要的锚点。模型可以照此继续读取，不计算 UTF-8 字节边界或重新拼接多个内部参数。

在按需披露工具的场景，`nextRead` 给出原工具名称与参数，可直接交给 `tool_invoke`；不能把未注册工具伪装成模型直接可调用的函数。

同一个续读引用表示相同的读取动作，重复调用不会悄悄消耗一个服务器端游标。固定历史读取保持原 head 和范围；追加型进程输出则保持原进程与字节位置，按原语义读取后来出现的数据。刷新当前任务状态是新的查询，不覆写原分页对象。

原 offset、行号和显式范围仍可用于主动定位。短引用解决机械搬运，不能剥夺模型直接指定范围的能力。

### 6.4 进程、脚本与后台工作

`process_spawn` 返回的进程引用可直接用于读取、输入、等待、停止及接续条件；脚本环境引用可直接用于运行、关闭及等待。隐藏用于连接这些资源的长 Operation 和环境内部身份。

引用固定到原 managed process，而非一个可能被操作系统复用的 PID。停止的请求、实际退出、输出收尾继续由原进程 owner 区分；变短的标识不改变这些行为。

定时接续、服务转发和后台检索使用相同方式引用相应对象。引用只负责定位，是否等待、取消或继续仍由工具动作与模型选择表达。

### 6.5 设置、浏览器与桌面

设置项名称保留语义可读性。需要基于已读修订更新时，可以引用该次读取，由系统携带 owner、作用域和原修订。修改内容仍由模型明确给出；不能先偷偷读取最新修订，再用它覆盖模型实际见过的旧值。原 owner 不要求版本条件的动作也不增加新条件。

桌面和浏览器已有的短元素标识继续使用。一个观察引用可关联原页面或窗口、观察时期与有效元素集合，不再让模型重复拼装这些关联值。人工接管、窗口替换或观察失效后的判断保留在原 owner；引用不会自动变成另一窗口的最新观察。

模型仍可以直接使用已有路径、选择器、坐标和其他有意义的目标方式。这里统一对象绑定，不强制每次动作都走新的查询链。

## 7. 引用解析与存储设计

### 7.1 在原 Catalog 内维护轻量引用索引

统一引用索引由执行当前会话的 Rust Catalog 管理，只保存短引用到原 typed 对象的映射。文件字节仍归 Storage，材料归材料 owner，外部会话归对应 Harness；索引不复制正文，也不成为这些对象的新写入者。

一条映射表达三件事：引用种类、原资源所有者与身份、需要固定的版本或选择范围。相同目标与固定条件复用同一引用。原对象换版本时按其语义产生新观察引用，不修改旧映射。

普通引用使用 Catalog 持久分配的单调编号，可用紧凑数字表示；分配高水位不因回收下降。Agent 短码沿用原实现，执行序号在原 Agent 关系上持久分配。不会依据查询结果的行号临时生成编号。

引用空间属于实际 Catalog。这个空间身份由原请求、连接与交付元数据携带，不要求模型在每个调用中附带 Host UUID。一个 Host 中的 `file:8` 不能因为切换连接而被解释成另一个 Host 恰好同号的文件。

### 7.2 在原结果发布链上分配，准备请求时稳定复用

推荐的接入顺序是：

```text
原工具或输入 owner 准备结果
→ 标出结果中真实可操作的对象
→ Catalog 分配／复用短引用并关联原持有者
→ 发布原结果与模型可见引用
→ 后续请求按同一映射生成稳定内容
```

沿现有内容准备、发布和回收边界处理引用。大正文 I/O 与来源核验在原工作阶段进行；Catalog 提交段只处理短元数据与关系。准备中断留下的未发布映射随原准备材料清理，不产生虚假已送达记录。

原始回执保持完整，模型可见内容是该结果的稳定投影。UI、调试或导出需要原内部身份时读取原记录，不在日常模型输出中同时放一串长 ID。投影复用原正文与内容引用，避免为每次请求复制一份完整工具历史。

### 7.3 调用解析在原受理边界完成

模型选择短引用后，工具按声明的目标类型解析，得到原对象和固定条件，再进入原业务逻辑。原调用文本与已解析目标分别保留在现有 invocation／准备记录中，不能用改写后的参数冒充模型原始调用。

只读查询可以捕获当前状态；有副作用的操作在准备受理时固定实际目标。恢复或同键重试使用已固定的目标，不再次解释“当前 Agent”，也不重新挑选最新文件版本。

原 owner 继续判断目标是否存在、文件版本是否一致、进程是否仍是原进程，以及实际访问关系。短引用不会新增权限范围，也不会成为绕过原资源规则的入口。本案同样不因自动上下文范围缩小而收紧原查询能力。

参数错误应说明模型下一步能做什么，例如“这个引用是进程，当前工具需要文件”“该文件已被修改，可重新读取路径”。不把内部映射表、哈希或需要人工修复数据库的建议倾倒给模型。

### 7.4 按 typed 字段接入，不扫描任意正文替换

原生工具在结果投影和参数解析处接入；Host 内置工具通过私有协议与同一引用索引协调，仍调用原领域 owner。`tool_invoke` 和脚本中的嵌套工具调用走相同机制。

只有被工具契约明确声明为对象引用的位置才转换。用户正文、源代码、命令、第三方 JSON、URL 和普通字符串保持原样，不能凭字段名包含 `id` 就递归替换。

扩展可通过现有工具／结果契约声明对象类型及其读取位置，使用相同引用服务。第三方 MCP 或外部 Harness 的不透明标识，在没有明确类型与消费入口时继续遵循原协议；不猜测其含义，也不要求第三方先迁移才能使用。原生与内置能力不能以此为由继续输出可自行解析的冗余长标识。

### 7.5 生命周期与清理

引用的资源寿命跟随原历史、队列、附件、报告、未结束操作及其既有保留关系。映射自身不永久钉住大文件、已结束进程日志或所有旧消息。

仍被有效历史或待处理操作使用的引用可以恢复解析；没有持有者的映射可随原维护流程回收。已分配编号不复用，不需要为每个删除对象永久保留一份正文或完整墓碑。

已删除、不可达或已回收的目标按原状态返回可理解结果，不把旧引用悄悄指向新对象。整个设计不增加引用 TTL、数量配额或每轮注册上限。

### 7.6 跨 Agent、跨 Host 与历史分支

同一 Catalog 内转发同一对象时可沿用引用；结构化交付继续建立接收方的原资源关系。跨 Catalog 时由发送／接收链携带原 owner、对象和固定版本，接收端分配本地引用，模型不负责转换。

转发正文保持原样。正文含发送方短引用且接收方引用不同的，可在交付描述中给出简短对应关系；不通过正则重写整段正文。仅粘贴一个没有来源信息的短字符串不能被系统猜成另一 Catalog 的对象。

回退或分叉不修改原引用，旧执行仍是旧执行。新分支的操作使用自己的实际来源；不能因为继承了一段历史，就把其中的文件引用悄悄改成新工作区的同名路径。历史背景选择、附件转交、文件来源选择继续分别表达各自意图。

## 8. 上下文稳定性与成本

正常模型步骤沿已交付历史追加新材料。执行概况只在查询时生成，查询结果作为原工具结果固定下来；它不在后续每次请求中刷新成新状态。模型需要新进展时可以重新查询。

引用在原对象或固定观察范围上复用。同一结果不会因为换请求、重启或列表排序而重新分配标识，也不把“本次查看时间”附在所有旧结果前面。

已有模型可见历史保持原形式。新引用用于新产生或新读取的结果，不在升级后的每次请求中批量改写旧消息里的长 ID。已冻结的请求继续使用原序列化内容；正常配置变化、显式回退、遗忘和压缩仍可能改变后续上下文。

性能收益来自减少实际工作：

- 普通模型步骤不再枚举全部当前任务、所有分支、最新动作和报告。
- 目录先读取短元数据，只有被选择的任务才读取正文。
- 状态概况从原 Run、Operation、等待对象和最近消息定位所需信息。
- 引用解析按持久索引定位原对象，不扫描整段对话寻找相同字符串。
- 发布相同对象复用映射；不按每个 token、每次渲染或每个模型步骤重复落盘。

不以频繁重写摘要、额外调用模型或删除正常动作为代价换取缓存率。本轮不新增后台轮询模型，也不引入用于维持这套机制的第二套任务日志。

### #330 的结论边界

可以直接验证的是：移除临时概览后，在没有压缩、配置或明确内容变更的正常续接中，已送达历史及引用位置保持稳定。

线上缓存命中还取决于实际请求内容、provider 协议和服务端行为。#330 的 11,008 根因需要相邻真实请求的差异证据。本案实现结果可以作为排除一类结构问题的依据，发布说明不把它写成已证实的特定缓存故障修复。若后续调查需要请求对比，应使用用户明确提供的脱敏材料或定向复现，不新增默认记录用户完整提示词的日志。

## 9. 旧数据与接口迁移

### 9.1 数据升级

由 Catalog 原升级入口交付所需引用索引及执行编号变化，保留原 Thread、Run、Operation、execution、消息和文件身份。具体是否需要调整 format，由实际 schema 变化决定；不要求用户手工修复或重建会话库。

已有 Agent 短码直接沿用。旧执行的编号根据原持久受理顺序建立，不按本次查询排序分配；可以在迁移或首次访问该 Agent 时完成，但同一 Agent 的编号与分配高水位需要原子确定。

不为上线短引用扫描、重写全部历史正文，也不一次性复制所有历史资源。旧对象在首次需要暴露短引用时建立映射，重复读取得到相同结果。已有长引用继续解析到原目标，让旧报告、已排队消息和已冻结调用可继续完成。

迁移中的旧 `agent-status` 回执不等同于模型已经读到完整报告。保留其既有交付事实，不因移除旧机制补播所有旧工作；新的实际交付沿原报告／消息身份记录。

### 9.2 工具与消费者同步

原生工具、`tool_invoke`、脚本内工具调用、Host 内置工具及对应返回投影一起接入。工具说明中的例子使用真实支持的字段与引用，不再要求模型先换算另一层 ID。

保持原始模型调用可回放、可诊断；校验时分别核对原调用和已固定的解析结果，避免把短参数与内部长参数直接作 JSON 相等比较而误拒绝。

UI 从同一原记录获得名称、状态和导航关系，不假设模型返回的 `operationId` 一定是数据库主键。历史气泡、协作面板、任务卡、报告、复制引用与导出入口需要同步适配。

对外导出的结构化记录保留引用空间和必要的原对象关联；人类阅读的 Markdown 可展示名称、短引用与可用链接。跨 Catalog 导入按原关联重新绑定，不能将外来 `item:47` 直接解析成本机同号条目。

已运行的旧请求保留原工具契约。新请求使用新的公开 schema，版本选择由系统完成，不重新要求模型回传工具版本哈希。

## 10. 实施拆分与代码落点

各部分可以分提交实现，但完整交付需要把入口、返回和后续消费接通。不能只缩短展示文字，或者删掉概览却保留依赖它的报告记账。

| 部分 | 主要落点 | 完成条件 |
| --- | --- | --- |
| A. 引用与执行编号底座 | `catalog_threads.rs`、`catalog_delegated.rs`、Catalog 原升级与保留机制；新增轻量 typed 引用索引模块 | 稳定分配、精确解析、原调用与固定目标可恢复，旧身份可用 |
| B. 任务目录与概况 | `catalog_family.rs`、`family_tools.rs`、`collaboration.rs`、`catalog_retrieval.rs`、原外部会话读取 owner | 目录简洁，概况有实际消息与动作，普通会话和真实外部执行按原记录读取 |
| C. 报告投递与确认 | `catalog_bot_reports.rs`、`catalog_work_reports.rs`、`catalog_child_delivery.rs`、`catalog_messages.rs`、`catalog_ingress.rs`、`catalog_attention_facts.rs` | Bot、普通任务、复用交办及准备失败均沿原入口交付；等待与自动回报去重 |

| F. 文件与其他工具 | 文件／进程／脚本执行器、Host 设置／Office／材料／Computer 服务、扩展契约 | 原生及内置能力按第 6 节完成输入与结果的双向接线 |
| G. 消费者与说明 | UI 的任务／协作／历史读取、共享 DTO、协议生成、领域文档与工具帮助 | 界面导航与旧历史可用，公开说明与实际默认行为一致 |

实施时先确定引用表示和解析合同，再接查询与结果发布。报告通道及交付确认接通后才能移除旧概览依赖。文件、媒体和其他领域共享同一引用底座，避免先各做一套，最后再互相兑换。

原始资源访问与变更仍经过各自 owner。私有协议有变化时更新 schema 并重新生成对应类型，不能仅在 TypeScript 侧伪造新字段。

## 11. 行为验收

复用现有协作、消息队列、历史读取、文件冲突和 provider 请求测试，只补能保护新行为的关键场景。下面是验收关注点，不要求为每行机械新增独立测试，也不要求执行无关平台全量测试。

| 场景 | 应观察到的行为 |
| --- | --- |
| 普通连续工具调用，其他任务不断推进 | 当前请求不会反复附加全队状态；已经交付的历史保持原位置与内容 |
| Agent 发消息、报告到达，同时接收方在执行工具 | 原队列在正确输入边界交付；正在发送的模型请求不被改写 |
| `wait_child` 与自动报告相遇，或已经显式读过报告 | 同一报告不重复堆入正文；仍可从原引用读取未读部分 |
| 普通主 Agent、Bot、被复用 Agent 的不同交办者 | 回报关联实际交办者与执行；不混到最初父任务或其他 Bot 会话 |
| 子任务准备失败、父任务取消、Host 重启 | 保留真实失败／取消及待交付事实；不伪造子 Run，不反向恢复已取消工作 |
| 同一 Agent 多次接续、多分支并行、改名、回退 | 短码和执行编号稳定；概况与精确执行读取各自正确，控制目标不漂移 |
| 原文件在读取后被修改，或两份来源使用同一路径 | 文件引用保留原来源与版本，冲突判断有效；编码、BOM 和换行沿所选读取结果保持 |
| 历史图片、文档、报告、进程输出续读 | 上游引用可直接消费，分页重试不丢内容；不要求回填可推导哈希 |
| 嵌套工具、附件转发、跨 Host 交付 | 使用同一引用规则；原资源关系正确，无按同号误解析或任意正文替换 |
| 老库升级、旧长引用与历史请求 | 自动升级可完成，旧目标不被解释成最新目标，历史正文不批量改写 |
| 原持有者全部释放后的维护 | 正文和资源依原机制回收，引用映射不造成永久保留；旧编号不复用 |

对上下文稳定性的验证使用合成对话和冻结请求做相邻比较，包含至少一次协作消息与报告交付。验证的是内容与顺序的连续性，不以测试替代服务端缓存测量。

## 12. 交付说明

实施完成后，将当前合同归入[协作](../collaboration.md)、[运行时](../runtime.md)、[资源](../resources.md)与相邻工具文档，并同步本提案的状态。

对用户的变化应体现为：模型更容易找工作、判断进展、引用原文件与结果；协作信息及时到达，聊天和上下文不再反复插入整队概览。提示词中只保留准确的能力说明，不把本设计的存储、交付和验收规则变成模型必须逐条执行的流程。
