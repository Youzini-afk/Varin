# 科研模式与 Agent 协作设计

状态：2026-10-23 方案已接入实现。设计时审阅的源码基线为 `25f52fdec`；本文保留产品决策，当前派发、历史继承和材料归属见[运行时](../runtime.md#模式工具披露与协作)。

本次先做好用户直接与科研 Agent 合作的体验：能够讨论问题、阅读材料、探索想法、计算验证、开展实践，并在需要时组织其他 Agent 参与。工具、预制配置和上下文应帮助这些工作自然衔接，具体方法与推进顺序由用户意图、任务和实际发现决定。

核心方案是提供少量宽泛的预制配置：科研搭档，以及各模式共用的现有 Worker 与调研 Agent；快速检索继续承担轻量查找。Worker 移除仅面向编程的限定，用途说明不枚举工作类型或领域。临时派发继承当前模型，预制派发使用用户保存的配置，两者都支持按本次任务取名。新增一个可选的历史继承参数，调整科研工具的默认披露，移除 `research_decide`。各模式不注入专门的模式提示词，预制用途与工具说明各自保持简洁。

## 1. 范围与产品目标

### 本轮范围

| 内容 | 本轮决定 |
| --- | --- |
| 科研主 Agent | 承担与用户的研究讨论、任务推进、协作和成果整合 |
| 科研预制 Agent | 增加科研搭档，复用现有 Worker；职责由每次派发的任务确定 |
| 调研与快速检索 | 明确区分用途和模型配置；调研同时提供给通用、科研、Coding 与办公 |
| 派发 | 复用现有临时派发、预制选择、命名、续接与通信，增加可选 `inheritContext` |
| 模型 | 继承派发者模型或使用用户已保存的预制绑定；模型绑定留在配置与运行时 |
| 工具 | 调整默认披露，改善搜索、阅读、材料使用与执行结果的衔接 |
| 指令 | 不注入模式提示词；保留简短的预制用途说明及平台已有通用约定 |
| 科研决策工具 | 删除 `research_decide` 的活动入口及专属实现 |

Bot 的长期管理留待后续设计。通用披露与全模式发现改进见[通用模式设计](general-agent-harness.md)，办公能力见[办公模式与浏览器、电脑协作设计](office-agent-harness.md)，共享预制、工具与资源机制。本轮也不做派发时动态选择提供商或模型，不建立模型候选目录、自动选模器和固定科研矩阵。已有用户自定义 Agent、模型服务与模型绑定继续有效。

成功的体验是：用户可以从一处疑问开始，随时转向原文、计算、实验或协作，再带着发现继续讨论。一次理解、一次有价值的讨论、一个被推翻的假设，都可以构成任务的有效结果。产物形态取决于用户正在做的事。

### 典型需求

| 用户意图 | 需要解决的摩擦 | 产品提供的帮助 |
| --- | --- | --- |
| 理解论文、概念、方法或证明 | 解释与具体材料脱节，符号、条件或图表对不上 | 定位原文、公式和图表，按需计算、举例与继续追问 |
| 推敲一个想法 | 过早包装方案，尚未理解问题就进入计划与执行 | 持续讨论，必要时调研已有工作、引入另一种解释或做验证 |
| 调查一个问题 | 返回很多链接，相关性、阅读深度和材料之间的关系仍需人整理 | 调研 Agent 取得材料、跟进线索并综合发现，保留可继续查阅的位置 |
| 验证一个判断 | 文字讨论与数据、代码、运行环境之间需要手工搬运 | 使用通用执行工具，交付真实运行结果 |
| 分析结果 | 对异常、失败或反例理解不足，结果与原判断失去联系 | 继续读数据和实现，比较解释，必要时接续同一个 Agent |
| 表达与验收 | 写作、论证、图表与已有材料分离 | 在同一工作中修改和检查；需要独立视角时派发科研搭档 |

这些是交错出现的使用情境，界面和运行时不把它们做成必须依次通过的阶段。

## 3. 主 Agent 与预制配置

### 3.1 科研主 Agent

主 Agent 保持与用户交流的连续性，理解当前研究问题，可以亲自阅读、推导、计算、实践，也可以派发工作并整合发现。它不需要先把每个问题拆成任务树。

预制 Agent 提供可复用的配置。是否使用、何时使用、负责哪一部分，由本次工作决定。用户不需要为了问一个问题先选择一套科研流程。

### 3.2 预制目录

| 用户可见预制 | 用途 | 默认适用范围 | 模型配置 |
| --- | --- | --- | --- |
| 科研搭档 | 并行思考、研究某个方向、相互讨论、分析分歧、论文验收等 | 科研 | 适合研究与判断的模型，或继承派发者 |
| Worker | 围绕整体目标自主推进派发任务，交付可继续使用的成果 | 通用、科研、Coding 与办公 | 沿用现有 `worker` 配置和继承规则 |
| 调研 Agent | 网络、项目、技术方案、创意、论文调查，深入阅读并整理发现 | 通用、科研、Coding 与办公 | 用户选择较强的理解和综合模型，或继承派发者 |
| 验证 Agent | 沿用当前验证用途 | Coding 默认目录 | 保留既有绑定 |

科研搭档可以具有与主 Agent 相近的能力，独立上下文和不同任务角度使它能够提出自己的判断。其发现可以改变主 Agent 的看法，也可以形成后续研究方向。主 Agent 负责协调和交付，具体研究判断依据各方掌握的材料与结果展开。

科研搭档的派发示例包括“从另一个假设解释这个现象”“继续调查这处分歧”“检查论文的方法与实验是否充分”。这些任务共用一个宽泛预制，不分别注册为永久角色。

Worker 复用现有 `worker` 预制身份和模型配置。当前说明已经包含理解整体目标、协调相关工作、依据发现调整方法，以及交付可支持后续工作的结果，这些通用原则保留。移除其中仅面向编程的措辞，不通过工作类型、领域、阶段或模型速度重新划定职责。

预制目录的短描述供主 Agent 选择配置，Worker 自身的默认说明则表达自主判断、持续推进、问题处理、协作与成果质量；两者分别编写。是否派发以及交给它什么，由当前任务决定。主 Agent 保持完整工作能力。所有预制的默认能力按实际环境准备，用户显式配置继续有效。

用户保存的显式工具选择、指令和模型仍按原配置生效。上表是产品默认目录，已有自定义 Agent 的模式范围继续由用户配置决定。

### 3.3 快速检索与调研

快速检索围绕较明确的问题定位代码、文档与事实。它保留现有 `code_retrieval` 内部执行路径和 `explore` 模型槽，不要求为一次查找建立正式协作成员。

调研 Agent 面向需要探索、深入阅读、比较与综合的工作。它使用正常派发、消息和续接机制，可以与主 Agent 反复交流，使用独立模型配置。

区分依据是任务的深度和综合需求。查一个网页上的明确事实可以很轻；分析一个庞大本地项目也可能需要调研。默认说明应通过这类例子帮助主 Agent 选择，工具和网络能力不按这两个名称机械隔离。

建议复用现有可派发 `retrieval` 预制及 `retrievalAgent` 模型槽承载“调研 Agent”，更新产品默认名称、用途和指令；`explore` 继续服务快速检索。已有用户自定义名称、指令、模型与工具覆盖保留，不把已有绑定自动换成其他模型。

### 3.4 配置身份与任务名称

预制类型表示配置，实例名称表示本次参与的工作。两者分别保存。

选择“科研搭档”的两个成员，可以分别命名为“机制分析”和“另一条思路”；Worker 同样按本次任务取名。聊天、协作面板、工作概览沿用实际名称、稳定短码和头像。

省略 `name` 时继续使用已有的任务首行规则。复用和改名沿用当前 Thread 身份，不因改名重新创建 Agent。预制类型可以在现有详情中作为辅助信息，不能替代实例名称。

## 4. 派发与上下文

### 4.1 保持简单的派发接口

| 输入或选择 | 目标行为 |
| --- | --- |
| 只提供 `task` | 创建临时 Agent，继承派发者当前模型，沿用现有可委派能力规则 |
| 提供 `preset` | 使用该预制已准备的指令、能力和模型配置 |
| 提供 `name` | 按本次用途命名，预制和临时派发都适用 |
| `inheritContext` 省略或为 `false` | 保持独立任务上下文的默认行为 |
| `inheritContext: true` | 取得派发时主任务已有的对话上下文，随后在自己的线程中继续 |
| 向已有 Agent 继续发送任务 | 自然沿用该 Agent 自己的历史，不重新应用创建时的继承选项 |

现有 `sourceAgent`、`workMode` 和 `tools` 保持原来的含义。历史继承与文件来源选择是独立操作。

主 Agent 选择预制时只需要可调用标识、名称和用途，以及实际是否可用。提供商、模型绑定与凭据由用户设置和现有模型 owner 处理，不加入预制用途说明，也不增加模型目录查询工具。

本轮派发参数不增加 `model`、`provider` 或自动选模偏好。用户已经保存的自定义 Agent 仍可使用自己的模型；这与临时派发覆盖模型是两回事。

以下标识为建议的新预制标识，尚未注册。示例只展示用户有意义的调用部分：

```json
{
  "preset": "research_peer",
  "name": "机制分析",
  "task": "结合我们已经讨论的材料，继续分析这个机制是否能解释观察到的结果。",
  "inheritContext": true
}
```

```json
{
  "name": "独立推导",
  "task": "从给定定义出发推导这个关系，说明成立的条件。"
}
```

`task` 足以表达临时职责，主 Agent 无需同时填写专长、阶段、证据模板、验收清单等表单。

### 4.2 `inheritContext` 的具体语义

继承发生在创建新 Agent 时，来源是实际派发者当前分支在派发时已形成的对话上下文。它是一个固定起点；父任务之后产生的消息通过原有通信机制传递，不持续复制到子线程。

启用继承后，子 Agent 仍使用自己的预制指令、当前任务、模型、工具和执行来源。主任务历史提供背景，本次 `task` 明确当前分工。继承历史不同时切换文件基础，也不把父模型的系统配置套到子模型上。

历史可能已经经过正常上下文整理。应复用现有有效上下文与原始历史读取机制，不为了派发额外调用一次模型生成交接摘要，也不要求把全部归档内容一次塞入目标模型窗口。后续读取和压缩继续遵循平台现有上下文机制。

需要在实现中处理的具体边界只有创建时真正涉及的内容：

- 由 Catalog 固定派发所在分支及其历史边界；恢复同一次派发使用同一份选择。
- 使用已有消息、附件与材料引用。对话前缀尽可能共享原始内容引用，避免每派发一次就复制一份完整历史正文。
- 本次尚未完成的派发调用及同批未结算工具调用不作为可重放的历史工作带入子 Agent；由已有请求组装机制选择完整、可供目标模型读取的上下文。
- 材料正文和附件沿用原资源 owner 的引用与共享路径；继承文字引用不会自行生成另一份文件来源。
- 父任务删除、子任务继续读取及子任务删除后的回收，复用现有内容依赖与收集机制，保留仍在使用的内容，释放已无引用的内容。
- 开启继承却无法准备背景时，沿现有子任务准备失败路径报告具体问题，保留本次请求供重试。

这些属于实现行为，不扩展为用户需要理解的一组历史模式。模型端只增加一个可选布尔参数，界面需要解释时显示“继承派发时的对话”。

### 4.3 交流与复用

继续使用 `send`、`threads`、`read_thread`、子任务状态与报告工具。搭档可以收到补充材料、回应另一个成员的发现，或在后续任务中继续原分析。现有协作面板保留按成员进入完整对话的方式。

是否独立探索、相互讨论、接续别人的结果或直接完成任务，由实际工作决定。平台不添加固定辩论轮数、强制共识、自动复审链或每次完成后的必选下一角色。

## 5. 工具披露

### 5.1 默认可见的主路径

下表给出科研 focus 的默认披露目标。工具实际出现仍取决于已配置能力、来源和用户显式选择；工具用途与完整参数继续来自原注册声明。

| 用途 | 默认直接披露的现有工具 |
| --- | --- |
| 搜索 | `websearch`、`research_search`、`code_retrieval` |
| 阅读与材料 | `webfetch`、`document_read`、`materials`、`resource_read` |
| 文件 | `file_list`、`file_search`、`file_read`、`file_write`、`file_edit` |
| 终端执行 | `process_spawn`、`process_read`、`process_write`、`process_inspect`、`process_stop`、`wait_process` |
| 脚本与组合执行 | `script_open`、`script_run`、`script_close` |
| 协作 | `dispatch`、`child_status`、`child_report`、`wait_child`、`child_cancel`、`threads`、`read_thread`、`send` |
| 交流与工作状态 | `ask_user`、`question_status`、`todo`、`memory`、`render_ui`；有 Goal 的请求沿用 `goal_report` |
| 能力发现与调用 | `tool_describe`、`tool_invoke` |

这些工具允许讨论、阅读和动手验证自然切换。列在常驻集合里只表示容易调用，不要求模型为了显示正在工作而使用它们。

科研搭档采用均衡的科研能力组合；Worker 的用途说明保持开放；调研 Agent 突出资料获取、原文阅读和综合。初期复用共同能力，保持说明简洁，不增加一个根据每句话反复推断工具清单的模型。

### 5.2 按需取得的能力

| 能力 | 披露方式 |
| --- | --- |
| 文件恢复与恢复点 | 保留原工具，通过目录取得 |
| 进程窗口尺寸调整、Agent 改名 | 保留原操作，作为低频工具按需取得 |
| 代码交换 `submit_code`、`update` | 科研默认按需；Coding 原有常用路径保留 |
| 定时与接续任务 | 沿用 `follow_up`，按需发现；不把每次研究变成后台任务 |
| 图像生成与编辑 | 使用已有配置与工具，科研默认按需 |
| 浏览器交互、计算机使用、环境准备 | 使用现有目录和实际 Host 能力 |
| 长运行、远端运行与实验管理 | 接入已存在的实验服务时提供清晰的用途入口 |
| 专门文档加工、引用导出、学科数据库 | 按实际安装能力发现，尚不存在的能力不放入可用列表 |

按需工具继续经过 `tool_describe` 和 `tool_invoke`。读取说明不会把目标名称自动注册为当前模型函数。目录分组需要能让模型按用途找到入口；“科研”分组删除快速决策文案，实际可用的实验能力不能只埋在无说明的其他扩展中。

MCP 保持已有的直接披露与发现机制，本轮不改变用户已有 MCP 工具选择。

### 5.3 实现上的调整

目前原生 `is_always_declared` 固定列表与扩展 `always_declared` 叠加，只能追加常驻工具。应在既有 Run/request 准备路径中形成确定的模式披露选择，使直接声明与按需目录能够分别表达。

完整可执行目录、用户选择与模型本次可见函数列表继续分开。新增科研默认组合应复用同一份工具声明，provider 接收的列表和原生调用校验使用同一次准备结果。Coding 的已有披露保持稳定，调研预制所需的实际搜索与阅读能力随其预制接入。

工具的可见性和执行能力不能分别在 UI、Host 和 Rust 中维护三份互不关联的名称表。默认组合可以配置化表达，最终选择与执行仍由现有准备和原生运行时负责。

目录分组、工具说明、关联能力查询及错误反馈采用[全模式共享的发现改进](general-agent-harness.md#6-全模式共享的发现与结果改进)。本节保留科研默认清单，共享发现改进不要求各模式采用相同常驻集合。

## 6. 搜索、阅读、材料与实践

### 6.1 搜索工具提供可继续工作的结果

`research_search` 继续负责搜索论文、查询论文和追踪参考文献、被引与相关工作。`websearch` 负责网页、项目、代码、技术文档及其他网络材料。调研 Agent 可以组合使用。

结果应包含服务实际提供的论文身份、标题、作者、年份、摘要、来源与可访问地址，并清楚表达分页和部分失败。查询条件只使用服务真实支持的过滤方式，不增加无依据的全局检索配额。

论文元数据、摘要、全文链接和已经取得的全文分别表达。来自不同服务的相同 DOI 可以关联；预印本、正式版本和不同内容快照保留版本区别。相关性分析由调用方或调研 Agent 根据当前问题完成。

高质量返回的重点是帮助下一步：可以继续翻页、查某篇论文、跟进引用或读取原文。结果多时保留继续读取入口，明确本次实际返回的范围。一次搜索结束不产生“已经找全”的人为完成标记。

### 6.2 文档读取优先做好现有 PDF 路径

现有 `overview`、`text`、`page-image`、`structure`、查找和位置读取应形成一致的路径。Agent 可以先了解结构、定位术语或图表，再读取正文及原页，不必每次重新取得整个文件。

工具结果保留来源、页码或其他实际位置、读取范围和可继续使用的材料标识。表格处理保留表头、单位、注释及跨页关系；正文解析遗漏公式或图形时，可以继续查看原页或局部区域。OCR 和结构解析依照 Host 实际可用组件返回状态。

`webfetch` 与 `document_read` 共享已取得的材料身份。URL、固定材料、本地文件和实验产物沿各自原入口读取，后续阅读可复用同一来源，不要求模型为了换一个视图重复下载。

DOCX、表格和演示材料是后续共享文档能力的扩展方向。本轮不为了科研重建完整办公解析体系；当前支持什么格式、能取得什么内容，要在工具说明与失败结果中保持一致。

### 6.3 材料组织与交接

当前任务已有材料应该容易列出、搜索和读取。集合按需要创建，用来反复使用一组论文、网页与补充材料；临时阅读可直接进行。

正文、附录、实现代码和数据之间的关联优先利用已有 `materials` 成员身份、角色与注释。资料分享沿当前原生 Thread 关联和材料 owner 处理，不新增第二套引用格式或科研专用存储。

派发任务可以直接使用已有材料标识。需要显式共享时沿现有材料操作完成，避免把全部正文复制到派发参数中。上下文继承也使用同一条资料访问路径。

### 6.4 计算和实践

主 Agent、科研搭档、调研 Agent 与 Worker 都可以按任务需要使用终端。Python、R 或其他程序的使用取决于实际执行环境。工具返回实际进程、输出、状态、文件及运行错误，模型负责理解结果。

普通计算直接运行；需要较长执行、远端环境或多次比较时，再使用实验服务。实验记录重点关联真实代码、数据、运行和产物，平台自动取得的事实无需模型再次手工填写。

无项目的研究对话仍能使用网络搜索和已有材料。真正需要文件或进程时，沿现有来源准备路径选择工作目录；阅读一篇论文不以创建代码仓库或独立工作副本为前置操作。

科研搭档和 Worker 的文件工作方式复用现有 `workMode`。默认来源与终端能力应成套可用，不因为角色名称中的“思考”“调研”就裁掉执行能力。涉及固定文件来源或并行改动时继续使用现有来源和隔离机制，不另设科研资源管理层。

### 6.5 结果质量的共同要求

工具输出优先给实际内容、原位置、执行状态和可继续读取的引用。错误对应失败的具体操作；部分成功保留已有成果。搜索摘要、正文、模型推断和运行结果各自有清楚来源。

这些事实尽量由工具产生。主 Agent 和子 Agent 的自然语言成果按任务组织，不强制统一成证据卡、固定字段报告或带分数的研究结论。已有文件、表格、图和交互内容继续可以作为成果。

## 7. 模式与指令的边界

科研和办公均不注入专门的模式提示词。模式负责默认工具披露、预制目录和能力入口，不向模型规定研究阶段、工作流程或思考方式。当前 `thread-context.ts` 按 focus 自动生成 `work_focus` 段的路径需要移除；focus 元数据继续服务配置和实际能力准备，`agent_profile` 与用户保存的指令保持原有职责。

预制目录提供简短用途与参与关系，成员自身的默认说明保留有价值的通用工作原则。工具调用方法放在工具说明中，项目约定与用户偏好继续来自现有指令和技能。相同约定不在每一层重复。下面是成员默认说明候选，沿用当前内置英文指令惯例；界面名称使用中文，用户原有覆盖继续有效。

| 位置 | 指令候选 |
| --- | --- |
| 科研搭档 | You are a research collaborator. Take on the assigned work with your own judgment and contribute useful findings, ideas, or results to the collaboration. |
| Worker | Understand how the assigned work fits the overall goal. Use your judgment to carry it through to a usable result, working through issues as they arise and coordinating with related work. Adjust your approach based on findings, and make the outcome clear enough for subsequent work to build on. |
| 调研 Agent | Investigate the assigned question across relevant sources. Read and follow useful leads, compare findings, and provide a usable synthesis with references that support further work. |

Worker 的中文含义是：理解所承担任务与整体目标的关系，自主判断并推进工作。处理过程中遇到的问题，与相关工作保持协调，结合新的发现调整方法，交付清楚且能够支持后续工作的成果。这段说明保留工作质量要求，不列举任务种类，也不规定固定步骤、工具、验证次数或汇报格式。目录短描述使用第 3.2 节中的用途，不能用短描述替代成员默认说明。

快速检索继续围绕明确问题提供快速、准确的定位与必要说明。其指令与调研指令分开维护，调研不附带快速检索内部执行的“不要创建正式协作任务”约定。

主 Agent 可见的预制目录提供简短名称、用途和调用标识。角色开关、模型准备和实际工具能力共同决定可用项。用户无需在每个任务中指定模型，也不需要解释完整研究背景才能开始一次派发。

科研模式不附加统一步骤、必用角色、检索数量、工具调用次数、讨论轮数或必交文件要求。系统综述等有明确方法要求的任务，可以使用用户选择的技能、项目约定或本次任务说明表达。

## 8. 移除科研决策工具与整理旧配置

`research_decide` 的实际作用是把候选交给快速决策配置作相关性、阅读价值等判断。本轮删除它作为科研能力的活动入口，不再要求用户配置这个额外模型来完成研究。

清理覆盖工具声明、内置扩展导出与装配、Host capability、执行路径、科研常驻披露、专属配置入口、工具目录文案及相应测试。历史调用仍可以通过现有历史展示机制阅读，删除可调用入口不删除历史记录或材料。

快速决策的共享配置、推理 owner 或其他用途是否还需要保留，由实际消费者决定。实现时按调用引用清理专属代码，不根据 `research_decide` 一个工具的移除删除用户的模型服务或其他仍在使用的功能。

建议新增科研搭档及对应模型配置；Worker 沿用现有 `worker`，不新增“实践 Agent”预制或模型槽。调研复用 `retrieval` / `retrievalAgent`，快速检索继续使用 `explore`。设置目录从真实预制定义生成，显示启用、继承或所选模型、指令、工具等已有编辑项。

旧的 `researchInvestigation`、`researchExperimentalDesign`、`researchFastExploration`、`researchHighThroughputExecution` 不作为新预制的隐式模型来源。实施前需核对设置持久化的弃用字段处理：空的旧入口可以清理；已保存值应保持可读取与可整理，不能使整份设置解析失败或悄悄改变新 Agent 的绑定。这是用户设置整理，不建立旧科研矩阵的运行兼容层。

## 9. 界面与体验

沿用现有聊天阅读模式、工具展示、协作面板、成员对话、工作概览与 Agent 头像，不在本轮重做科研工作台布局。

需要变化的界面集中在已有位置：

- Agents 设置提供科研搭档、Worker 和调研的实际可用配置；快速检索与调研的名称、用途和模型设置区分清楚。
- Coding 可以使用调研 Agent；科研默认提供科研搭档、Worker 和调研。用户自己的预制仍按其设置范围显示。
- 办公共享调研、Worker 与快速检索配置，具体办公能力由其设计稿定义，不复制一套同用途模型槽。
- 派发与协作展示实例名称，预制类型留作辅助信息。研究方向名和工作名称不会被角色名覆盖。
- 启用历史继承的派发，在原调用详情中表达这个选择，无需增加一套上下文管理面板。
- 搜索结果、论文页和实际产物沿既有展示入口打开；摘要使用已返回的真实字段或 Agent 正文。

科研工具展示的作用是让用户能顺畅进入材料与成果。不会要求 Agent 为每一次工具调用额外生成“正在研究什么”的装饰性标题，也不把每一个发现自动变成大卡片。

用户想直接参与研究时可以进入成员对话；想关注主线时可以使用现有对话优先展示。协作完成不强制生成额外综述，主 Agent 按原任务需要整合结果。

## 10. 实现组织

以下按真实职责组织实现，阶段用于保持改动可理解，不代表产品要求用户依次执行。

| 实现单元 | 主要工作 | 原有入口 |
| --- | --- | --- |
| 预制、设置与默认指令 | 新增科研搭档，复用 Worker 并移除编程限定，不枚举其工作类型；检索与调研分离；保留用户覆盖及实例命名 | protocol presets/model slots、Host child profiles、设置与 i18n |
| 模式指令清理 | 移除自动生成的 `work_focus` 指令段，保留配置元数据、基础指令及用户覆盖 | Host thread context 与请求准备 |
| 科研工具披露 | 从只追加常驻改为可表达科研组合；直接声明与目录一致；Coding 接入调研能力 | Rust tool disclosure、Host extension tool owner、Run/request 准备 |
| 历史继承 | 增加可选参数、固定历史选择、共享内容引用、正常组装与续接 | 原生 dispatch、child admission、Catalog 历史与请求上下文 |
| 科研决策清理 | 删除活动入口、专属执行与配置消费者，保留仍有效的共享功能 | research-decision 扩展、Host runtime、工具目录与 UI |
| 工具结果与材料衔接 | 搜索身份和读取状态、PDF 定位与原页、资料共享及真实运行产物 | research discovery、web/materials、document reader、实验服务 |
| 体验与文档 | 设置、派发详情和工具说明更新；当前架构文档在实现完成后同步 | 现有 UI 与领域文档 |

Thread、历史、执行和受理仍由 Rust Catalog 负责，文件与执行来源仍由原资源 owner 负责。Host 组合模型、预制和扩展能力，UI 展示与编辑原有配置。新增历史参数按项目的 schema 生成流程贯穿相关类型，不手改生成文件，也不另建 TS 历史存储。

实现中需要沿具体代码确认的事项限于：旧科研设置的已保存值如何保留整理、现有实验服务实际向模型披露的入口、历史继承如何复用当前有效上下文及内容引用。这些不改变本稿确定的产品行为，也不引入新的用户选项。

## 11. 验收情境

验收围绕真实行为，优先复用已有验证。下表是应覆盖的产品结果，不要求为每行另写一套测试或重复跑全量检查。

| 情境 | 应看到的行为 |
| --- | --- |
| 用户只想讨论一个想法 | 主 Agent 可以自然讨论，没有必建计划、必派发或必运行实验的要求 |
| 切换科研或办公模式 | 准备对应默认能力，不注入专门的模式提示词，不删除用户指令 |
| 用户询问论文中的公式或图表 | 能从已有材料定位正文与原页，继续讨论同一内容 |
| 一个明确的代码或文档定位问题 | 可以使用快速检索，不自动升级为正式调研任务 |
| Coding 中调查一个开源项目或技术方案 | 可以直接选择调研 Agent，完成阅读和综合后继续开发 |
| 科研搭档承担讨论、独立方向或论文验收 | 同一预制可以接受不同任务，不要求切换一套岗位 |
| 实践任务执行计算或实验 | 使用实际环境与终端，返回真实状态和可继续使用的结果 |
| 两个同预制成员分别取名 | 界面和协作记录显示各自实例名称，身份、头像与续接保持稳定 |
| 普通临时派发与已保存预制派发 | 前者继承派发者模型，后者遵循已保存配置；主 Agent 无需查询模型目录 |
| Worker 在不同模式中使用 | 复用同一预制和已有模型配置；用途说明不限定编程或枚举工作类型 |
| `inheritContext` 省略或关闭 | 新任务保持现有独立上下文行为 |
| `inheritContext` 开启后父任务继续产生消息 | 子任务得到派发时固定的背景，后来的父消息通过通信进入，不自动混入 |
| 继续已有搭档 | 沿用其自身历史，不再次复制主任务历史或重建 Agent |
| 长历史、多次派发和任务删除 | 沿既有上下文机制工作，原内容引用可共享，仍在使用的内容可读，未引用内容可回收 |
| 按需工具被发现并调用 | 通过已注册的通用入口执行，不把未声明名称直接作为模型函数 |
| 搜索部分失败、PDF 解析不完整、实验失败 | 具体状态清楚，已取得材料与成果可以继续使用 |
| 移除 `research_decide` | 新请求与目录不再提供入口，既有历史可读，用户其他模型配置正常 |
| 修改默认预制和科研 focus | 用户已有显式覆盖、当前正在运行的配置和其他模式按原生生效边界保持一致 |
