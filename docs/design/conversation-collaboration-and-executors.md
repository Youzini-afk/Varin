# 会话协作与外部执行者

状态：设计提案，尚未实施。日期：2026-11-15。源码基线：`9f369c9fb`。

本文确定原生会话之间的协作、外部执行者发现与直接派发，以及现有适配器的完善方向。当前行为仍见 [Agent 协作](../collaboration.md)、[Bot](../bot.md)和[外部 Agent](../external-agents.md)。本文接续[外部 Harness 接入设计](external-harness-integration.md)；其中关于必须通过预设派发、跨根会话联系和后续实施顺序的取舍，以本文为准。

本轮暂缓向外部 Harness 暴露 Varin 协作工具，包括 MCP、CLI 和 Skill 桥接。外部程序已有的工具、MCP、登录与项目配置继续由其自身管理。设计不引入新的用户系统、任务池、消息服务或执行器注册中心。

## 1. 用户最终能做什么

- 用户说“让 Codex 处理这个问题”，Varin 能发现实际执行设备上的 Codex，直接派发；用户无需先建立一个子 Agent 预设。
- 两个独立创建的原生主任务能相互联系、交换材料、请求帮助和回复。同一任务树中的主子、子子继续使用相同入口。
- Bot 可以联系另一个 Bot 的具体会话，也可以复用已有普通任务。双方保留各自的身份、记忆、历史和工作安排。
- 外部任务使用实际支持的模型、选项、附件和交互能力；Bot 与用户看到同一份执行状态、结果和需要处理的问题。
- 已开始的任务可以补充输入、停止和恢复；具体行为遵循所选 Harness 的真实能力，连接回收保留仍在工作的进程和来源。

Varin 可以直接完成工作，也可以自主选择协作。系统提示介绍这些能力与状态语义，不要求每次查询目录、先派发、逐项汇报或按固定角色流程工作。

## 2. 当前实现与缺口

### 2.1 原生会话

| 场景 | 当前行为 | 本次变化 |
| --- | --- | --- |
| 主子、同一家族的子子 | `send` 支持通知、请求、回复和等待 | 保留消息与接续机制 |
| 同一个 Bot 会话派出的多个任务 | 沿真实父级回溯到同一家族，可以交流 | 保留派发归属；不以界面的主任务层级判断权限 |
| 独立创建的普通主任务 | 不同家族默认拒绝发送，普通目录也主要局限于家族 | 将产品会话发现、读取和联系扩展到同一可访问范围 |
| Bot 与普通任务 | 已有跨家族联系通道 | 并入统一的会话访问判定 |
| Bot 与 Bot、同一 Bot 的不同直接会话 | 已能发现和读取；默认不能发送，显式事项关联是例外 | 支持直接联系，事项用于描述和跟进工作 |

决定性实现位于 [消息路由](../../kernel/crates/varin-runtime/src/catalog_messages.rs)、[任务家族计算](../../kernel/crates/varin-runtime/src/catalog_scheduling.rs)、[Bot 读取与联系判定](../../kernel/crates/varin-runtime/src/catalog_bot_work.rs)及[会话目录](../../kernel/crates/varin-runtime/src/catalog_family.rs)。现有 [Bot 测试](../../kernel/crates/varin-runtime/src/catalog_bot_tests.rs)明确断言 Bot 会话之间可读而默认不可发。

Bot 派发的任务是普通执行 Thread，在工作台里可以作为主任务进入；Catalog 仍保存其真实委派关系。任务在侧栏放在哪一层，与它能联系谁、由谁回收，是三个分别处理的问题。

### 2.2 外部执行者

现有 `dispatch` 通过预设中的 `external.configurationId` 选择外部程序。[子 Agent 目录](../../packages/web/application-host/lib/kernel/child-profiles.ts)读取外部配置，[派发工具](../../kernel/crates/varin-kernel/src/collaboration.rs)受理外部 child，[外部服务](../../packages/web/application-host/lib/external-agents/service.ts)准备来源、创建会话并推进真实 turn。结果进入原 Catalog 报告与 Bot 工作事件。

这条执行链已存在。缺口是自由派发没有执行者选择，模型缺少实际安装发现入口，且部分适配能力尚未接通。现有 HTTP `settings` 可选资源 Host，`detect` 仍只接收配置 ID；远端发现需要沿已有 managed Source 接口补齐。

## 3. 原生协作：联系范围与派发归属分开

### 3.1 哪些会话可以参与

同一 Varin 服务中、既有客户端认证与部署访问范围内的产品会话，统一成为可发现、可读取、可联系的协作对象。内部身份沿现有可信来源传递；这里不增加产品账号、成员邀请或逐对会话授权设置。

普通主 Agent、Bot 派发任务、执行子 Agent及 Bot 直接会话采用同一判定。读取公开会话历史沿现有正文、媒体与固定续页机制；内部快速检索、记忆整理和上下文维护运行保留内部身份，不作为协作成员。文件、长期记忆写入和实际执行权限继续由各自资源 owner 判断。

参与者精确到会话及分支。模型可以联系另一会话，也可以明确联系同一 Thread 的另一分支；修改当前只按 `sender == target` 拒绝的判断。原分支自己的后续工作仍使用现有输入、等待和安排入口。

远端执行任务沿协调 Host 中已有的任务身份参加协作，消息再由原 owner 投递到执行设备。两个彼此独立、没有既有连接和会话归属的 Varin 服务之间的 Bot 联邦不在本次范围内。

实现上，将产品会话的访问判定收拢到 Catalog 的原会话领域，供目录、正文、附件交付及消息路由共用；移除用任务家族替代通信范围的检查及 Bot 专属豁免。任务家族查询保留给组织、派发链和生命周期，不把所有家族合并成一个根。

### 3.2 发现与选择收件人

复用 `threads`、`read_thread` 和既有模型短引用。`threads` 支持全可访问会话及当前家族筛选，默认搜索可访问产品会话；现有 `scope: current/history/all` 继续表示执行范围，另用关系筛选表达家族，避免混用。

目录按名称、任务、Bot、项目／分组、执行后端和活动状态定向查询。简表只返回定位所需的名称、短引用、用途、当前状态、后端和来源关系；正文、分支及最近动作按需读取。收到消息时直接提供原发送会话／分支与可回复引用，接收者不必重新搜索发送者。

Bot 名称用于发现身份，消息最终投递到具体会话。已在交流的合作沿原会话继续；首次联系从目录读取该 Bot 当前可用的默认接收会话，也可明确选其他会话。会话归档、删除或暂不可用时给出原目标状态，不把消息悄悄投到另一个会话，也不为每次联系自动创建新会话。

### 3.3 发送、回复和等待

继续使用 `send`，不增加另一套聊天协议：

| 操作 | 接收与结果 |
| --- | --- |
| `inform` | 保存通知，留待目标下次正常处理；不单独启动模型 |
| `request` | 在原输入边界进入活动执行，或沿既有激活路径启动空闲会话 |
| `afterCurrent: true` | 当前执行结束后处理新工作；保留原请求身份 |
| `replyTo` | 回复实际收到的原消息，固定回原发送分支 |
| `wait` | 观察该次请求的回复；结束等待保留已经交付的请求 |
| `attachments` | 交付现有固定文件引用或当前可读来源中的文件 |

补齐路由后，还要让首次收到请求、尚无首轮 Run 的普通会话和 Bot 会话沿原 launch／激活 owner 准备执行；缺少模型或已有明确暂停时显示具体待处理原因。Bot 休眠、用户停止和原任务预算继续保留实际含义。

普通请求的终态回复复用 [work report](../../kernel/crates/varin-runtime/src/catalog_work_reports.rs)，返回承载原请求的执行状态和原最终答复引用。显式回复沿 `replyTo` 关联，wait、报告与通知消费同一原请求事实，避免重复交付。一轮承载多个请求时，报告注明它们关联同一次执行，不声称为每个请求单独生成了结果；需要独立一轮时使用已有顺序交办能力。

原生等待期间的消息可达性一并验收：新请求按原观察等待／输入机制处理，不因正在等别人的结果而丢弃收信。Bot 可以因真实请求或结果接续；普通 Agent 的被动通知保持被动。自动报告保留报告身份，避免被重新识别为需要再自动汇报的工作请求。

### 3.4 任务控制与资源归属

| 关系 | 通信和结果 | 停止与回收 |
| --- | --- | --- |
| `dispatch` 创建的新子任务 | 原交办者收到结果；其他会话也可联系 | 原派发树、取消入口及资源 owner 管理 |
| `send` 联系既有独立任务 | 本次请求与回复建立关联 | 不增加父子关系；发送方结束不回收接收方 |
| Bot 联系另一个 Bot | 原接收会话处理，回复返回原发送会话 | 各自保留休眠、记忆、日程与生命周期 |
| 同一来源上的多个执行者 | 可交换消息及原文件引用 | 文件写入仍沿版本／冲突语义处理 |

读取和通信开放不自动扩大 `child_cancel`、树取消或删除的作用范围。撤回未交付请求、结束等待与停止接收方整个执行分别沿已有操作表达。归档、分类和移动不改写交办者或资源归属。

文件交接复用原附件与 Integration：同一共享来源直接读取实际文件；不同来源用固定附件或真实三方基线交接。通信关系本身不产生可合并的工作区基线，也不把对方家目录变成自己的文件权限。

## 4. 外部执行者的发现与直接派发

### 4.1 执行者参数

`dispatch` 增加可选 `executor`。它选择具体执行配置，协议种类仍由该配置决定；两个不同配置的 Codex、不同设备的 Codex 都可以独立选择。以下为目标接口示意：

```js
dispatch({ task: "分析这个问题" })                         // 自由派发默认 Varin
dispatch({ task: "修复这个问题", executor: "codex" })      // 当前执行设备的 Codex
dispatch({ task: "检查服务端实现", executor: "exec:7B2F" }) // 发现工具返回的具体执行者
```

解析顺序为：本次明确选择的执行者 → 已选预设绑定的执行者 → Varin。`executor: "varin"` 是明确选回原生执行；省略不改写已有外部预设的行为。它与手动新会话的默认 Agent 设置分别保存，自由派发不会因用户上一次手动打开 Codex 而换后端。

预设仍可保存名称、用途、头像、指令及常用执行配置。显式选择不同执行者时保留通用的角色字段，模型、工具和模式从实际执行者的配置体系解析；不把原生渠道模型和工具清单转换为外部参数。调用中明确传入了不适用于该后端的字段时，说明具体冲突及应使用的参数。无需通过临时保存“外部预设”才能执行这次任务。

外部选项使用独立的 `executorOptions`，承接已有 `ExternalInput` 的 `model`、`thinking`、`mode`、`config` 语义；只需填写本次要覆盖的值。原生 `model`、`thinking` 继续使用原生渠道目录。外部默认值顺序为本次明确选择、适用于该执行者的预设选项、该连接配置的默认值，最终由外部程序提供未覆盖项。

`tools` 和 `workFocus` 描述 Varin 原生能力；外部使用自己的工具与模式。`workMode`、项目／文件来源、背景引用、名称和附件保留现有派发用途。外部 `read_only` 只有在适配器接通实际沙箱或等效执行边界后才可选择；已支持的共享、隔离来源继续可用。

### 4.2 模型如何发现

增加轻量 `executors` 发现入口，直接调用现有 ExternalAgentService 和已连接工作设备；不创建第二份注册表。它发现可启动的执行配置，`threads` 继续发现已经存在的工作会话。

| 查询 | 返回 |
| --- | --- |
| `action: "list"` | 当前目标设备上的 Varin、已发现内置程序及自定义外部配置；支持名称查询 |
| `action: "inspect", executor` | 一个执行者的配置默认、能力来源及实际可用选项 |
| `action: "detect"` | 在选定设备重新检测指定程序或请求范围内的程序，更新检测结果 |

查询可带已有 `projectId` 或 `sourceAgent`，沿与 `dispatch` 相同的来源解析找到执行设备；也可使用工具返回的工作设备引用进行发现。默认查当前执行来源的设备，可明确查询其他已连接设备。设备引用复用工作连接和现有短引用机制，模型无需提供 `resourceOwner` JSON、连接地址或认证数据。

简表形态示意：

```text
Codex · 开发机 · 已安装 · 使用自身默认配置 · executor: exec:7B2F
Claude Code · 开发机 · 已停用
Pi · 开发机 · 未找到程序
```

首次缺少检测事实时，按已有安装路径解析及版本探测取得事实；已有结果可用于列表展示，并带检测时间。明确刷新才重复探测对应范围，不为每次模型请求扫描设备，也不为列目录启动全部 Harness 会话。未检测、检测失败、程序缺失分别表达；已知有效配置可直接派发，不强制先调用发现工具。

`inspect` 优先返回现有连接能力或同配置的能力缓存，标明来源。需要初始化才能取得的登录状态、模型及选项，在实际连接准备时取得；目录不提前为所有候选建立会话。版本检测只说明安装事实，不能发布“已登录”“可调用模型”这样的未知状态。

执行者引用绑定 Host 与原配置身份。当前来源设备上的内置别名可写作 `codex`；重名、多配置或跨设备场景使用返回的具体引用。可执行路径和启动参数由原配置 owner 解析，模型工具不接受任意命令代替执行者引用。

### 4.3 自动发现与用户停用

已支持的内置程序可以在发现后直接选用；自定义 ACP 沿用户现有连接配置接入。设置中的启用意图在原配置中表达为“自动发现／启用／停用”：自动发现使用实际安装的内置程序，启用保留用户指定配置，停用保留用户明确选择。

旧存储中的 `enabled: true/false` 分别迁移为启用／停用。没有落盘、仅由内置模板补出的 `enabled: false` 变为自动发现；若旧存储无法区分一次保存的默认值与用户停用，保留已有停用，不猜测历史操作。迁移归原 Catalog 配置 owner，一次升级完成。扫描和派发都不会把显式停用自动改成启用。

启用、安装、连接和认证分别显示，避免一个绿色“可用”同时代表四种事实。保留明确的程序路径、参数及自定义 ACP 配置入口，使用者可以选择自己安装的构建。

### 4.4 执行设备与工作来源

| 选择 | 解析行为 |
| --- | --- |
| 沿当前来源或明确选择项目／来源 Agent | 在该来源的实际执行 Host 查找并启动执行者 |
| 明确选择另一设备执行者，未指定文件来源 | 使用目标 Host 已有默认来源／私有工作目录机制；需要材料时沿原附件服务交付 |
| 明确文件来源与执行者不在同一可执行位置 | 返回二者的实际位置，允许改选目标设备来源或按已有资源能力交接；不把协调机同名路径当成目标文件 |

前端、协调 Harness 与文件所在设备的部署保持独立。程序、登录、版本和原生 session 在实际执行 Host 上解析；远端发现、连接和控制扩展既有 `externalSettings`、`externalBinding`、`externalSpawn` 与 `externalControl`，复用认证、配对及 relay。

### 4.5 派发受理与配置更新

Rust 派发选择增加明确的原生／外部目标，外部选择可以来自预设，也可以来自执行者引用。两者都进入原 `external_children`、`external_conversations`、turn 与报告路径，不制造原生 Run，不让直接聊天与任务派发使用不同适配器。

受理保存本次任务、执行者身份、明确选项、来源与交办关系。真正准备调用时由目标 Host 解析当前程序配置及能力。已投递输入和在途原生 turn 保持原关联；重启后的恢复与之后的新工作使用当前实现重新准备，不以旧工具定义、缓存能力或版本哈希要求整个旧配置永久相等。

原生 session 的恢复仍固定同一会话。若新配置无法恢复原 session，保留原历史和具体原因；用户或模型可以明确新建关联任务，但不以新会话冒充恢复成功。结果不明的已投递输入沿原回执核对，只有确认尚未投递的准备才可继续原请求。

## 5. 外部适配的完善方式

### 5.1 能力由实际接线决定

沿已有 `ExternalAgentCapabilities`、`HarnessConnection` 和服务投影完善，区分静态适配支持、当前会话协商和运行状态。能力目录只说明调用行为，不维护另一套任务状态机。

- **输入方式**：轮次间排队、可选运行中插话；插话能力需要实际方法、输入关联、受理证据和取消语义共同接通。
- **选项**：模型、思考、模式和额外配置取本次连接返回的真实值；未知默认保持省略，更新失败保留原选择及错误。
- **恢复**：原 session 是否可恢复、用哪种原生方法恢复；缓存只用于发现和展示，实际连接确认结果。
- **控制与观察**：停止作用于轮次还是连接、能观察哪些工具／后台工作、能回答哪类交互，按实际适配声明。

已探明不支持与尚未取得信息分别表达。模型仅按需读取候选差异，稳定系统提示中不放完整动态模型表、版本信息或设备扫描结果；配置变化通过工具结果和原会话状态更新，保留前缀缓存与上下文连续性。

### 5.2 补充输入与运行中插话

先完善现有队列从受理、等待、投递到完成的状态及原请求关联。随后逐后端核验所用正式协议／SDK的插话接口；确实可用时扩展可选 adapter 方法，并接入原输入队列的投递方式。

运行中插话属于活动外部 turn 的补充输入，保存自己的消息回执与消费关联；不能为适配方便制造一次已经完成的新 turn。排队的新任务在上一轮实际结束后创建自己的 turn。`afterCurrent` 明确选排队；普通补充按会话选项和真实能力处理。用户明确选择插话而能力不可用时保留草稿／请求并说明原因，提供排队选择。

插话还需处理“发送过程中原 turn 恰好结束”：能确认未受理时可按明确选择转入下一轮，受理不明则保留原请求待核对，不重复发送。取消某条补充消息也不能误停下一轮任务。

### 5.3 各适配器具体要打磨的部分

| 适配器 | 在现有实现上完善 |
| --- | --- |
| Codex app-server | 核验并接通可用的活动 turn 输入接口与模式／权限选项；保留 thread、turn 和交互的原生关联。完善模型目录失败重试、工具／内部 Agent 活动与终态的对应，确认停止只作用于目标执行。 |
| Claude Code SDK | 核验持续输入、配置变更及公开选项的实际支持；保持用户配置加载。统一输入 UUID、tool-use、审批回调与 result 的关联，明确配置已请求和原生已确认的区别；SDK 后台 task 与当前 turn 分别结算。 |
| Pi RPC | 核验原生 steer／follow-up 等输入接口；接通时保留 handled disposition、输入归属及 `agent_settled` 结算。已有 pending、compaction、后台忙碌状态共同决定何时能投递和回收。 |
| ACP | 按实际协商接通模型／模式／配置、权限、问题和材料；整理 stop reason 与错误含义，保留工具、思考、正文的原事件顺序。确有使用需求且协议提供的文件／终端回调接到既有文件与进程 owner 后再声明能力。profile 特有交互留在原适配扩展位置。 |

这些是实施时的核验与接线目标。当前源码尚不能确认的上游能力，实施时查所用版本的正式契约并做对应验证；不因为另一个客户端有同名按钮就宣称可支持，也不把现有 `steering: false` 固化为永久限制。

模型目录、附件、审批、取消、错误恢复沿直接聊天和任务派发共用路径完善。提示和错误文案从实际字段生成，不依赖辅助模型总结，不要求执行 Agent 为 UI 额外填写进度表。

### 5.4 协作与交互的实际边界

Varin 能向外部会话交办、补充材料并接收原结果；外部 Agent 主动调用 Varin 的 `threads`、`send`、`dispatch` 暂不实现。外部内部子 Agent 按协议提供的信息展示，保留其外部身份；可观察并不自动取得单独取消或再次派发的能力。

原生 Agent 联系 Varin 已登记的外部会话，也应按原会话访问范围和实际输入能力处理，移除仅凭派发家族判断可联系范围的条件。用户手动建立的外部会话无需补造一条首次派发关系：在原 external message／turn 记录中关联本次请求者、输入与结果，沿同一个外部队列交付和回报。外部程序在其他终端创建、尚未接入 Varin 的会话导入与进程接管仍属后续能力。

待处理问题进入现有问题／权限区域和 Bot 工作详情，使用原请求的真实正文、选项与操作摘要。Agent 间普通消息保留发送者身份，不能冒充用户批准；权限由原交互 owner 和用户选择处理。登录继续使用外部程序原账号和正式入口。

附件使用既有固定引用、typed media 与执行 Host 路径准备。图片直接输入和作为文件提供的区别应明确；路径不跨设备照搬。正文、工具与思考使用原事件身份和顺序持久化，断线重连后仍能按原顺序呈现，不因组件挂载顺序重新排列。

## 6. 任务状态、监控、恢复与回收

### 6.1 Bot 与用户观察同一个执行

继续由 Rust Catalog 保存派发、输入、turn、报告及待处理事件，Host 翻译外部协议。任务详情、Bot 工作概览和模型状态查询读取同一份事实：

| 事实 | 应呈现的含义 |
| --- | --- |
| 准备程序／连接／来源 | 尚未真正投递模型输入，可定位准备阶段和错误 |
| 输入已经耐久受理 | 已进入 Varin 队列，仍可能等待上一轮或交互处理 |
| 原生请求已投递 | 保存实际执行关联；与收到第一段输出分别记录 |
| 等待问题或权限 | 展示原请求及处理入口，不作为普通无活动卡住 |
| 正文、工具或后台工作事件 | 更新实际可见进度，保留事件原来的类型 |
| 原生轮次完成／失败／取消 | 保存本轮结果，按这次交办关系回报 |
| 连接中断或 Host 意外退出 | 区分未投递失败与已投递结果不明，保留历史及恢复入口 |

外部轮次结束、外部内部工作结束和连接可以回收分别判断。一次轮次结束可以产生结果回报，若协议仍报告后台工作，则继续展示活动并保留其进程与来源；不把所有后台活动捏成一个永远不结束的主 turn。

### 6.2 无活动提醒

复用已有 Bot 可配置无活动阈值、continuation 计时源和持久工作事件。原生执行沿请求／工具派发事实计时；外部沿实际暴露的 turn 开始和新工具调用等执行事实计时。文本增量说明输出仍在到达，单独作为观察信息，不猜测它背后发起了几次模型请求。

提醒给出执行引用、当前实际状态、最近可观察动作、等待原因及持续时间；外部观测范围有限时直接说明所见事实。已有权限问题、明确等待、取消中和终态按对应状态处理。提醒不自动判失败、不强制终止，也不自动重发任务。

同一活动区间复用原提醒身份。新活动或结束使未消费旧提醒失效；完成、失败、准备失败、异常中断及待恢复沿原工作回报送达交办方。跟进既有任务仍用原事项／关注机制，不因目录可读而默认监控所有会话。

### 6.3 停止与恢复

- 普通停止发送实际协议取消，等待真实终态；协议已响应取消请求但执行尚未结束时显示“正在停止”。明确强制停止沿 Rust 进程树 owner 确认退出。
- 停止请求固定原 turn，迟到控制不得停止其后继。取消等待只结束观察；取消尚未投递的任务只撤销对应输入。
- 重连恢复原 session 和观察能力。未投递队列沿原请求继续；已投递而结果不明的输入保留待核对状态，恢复不重复执行。
- 后端能查询原执行结果时优先核对；无法查询时给出具体恢复选择。外部程序升级后重新协商能力，历史结果保持原事实，后续任务采用当前实现。

### 6.4 回收

保留现有空闲连接回收设置与 Rust 进程／来源 owner。活动 turn、待答交互、未结算输入、队列和实际报告的后台工作保留原持有关系；回收结束连接，不删除用户的外部原生历史、账号或项目配置。

各适配器完善 `backgroundTasks` 的含义及可观测范围。Codex 的内部 Agent、Claude task、Pi 忙碌状态与 ACP 工具活动提供不同证据，不能一概解释为完整子任务数。连接恢复时核对协议可提供的现状；未知后台状态不靠固定等待时间伪造结束。

不支持原 session 恢复的后端保留现有不自动回收策略；用户仍可明确关闭。关闭前端面板只结束观察，不取消任务。资源释放失败保留原清理责任和可重试操作，不新建另一套回收队列。

## 7. 产品交互

### 7.1 设置与执行者选择

沿现有“外部 Agent”设置页加入执行设备选择、检测／刷新和清晰的安装与连接状态。已发现程序与自定义配置使用现有紧凑列表；模型、思考及模式按实际能力展示，详细路径和启动参数留在展开编辑区。原“Agents”页面继续编辑常用角色组合，可选执行者；直接派发不再以该页面为必经步骤。

采用已有 Harness 图标、名称和克制的状态文字。浅色／深色分别使用主题语义色；保留现有展开、收起和状态过渡，窄屏先压缩可伸缩区域，再让操作换行。新增文案同时进入既有本地化目录。

### 7.2 任务与会话

派发后沿现有任务项和旁侧详情进入真实会话。任务名称表达工作，Harness 标记表达执行后端，Bot 小头像继续表达交办来源；在现有层级里安排这些信息，不把每项都变成一张大状态卡。

原生与外部过程复用聊天正文、工具展开、问题／权限、队列和工作详情。明确显示“待投递”“已投递”“等待回复”各自的事实。连接、登录、模型目录或实际执行失败在对应位置给出具体原因和处理动作，保留草稿及原请求身份。

跨任务通信进入现有协作流，显示真实双方和可打开的原消息／会话。直接联系的独立任务可以从协作记录访问，不挂成发送方的子任务；任务树继续默认收起并记住用户选择。侧栏仍按原模式区分 Bot 直接会话和工作台／IDE 任务，协作目录开放不新增“全部会话”侧栏入口。

Bot 联系另一 Bot 后，在原聊天和右侧工作／协作详情中查看请求与回复；不增加聊天标题下的工作栏。用户可以进入原接收会话处理问题、补充输入或查看结果，再回到发起位置。任务报告引用真实答复，过程摘要使用已有事件字段。

## 8. 实现落点与实施顺序

| 现有 owner／入口 | 修改内容 |
| --- | --- |
| Catalog 会话目录、`catalog_family`、`catalog_messages`、`catalog_bot_work` | 统一产品会话访问判定，放开跨家族联系及精确分支路由；保留管理和资源边界 |
| 原输入队列、activation、reply wait、work report、Bot work events | 打通普通主任务和 Bot 的收件、回复、接续及原请求结果交付 |
| 原生 `dispatch` schema、选择及 external child | 加入直接执行者选择和外部选项，预设与自由派发共用真实目标 |
| ExternalAgentService、配置／能力缓存、managed Source 接口 | 设备范围的发现与检测、配置意图迁移、目标解析、连接与控制 |
| Codex／Claude／Pi／ACP adapters 与 HarnessConnection | 补全真实输入、选项、交互、活动、结束与恢复能力 |
| application-client、设置页、会话与协作投影 | 共用类型、真实能力控件、原消息入口、任务标记及本地化 |

原生协作先以“两个独立会话请求并回复”和“两个 Bot 会话协作”贯通目录、消息、激活、报告及用户入口。修改访问判定时逐项追踪现有家族读取的调用者，防止文件来源、树取消和管理操作随通信范围意外扩大。Bot scope、活动状态与监控也要区分自己派发的工作和联系的独立会话，不能因收到某 Bot 的请求就改变执行者的生命周期归属。已有明确冻结的附件与历史引用继续使用原交付身份。

外部执行者先贯通“发现目标设备的程序 → 无预设直接派发 → 实际执行 → 回报 → 同会话补充工作”。随后按适配器逐项打磨输入、交互和生命周期，每项都共用直接聊天与派发路径。运行中插话的交付以真实协议接线为准，现有轮次队列可独立完善。

持久结构变更由原 Catalog upgrade 一次迁移；不长期保留多代配置解析分支。查询输出与工具定义更新不要求重建旧任务，历史报告和已受理输入保留原身份。实现完成的内容并入领域文档，本设计随完成范围收敛。

## 9. 验收依据

优先扩展现有会话、消息、派发及适配器测试，围绕真实行为保留少量有区分度的场景：

| 场景 | 要证明的行为 |
| --- | --- |
| 独立主任务、主子、子子、不同 Bot 互相联系 | 能发现、发送、读取所需材料、回复原分支；不用伪造父子关系 |
| 同一 Bot 的不同会话、同一 Thread 的不同分支 | 收件位置和回报位置精确，不串到档案入口或最新会话 |
| 空闲／未启动、运行中、正在等待及明确暂停的收件人 | 沿原激活与输入语义处理；原暂停或问题真实可见 |
| 明确回复、终态报告、多个请求共用一轮 | 原请求关联准确，无重复交付和自动报告循环 |
| 发送方停止／关闭与接收方继续运行 | 等待、联系和派发归属分别处理，不误取消或回收独立任务 |
| 无预设派发、外部预设、显式覆盖执行者 | 解析优先级确定，未覆盖选项采用真实默认；未知能力不虚构 |
| 联系手动创建或其他任务派出的外部会话 | 复用原 session 与队列，本次结果回到实际请求者；不伪造首次派发归属 |
| 未配置内置程序、旧启用／停用、自定义 ACP | 自动发现可用，历史停用得到保留，缺失程序和检测失败有区别 |
| 同名程序在本地和远端、来源位置不匹配 | 使用目标 Host 的程序、配置和文件，不借用协调端环境 |
| 轮次队列及实际支持的插话 | 受理、消费、结束和消息归属准确，结束竞争不重复投递 |
| 权限／问题撤回、附件、乱序或迟到事件 | 操作绑定原请求，材料可读，正文与思考顺序稳定 |
| 完成／失败／中断、无活动提醒、停止与回收 | Bot 获得对应事实；后台工作保留资源，恢复沿原 session |
| 版本更新后恢复和新工作 | 当前适配与能力可继续使用，旧定义不阻塞后续执行 |

可复现协议差异用现有 [dedicated adapters 测试](../../packages/web/application-host/lib/external-agents/dedicated-adapters.test.ts)、[Claude bridge 测试](../../packages/web/application-host/lib/external-agents/claude-bridge.test.ts)、[ACP 测试](../../packages/web/application-host/lib/external-agents/acp.test.ts)验证；派发和报告优先复用[原生 Host 派发集成测试](../../packages/web/application-host/lib/kernel/child-dispatch-review.native.test.ts)。新增适配能力再用相关真实程序做最小验证，记录程序／协议版本与实际覆盖能力，不为每项修改重复跑所有后端。

本文交付只核对源码依据、设计自洽及文档链接，不运行模型任务、不打包 EXE。实施验收以实际改动范围选择检查；MCP／CLI／Skill 对外协作桥接不进入本轮验收。
