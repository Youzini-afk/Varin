# 聊天与设置的整体体验设计

状态：基于现有实现重做的设计提案，待 HTML 稿评审。2026-10-23。

本文规定下一轮体验改造的完整目标与交互合同，不代表全部行为已经进入产品。
独立稿件：[聊天与设置 HTML 设计稿](chat-settings-preview.html)。直接用浏览器打开，可离线使用。
稿件使用同一组示例事件切换三种完整聊天模式，不连接真实 Host、不修改用户设置、不执行工具。
原内联可视化中的通栏侧栏、额外思考入口、手工工具意图说明不作为本设计依据。
实现后将稳定规则并入[工作台](../workbench.md)与源码旁说明，避免长期维护两套现状文档。

## 1. 产品判断

Varin 的单个工具已经有按用途组织的界面。下一步需要以用户经历完整任务、完成一次配置为单位安排信息。
聊天应当可以连续阅读，执行过程有明确归属，值得处理的事情能够被看见。设置应帮助用户做决定，并准确解释配置与实际能力的关系。

用户进入任何一个进行中的会话，应该能迅速找到：当前在做什么、已经得到什么、是否需要自己介入。
回看会话时，应该能先读懂结论，再沿原始动作追到依据。配置能力时，应该能知道改的是谁、缺少什么、什么时候生效。

设计延续已确定的方向：

- 「对话优先」作为未设置时的默认模式；已有用户选择继续保留。
- 每段模型正文后，普通过程使用一条可展开的动态摘要。下一段正文到达后，前段过程收为已发生事实的摘要。
- 子 Agent 保留独立头像、任务和状态；已有终端、差异、检索、材料等用途设计继续使用。
- 工作概览保留当前「占位悬浮卡片」：完整、轻览、关闭三种状态；完整宽度初始 280px，可拖动；轻览宽度 240px。卡片有自身边界、圆角、阴影及内部滚动，按内容决定高度，不改成通栏侧栏。
- 小窗口沿现有容器布局把概览放到聊天上方；计划概要聚焦当前步骤，完整计划在卡片内原位切换阅读与编辑。
- 文件写入可在参数流式生成时预览；思考可见、可展开、有阅读窗口；长内容自然换行。
- 轮末左侧保留操作按钮、右侧直接显示用量；问答区与输入框等宽，放在输入框上方。
- 新会话沿用项目现有界面。多问题、多选和持续授权同时设计工具与权限链路，不能只补前端按钮。

这轮设计同时解决默认折叠后的内容组织。打开过程之后，也应有清楚的对象、动作、结果和关系。

## 2. 现状依据与问题

| 现象 | 当前结构中的依据 | 对用户的影响 |
| --- | --- | --- |
| 后续任务同时显示「已完成」「等待观察」「已取消」 | `ChatFollowupTool` 分别渲染调用状态、条件 observed 与任务 state | 用户需要自己区分不同对象的状态 |
| 空列表结果也呈现登记回执 | follow-up 结果按兜底 record 呈现，缺少记录时使用 registrationRecorded 文案 | 查询结果看起来像新创建了任务 |
| 长资源与任务 ID 进入标题 | 工具主体描述可能直接使用原始引用 | 正常阅读被实现细节占据 |
| 一屏工具很多，信息却不集中 | 单个工具各自拥有标题、状态、说明、详情与间距 | 每条看似完整，整段缺少主次与归属 |
| 开关开启但辅助模型为空 | `WebSettings` 将模型字段与能力开关组合呈现 | 「开启」容易被理解为能力已经可用 |
| 可执行文件路径与常用选择平铺 | 文档读取区直接列出 Docling、Tesseract、OCR 语言等字段 | 初次配置就必须理解实现和环境 |
| 标签与控件横跨宽页面 | 通用 FieldRow 与较宽 SettingsPageLayout 共同作用 | 视线来回寻找对应关系，留白没有帮助理解 |

已有的 `chatDialogueProjection`、稳定时间线身份、用途工具组件、Settings primitives、设置目录和保存反馈是后续实现基础。
本设计不重新建立执行 owner、配置 owner 或历史存储。

## 3. 信息如何分配到界面

### 3.1 阅读层级

| 层次 | 内容 | 默认呈现 | 用户继续深入 |
| --- | --- | --- | --- |
| 对话正文 | 用户意图、模型解释、发现、回答 | 连续正文，最高阅读清晰度 | 引用、复制、来源导航 |
| 当前工作 | 正在进行的普通动作、思考 | 当前正文下的一条动态过程摘要 | 就地展开相关执行过程 |
| 协作关系 | 子 Agent 的任务与状态 | 独立头像行，位置保留在派发发生处 | 打开该任务、查看报告或继续沟通 |
| 需要介入 | 问题、权限、冲突、阻塞、效果未知 | 出现在发生处，直接给出下一步 | 选择、补充信息、查看依据 |
| 可用产出 | 文件改动、报告、图片、可交互作品 | 紧贴相关解释，采用用途合适的预览 | 查看差异、打开文档、使用作品 |
| 执行证据 | 参数、原始回执、内部 ID、完整诊断 | 过程详情内的局部入口 | 原始记录、复制、定位 |

层级不是固定数据类型白名单。同一个文件读取，正常成功属于过程；权限阻塞可能需要用户介入；读取出的关键证据由模型在正文解释。
UI 只组织已有事实，不生成新结论，也不根据日志自行判断问题已经解决。

### 3.2 页面职责

| 区域 | 负责回答的问题 | 长期保留的内容 |
| --- | --- | --- |
| 聊天 | 为什么这样做、发现了什么、我需要做什么 | 对话、动作的发生记录、结果与来源 |
| 工作概览 | 工作目前走到哪里、还有谁在做、有什么可用结果 | 当前计划摘要、任务状态、产出入口 |
| 专用详情 | 某个对象的完整内容和操作是什么 | 计划、任务、文档、差异、运行详情 |
| 诊断详情 | 具体请求与失败证据是什么 | 原始参数、状态、回执、错误与标识 |

同一事实允许在不同区域出现，但呈现目的必须不同。概览展示某任务的当前状态，聊天保留它在当时发生的事件。
页面切换、关闭概览、折叠过程都不改变任务、进程或观察器的实际执行状态。

## 4. 聊天的完整组织

### 4.0 三种模式分别设计

三种模式消费相同的消息、工具调用、运行状态与结果。切换不更换示例、不改变执行事实，也不为其中一种模式补写额外说明。

| 模式（现有设置文案） | 当前基础 | 本稿中的完整安排 |
| --- | --- | --- |
| 按时间展开 live | 正文、思考、工具按发生顺序展示 | 保留顺序与用途组件，通过段间距、紧凑事实标题和状态分量改善阅读；思考仍是原来的单行预览/展开窗口 |
| 对话优先 dialogue | 每段正文后的普通活动收为一组，dispatch / ask_user 独立 | 保留每段模型发言；过程一行动态显示、可展开；展开后直接使用原思考和工具组件，子 Agent 行保持可见 |
| 集中展示回答 sorted | projectChatSortedTurn 将思考、工具、同消息中的执行说明收进活动；独立回答留在外层 | 完整呈现本轮活动与回答。提议将子任务身份单独保留在活动组外，并从内部去重；这是对当前 sorted 的明确调整，其余沿原分类规则 |

「执行说明」只指模型已经输出、且与工具调用同属一条消息的正文。前端不生成此类文字。
集中展示回答时，没有独立回答就不凭空放一段“总结”填充界面。
思考显示、思考自动展开、命令自动展开、编辑自动展开、活动默认展开等现有偏好继续有效。

### 4.1 以模型正文为阅读边界

```text
我先检查计划面板的布局和编辑逻辑。

› 读取了 4 个文件 · 执行了 2 条命令

[头像] Layout Scout · 检查窄窗口的换行问题 · 已返回

问题出在计划预览直接渲染全部条目。接下来会聚焦当前步骤，编辑也放回原位置。

› 正在写入 ThreadPlan.tsx
```

同一段正文后的普通动作持续更新这一条摘要；新的模型正文到达后，前段摘要表达已发生的工作，后段拥有自己的过程行。
单段流式文字内部按原消息连续追加，不能按每个 delta 拆成新段。
模型没有先说话时，过程仍可出现于本轮用户要求之后，不凭空插入解释性正文。

子 Agent、询问、权限与独立产出保留自己的语义位置。它们不制造重复的普通过程摘要；脚本里发生的子任务也只出现一次。
同一段里有并发动作时，一行表达当前主体与「另有 N 项进行中」，展开后看见所有活跃动作；不能因展示最近事件而隐去等待中的工作。

### 4.2 动态摘要

摘要由原始对象和确认状态生成，不额外调用模型，也不使用会话中尚未确认的自述作为成功回执。

工具没有通用的「本次操作目的」字段。下面是实现和稿件共同遵守的数据合同：

| 展示内容 | 现有可用字段 | 显示例子与回退 |
| --- | --- | --- |
| 文件读取对象与范围 | call.arguments.path / files[].path；startLine/endLine 或 offset | 读取文件 · ThreadPlan.tsx · L70–130。没有路径时只显示准备读取，不补写“计划阅读、编辑状态与保存入口” |
| 搜索对象和范围 | query / queries、paths、fixedStrings；返回的 records | 直接显示查询词与目录，不改写成任务意图 |
| 进程命令与结果 | command + args、processId、已加载的原 spawn、snapshot.exitCode、confirmedBytes | 原命令、退出码、字节数；找不到原进程时保留 ID，不补造用途 |
| 文件写入与编辑 | path/content 或 path/readVersion/edits[].oldText/newText；实际写入回执 | 内容预览与真实应用状态；参数生成完成不等于应用完成 |
| 脚本标题 | 现有可选 arguments.title，或已观测子调用名称的固定分类 | 没有 title 时照常显示「运行脚本」等现有回退；不新增必填描述 |
| 子 Agent 名称与任务 | 原有 name、task、avatar、子任务状态 | 说明来自原派发参数，不额外要求 UI 专用摘要 |
| 思考 | ChatThinkingContent.thinking | 原始公开思考的单行预览和展开窗口，不再添加“查看这一段思考” |

参数已核对现行内核 schema：tools_read.rs:167、tools_discovery.rs:536、tools.rs:2640。
脚本内调用使用现有 tools.invoke({callId,name,arguments})，并保留 environmentId。
普通工具的数据例子采用现有呈现边界的字段形态。多问题、多选与持续授权需要扩展现有合同，单独在第 5 节说明；HTML 的字段来源也标明 proposed。工具元数据的静态说明不能冒充本次调用意图。

| 实际事实 | 建议摘要 |
| --- | --- |
| 正在读取已知对象 | 正在读取 ThreadPlan.tsx |
| 参数尚未完整到达 | 正在准备文件写入 |
| 正在生成写入内容 | 正在准备 ThreadPlan.tsx 的内容 |
| 执行器正在应用内容 | 正在写入 ThreadPlan.tsx |
| 有公开思考、尚无动作 | 正在思考；展开可读公开思考 |
| 普通调用结束 | 读取了 4 个文件 · 执行了 2 条命令 |
| 只能确认调用次数 | 读取文件 5 次；不推断唯一文件数 |
| 存在未解决的局部失败 | 读取文件 4 次 · 1 项未完成 |
| 已有明确关联的恢复结果 | 读取文件 5 次 · 1 次失败已恢复 |
| 服务正在按既有策略重试 | 请求暂未成功，正在重试；详情显示实际次数 |

「修改了 N 个文件」必须来自已确认的文件效果及原始资源身份。待保存草稿、分支内变更、已应用文件采用各自标签。
重试保留尝试次数，同一原始调用的多次呈现只统计一次。尚未结束的命令没有「已运行成功」含义。

摘要中的对象名称优先使用文件名、任务标题、站点或能力名称。只有 ID 时表达「读取资源」「管理后续任务」，完整 ID 进入详情。
同名对象需要区分时增加最短可辨识父路径或 Host；完整路径可查看和复制，并沿原始来源导航。

### 4.3 展开后的过程

过程默认使用一层展开，内部按原始顺序呈现。左侧轻量的连续线只表达归属，不把每个工具再包成卡片。
普通读操作采用动作、对象、必要结果的一行。展开文件时显示实际代码或匹配片段，终端保留命令与输出关系，写入沿用流式差异。

用户手动打开的过程不因新消息、完成事件或自动摘要而突然收起。下一段过程保持自己的默认状态。
长日志、差异、思考各自使用有足够阅读面积的局部窗口；用户向上读时暂停该窗口的追随。正文不成为多层套叠的滚动框。
代码预览默认换行；需要保持列结构的表格或用户选择的原样代码，才提供明确的横向阅读方式。

公开思考直接复用 ChatThinkingBlock：脑图标、「思考」、一行实际内容预览和右侧箭头。
新内容沿单行窗口向上滚动，保留渐隐；点击后展开原阅读窗口，长内容内部滚动，收起沿原高度动画。
过程内不再额外套一个「查看这一段思考」的 disclosure。关闭「显示思考」不影响工具可见性。
对话优先模式下，思考自动展开设置作用于已打开的过程内容，不越过过程折叠层抢占正文。

### 4.4 子 Agent

沿用头像身份与实际任务名称。独立行表达「谁负责什么、目前如何」，不把 dispatch 原始参数作为主要说明。
多次与同一子任务沟通保留时间关系，可在过程内表达发送动作；任务主体沿稳定 Thread 身份导航，不创建相同头像的多个伪任务。

派发尚未获得受理回执时显示「正在派发」。受理后显示「进行中」；受理未知显示「派发结果待确认」，不提供会重复创建任务的盲目重试。
任务失败由任务行说明，主 Agent 仍可继续工作。只有实际阻塞主任务时才升级主线状态。
打开子会话保留父会话阅读位置；任务报告可就地查看，完整沟通进入协作视图。

### 4.5 后续任务与长期工作

创建、暂停、取消等事件在聊天保留简短回执；持续管理进入工作概览的任务详情。
「列出」空结果写「暂无后续任务」，不显示登记成功。创建成功但等待条件时写「已安排：文件变化后继续」，详情解释触发条件。

任务已取消时，当前主状态为「已取消」，条件区采用「取消前尚未触发」或历史记录。
工具请求成功只留在调用详情，不在同一标题旁再用「已完成」制造第二个任务状态。
查看历史调用与当前任务信息时分别标识「当时记录」「当前状态」，不悄悄把历史完成记录改写成今天的状态。

### 4.6 结果与结束

正文完成后，实际产出靠近引用它的解释。多个文件用紧凑的变更列表，报告用文档入口，图片与作品保留有用预览。
过程内部的工具回执与产出入口引用同一个原始资源，避免复制两份完整预览。
轮次底部按「左侧功能按钮、右侧用量」直接呈现。复用 ChatTurnUsageFooter、ChatAssistantUsageFooter 与既有复制、关联会话、分支、更多操作；按这个目标保留排列，不把统计收成点击后才打开的入口。正常工具不再逐个强调「已完成」。

用量沿已有 ChatUsage 与聚合规则：输入、输出，以及有数据的缓存读取、缓存创建、推理、总量和速率。缓存缺失或为 0 时隐藏该项；总量来自原上报字段，不把缓存数再加到输入数上。actual / estimated 分组保留区别，未上报显示未知。统计与按钮在窄窗允许自然换行，按钮始终可见；不改成指标卡片。HTML 提供有缓存、零缓存、未上报三个状态帧，数值均为示例。

右侧同一行补充「缓存率」，表示缓存命中率：缓存读取 token ÷ 完整输入 token。只在缓存读取大于 0、完整输入量大于 0 且统计口径与数据齐全时显示，最多一位小数；无缓存、只有缓存创建或分母未知时隐藏。多请求按去重后的 token 总量加权计算，不平均各次百分比，不把缺失回执当作 0。

实施前需要统一渠道口径：当前 Chat provider 将 prompt_tokens 写入 input，Anthropic 将原 input_tokens、cache_read_input_tokens、cache_creation_input_tokens 分开传递，historyPresentation 又直接映射到 ChatUsage，不能统一直接用现有 cacheRead/input。应在用量 owner 保留渠道语义并投影出完整输入量：已包含缓存的输入只计一次；分项上报则合并非缓存输入、缓存读取和缓存创建，创建时长子项不重复累加。当前 usagePresentation 虽声明 cacheHitPercent，但尚未计算；本设计要求补齐这条链路。HTML 以 includes-cache 明确标注示例输入口径，展示 10,240 / 12,480 = 82.1%，不冒充现有运行时已支持该口径字段。

有尚未完成的事情时，结束处明确列出其影响与可执行入口。没有结果回执时显示「结果待确认」，不能用绿色成功把它盖过去。
结束事件不会自动滚动到用户没读过的位置，不重排已经读过的段落。

## 5. 状态与注意力合同

界面分别保留 execution（执行）、effect（效果）、observation（观察）和用户待办等事实。
主状态根据所呈现的对象选择，视觉分量依据当前影响；没有人工「重要度分数」或按日志关键词猜测的严重程度体系。

| 状态 | 主线表达 | 过程/详情 | 主要操作 |
| --- | --- | --- | --- |
| 正常执行 | 当前动作 | 顺序过程与原始来源 | 展开、停止原任务 |
| 自动重试中 | 正在重试、仍在处理 | 实际尝试与已知原因 | 查看、按原能力取消 |
| 失败后确认恢复 | 简要继续说明或过程摘要 | 原失败与恢复关联均保留 | 查看恢复过程 |
| 单个子任务失败，主任务继续 | 子任务行表达失败 | 原任务错误和已有产出 | 查看任务、继续沟通 |
| 需要回答/权限/冲突处理 | 原处直接呈现问题与影响 | 可查看依据 | 明确提交或拒绝动作 |
| 执行被阻塞 | 说明具体阻塞点 | 原错误和已完成部分 | 对应解决入口 |
| 请求已发出，效果未知 | 结果待确认 | 保留原 operation/key | 查询原操作，不能重放写入 |
| 观察连接断开 | 连接中断，正在恢复观察 | 上次已确认状态与时间 | 恢复连接；不声称任务停止 |
| 用户要求停止，尚无停止回执 | 正在停止 | 已发生效果继续可见 | 等待原 owner 的最终状态 |
| 本轮结束但后台任务仍存在 | 本轮结束，后台任务继续 | 概览列出仍活跃任务 | 打开或管理对应任务 |

同时有多个需处理项时，当前直接影响推进的事项首先可见，其他待办显示数量与对象。全部待办都可访问，不静默丢弃。
若无明确阻塞关系，保持发生顺序，不凭类型猜测谁更严重。用户阅读历史时，在当前工作入口提供待办提示，不把页面拉回底部。

已恢复状态必须有执行链中的明确证据；没有关联信息时保留「此前失败」，UI 不把后续相似调用当作补偿成功。
网络断开、provider 失败和工具副作用未知各用自己的状态，不统一包装成「重试一下」。

### 5.1 问答区与输入框共处

问答区放在聊天输入框正上方，共用内容列宽度与左右边界。两者保留约 12px 间距；输入框继续承担底部安全留白。取消固定在整窗底部、宽度只有 max-w-lg 的浮层。概览展开或调宽时，问答区随输入列一起收缩。

问答区参与布局、独立滚动。标题与操作区固定在面板内部，长题目、长选项和补充输入在中间滚动；聊天历史仍可单独滚动。HTML 使用约半个视口的阅读高度，实际实现按输入框高度、可见视口和软键盘调整，让题目与输入区都能使用。这个高度只约束视窗，不截断问题或限制题数。

没有遮罩、焦点陷阱，也不自动聚焦新到达的问题。用户可以继续在聊天输入框打字、添加附件、提交补充；这些输入沿原队列机制处理。回答题目的草稿与聊天草稿分别保存，发送聊天消息不会提交答案。

收起箭头或 Escape 只把问答区收成一条「需要你的回答」入口，保留选择、补充文字、当前题号与滚动位置。展开/收起沿高度和透明度过渡，尊重减少动态效果偏好。「取消回答」是单独动作，对应取消原询问。时间线仍保留询问的发生位置，点击可重新打开并定位相应请求。

### 5.2 多题、多选和提交

- 一个请求有多道题：上方用题号导航与已填写数量，主体一次呈现一道完整题目；上一题、下一题和「检查答案」都可自由切换。题号采用前端序号，不要求模型额外提供短标题。
- 选项始终纵向排列、完整换行。单选用 radio，多选用 checkbox；多选题明确标注「可多选」，不会选中一个后自动跳题。无默认预选；保留清除选择与自由输入，自己的回答也能满足必答题。
- 必答题默认要求一个选择或非空文字；选填题明确标记，可跳过。必答题未填写时，提交按钮不可用，题号与检查页可定位缺项。
- 「检查答案」集中展示题目与已填写内容，每题可返回修改。一次「提交全部回答」提交该请求的完整答案；不逐题发消息，不让 Agent 在用户还在回答后续题时提前继续。
- 多个独立请求：同一面板提供请求切换与数量，按原发生顺序保留；每个请求单独提交、单独取消。提交一个后展示下一个，其他请求的草稿不受影响。是否能提交沿原 Operation 的可回答状态判定。
- 提交中锁定当前请求的答案与提交按钮，其他请求和聊天输入仍可使用。明确失败保留草稿并显示重试；受理未知查询同一请求，不能当成未提交而生成新请求。成功回执到达后，原时间线记录收为「已回答」，可展开查看全部答案。

草稿身份至少包含 Host、Thread、branch、operation 和题目 ID，绑定原问题版本。模式切换、收起、打开设置不清空草稿；题目发生实际变更时保留旧稿并明确提示。取消、过期、只读历史均不得继续提交，答案受理仍由运行时负责。

### 5.3 问答工具的改造合同

现状证据：kernel 的 questions.rs 只接受 question:string 与 options:string[]，QuestionAnswerParams.answer 为 string；ThreadQuestion 仅有一个 selected 字符串。ThreadQuestions 能排列多个原 Operation，但这与单次调用含多题、多选不同。

提议将新调用统一为 questions 数组。每题有稳定 id、question、可选 options、selection 和 required；选项用稳定 id 与 label。selection 默认 single，multiple 表示多选，无 options 就是自由输入；required 默认 true。题目与选项 ID 用于对应答案，不参与用户文案。自由回答和补充输入始终可用，不另设“允许其他答案”的开关，也不要求模型提供界面摘要、导航标签或完成文案。

例如模型提供：

    {
      "questions": [
        {
          "id": "details",
          "question": "这次希望一起调整哪些交互？",
          "selection": "multiple",
          "options": [
            { "id": "wrap", "label": "长内容自动换行" },
            { "id": "inline", "label": "计划原位编辑" }
          ]
        },
        { "id": "notes", "question": "还有需要保留的细节吗？", "required": false }
      ]
    }

回答应作为原 operation 上的结构化提交：

    {
      "operationId": "<原 operation>",
      "answers": [
        { "questionId": "details", "selectedOptionIds": ["wrap", "inline"], "text": "保留现在的面板宽度。" },
        { "questionId": "notes", "selectedOptionIds": [], "text": "", "skipped": true }
      ]
    }

运行时依据原始问题校验题目 ID、选项 ID、重复项、单选数量与必答状态，并按原问题顺序生成可读结果；不能依赖拼接字符串猜测用户选了什么。取消作为原操作取消，不伪装成 answer="已取消"。没有基于 UI 容量设置固定题数或选项数上限。

实施贯穿工具 schema/披露、Kernel questions 执行器、Catalog 问题状态与历史、protocol 及生成 DTO、application-client、ThreadQuestion/ThreadQuestions，以及 question_status 的结构化结果。保留原 Wait 与 operation 身份、受理去重和结果查询；不新建问答队列或第二份运行历史。历史中的已有单题文本按原事实展示，新模型调用使用更新后的 schema。

HTML 中单题场景保留现有参数形态，多题场景带有 contract:proposed 标记；这个提案尚未改动运行时。

### 5.4 权限：允许一次、一直允许、拒绝

ThreadPermission 继续在时间线底部独立处理权限。三个动作并列可见：允许一次、一直允许、拒绝。授权对象、作用范围在按钮之前读得到，原操作参数放在可展开详情；授权不混进普通问答。

以写报告为例，「一直允许」的可见范围是：当前用户 · Local 主机，file_write 写入 D:/reports/plan-review.md 这个文件。相同工具写入该文件的新内容也适用。持续规则可在「工具与执行」中查看与撤销；已完成授权的历史决定继续保留。目录、命令或外部服务等其他工具应由其可信 owner 生成对应的授权范围，不能只凭工具名拼一个全部放行规则。

现状有两条不同链路：

| 现有机制 | 实际语义 | 本次如何使用 |
| --- | --- | --- |
| decidePermission / Catalog::decide_permission | 只接收 allow_once 或 deny；绑定原 call/scope 与活跃 owner，一次消费 | 本次操作继续沿原决定与等待机制执行 |
| PermissionRule / 用户 permissions.rules | 按 tool、可选参数匹配规则持久保存 allow/ask/deny | 持续授权复用用户规则 owner 与现有编辑、删除入口 |
| 工作区权限规则 | 合并时只保留 ask/deny，优先于用户放行 | 不能把「一直允许」保存到工作区 allow，制造无效设置 |

因此新增的是可信端的“保存用户规则并批准原操作”能力，前端只提交原 operation/permission 身份与服务端给出的范围选择。不能直接向现有 decision 字段塞入 allow_always，也不能由 renderer 自行构造正则写入配置。

保存前核对原请求仍可决定、真实资源范围与规则优先级。对文件使用 owner 解析后的目标及准确匹配，处理相对路径、分隔符与实际资源身份；不因字符串前缀相似放行其他路径。持续规则沿已有用户配置保存，保留项目约束、allowed-directory 与执行能力边界。若原约束仍要求询问，界面应直接说明规则为何不能生效，不能显示永久授权成功。

保存结果与本次决定分别确认：保存失败时仍等待，提供重试、允许一次、拒绝；保存成功而原请求已失效时保留规则回执，同时说明本次操作未继续。重复提交用原身份和保存意图去重，不能重复追加规则或重做写入。撤销不回滚已经发生的文件效果。

目前权限设置标记 next-run。实现“一直允许”时，需要由原权限 owner 将用户明确保存/撤销的规则版本应用于后续尚未获准的匹配操作，包括当前运行之后的检查；既有已获准操作保留其决定。不要只更新设置页，让同一轮后续调用继续重复询问。原 scope 或 owner 发生变化则重新按实际规则判断。

关键来源：packages/protocol/src/permission-gate.ts、packages/ui/src/components/sections/harness/PermissionsSettings.tsx、kernel/crates/varin-runtime/src/catalog_permissions.rs、application-client 的 decidePermission 合同。HTML 演示范围说明、保存失败与撤销，不会写入真实授权。

## 6. 输入框、概览与空间

新会话保留 ThreadConversation 的现有标志、项目相关标题和输入区布局，包括原入口、配置选择与发送行为。撤掉前一版稿件自行添加的开场文案和建议按钮，不重新设计空会话。HTML 使用现有 varin-mark 与中文标题，仅用于表达保留关系。

输入框优先呈现输入和发送。模型是常用选择；思考等级靠近模型；来源与执行权限保持可见、可理解。
附件入口、语音和发送有稳定位置。单一执行后端不占一个无意义的选择器；实际可切换时恢复入口，其他原有能力进入明确的局部菜单。
当前运行的配置与「下一次发送」的配置分开表达，修改输入框不会使已运行请求看起来换了模型。

执行中允许用户继续输入，界面按真实 admission 能力区分排队、补充和新回合。草稿、队列状态和发送失败保留原输入，不用动画吞掉内容。
停止操作只指向原运行对象；成功提交停止请求后，显示正在停止而不是立即已停止。

工作概览沿 WorkOverviewControl 保留占位悬浮卡片，计划只保留当前附近摘要，子任务显示角色与进展，产出只显示入口。
完整/轻览/关闭沿现有状态切换，标题栏保留更多、轻览和关闭。完整模式可调宽；正文、输入框真实让出布局空间。
打开完整计划在该区域原位切换，返回恢复概览。计划编辑替换阅读内容，保存/取消可见，保留并发修改与草稿语义。

布局以可用内容宽度响应。宽屏并列正文与概览；窄窗沿当前容器规则上下排列，概览限制在可用高度的一部分，内部滚动。
模型与工具内容不因响应式变化丢失展开状态，键盘焦点回到原触发位置。

### 7.1 页面与字段层级

页面标题说明用户正在管理什么。下面用简短范围信息说明当前 Host、作用域与覆盖关系；说明文字紧邻它解释的决定。
常见偏好直接操作；选中某种能力后，在原位置展示依赖设置；环境与实现参数进入明确命名的配置详情。

| 字段类型 | 使用形态 |
| --- | --- |
| 一个独立偏好 | 紧凑横排标签与开关 |
| 少量互斥选择 | 可读的选项与简短影响；长选项纵向排列 |

| 对象集合 | 服务/规则列表，选中后进入对象详情 |

### 7.2 配置状态

| 已知事实 | 用户文案 |
| --- | --- |
| 功能关闭 | 已关闭 |
| 用户启用但依赖未选 | 待配置 · 选择辅助模型 |
| 配置已被 owner 保存 | 已配置；只表达配置事实 |
| 已有有效运行观测 | 可用或不可用，并提供观测来源/时间 |
| 当前平台明确不支持 | 当前 Host 不支持，解释可用环境 |
| 正在写入设置 | 保存中，保留当前输入 |
| 保存被拒绝 | 保存失败，具体原因与重试，草稿保留 |
| 配置被项目覆盖 | 当前项目使用覆盖值；可查看有效值与来源 |

不开新后台探测来给每项设置染绿色。模型已选择或密钥已保存不自动等于连接成功。
开关可以表达用户意图，同时用「待配置」清楚解释尚未生效；也可以由需要原子提交的编辑单元在依赖齐全后一起保存。
最终选择依照已有 owner 合同，不由通用组件擅自改写后端设置。

### 7.3 范围、保存和生效

页头显示本页真实作用域。只有支持 project scope 的字段才出现项目编辑入口；Host 全局页不能伪装成任意范围切换。
项目覆盖显示有效值及来源，重置动作叫「使用继承值」，并能看到继承后会变成什么。

即时偏好沿既有保存机制，在真实确认后短暂提示已保存。服务等多字段编辑作为明确的编辑单元，使用保存/取消；错误留在该单元。
混合页面不设置一个让人误以为能提交全部字段的全局保存按钮。离开未保存单元沿用既有 draft/navigation guard。
下一次请求、新会话、重启 Host 后生效等时机靠近有关配置，不能一概写成即时生效。
切换 Host 不把原 Host 的迟到保存响应写入新页面，范围改变时保留或明确处理草稿。

先选择服务或账号，再管理模型与用途。模型的协议、路径、参数在具体模型详情中呈现。
对话、辅助阅读、检索等用途显示已选对象或待配置，不要求用户先理解全部 provider 字段。
连接状态来自明确观测，配置状态与连接状态分开。编辑失败保留草稿；切换对象不能误把密钥或参数保存给另一个服务。
使用位置可导航到对应能力，避免同一个用途在多个页面维护独立副本。

### 存储

沿现有 inventory 分类展示：恢复与工作状态对象、独立工作副本、对话与附件、记忆与知识向量、共享模型资源、其他应用数据。
设备、工作区范围与共享范围分开选择，未知统计保留未知，不能换成前端随意合并的几类。
清理动作绑定对象、预计释放范围与实际影响。无可靠统计时显示未知，不用 0 B 代替。
删除会话应包含其可释放关联资源；共享引用、正在占用、可重试失败需有明确结果，不把逻辑删除当成空间已回收。
预览中的清理只是交互演示。正式实现继续使用原存储/清理 owner，不让 UI 创建清理计时器或文件删除路径。

### 对话默认

保留全局/项目信任与继承语义。重试直接对应现有 ModelRetrySettings：enabled、maxRetries、initialDelayMs、maxDelayMs 与 rules。
规则保留 field、match、pattern、action 及顺序。可以改善平铺密度与原位编辑，但不新增第二套匹配配置。
保存与规则测试继续使用原运行时入口，HTML 稿只提供编辑和状态示例。

## 9. 视觉语言

采用中性工作台、清晰正文和低干扰过程。独立产出保留适合内容的表现力，普通记录主要依靠排版组织。
所有颜色跟随产品明暗主题；辅助文字必须可读，不能用过低对比度实现「安静」。

以下数值是首轮样稿的设计基准，可随真实字号与窗口评审调整，不是功能边界：

| 角色 | 初始基准 | 目的 |
| --- | --- | --- |
| 聊天正文 | 15–16 px，行高约 1.7 | 支持中文与混合代码的连续阅读 |
| 过程与局部操作 | 13 px，行高约 1.55 | 与正文区分，同时能直接读清 |
| 来源、时间与次要说明 | 12 px | 保持可访问性，不继续缩小 |
| 正文段内间距 | 10–14 px | 表达同一解释中的连续性 |
| 同一过程内部 | 6–10 px | 建立动作与结果关系 |
| 模型发言/阶段之间 | 24–32 px | 形成阅读停顿 |
| 正文阅读宽度 | 约 640–760 px，随布局缩放 | 避免超长行；不以固定宽度压坏窄窗 |
| 概览宽度 | 初始约 260–300 px，可调整 | 侧栏可读且为正文保留空间 |

圆角用于可操作的输入、菜单和独立对象，不给每段执行记录加容器。
分隔线表达章节和所属关系，状态颜色只用于真实提示；正常完成保持中性，危险和待处理与文字共同表达。
图标有明确用途，不为每一种普通动作寻找新的装饰性色彩。头像沿用 Agent 身份视觉，不替换为统一工具卡片。
过长路径在正文自然换行，在紧凑标题按可辨识对象省略并提供完整查看。没有可用名称时不编造名称。

## 10. 动画、阅读位置与无障碍

| 变化 | 设计行为 |
| --- | --- |
| 当前动作更换 | 同一行轻微纵向/透明度交接，保持容器高度；token 增量不反复触发 |
| 展开/收起 | 实际内容高度过渡，初始约 180–220 ms；收起后才释放不需要的 DOM |
| 当前工作结束 | 动态标记停止，摘要原位更新；手动展开状态不变 |
| 用户回答被受理 | 选择区收为明确回执，继续过程接在原处；受理未知保留原请求 |
| 进入计划/任务详情 | 侧栏内容原位交接，保留返回与滚动位置 |
| 设置依赖出现 | 紧贴主选项向下展开，不弹出额外模态窗口 |
| 新内容到达 | 在底部时追随；用户上翻后显示新内容入口，不抢走阅读位置 |

用户输入、连续勾选和拖动不附加人为等待。快速事件合并到可读的更新帧，原始记录全部保留。
长请求可以显示真实耗时和实际状态；没有进度数据时不伪造百分比或循环完成动画。
减少动态效果遵循系统和用户偏好，保留必要的状态变化与焦点反馈，取消位移与反复脉动。

键盘能打开过程、访问详情、选择长答案、提交、取消和返回。折叠内容不留隐形可聚焦元素。
状态播报按有意义变化进行，不逐 token/计时播报。颜色之外同时提供文本与图形。
缩放、长中文、连续英文路径与小窗口均使用真实换行；需要横向保留的数据视图显式标明用途。
用户正在点击或编辑时不移动其主要操作目标；展开已有过程也不能使正在阅读的历史跳到末尾。

## 11. 实现结构与边界

### 11.1 呈现投影

在现有 Thread/HistoryPresentation 之上组织阅读层级，继续沿用 Run、request、call、history item 与 source identity。
UI 可以派生 narrative/process/delegation/attention/output 等呈现角色，但不将角色写回为新的执行状态或第二份历史。
同一个原始对象的主线摘要、概览入口和详情共享 identity；流式到持久记录的交接不得重复计数、重置展开或换掉来源。

对失败是否阻塞、重试是否恢复、效果是否已确认，只消费原 owner 的事实。若现有 DTO 缺少决定性关系，补最小领域事实或保留未知，不由 CSS/工具名猜测。
诊断记录可以按需读取；进入会话不应为了统计标题就下载所有原始工具正文。已加载数据不足时不伪造完整计数。

相关入口：

- `packages/ui/src/components/conversation/chatDialogueProjection.ts`：正文与过程分组。
- `ChatDialogueActivity.tsx`：摘要与展开；`chatTimelineBlocks.ts`、`ChatTimeline.tsx`：稳定行与导航。
- `ChatFollowupTool.tsx` 等用途组件：对象主状态与证据分层。
- `packages/ui/src/lib/agent-runtime/thread-projection.ts`：原进度身份与持久交接。
- `packages/ui/src/components/thread/ThreadOverview.tsx`、`WorkOverviewControl.tsx`：概览与布局。

这些是改造入口，不预先要求把所有呈现合并成一个巨大组件。

### 11.2 设置组合

保留 `settings-catalog` 的稳定字段与作用域、`metadata/search` 的导航和发现合同。
共享 primitive 负责对齐、键盘、帮助展开和保存反馈；领域页面负责能力依赖、有效配置与解释。
调整 FieldRow/StackedField 的使用位置，不通过给所有行增加更多布尔参数来制造万能模板。
保存仍由现有 owner 完成；新增状态文案必须对应真实的 draft、ack、scope 或观测事实。
Desktop/Web/mobile 共用语义，各自选择适合空间的布局。

## 12. 完整交付切分与评审场景

先按本设计完成整体评审，再按责任边界交付完整单元。分批实现用于控制依赖，不降低最终覆盖范围。

| 单元 | 完整结果 |
| --- | --- |
| 状态与文案 | 任务主状态、调用结果、效果与观察分开，长 ID 进入详情，空结果准确 |
| 聊天阅读 | 正文/过程/协作/待办/产出联动，完成后安静收束，所有模式与来源导航保留 |
| 空间与动态 | 概览占位、输入层级、详情返回、滚动锚点、键盘与减少动态效果 |
| 设置结构 | 导航、范围、有效配置、保存单元、搜索展开与能力依赖 |
| 领域页应用 | 逐项覆盖现有页面；常见偏好、对象配置、能力组合、数据管理各有合适布局 |

评审采用下面的真实使用问题，而不是截图是否「看起来简洁」：

1. 不展开过程，能否读懂本轮发现与结果？展开后能否找到某一次读取/写入的真实依据？
2. 连续工具、并行子任务、长思考同时发生时，当前工作是否清楚，旧内容是否稳定？
3. 一次失败已恢复、另一次仍阻塞时，能否分辨影响？未知写入能否避免被伪装成失败重试？
4. 用户上翻、展开过程、编辑计划或回答问题时，新事件会不会夺走位置与输入？
5. 长答案、长路径、多文件差异在窄窗口是否仍可读？概览是否真实让出/占用布局空间？
6. 本轮结束而后台任务继续时，两个状态能否同时被正确理解？
7. 开关开启但模型未配置、配置被项目覆盖、Host 不支持时，是否有准确的当前状态与下一步？
8. 服务保存失败、切换 Host、离开有草稿的页面时，输入和原始范围是否保留？
9. 搜索一个高级参数是否能直达并展开？用户能否从界面知道修改的生效时机？
10. 清理只释放一部分或仍有资源占用时，空间结果是否准确，不把「请求已提交」当成「清理完成」？

HTML 稿内的「数据与覆盖」页列出可直接打开的场景和三种模式，包括纯对话、长思考、流式写入、脚本子调用、并行与脚本内派发、长选项单题、多题多选、多个独立询问、回答提交失败、持续授权与保存失败、轮末缓存用量与缺失上报、模型重试、读取失败、效果未知、观察中断、取消、后台进程、空/截断结果、字段不足、后续任务、长历史与沿用现状的新会话。所有组合使用同一份事件数据。

本轮产出是设计与独立 HTML 稿，不修改产品运行逻辑、不运行构建或项目验证。实施时按实际风险选择必要证据，不将本清单变为固定全量检查流程。
