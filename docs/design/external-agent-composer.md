# 外部 Agent 输入框：连接、控件与状态

状态：2026-11-05 设计方向已确认，尚未实施。来源 [#275](https://github.com/Youzini-afk/Varin/issues/275)。
参考 codeg `769610c6`（v0.29.0）的只读源码，结论来自源码，没有逐个运行其后端。当前支持边界仍以[外部 Agent](../external-agents.md)为准。

## 1. 问题在哪

[外部 Harness 设计](external-harness-integration.md) 5.1、8.1、8.2 节的目标是：沿用模型旁的原入口，在原生位置展示后端自己的模式，探测目录不需要用户先手动建会话。落地时外部后端走了另一条路：

- `ThreadComposer` 把外部后端当作 `backendControls` 替换槽。一旦传入，右下角的模型和思考、左下角的权限与目标按钮、`/model` `/thinking` `/permissions` 层一起消失，只剩后端选择器。
- 补位的 `ExternalSessionControls` 放在输入框上方：一行“会话当前配置”，一排原生 `<select>`（模型、思考、模式、其他选项），再加“Agent 命令”折叠列表。命令列表与 `/` 菜单里已有的后端命令重复（`ThreadComposer.tsx:172`）。
- 连接要手动点“准备连接”，已开始的会话断开后也要点“连接”。Host 没有空闲回收，进程准备后一直保留到断开或 Host 退出。
- Host 收到 ACP `usage_update`（上下文 used/size）后直接丢弃（`acp.ts:195`）。输入框下没有上下文、用量或连接状态。
- 图片入口始终可点（`imageDisabled={false}`），到发送时才按 `capabilities.images` 拒绝。

Host 侧的能力归一化其实已经做得不错。`AcpOptions` 把 ACP `configOptions` 的 model、thought_level、mode 类别和旧的 `models` / `modes` 字段统一成 `capabilities.models` / `modes`，还有 Grok 方言。差距主要在连接生命周期和输入框的呈现合同，不在协议解析。

## 2. codeg 的做法

codeg 几乎所有后端都走 ACP 或各家的 ACP 包装器，输入框只认一套数据：`modes`、`configOptions`、`availableCommands`、`promptCapabilities` 和 `usage`。

| 方面 | 机制 | 源码 |
| --- | --- | --- |
| 自动连接 | 标签页激活且工作目录已知就连接（initialize + session/new 或 load）。切换 Agent 或目录时重连；输入框获得焦点时，如果断开或出错就再连。同参数调用去重，状态抖动不会触发重连循环 | `src/hooks/use-connection-lifecycle.ts` |
| 空闲回收 | 后台每分钟扫描：已连接、没有待批权限、闲置超过 3 分钟（`CODEG_ACP_IDLE_TIMEOUT_SECS`）就断开。打开的标签页约每 30 秒续期；进行中的轮次和后台子任务豁免 | `src-tauri/src/acp/idle_sweep.rs` |
| 选择器缓存 | 按 Agent 类型缓存上次收到的 modes 和 configOptions，连接完成前先显示缓存，不闪加载态。发送要等后端真正发出 `selectorsReady` | `src/contexts/acp-connections-context.tsx` 的 `getCachedSelectors` |
| 偏好 | 按 Agent 类型记住用户的选择，连接时交给后端。后端先 `set_mode` / `set_config_option`，再发初始事件，所以前端看到的第一份快照已经是用户偏好。失效的值跳过，不阻塞启动 | `src/lib/selector-prefs-storage.ts`、`connection.rs` 的 `apply_preferred_session_options` |
| 底部工具栏 | 每个 config option 一个芯片：布尔值原地切换，长模型列表用可搜索的虚拟列表，其余用下拉。modes 用后端原名，与 configOptions 二选一。窄宽度时折叠成一个主从面板 | `src/components/chat/message-input.tsx`、`session-selectors-panel.tsx` |
| 补齐缺口 | 后端没提供的选择器由适配层合成。例如 Grok 按模型 `_meta` 合成思考强度选项，经 `set_model` 的 `_meta.reasoningEffort` 下发；Grok 的权限模式没有 ACP 通道，改用启动参数 | `connection.rs` 的 `synthesize_grok_config_options` |
| 命令 | `available_commands` 进 `/` 补全，“+”菜单另有可搜索的命令子菜单。Codex 额外用 `$` 补全 skills | `src/components/chat/composer/composer-add-menu.tsx` |
| 附件 | 按 `promptCapabilities` 决定：`image` 直传图片，`embeddedContext` 嵌入资源，否则用 `resource_link` | `use-composer-attachments.ts` |
| 状态行 | 输入框下方一行：目录和分支、上下文占用环、连接状态。上下文优先取 `usage_update` 的 used/size，没有时回退到原生会话文件统计。连接状态可以点开，看真实状态，“重连”恢复原会话 | `composer-context-usage.tsx`、`composer-connection-status.tsx` |
| 失败与配置漂移 | 失败按类型显示，带重试、登录、新会话等动作。设置在进程启动后改变时，提示“重连以应用” | `session-failure-banner.tsx`、`session-config-stale-banner.tsx` |

权限方面，codeg 的模式选择器原样列出后端自己的模式，不映射成统一档位；权限请求在会话里用卡片处理。

## 3. 学什么，不学什么

要学的：自动准备与空闲回收、能力缓存、和原生一致的工具栏位置、用后端原名的模式、按能力决定附件入口，以及把上下文和连接状态放到输入框下。

不照搬的：

- **从原生会话文件读统计**：Varin 不导入其他 Harness 的私有存储，用量只取协议实际提供的口径。
- **改选择立即写入会话**：codeg 每次改选都调用 `set_config_option`。Varin 的输入在投递前耐久受理，并固定本次选项；队列里的输入各自带着选项，不能被之后的改动重新解释。所以保留“下一次请求覆盖”的语义，只改呈现方式。
- **按 Agent 记住上次选择**：codeg 把用户上次的选择存在浏览器 localStorage，新连接自动套用。Varin 的原生新会话用的是设置里的默认值，不是上次用的模型；外部后端也一样，不记“上次”。默认值规则见 4.2 节。

## 4. 方案

### 4.1 连接：自动准备，去掉按钮

- **何时准备**：草稿选中外部后端、目录已确定，并且出现下列用户操作之一时自动准备：在后端选择器里切换到外部后端、点进输入框或开始输入、打开模型或模式菜单。这些操作通常比发送早几秒，进程可以提前启动。首次发送时如果还没就绪，就先准备再发送。“准备连接”按钮去掉；取消、错误和登录入口移到状态行。
- **不在打开草稿时准备**：新会话的默认后端可能就是外部 Agent。只是打开或浏览草稿，不应拉起 CLI 进程或触发登录。
- **绑定**：沿用现有规则。准备仍会创建可重试的绑定；草稿丢弃或换后端时，只删除已确认没有输入的准备绑定。
- **空闲回收**：回收只停掉进程，保留绑定；再次聚焦或发送时按原会话恢复。以下情况不回收：
  - 还有客户端在观察这个草稿或会话。直接沿用现有的观察订阅，不另加心跳。
  - 有运行中的轮次、待回答的问题或授权、未结算的投递，或者仍有后台子任务。

  没有客户端观察之后，未发送过消息的准备闲置 5 分钟回收，已开始的会话闲置 15 分钟回收。已开始的会话恢复时可能要按原会话重放历史，代价更高，所以阈值更宽。这两个数是默认值，不是硬限制，以后可以放进设置。回收必须由 Rust 进程所有者真正停止进程，不能拿 HTTP 断开代替。
- **能力缓存**：Host 按“后端配置 + 程序版本”记住上次真实拿到的能力（模型、思考、模式、命令）。准备期间工具栏先用缓存显示，标为“上次”，并且可以选择。就绪后用实时目录校验，失效的选择按现有逻辑清除并提示。只有实时就绪后才放行发送。

### 4.2 底部工具栏：和原生用同一套位置

```text
顶栏右侧：  [◔ 14%] [整理中]                          ← 上下文只在这里，外部会话也接进来
原生输入框：[+] [权限] [目标]  ···········  [思考] [模型] [Varin ▾] [侧重]  🎤 ↑
外部输入框：[+] [模式]         ···········  [思考] [模型] [Codex ▾]          🎤 ↑
输入框下：  [📁 项目 / 分支]  ························  [● 已连接]
```

- **项目选择**：从工具栏移到输入框下一行的左侧。工具栏只放和这条消息有关的设置，外部后端多出模式和选项后也不拥挤。
- **思考和模型**：保持两个独立控件，和原生一致，不合并成一个“Gemini 4 Argon medium”按钮。
- **模型**：来自 `capabilities.models`，长列表可以搜索。目录读取失败时，在菜单里显示原因和重试。
- **思考**：来自 `externalThinkingOptions`。没有可选等级就不显示，和原生一样。
- **模式**：放在原生权限控件的位置，图标和名称用后端自己的，例如 Claude Code 的 plan、acceptEdits。不映射成“仅可查看 / 工作区内修改 / 完全权限”。后端没有模式就不占位。Varin 的权限控件约束不了外部后端自己的执行循环，所以外部后端下不显示它。
- **其他选项**：其余 config option 各自显示成控件，排在模式后面。是/否类的点一下就切换，有多个取值的用下拉。只有宽度确实放不下时，才把左侧这组控件折叠成一个“会话选项”弹层，不为了好看把控件藏起来。
- **取值显示**：芯片显示下一次发送将使用的值。没有覆盖时显示会话当前值（取自 `capabilities.current`），用弱色；有覆盖时用正常色。菜单第一项是“沿用会话配置（当前：X）”。原来的“会话当前配置”那一行并入菜单头。
- **默认值**：新草稿默认“沿用 Agent 配置”，也就是那个 CLI 自己的默认。用户想在 Varin 里单独固定默认值时，在“外部 Agent”设置的对应条目里选模型、思考和模式；候选项来自 4.1 节的能力缓存，保存在 Host 设置中。这和原生“对话默认”的规则一致。
- **斜杠层**：`/model`、`/thinking`、`/mode` 对外部后端同样可用，数据来自外部能力。后端自带的同名命令仍在“后端”分组下单独保留。
- **范围**：删除 `ExternalSessionControls` 整块表单。草稿页和已开始的会话页使用同一套控件。

### 4.3 命令与“+”菜单

- 删除“Agent 命令（插入草稿）”折叠列表，命令只从 `/` 进入；可以在“+”菜单里加一个可搜索的命令子菜单。命令仍然只插入草稿，不自动执行。
- 图片项按 `capabilities.images` 置灰，文件项按 `capabilities.files` 置灰，并说明原因，不要等到发送才拒绝。目前四类适配器都声明了文件路线，所以文件项通常可用。
- 目标、计划、压缩属于 Varin 运行时，外部后端下不出现。外部后端自己的同类命令照常出现在 `/` 里。

### 4.4 上下文与状态：不重复放

- **上下文**：只保留顶栏现有的占用指示和上下文准备状态，不在输入框附近再放一份。外部会话目前不显示这个指示，因为它没有原生 Thread 身份（`useExternalAgentStore.ts:56`）；要把外部会话的数据接进同一个指示。
  - 数据：ACP `usage_update` 的 used/size 作为独立的上下文占用字段进入快照，不计入用量。Codex、Claude、Pi 用协议实际给出的窗口信息补上；拿不到就不显示，不做估算。
  - 点击：原生会话照旧打开上下文面板；外部会话没有 Varin 的上下文面板，改为弹出小框，显示占用和会话累计用量。累计用量沿用 `turn.usage` 的口径和“会话累计 / 上一请求”的标注，缓存率只在有数据时出现。每轮用量继续显示在消息底部。
- **状态**：输入框下一行的右侧。目前只有外部后端的连接状态：准备中、已连接、已回收（下次使用时恢复）、需要登录、失败。点开显示后端、版本、目录、原生会话 ID 和“重连”。原生会话这一侧先留空。
- **计时**：首字延迟、输出速度、工具耗时这些指标需要可信的时间来源，本轮不做。

### 4.5 失败与配置漂移（后续）

- 失败按类别（连接、登录、额度、请求被拒、服务）停在输入框下，带上对应动作：重试、登录、新会话。
- 进程启动后，如果后端配置或可执行文件发生变化，提示“重连以应用”；轮次运行中禁用这个操作。

## 5. 适配层的差距（不在本轮范围）

codeg 在每个后端上做的工作远多于 Varin，包括：按 Agent 设定环境变量策略、同步 Antigravity 的设置文件并支持无浏览器登录、版本固定的安装与更新、Grok 的问答和退出计划模式处理、向 ACP 后端传递 MCP 服务等。这些差距决定上面的控件能拿到多少真实数据。和这次 issue 直接相关的有两点：

- issue 里用的 Antigravity 不是内置预设，用户应该是通过自定义 ACP 接进来的。没有逐个后端的预设与验证，模型、模式这些控件就只能显示后端碰巧提供的数据。
- Varin 建立 ACP 会话时传的是空 `mcpServers`。CLI、Skills、MCP 的共享按此前的决定暂缓，不在本文范围内。
