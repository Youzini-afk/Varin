# Varin 多 Agent 协作：综合主线、Worker 与检索

Status: implemented / wired；已完成相关行为回归及真实 Rust 内核定向验证。付费模型协作质量和安装包完整点击流程未由本轮验证。

Last updated: 2026-10-06

本文负责常规多 Agent 的职责、通信、等待、会话查看与代码协作。在这些事项上修订
[harness-verification.md §9.2–9.3](harness-verification.md)，保留原有 Thread/Run、Pi 会话、
Rust WorkingState/Integration 和 Documents 的职责边界。
科研工作侧重、Bot 长期运行及用户自定义配置继续由各自设计负责；本次讨论不构成删除它们的决定。

## 1. 目标与职责

多 Agent 的目标是让适合独立推进的工作同时进行，缩短整体完成时间，同时保持实现的一致性。
普通批量读取和命令执行仍可使用工具并行；不需要为每个操作建立子线程。

常规子 Agent 收敛为 Worker 和检索两类，主 Agent 始终保有完整的调查、设计、实现与整合能力。

| 参与者 | 主要责任 | 工作方式 |
| --- | --- | --- |
| 主 Agent | 理解真实需求、整体设计与取舍、关键实现、协调依赖、综合整合、最终交付 | 默认亲自推进，按明确收益委派；分派后继续承担综合工作 |
| Worker | 完成一项有实际成果的任务，包括理解相关背景、实现、必要验证与协作 | 可跨文件和模块；实现中的问题可与主线或其他 Worker 讨论 |
| 检索 Agent | 定位代码、追踪调用链、查阅资料并返回可追读的事实与依据 | 面向检索和阅读，不承担产品修改；复用现有检索、材料与阅读能力 |

快速实现、复杂实现、前端、审查、检查等用途可以用任务要求和执行配置表达，不再分别作为常规内置子 Agent 类别维护。
需要独立审查时，可派发一个具有对应只读权限的 Worker 任务；审查与测试不成为每轮委派之后的固定追加流程。
模型、思考强度和工具按任务及用户配置选择，“快速”不代表必须使用较弱模型。
用户自定义指令、启用状态和模型选择保留。已配置的旧实现/前端/审查/检查预设转为可编辑的 saved-* 配置；旧 hardImplement 槽在未配置 Worker 时迁入 Worker。

## 2. 主 Agent 的综合责任

主 Agent 遇到问题先理解和判断。复杂、麻烦或尚不清楚的问题本身，不构成立即启动 Worker 的理由。
委派应有实际收益，例如存在可独立交付的部分、可以同时解决的依赖或值得独立开展的调查。
没有合适的并行工作时，主线继续实现或等待已有结果。

主线需要持续理解整个任务，不能只维护状态列表或依据 Worker 的完成报告决定交付：

- 分派前明确整体目标、关键约束、公共接口与已有决定，并亲自解决影响拆分的关键未知。
- 分派时交代责任、预期成果、相关背景和协作对象。责任范围可以跨模块，不要求机械地按文件数量切分。
- 进行中处理整体取舍、需求变化和交叉修改，继续推进未委派工作；分工不合适时及时调整或接手。
- 接收结果后亲自理解关键实现，贯通主要流程，消除本次改动引入的重复抽象、接口不一致与不必要复杂度。
- 最终根据实际风险验证整合后的行为。代码可自动合并、各 Worker 的检查分别通过，都不能代替整体判断。

Worker 可以指出任务边界或原设计的问题。主线据此修改方案，不要求所有执行者沿最初的拆法硬做下去。
整体整合允许主线直接改代码，优化范围围绕本次目标与实际集成问题，不自动扩展成无关的全仓重构。

主提示词需要表达的原则：

> 你对任务的整体方案、实现一致性和最终结果负责，默认亲自推进工作。按实际收益使用 Worker，
> 并持续理解其关键实现。委派后继续处理全局设计、跨任务依赖和未委派工作；收到结果后结合整体目标
> 完成必要的调整与整合。不要因遇到困难就立即委派，也不要仅凭 Worker 的报告判断任务已经完成。

这是行为原则，具体提示词措辞随原生装配实施，不依赖强制的任务数量、固定规划模板或额外评判模型。
优先把主 Agent 直接调度的一层并行做好；真实工作需要时允许嵌套，不增加永久调度或合并 Agent。

## 3. 通信与共同理解

复用现有定向消息机制。Worker 可以直接讨论接口、告知依赖已可用、请求帮助和回复问题，主线无需逐条转述。
例如前端 Worker 可以向后端 Worker 询问错误结构，双方明确后同步给主线，再继续各自实现。

普通细节由相关执行者协商。影响公共接口、整体行为、任务边界或需求取舍的决定同步给主 Agent，
由主线结合其他工作判断。通信不要求固定开会、周期汇报、全员广播或致谢往返。

沿用消息的用途区分：

| 消息 | 接收后的含义 |
| --- | --- |
| 通知（现有 `inform`） | 保留信息，在接收方后续正常处理时可见；普通进度不单独唤醒模型 |
| 请求（现有 `request`） | 要求目标处理具体问题；目标工作中时进入合适的输入边界，空闲时可启动执行 |
| 关联回复（现有 `replyTo`） | 对应一个明确请求，可以解除等待该请求的依赖 |

每条消息保留实际发送者与目标。投递和执行分开记账，同一请求重试不重复启动任务。
消息可以引用会话记录、工具结果和代码提交记录；发出消息不代表对应代码已应用到目标。

## 4. 工作、等待与唤醒

主 Agent 与 Worker 都应能选择继续工作、等待依赖或等待到某个时间。
等待期间不持续请求模型，也不让模型反复调用状态查询；宿主订阅相关事件，满足条件后恢复处理。

| 选择 | 行为 |
| --- | --- |
| 继续工作 | 分派或发消息后处理其他事项，相关信息进入收件队列，在后续输入边界处理 |
| 等待依赖 | 指明所等的任务、请求或结果；符合条件的事件到来后恢复，不要求反复重新登记等待 |
| 带期限等待 | 同样监听事件；事件提前到来可恢复，没有事件时到指定时间再恢复 |

“等待中”保留任务未完成的含义，与完成、取消、需要用户输入分别呈现。
没有期限的依赖等待不因固定轮询周期而产生新一轮模型调用。已有根任务并发设置继续适用，
等待中的执行释放实际占用的模型执行名额，恢复时重新取得名额；不能把等待误认作退出或可删除工作目录。

宿主应保存等待对象、唤醒条件、可选期限、所属任务/执行和事件消费进度。
恢复前核对实际执行状态，使用既有消息/执行收据避免重复启动；重启后根据持久状态重新接续等待。
这里只挂起模型工作，不承诺同时卸载进程或清空其内存。

子任务完成、明确请求/回复、需要处理的故障，以及用户的新输入，可以作为恢复原因。
普通工具进度只更新 UI。一次恢复可以处理已经到达的多条相关事件，不要求为每一条完成通知另开一次模型调用。
结果发布与等待登记之间的交错不能丢事件；取消或任务真正完成后，旧事件不得重新启动它。

对主会话补齐“工作未完成但已挂起”的恢复路径：子任务完成后，按已登记的等待条件继续主线。
未登记等待且已经交付完成的会话，不因历史子任务的普通完成通知被无条件重开。
这些语义放在既有 Thread/Run、消息和续接机制中，避免再建一套调度权威。

## 5. 同一任务内查看会话

同一主任务中的主线程、同级子线程及进一步派出的子线程，可以发现并只读查看彼此的工作记录。
范围由真实任务关系确定，不通过“恰好处在同一个项目目录”推断。
会话读取与停止、重派、改配置等控制操作分别授权；允许互读不会自动授予互相控制的权限。

统一的线程列表提供任务名称、职责、父子关系与当前状态，供主线和 Worker 找到协作对象。
读取方式应接近文件查看：

- 当前活动与最近若干条记录。
- 指定记录范围，或者从上次位置继续读取。
- 按关键词、文件路径查找相关记录。
- 定位一条记录，展开前后内容或某次工具调用的输入与结果。
- 选定一次历史执行，读取其工作过程和报告。

条目携带稳定 ID、来源执行、顺序与续读位置。活动历史可以继续追加，不能让新消息使旧引用指向另一段内容。
长工具结果复用已有输出读取机制；工具调用与结果保持关联，不把局部片段伪装成完整执行。
可读内容来自已产生的消息和工具记录；未产生的内容不可凭空补成进度或结论。

读取不启动目标模型、不恢复工作目录，也不自动将全队会话复制进每个 Agent 的上下文。
Agent 按需读取，用户也能在已有会话面板中查看并跳转。
用户侧沿用任务概览弹出会话面板、面板内跳转、主会话下树状子线程的既有交互方向。
以任务名、状态、成果和需要处理的问题为主要信息，不增加设置页中的独立任务监视器。

## 6. 向目标线程提交选定代码

### 6.1 一次操作的产品合同

Agent 应能直接表达“把这些文件或改动片段提交给 B”，一次操作完成选取、固定本次改动、投递与尝试应用。
无需先手动发布结果版本、创建 Git commit，再要求接收方调用拉取工具。
底层继续保留确定的来源、版本和操作记录，Agent 不必为此完成额外的仪式性步骤。

支持选择整个文件的改动，也支持同一文件中的具体改动片段。两个典型请求：

> 把我对 `api/types.ts` 的接口定义改动提交给前端 Worker，其他修改不带过去。
>
> 把这个函数的修改提交给主会话。

所选内容作为补丁进入目标的当前工作状态。文件选择默认表达该文件的改动，不代表无条件覆盖目标完整文件。
片段携带对应的原内容、上下文和来源身份，不能仅保存易漂移的行号；新增文件、删除和其他文件操作也保留其实际含义。
公开入口为 submit_code：threadId 指定同任务的可写线程或 parent；files[].path 选文件的实际改动，files[].edits 的 before/after 选唯一原文及替换内容。片段限可读取的 UTF-8 文本，整文件变化沿原生路径状态保留新增、删除和二进制含义。submissionId 可显式指定重试身份；省略时由会话、当前历史位置和工具调用身份生成。

### 6.2 精细合并与并发写入

Worktree 提供独立执行目录；本次提交沿现有 WorkingState/Integration 生成和应用选定改动。
不另建直接写目标磁盘的旁路，也不要求所有线程先物化真实目录或拥有 Git 仓库。
Git 可参与差异和执行目录管理，未提交文件及编辑器草稿仍沿各自现有权威处理。

提交仅纳入选定改动：

- 未选中的文件与同文件未选中的修改，不进入本次源改动集，也不因这次提交被覆盖。
- 目标现有的独立改动予以保留；能够合并的非重叠修改正常应用。
- 双方对所选内容存在真实分歧时报告冲突，保留可供接收方或主线处理的依据。
- 片段的实际依赖由执行者识别并一并提交或告知；文件无冲突不等于行为已经正确。

目标在能协调相关文件写入的边界应用。正在写入同一内容时可以等待，等待投递或应用不得长期占住全任务的
共享队列并阻塞其他线程的检索、读写和消息。应用前核对目标仍对应本次读取的内容，避免覆盖刚发生的编辑。
一份提交里哪些改动被应用、哪些仍待处理必须明确，不能以“部分成功”隐藏剩余冲突。

### 6.3 回执、来源与最终整合

回执区分已应用、已接收待应用、冲突和失败。等待时返回可追踪记录，完成后通知双方；
接收成功不能作为代码已生效的依据。相同提交的重试复用同一身份，不重复应用。

记录发送者、接收者、所选改动、源/目标内容依据及实际应用结果。
双方后续可以继续工作，重新提交产生的新修改；主线最终整合时应识别已经交换的改动及其解决结果，
避免把旧修改再应用一遍、撤销接收方之后的修改，或者将已处理的冲突重复交给用户。
不能用“这个文件曾同步过”来跳过后来的独立改动。

同级 Worker 可以直接提交，主 Agent 不逐份审批普通协作补丁；公共接口或整体行为的变化应同步给主线。
主线仍负责最终设计与功能整合，局部提交成功不自动使源任务或目标任务完成。

## 7. 原生基础与启动成本

继续使用现有 Thread/Run 记录工作与执行，Pi 保存会话，Host 管理关系、投递、等待与协调，
Rust 内核管理不可变工作状态、受控文件操作及 Integration，Documents 管理未保存编辑内容。
独立工作默认使用隔离工作状态，读取和文本修改可留在虚拟分支，Shell/LSP 等需要真实路径时再生成实际目录。

同一 Git 工作起点的隔离子任务现在可以复用已确认的原生基线：每次仍核对当前路径及原始字节身份，
并确认保留的不可变根未被释放或重订。Git 原始内容哈希通过一次批处理获取，不受过滤器或换行规范化影响。
派生缓存只保留根引用及身份摘要，各 Worker 仍拥有独立工作分支；内容变化、编辑器草稿、忽略文件复制等不满足条件时重新捕获。
本轮验证了复用和失效行为，没有测量端到端加速倍数。

## 9. 验证与边界

复用了相关套件，补充的是能发现真实丢结果、覆盖文件或等待死锁的少量行为场景：

- 同任务互读及可写目标授权、无关任务/只读目标拒绝，读取不启动目标。
- 普通主线等待的重启恢复与登记前已到的代码回执；用户输入、取消、运行状态和消息身份继续沿既有链路处理。
- 所选片段保留未发送内容，接收者独立编辑得到保留；真实冲突报告且不覆盖目标。
- 待应用重启接续、中断捕获释放、固定回执重试，以及接收者后来编辑后的重复提交。
- 完整整合后的撤回修改，包括原生相对初始基线的 changedPaths 为空时仍发现撤回冲突。
