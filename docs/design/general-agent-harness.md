# 通用模式与工具披露设计

状态：2026-10-23 方案已接入实现。设计时审阅的源码基线为 `25f52fdec`；本文保留讨论形成的方案，当前机制见[运行时](../runtime.md#模式工具披露与协作)。

通用模式提供均衡、完整的基础能力，用户可以从讨论、阅读或行动开始，随任务需要继续使用其他能力。“微简洁”体现为减少起始上下文中的领域细节和不必要的发现成本，保留模型的判断空间与实际行动能力。

本稿包含两类工作：通用模式的默认工具披露和共享 Agent 配置；作用于全模式的工具目录、说明、发现结果与错误反馈改进。二者分别定义、共同实现。

## 1. 决策与范围

| 议题 | 决定 |
| --- | --- |
| 模式身份 | 新增独立 `general`，现有 `code` 明确为 Coding；无显式侧重时的新会话默认通用 |
| 模式提示词 | 不注入专门的通用模式提示词，沿用科研与办公设计中移除模式指令的决定 |
| 常驻能力 | 保留阅读、文件修改、执行、协作、交流、状态和成果表达的完整基础路径 |
| 明确保留直接披露 | 恢复点、文件恢复、代码交换、Agent 改名、定时接续和 MCP 使用能力 |
| 按需能力 | 浏览器、电脑、专用格式操作、环境管理及其他低频细节，通过清楚的目录入口取得 |
| 预制与检索 | 共享 Worker、调研 Agent 和快速检索，不另造通用专属角色 |
| 共享优化 | 工具发现和返回质量对所有模式生效，不为通用建立独立发现系统 |
| 模型自由度 | 工具说明表达能力和真实接口条件，不编排模型的工作步骤 |
| 界面 | 本轮不设计新界面、布局、动画或交互模式 |

模型选择、文件、会话、用户配置和运行规则沿现有机制。本稿不围绕这些共同规则扩展产品设计，也不引入自动选模、自动任务分类或自动模式切换。

浏览器和办公格式能力的建设见[办公设计](office-agent-harness.md)；预制、临时派发与可选历史继承见[科研协作设计](research-agent-harness.md)。这些能力按各自设计实现，通用模式复用其实际可用入口。

## 2. 通用与其他模式的关系

通用模式适合任务方向尚未完全明确、需要组合不同能力的工作。用户可以先讨论，再阅读材料、查找信息、计算、制作或修改成果，使用相关能力时无需先切换模式。

| 模式 | 默认披露侧重 |
| --- | --- |
| 通用 | 均衡的基础阅读、行动、协作和表达，其他能力按需取得 |
| Coding | 代码定位、开发执行和相关协作的常用能力 |
| 科研 | 学术材料、研究阅读与科研协作的常用能力 |
| 办公 | 文件与文档处理、浏览器、电脑操作的常用能力 |

模式表达默认工作侧重。任务可以组合其他领域的能力，预制和工具的实际可用性继续由原配置与能力准备决定。专业模式直接披露更多相关能力，通用模式则保持较均衡的起始组合。

不为了让模式看起来不同而增加不同的模型人设、工作协议、角色链或独立上下文机制。也不以常驻工具数量少作为单独目标；工具应能支撑完整工作，并有合理的发现成本。

## 3. 当前实现

| 已核实的代码现状 | 对设计的影响 |
| --- | --- |
| `WorkFocusId` 当前只有 `code`、`research` | 通用需要独立身份，办公的新增 focus 与本次变更共同处理 |
| `workFocus.code` 的当前中文名称为“通用”，说明包含编程与日常任务 | 新增 `general` 后区分通用与 Coding 的名称和默认组合 |
| `thread-context.ts` 按 focus 自动生成 `work_focus` 指令段 | 沿已有设计移除自动模式指令，不改为另一段通用模式提示词 |
| 原生 `is_always_declared` 使用固定名称列表 | 需要表达各模式的默认直接集合，不能继续用一份全局表覆盖全部模式 |
| 扩展 `always_declared` 与原生常驻表叠加，科研目前额外提升两个工具 | 默认披露应在同一请求准备过程中形成，避免只能追加、无法表达按需选择 |
| `tool_describe` 已支持分组、名称查询，返回调用引用；`tool_invoke` 执行未直接声明的目标 | 优先改善已有分组和结果，不新建能力发现代理或第二套工具执行入口 |
| 直接函数与通用调用的校验已有明确区分 | 目录说明、模型函数和执行校验要继续一致 |
| MCP owner 已管理直接披露与发现/调用入口，原生常驻逻辑保留 `mcp_*` | 保留直接使用路径，不把 MCP 再放到通用目录后面 |
| Worker、可派发检索、内部快速检索已有各自配置 | 复用科研稿确定的共享调整，不增加同用途模型槽 |

本文后续清单描述目标行为，不把尚未实现的办公能力或浏览器接口当作已注册工具。

## 4. 通用模式的直接披露集合

下表是通用默认集合。直接披露表示工具定义直接进入本次模型请求，不要求先查询通用目录。工具仍需实际可用；列入默认集合不会凭空创建执行能力。

| 用途 | 直接披露的工具或入口 |
| --- | --- |
| 网络与资源阅读 | `websearch`、`webfetch`、`resource_read`、`document_read` |
| 文件定位与内容 | `file_list`、`file_search`、`file_read`、`file_write`、`file_edit` |
| 快速检索 | 现有 `code_retrieval` 入口，沿共享设计改善对可用资料的检索 |
| 运行与计算 | `process_spawn`、`process_read`、`process_write`、`process_inspect`、`process_stop`、`wait_process` |
| Agent 协作 | `dispatch`、`send`、`child_status`、`child_report`、`wait_child`、`child_cancel` |
| Agent 命名 | `agent_rename` |
| 用户交流与状态 | `ask_user`、`question_status`、`todo`、`memory` |
| 定时与接续 | `follow_up` |
| 文件恢复 | `recovery_points`、`file_restore` |
| 代码交换 | `submit_code`、`update` |
| 成果表达 | `render_ui`、实际已配置的 `image_generate`、`image_edit` |
| 能力发现与调用 | `tool_describe`、`tool_invoke` |
| MCP 使用 | MCP owner 原有的发现、调用和其他已准备入口，以及按既有配置直接披露的服务工具 |
| Goal 状态 | 有实际 Goal 的请求沿现有条件提供 `goal_report` |

### 4.1 完整的基础行动能力

文件与终端能力保持常驻。模型能够启动工作、读取进展、输入后续内容和结束操作，不必为正常推进反复寻找基本操作。

恢复点、文件恢复、代码交换、Agent 改名和定时接续明确放在直接集合中。它们各自已有稳定用途，不因为通用模式希望简洁而增加额外发现步骤。

工具可用不构成使用要求。常驻 `todo` 不要求先建立计划，常驻协作不要求派发，常驻恢复不要求每次编辑先查询恢复点。模型依任务使用这些能力，工具说明不添加上述流程。

`document_read` 继续如实表达当前 PDF 支持；办公格式能力实施后按真实接口组合，不用名称笼统承诺所有格式。`code_retrieval` 沿共享快速检索设计使用，不为通用另造检索循环或专属索引。

### 4.2 MCP 直接使用

MCP 的使用入口本身常驻，包括实际准备的 `mcp_discover`、`mcp_call` 以及资源、模板、提示等对应入口。已选直接服务工具继续直接披露。

模型从现有 MCP 入口即可开始使用，不需要先经 `tool_describe` 查到 MCP，再进入 MCP 的发现流程。原生通用目录不再包一层同用途入口。

服务工具沿现有 direct、codemode、deferred、hidden 配置披露。需要取得某个服务的实际工具声明时使用原 MCP 发现机制；已有有效声明和调用引用可以继续使用。具体工具的 schema 版本仍来自原 MCP owner。

MCP 常驻入口与服务连接生命周期保持各自职责。未用到的按需服务继续按现有机制准备，目录入口可用不意味着启动所有服务。

这项设计保持当前 MCP owner 的单一职责，既不新建 MCP 客户端，也不改变服务工具原有调用与返回方式。

## 5. 通用模式的按需集合

按需能力仍属于正常可用目录，通过现有 `tool_describe` 取得说明，经 `tool_invoke` 调用。目录描述应让模型清楚知道能力存在及其用途。

| 能力 | 通用模式中的处理 |
| --- | --- |
| Browser Use | 通过浏览器分组取得实际页面发现、读取、操作和文件交接等说明 |
| Computer Use | 通过电脑分组取得真实可用的发现、观察、控制、输入及原有子任务分配入口 |
| 专用文档、表格与演示操作 | 按目标格式和实际后端取得编辑、预览、计算或导出能力 |
| 学术与其他专用检索 | 需要对应资料源时使用现有工具和服务；`research_decide` 按科研稿移除 |
| 材料集合组织 | `materials` 按需使用，基础资源阅读仍然常驻 |
| 脚本组合执行 | `script_open`、`script_run`、`script_close` 按需取得；进程和终端基础工具常驻 |
| 进程窗口调整 | `process_resize` 按需取得 |
| 其他会话查询 | `threads`、`read_thread` 按需取得；当前工作协作接口仍常驻 |
| 环境与扩展管理 | 环境准备、安装、转发、设置和扩展开发能力按需取得 |
| 其他已安装扩展 | 依实际能力进入适合的分组，沿原注册和执行路径使用 |

“按需”指说明与函数披露方式，不要求用户另外开启某个模式。办公模式可以直接披露更多浏览器和电脑操作，科研模式可以直接披露学术检索；它们继续使用同一套可执行声明。

终端执行与脚本组合执行有不同用途。前者提供直接运行程序和与进程交互的能力；后者提供工具组合环境。本稿只调整默认披露，不合并执行机制。

## 6. 全模式共享的发现与结果改进

本节作用于通用、Coding、科研和办公，不属于某一模式的专属能力。各模式可以有不同常驻清单，但查询同一能力时应得到一致、准确的说明。

### 6.1 让模型能从用途找到能力

沿现有分组和按名称查询入口优化目录。分组说明应对应当前真实用途，避免把大量不同能力都归入没有解释的“其他扩展”。

具体区分文件格式处理与应用内 Office 操作，区分内置浏览器页面与 Computer 所分配的浏览器；相关说明使用实际支持范围，不根据工具名称猜测能力。

初始目录入口提供简洁的可用分组索引，详细参数在查询时返回。能力目录来自实际注册与准备结果，不另建根据用户每句话预测工具需求的模型或分类流程。

### 6.2 查询结果一次提供有用信息

按名称查询时返回实际用途、参数、版本、调用方式和相关可用状态。按分组查询时，模型应能了解这组能力的组成和开始使用的方法。

必要的关联能力在同一次分组查询中容易找到。例如页面操作的说明能够同时找到对应读取入口；电脑控制需要的原有发现和分配能力不会藏在无法推断的另一个位置。此信息来自真实接口关系，无需建设新的依赖图系统。

可关联查询不意味着一次返回所有工具的完整说明。优先在已有结果结构上改进摘要、分组和指定工具的详细读取，避免把一个查询变成所有领域的长手册。

已取得的说明和有效调用引用可以继续使用。没有版本变化或其他实际原因时，不要求每次调用前重复查询同一说明。

### 6.3 描述能力，不编排模型

工具说明保留以下内容：

- 工具作用、实际输入输出和支持范围。
- 必要参数、来源标识和真实接口前置条件。
- 如何继续读取结果、查询状态或使用返回的对象。
- 当前失败发生在哪个操作以及可用的下一步入口。

说明不增加统一的“先发现、再规划、再执行、最后验证”流程，不规定固定调用顺序、必须使用的工具组合或每次都执行的检查。

真实接口依赖仍要讲清，例如输入需要来自一次有效观察，或调用需要实际 schema 版本。参数已经可用时允许直接继续；模型根据当前状态选择方法。通用质量原则沿现有共享指令和预制说明保留，本稿不新增一篇全模式行为规程。

### 6.4 返回适合后续工作的结果

工具优先返回实际内容、对象身份、执行状态、读取范围和可继续使用的引用。长内容按原能力提供定位或继续读取方式，不能为了压缩返回而丢失后续操作所需的信息。

部分结果与失败原因分开表达，已产生的成果能够继续使用。缺少能力、参数不符、引用过期、执行失败等情况各自返回具体原因，避免统一落成“工具不可用”。

内容组织依工具用途选择，不强制所有工具返回一张相同的结果卡或一套冗长字段，也不要求 Agent 额外撰写工具摘要。

### 6.5 发现结果与实际函数一致

当前模型请求直接声明的工具按其名称调用。其他目录工具使用返回的引用和 `tool_invoke`。查询说明不会自动注册新的模型函数。

错误反馈应明确指出未执行的原因与正确入口。例如未直接声明的目标给出通用调用方式，过期引用指出需要重新读取哪项声明，实际不可用工具说明具体能力状态。不能通过猜测名称、自动替换目标或执行另一个工具来掩盖调用错误。

这类协议事实可以出现在工具说明和错误结果中。说明应简洁、具体，避免在系统提示词、每个工具描述和每次结果里重复同一段限制。

## 7. 共享 Agent 配置

| 配置 | 通用模式的选择 |
| --- | --- |
| Worker | 复用现有 `worker` 身份、模型配置与继承规则 |
| 调研 Agent | 复用科研稿确定的 `retrieval` / `retrievalAgent` 调整 |
| 快速检索 | 复用内部 `code_retrieval` 与 `explore` 配置，不为每次检索创建正式协作成员 |

Worker 移除仅面向编程的限定，同时保留理解整体目标、自主判断、处理问题、协调相关工作、依据发现调整方法和交付可用成果的原则。其说明不枚举任务种类或工作领域，也不限定为某个执行阶段。

Worker 的目录短描述与成员默认说明分别承担选择配置和指导工作的职责。完整文案统一见[科研协作稿](research-agent-harness.md#7-模式与指令的边界)，通用与办公均复用，不分别维护简化版。

主 Agent 保持完整工作能力，是否派发由当前任务决定。预制与临时派发沿原接口和实例命名规则；可选历史继承共用科研稿设计。用户自定义预制继续由已有配置机制处理，本稿不重设其作用范围。

模式不向主 Agent 提供模型绑定目录，也不要求它依据价格、速度或提供商选择具体模型。共享预制的配置与普通临时派发沿既定设计。

## 8. 模式与请求披露的实现

### 8.1 独立模式身份

在原 focus 契约中加入 `general`，并与办公稿的 `office` 一起贯穿协议、配置解析、准备逻辑和模式名称。现有 `code` 表示 Coding，避免同一个内部值同时表示两种不同默认组合。

没有显式设置侧重的新会话默认通用。已有保存值按其原含义处理；项目已有默认选择继续按原机制使用。这里只调整模式值、名称和默认来源，不扩展文件、模型或会话行为。

模式名称和说明沿现有 i18n 入口更新。本轮不提出新的选择器、页面布局或其他 UI 方案。

### 8.2 一次准备、同一份声明

沿当前请求准备路径形成直接披露集合，使原生和扩展工具采用同一选择结果。原始工具声明仍然拥有名称、版本、schema 和执行实现，模式只决定默认直接与按需的分配。

当前 `is_always_declared` 全局名称表与扩展布尔标记的叠加方式不足以表达本稿。实现需要调整其选择位置，使工具能够在通用按需、在专业模式直接披露，同时让查询目录和实际执行认可同一份选择。

MCP 仍由原 MCP owner 提供直接定义与发现/调用入口，通用披露层保留这组结果。不要把 MCP 服务工具同时塞进通用目录和 MCP 目录形成重复调用路径。

本次模型请求使用固定的工具定义和直接集合。按需读取说明后继续使用既有通用入口，不在每轮按猜测意图反复动态注册函数，也不新增按会话维护的“已解锁能力”系统。

历史请求继续保留原声明；后续新请求使用新默认组合。参数生成、provider 函数列表、原生校验和嵌套调用应遵守同一调用契约。

### 8.3 与另外两份设计的共用工作

| 实现内容 | 共用关系 |
| --- | --- |
| 移除模式提示词 | 与科研、办公同一次调整 |
| 默认直接/按需选择 | 用一个机制表达各模式清单，各清单可以不同 |
| 工具目录、说明和结果质量 | 全模式共享 |
| MCP 常驻入口 | 沿现有所有者保留，不新增包装 |
| Worker、调研和快速检索 | 沿共享预制与模型槽实施 |
| 浏览器、电脑与格式能力 | 由办公稿建设，通用采用实际可用的按需入口 |

## 9. 实现安排

| 工作单元 | 主要内容 | 原有入口 |
| --- | --- | --- |
| 模式定义 | 新增 `general`，区分 Coding 名称，接好既有默认选择机制 | protocol work focus、配置消费者、i18n |
| 披露选择 | 落实本稿常驻与按需集合，贯穿请求准备、目录和调用校验 | Rust tool disclosure、Host extension tool owner |
| MCP 路径 | 保留直接入口和按原配置直出的服务工具 | 原 MCP authority 与 kernel adapter |
| 共享发现优化 | 改善分组、说明、相关能力查询、调用引用和错误结果 | 既有 `tool_describe` / `tool_invoke` |
| 共享预制 | 通用复用 Worker、调研和快速检索的既定调整 | harness presets/model slots、child profiles |
| 文档整理 | 实现完成后更新当前运行时说明和对应工具说明 | 当前领域文档及源码旁说明 |

先贯通一份可表达各模式的披露选择，再调整各自清单。共享发现优化沿真实工具逐项改善，不为每个工具复制一套包装层。

实现不引入新的代理运行时、MCP 执行器或工具权限体系。具体支持范围来自实际声明与后端；本稿不要求先补齐全部办公功能才能提供独立通用模式。

## 10. 验收情境

验收围绕默认披露和实际调用，复用已有验证；不为清单中的每个工具重复增加测试，也不把工具名称快照本身当作行为验收。

| 情境 | 预期结果 |
| --- | --- |
| 新建无显式侧重的会话 | 默认通用，模式名称与内部身份一致 |
| 通用请求开始 | 直接提供本稿常驻能力，无专门模式提示词 |
| 文件修改之后需要恢复 | 直接调用恢复点与文件恢复，无额外通用发现步骤 |
| 协作中改名、交换代码或安排接续 | 相应工具直接可用，原调用行为保持一致 |
| 开始使用 MCP | 可直接进入原 MCP 工具；已直出的服务工具仍直接调用 |
| 按配置使用 deferred MCP 工具 | 沿 MCP 原发现与调用路径，不先经过通用目录 |
| 通用任务需要浏览器、电脑或专用格式能力 | 可以从明确分组取得实际说明，使用已注册通用入口继续 |
| 查询一组有前置关系的能力 | 能找到真实关联入口，说明不强制用户或模型遵循额外工作流程 |
| 已取得有效说明后再次调用 | 可以复用，不要求每次重新查询 |
| 错把按需工具作为直接函数调用 | 不执行错误调用，返回准确原因与正确调用入口 |
| 使用 Worker | 沿已有配置，保留完整通用工作原则，不枚举职责范围 |
| 在其他模式中查询同一工具 | 获得同一份实际说明和结果改进，无通用专属发现分支 |
| 没有某项实际能力 | 目录与准备结果如实表达，其他独立工具仍可使用 |

文档阶段只核对讨论决定、实际代码依据和链接。功能实施时按改动涉及的准备、声明和执行路径选择必要验证，不扩大成全平台回归工程。
