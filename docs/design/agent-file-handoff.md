# Agent 协作中的文件与附件交接

状态：设计提案，2026-11-03。本文定义待实现的统一文件交接能力；现有实现及缺口见第 2 节。适用于 Bot、原生主 Agent、子 Agent 与用户消息；外部 Harness 的适配边界见第 10 节。

用户在输入框中选择文件、引用任务及明确收件人的交互，见 [输入框功能菜单、技能与对象引用](composer-command-and-reference-menu.md)。两份设计共用附件身份和受理链路，菜单不另建文件保存与权限机制。

## 1. 产品目标与已确定的方向

用户把截图、文档、数据或其他文件交给 Varin，Varin 应当能把原件交给合适的执行者；执行者也能把文件发回、转交给同伴，或在收到补充材料后继续原任务。

模型负责选择接收者、任务、说明和文件。文件是否位于共享目录、是否来自上传、目标是否在独立工作区、需要建立哪些读取关系，由发送链路处理。派发者无需先检查双方目录、读取文件内容、手动复制或编写权限说明。

基本体验是：“把这份表格发给分析任务，告诉它按新的口径计算。”首次派发和向已有任务发送消息使用同一套附件选择方式。只发文件也成立，不要求补一句无意义的正文。

确定以下语义：

- `dispatch`、`send` 和用户输入都可携带文件附件；图片是其中一种呈现形式。
- 已有附件或产物直接引用；已知路径也可直接提交给系统解析，无需额外查询才能发送。
- 发送固定本次交接的文件版本。接收者稍后处理时仍然拿到这一版。
- 文件只在需要时读取、解析或准备为程序可访问的路径。不会因为传一个文件而捕获整个项目。
- 正文、附件和真实发送者共同构成一次交办或消息，沿既有队列、暂停、恢复、回报和取消规则运行。
- 文件引用与权限、内容保留由原资源 owner 管理。引用本身不携带发送方的整个工作区权限。
- 提示词只介绍能力和必要用法，不让模型承担文件搬运流程。

## 2. 当前实现与实际缺口

| 领域 | 当前实现 | 本设计需要补齐的部分 |
| --- | --- | --- |
| Agent 消息 | `MessageInput` / `send` 保存文本、目标、回复关系、工作请求及等待信息 | 消息没有附件字段，无法直接转交原件 |
| 首次派发 | `dispatch` 支持任务、模型、来源、项目、背景选择与上下文继承 | 缺少独立附件参数，转交文件不应依赖继承对话 |
| 图片 | 用户图片保留为 typed media；`read_thread` 可读取原消息的媒体 | 接收者要主动回读；普通消息转发不会自动附图 |
| 文档 | 上传类型包含 PDF、DOCX、XLSX、PPTX；保存原始字节，向模型提供材料引用 | 任意文件上传和统一附件交接尚未接通 |

| 过程与报告 | `read_thread` 读取历史和工具结果，`child_report` 读取最终报告及媒体 | 通用文件引用需要贯通历史、报告、回读与转发 |

## 3. 一致的模型使用方式

### 3.1 只增加附件选择，不增加搬运决策

`dispatch` 和 `send` 增加同名的 `attachments` 参数。每项选择一个已有引用，或者一个在调用方来源中解析的路径；两者互斥。内部 owner、Host、读取授权、内容摘要和版本不由模型填写。

示意用法如下，引用值由实际输入或工具结果提供：

```json
{
  "task": "分析这份表格，解释变化最大的几项",
  "attachments": [{ "ref": "attachment:…" }]
}
```

```json
{
  "kind": "request",
  "targetThreadId": "已有任务短码",
  "text": "补充这份文件，请按更新后的口径继续",
  "attachments": [{ "path": "reports/latest.csv" }]
}
```

`afterCurrent`、`replyTo`、`wait` 继续表达原来的消息行为。`inform` 带附件仍是被动消息；`request` 按原输入边界交付或启动接续。允许正文为空且附件非空；正文和附件均为空才拒绝。首次派发仍需要任务说明。

同一选择方式覆盖 Bot → 主 Agent、主 Agent → 子 Agent、子 Agent → 派发者和任务家族内同伴交流。用户在子任务聊天或协作面板上传文件时，也进入同一受理链路。

### 3.2 引用自然出现在原工作结果里

用户附件、原件已经固定的文档读取、文件生成或修改回执、导出与下载产物，都应提供可转交引用。模型看到文件时即可选择它，不需要再调用“注册附件”工具。

这里区分“可以选择”和“已经捕获内容”：

- 上传完成、原件快照、写入回执中的固定结果，可以直接引用已保留的版本。
- 文件列表等只知道名称和路径的结果，保持轻量路径选择，不为每个条目读取、哈希或登记一份内容对象。
- 路径选择在发送时解析。相对路径按调用方当次实际 Source 解释，绝对路径沿现有目录准入解析；目标项目或接收方的 cwd 不参与猜测。

文件名用于展示，不能作为身份。重名文件按各自引用区分。UI 可按所在消息显示编号，跨消息转发仍保留原文件身份。

### 3.3 不从普通文字中自动猜附件

正文提及一个路径仍然只是正文。只有显式附件选择、用户附件操作和真实 typed 文件结果进入交接链路。这使“讨论某文件”和“授权接收者获得该文件”具有明确区别，也避免把代码示例中的路径当成待上传对象。

系统提示只需说明：可以随任务或消息附带已有文件引用或可访问路径。具体权限、同源优化、版本固定、材料保留与重试规则写在实现和工具合同中。

## 4. 文件版本与共享来源

### 4.1 默认是本次发送的确定版本

已有引用固定其已记录的版本，发送时不重新追踪到路径最新内容。路径选择固定原 owner 完成本次一致读取的版本；如果发送者已经持有精确的读取或写入回执，应优先使用该引用。

普通实时文件在准备期间可能变化。捕获沿现有 Documents / Storage 的一致性机制处理，不能拼接不同版本的字节。无法得到一致版本时返回具体来源错误，不静默换成旧内容。捕获不是“鼠标点击那一纳秒”的跨进程原子快照，确切版本以本次成功的原始读取回执为准。

编辑器中的未保存内容遵循原 Documents 内容读取语义；用户明确分享草稿时标明其文档修订，不能暗中改发磁盘旧版。接收方看到的附件描述应能区分该草稿来源。

### 4.2 同源是系统优化条件

即使双方当前使用同一目录，发送附件仍然交付固定版本：

- 已有不可变对象、文件 revision 或版本化树可直接保留引用。
- 实时来源只捕获选中的文件，复用原 owner 已知且仍有效的内容身份。
- 不把可继续修改的原路径、软链接或可写硬链接当成固定附件。也不修改原文件权限来制造“只读附件”。

接收任务的项目和工作目录维持原设置。附件可来自其他项目或无项目的用户上传；交付该文件不授予其父目录访问能力，也不切换任务来源。

### 4.3 文件附件与代码交换

附件用于交付原件、输入材料或明确成果；`update` / `submit_code` 继续负责有基线的工作区改动合并、冲突与恢复。发送文件不自动覆盖接收方的项目文件。

接收方需要修改附件时，通过原文件或 Office 写入能力生成可写结果，再发送结果或明确写入目标。对固定引用直接执行原位覆盖，应给出“这是交付版本，请选择输出位置”的准确提示。

不为本设计引入“附件跟随源文件变化”的额外模式。需要继续共同修改来源时，使用已有 Shared 工作方式；派发者无需为了普通文件发送理解这一实现差别。

## 5. 接收后的读取、模型输入与命令执行

接收方的每条消息包含原发送者、正文和附件描述。描述只提供文件名、类型、大小、稳定引用与确实可用的读取入口，不包含 Base64、文件全文或复制出的提供商私有状态。

统一附件引用保留原 owner 和精确版本。它是接收任务能够解析的句柄，不是外部服务可直接使用的授权 URL。

| 使用方式 | 系统行为 |
| --- | --- |
| 图片输入 | 接收模型支持视觉时沿现有 typed media 投影实际图片，沿用图片编号；首次派发的模型选择从真实附件自动得到图片输入需求 |
| 文档阅读 | `document_read` / Office 读取入口接受统一引用，按实际格式和所需视图解析原件 |
| 文本或二进制文件 | 文件读取入口接受引用，保留原编码与字节；未知类型仍可保存、交付和下载 |
| 程序处理 | 为当前实际执行 Host 准备该附件的文件路径，沿原资源 owner 持有使用关系 |
| 历史与转发 | `read_thread`、`child_report` 返回原附件描述，可按需读取或继续交给其他获准目标 |

“能交付”和“有专用解析器”分别判断。ZIP、CSV、脚本、模型文件等不因缺少文档解析器而拒绝保存或转发，也不自动执行、解压或转换。

### 5.1 为命令提供真实路径

模型写 shell 命令时需要真实路径，不能把不透明引用直接拼进命令。选定以下接线方式：

- 当该附件已经在本次执行环境中拥有稳定可访问的路径时，描述中提供该路径。
- 否则通过现有 `resource_read` 增加附件的 `path` 视图，按需准备并返回路径。它只准备该附件，不读取其正文，也不扩大为目录物化。
- `file_read` 和文档工具可直接接受引用，不要求先获取路径；只有需要程序访问时才使用路径视图。
- 路径按当前实际执行环境解析，覆盖本地、managed Host 和 VM。路径缓存跟随原执行环境 generation；消息中持久保存的是稳定引用。

准备出的固定文件使用原 Storage 的对象和受管执行资源。已有路径可复用，没有时只落地被选中的文件。进程使用期间持有原资源关系；临时缓存不因 UI 关闭而被删除。

只读附件路径与可写输出路径分开。程序需要原位编辑时，调用原文件复制能力准备可写工作文件；该行为由实际处理任务的接收者选择，发送者无需提前安排。

### 5.2 接收模型不支持视觉时

发送文件本身不强制更换已有 Agent 的模型。已有任务可以接收图片文件引用，使用已具备的图像工具或将任务再交给合适执行者；系统明确说明当前模型没有直接视觉输入。

首次派发需要直接查看图片时，将实际附件模态纳入已有模型选择与校验，避免要求派发者重复填写已知事实。任何仅发送文件引用的处理都必须保留原图，不悄悄转成描述或声称模型已看过。

## 6. 受理、排队、重试与取消

文件准备可能需要 I/O，不能在 Catalog 控制锁中执行，也不能阻塞其他任务的消息和观察。沿原工具 Operation 或用户输入受理键，完成以下过程：

1. 验证原调用身份、目标和附件选择，创建可恢复的准备记录。
2. 原资源 owner 解析引用或路径，固定内容并建立本次交接的暂时保留。
3. 将正文、完整附件关系、接收方和读取准入结果提交到原消息／派发记录。
4. 接收方沿既有输入边界处理；首次派发在所需附件可读后启动执行。

`send` 的“已接受”表示完整消息已经耐久受理，不表示接收者已处理。`dispatch` 原有任务句柄可以先呈现“准备附件”，实际任务不能先看到缺失附件的半条交办。

同一条消息的附件作为一个整体交付。准备某一项失败时，保留正文和选择以供修正，返回具体失败项；不能悄悄去掉失败附件后把正文交给 Agent。发送方明确移除或替换失败项后可作为新的发送意图提交，不要求 Agent 为这种常规修正再次向用户请求批准。

不要求 Storage 与 Catalog 跨库事务：原资源 owner 以发送操作身份完成幂等保留，Catalog 保存其回执及交付事实。发布前确认接收方的读取关系已成立；重启按原操作恢复未完成交接。发布失败的暂时保留由原操作回收，不形成无主复制目录或第二套消息账本。

重试使用原操作、原目标和已经固定的内容。网络响应丢失不能再发一条消息，也不能重新捕获同路径的更新版本。引用解析尚未完成时，恢复其实际阶段；内容已固定后只恢复后续交付。

`inform`、活动任务的补充请求、`afterCurrent` 排队和空闲任务接续都使用同一附件保留机制。排队很久、模型切换、Host 重启、任务暂时暂停，都不改变已受理的文件版本。

取消等待不撤回已发送的附件。准备尚未交付时，取消沿原执行 owner 停止真实读写并释放暂时引用；已经交付的消息按原消息合同保留。多人发送继续逐目标保留原身份，部分成功后只重试未确认的目标。

## 7. 权限与生命周期

### 7.1 权限随明确交接建立

每次发送核验调用方对所选原文件的当前访问能力，以及向目标发送消息或派发任务的现有权限。随后为目标建立这份固定文件的读取关系。派发者不用再请求一套附件专用审批；真正需要的新路径访问沿现有权限机制处理。

一个文件 hash、路径字符串、材料 ID 或聊天里的文本提及都不能直接变成读取权。引用解析仍经过原 owner，不能从模型参数中接受伪造的 owner、目标 Host 或授权范围。

接收方可以在其现有可通信范围内再次发送自己可读的附件；每次仍由发送链路核验。它不继承原发送者对其他文件、其他会话或提供商凭据的权限。来源确有不可转授权约束时，由原 owner 返回具体限制。

### 7.2 保留与回收

已交付附件由接收消息／任务的持久关系保留。发送方删除源文件、结束 Run 或删除原会话，不会使接收者已收到的版本消失。

引用的使用者包括未处理消息、派发输入、已保存历史、报告和转发、实际运行进程及明确持久资料集。会话压缩只改变模型上下文，不删除原附件。当前 Run 结束、归档、面板关闭或取消观察都不单独触发附件内容删除。

删除会话按原保留图释放其关系，存活接收者继续引用原对象；最后一个真实使用者释放后，内容及派生解析缓存才可回收。执行路径缓存由原资源 owner 单独管理，释放缓存不丢失附件身份。

跨 Host 的已交付文件必须具备独立的耐久保留：同一资源 owner 下建立新的保留关系即可；不同资源 owner 之间，发布交付前通过既有传输链路取得目标端的持有回执。目标已经保留同一内容时只建立关系，不再次传字节。目标端暂时离线时，原操作继续保留准备状态或返回具体错误，不能先声称文件已送达。后续文件读取不依赖原会话或原 Host 继续在线。

## 8. 原生状态和模块职责

统一的是引用合同和使用方式，不搬迁所有原件到新数据库。

| owner / 模块 | 责任 |
| --- | --- |
| Rust Catalog | 附件与消息、派发、执行、报告的持久关联；接收身份、交付状态、幂等与恢复 |
| Rust Storage / ContentStore | 各自已有域中的不可变字节、引用保留、文件捕获与执行路径；避免跨域重复保存相同原件 |
| Host Documents / 材料服务 / 资源适配器 | 解析实际来源、校验权限、协调原 owner；按文件类型提供现有读取与解析能力 |
| application-client / protocol | 用户输入、附件选择、发送回执和历史投影的共享类型 |
| 模型工具与 provider adapter | `dispatch` / `send` 接受附件；按真实模型能力投影文本、图片及文件引用 |
| UI | 上传与选择、发送过程、附件预览、打开和下载；不拥有授权、复制或保留状态 |

内部附件描述需要表达“哪个原 owner 的哪个固定对象、是什么文件、谁因哪次交接可读”，但这些事实来自系统，不扩张为模型必须填写的字段表。

在 `MessageInput`、派发输入、输入队列及原生历史中增加 typed 附件引用；工具结果增加可转交的文件描述，避免把所有文件塞入只用于媒体的 `OutputPart::Media`。文件引用的正文投影与其原始关联一起保留，历史压缩、模型切换和续接沿原身份读取。

已有材料和图片直接通过各自的原 owner 适配到统一合同。新交接不扫描正文或正则提取 `snapshotId` 以建立授权。现有历史记录继续按原可读入口保留；如持久结构需要改变，由原存储 owner 完成一次自动升级。无需重传旧附件、重跑旧任务或建立双写兼容层。

## 9. 回报、界面和上下文

### 9.1 子任务回传文件

首版通过 `send` 的附件参数完成明确文件交付，`replyTo` 仍对应真实请求。产物生成工具直接提供可转交引用，子任务不必为回报再扫描目录。

最终报告保留本次执行已经交付给实际请求者的附件消息引用。主动发送和自动完成回报共用原交付身份；报告可以指向已交付的文件，不再复制一遍附件或制造第二条交付。接续执行按本次请求者匹配，不一律发回首次派发者。

不从最终文本里的所有 Markdown 路径自动收集文件，也不把发给其他同伴的文件纳入本次请求者报告。已有 typed 媒体回报沿原链路保持可读。

### 9.2 Chat 与协作面板

沿现有消息气泡、长消息收起与附件预览组织：正文后显示紧凑附件区，图片使用现有缩略图，文件显示格式图标、名称和必要大小信息。文件名可换行或截断，完整名称可查看；同名文件通过原消息和引用身份区分。

展开、收起、点击预览、下载和复制引用使用同一附件对象。收起长正文仍保留附件入口。发送中的文件准备与失败显示在所属消息旁，不额外弹出一套全屏传输界面。

用户输入框保留现有附件条；发送给一个或多个 Agent 时，复用同一附件选择。未准备完成不能显示为已送达；失败时保留草稿和附件选择，便于重试或移除。

附件上传从 PDF / Office 专用入口扩展为通用文件入口，保存原始字节与类型信息；专业解析继续由现有 reader 承担。未知格式使用通用文件表现，不新增格式白名单。

### 9.3 上下文与缓存

附件描述跟随消息进入增量尾部，不改写系统提示或每轮重建全量附件表。大文档和二进制正文按需读取，不因为交付就额外调用模型摘要，也不把编码后的字节写进文本上下文。

固定附件引用随原消息保留；相同文件在不同消息中出现可以共享字节，但不能合并掉不同发送者、说明、时间和交办关系。引用列表的展示顺序与本次发送一致，避免靠重复排序扰动已形成的上下文前缀。

## 10. 外部 Harness、跨平台与实际能力

统一附件合同进入外部派发和接续适配器，由适配器依据已协商能力转换：

- 支持原生图片或文件块时，沿其真实输入协议交付。
- 需要工作环境中的文件路径时，在实际执行 Host 准备所选附件，并把该路径和原说明交给外部任务。
- 本次后端既不能接收原生附件，也不能访问准备路径时，明确指出不支持的附件及原因；保留发送意图供用户或模型调整。

不会自动把图片转换成描述，不会在失败后另开同名会话冒充原任务收到文件。外部会话继续使用其自身执行身份、恢复协议和终止确认；附件交接不创建伪原生 Run。

Windows、macOS、Linux 使用同一语义，路径与文件系统能力由实际执行 owner 处理。普通附件交付无需启用独立工作区或安装挂载组件；现有挂载后端可作为路径复用方式，但不能成为附件的前置条件。移动端与 Web 通过 Host 上传和读取，不把客户端路径当成服务器路径。

## 11. 失败语义与资源开销

错误应定位到具体附件及阶段：原文件不存在、无读取权限、版本无法稳定捕获、目标不再接受消息、目标环境不可访问、后端输入不支持、实际传输失败。复用既有领域错误并补充附件身份，不统一吞成“发送失败”。

明确区分：尚未准备完、已受理待处理、已经处理，以及发送结果暂不确定。响应丢失后先读取原操作结果；结果未知不能自动重复交办。

开销由实际选择的文件决定：

- 已有固定引用复用内容和保留边，不重复读取、哈希、解析。
- 实时路径只捕获所选文件；目录列表不预先创建所有文件的附件对象。
- 大文件沿原二进制流和背压传输，不在 UI / Host 拼接巨型 Base64 JSON。
- 同内容跨目标可复用字节，每个目标仍保留独立交付和授权关系。
- 文件解析、预览与执行路径按需创建，缓存从原内容身份派生并可回收。

不新增随意的文件大小、附件数、并发或等待上限。遇到提供商协议的真实输入边界时，明确提供保留原文件的可用读取方式，或返回具体不支持；不得静默丢附件。

## 12. 实施顺序与完成标准

按依赖组织实现，但完成目标覆盖整条交接链路，不能停在只给 schema 增加参数。

1. **建立引用与保留合同。** 扩展原生消息、派发和历史类型，接通原对象 owner、发送准备、接收读取关系、幂等及生命周期。
2. **贯通原生发送与接收。** 用户输入、`dispatch`、`send`、已有任务接续、历史回读与报告引用共同接入；工具产物提供现成引用。
3. **接通实际消费。** 图片模型输入、文档和文件读取、执行路径准备、可写结果及跨 Host 交付。
4. **接入 UI 和外部适配。** 普通附件上传、Chat / 协作面板与外部 Harness 的真实能力转换。
5. **收敛旧路径与文档。** 新发送只写 typed 关系；更新 Bot、协作、资源和外部 Agent 当前文档，删除已经被取代的设计说明。

有价值的验收场景如下，按实际 owner 选取测试，不在各层重复构造同一 DTO：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 用户上传表格后 Bot 首次派发 | 无需预查目录、读取全文或继承整段聊天，子任务可读取原件 |
| 给运行中的任务补发文件 | 正文与附件在同一输入边界进入，未就绪时不投递半条消息 |
| 文件排队后源文件被修改或删除 | 接收方读取原交付版本，模型重启和任务接续后仍成立 |
| 同源与独立工作区 | 同一发送方式均可用，不覆盖目标项目、不捕获整库 |
| 文件写入或导出后回传 | 产物引用能直接发送，最终报告指向同次交付，不重复复制和通知 |
| 连续转发与删除原会话 | 存活接收方仍可读取，最后一个引用释放后原对象可回收 |
| 响应丢失、Host 重启、准备取消 | 恢复原操作和固定版本；不重发交办；取消等待不撤回消息 |
| 图片与未知文件类型 | 图片可进入真实视觉输入；未知类型保留原字节，可供工具或程序处理 |
| 本地与远端命令处理 | 返回当前执行 Host 的有效路径，进程使用期间文件保持可用 |
| 外部 Harness 部分能力不支持 | 实际支持的方式正常交付；不支持时明确失败且保留选择，不降为文字描述 |
| 无权限引用、重名、原件变化 | 原 owner 作出准确判断，不能靠名称、hash 或正文伪造文件读取权 |

这份设计完成的标志，是模型可以围绕“把这些文件交给谁、让它做什么”自然协作，系统能持续保证交付原件、接收可读、版本稳定和资源最终回收。
