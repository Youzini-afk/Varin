# 模型输入呈现与重复内容收敛

状态：设计提案，尚未实施。2026-11-11。本文依据本轮源码排查，只覆盖前两份正在实施方案之外的模型输入问题。

## 1. 范围与判断

前两份方案继续作为各自领域的实现依据：

- [协作上下文、任务查询与模型引用](collaboration-context-and-model-references.md)：协作消息与报告投递、临时概览移除、任务查询、短引用及各类工具的对象解析。
- [聊天定点引用与可拖动输入标记](chat-quoting-and-draggable-markers.md)：用户显式引用、标记编辑、拖动、附件交付及历史定位。

本文不重新设计上述功能，也不另列一套协作回执或引用服务。`@` 对象定位器、引用来源 JSON 和协作消息中的长身份组合，由这两个既有方案处理；本案只约定它们与公共模型输入入口的衔接。

本轮剩余问题有共同原因：**程序保存和追踪对象所需的结构，直接成为模型要阅读的内容；某些上游已经表达的内容，又被下游重复包装。**

需要改的是实际输入的构成。原始记录继续服务恢复、资源管理、UI 和诊断；模型输入围绕当前材料的含义、有效结果及后续操作来组织。不会用新增提示词让模型自行忽略噪声，也不增加辅助摘要请求、硬截断配额或新的上下文规划服务。

## 2. 本案确认的问题与边界

| 位置 | 源码确认的行为 | 本案要处理的部分 |
| --- | --- | --- |
| 公共外部输出 | `evidence_parts` 把 `output.data`、整个 `Provenance` 和固定声明放在前面，再追加 `parts` | 模型结果与内部来源分开；可读出处只表达一次 |
| 图片序列化 | `media_label` 将 `media.source` 整体写成 `Media source` JSON，与实际图片一起发送 | 图片旁只保留有意义的名称、顺序与来源含义；内部执行身份不再作为说明 |
| 定时接续的进程／Job 结果 | `quoted_output` 一边把已解析的 `parts` 加入正文，一边把包含原 `parts` 的存储结果放进 JSON | 同一输出只呈现一次；保留实际完成状态、错误、必要数据与读取入口 |
| 外部事件接续 | 事件来源元数据同时出现在 `events[].source` 和 `External event: ...` 文字里 | 事件身份、路由与去重记录留在 owner；模型收到一次可读事件及其业务内容 |
| 编辑器上下文 | 已保存文件、未保存缓冲、diff、测试失败及栈帧的文字投影含编辑修订与反复的能力声明 | 保留文件、范围、未保存状态及实际内容；内部修订和无用途的重复声明退出正文 |
| 压缩输入 | 整个 `ConversationItem` 被 JSON 序列化，再包进 `material/retention`；长材料切片还套一层 JSON 字符串 | 改为可读原文与精简的整理辅助信息，保持原文保留分组和回读能力 |
| 技能清单 | 每个技能都向模型输出资源版本哈希，`resource_read` 不要求模型提交该哈希 | 清单只提供选择和读取所需信息，版本固定由原注册与激活机制承担 |
| 记忆整理辅助模型 | 初始候选使用 `{...row, revision}`；后续读取直接序列化完整记录 | 明确整理模型需要看的记忆材料，内部持有者与修订校验不外露 |

证据入口：[公共输出与图片编码](../../kernel/crates/varin-runtime/src/providers/mod.rs)、[Responses 实际发送](../../kernel/crates/varin-runtime/src/providers/responses.rs)、[接续输入构造](../../kernel/crates/varin-runtime/src/catalog_followups.rs)、[事件批次投影](../../kernel/crates/varin-runtime/src/catalog_followup_event_input.rs)、[编辑器投影](../../packages/ui/src/lib/agent-editor/projection.ts)、[压缩来源](../../kernel/crates/varin-runtime/src/context_material.rs)、[原文保留注释](../../kernel/crates/varin-runtime/src/context_retention.rs)、[技能清单](../../packages/web/application-host/lib/agent-resources/render.ts)、[记忆维护](../../packages/web/application-host/lib/memory/memory-maintenance.ts)。

以下内容已核对，不作为新的问题扩大处理：

- 文件读取版本、附件读取引用、分页游标有真实操作用途；其表示与解析沿短引用方案完成。
- 普通附件描述目前主要是引用、文件名、类型和大小，并没有图片来源那套执行链；不因为它使用 JSON 就认定有问题。
- `thread-material-input.ts` 的旧材料文字拼接仍在，但生产 `ThreadAdapter` 已绑定附件 owner，通常先走实际附件准备分支。本案不把它计作每次上传文件都会发生的开销。
- 记忆召回的缓存 revision、上下文配置摘要和多数指令来源索引只存在于内部状态中。Bot 召回已采用瘦字段和增量交付，不需要重写召回系统。

## 3. 公共输入呈现的责任

### 3.1 保留两种用途，复用同一份内容

原结果描述发生过什么，并保留完整的执行、来源及资源关系。模型可读视图描述它需要理解和使用的内容。两者共享实际文字、图片和文件，不各复制一份大正文。

由各领域 owner 明确哪些是业务数据、哪些是内容部分、哪些只供内部使用。公共输入入口组合这些已经选定的内容；provider 适配器只负责编码成目标接口的文字、图片和工具结果。

这里不建立按字段名递归删除的“清洗器”。用户日志中的 `id`、第三方响应中的 `source`、用户正在讨论的哈希或版本，本身可能就是任务内容。处理对象是 Varin 自己生成的外层包装及已经明确的内部结构。

工具结果中的成功、失败、未执行、仍在运行、结果不确定等区别继续保留。结构化数据也继续可用：表格、JSON、进程退出码、检索结果等按原语义提供，不强制改成一句自然语言总结。

### 3.2 一个来源只解释一次

来源类型决定其含义与输入角色。外部事件、工具观察、其他 Agent 的消息仍有准确来源，不提升为系统指令或冒充用户新要求。

可读层使用简短的出处，例如“网页内容”“进程结束结果”“外部事件”，需要时带实际网站、文件名、发送者或发生时间。来源差异确实影响理解时表达一次即可。上游已经给出可读来源，下游不能再附完整来源 JSON 和同义声明。

`evidence_parts` 收敛为公共组合入口，取消无条件序列化整个 `Provenance` 的行为。保留原类型判断与来源约束；MCP sampling 等已经有明确角色的特殊输入继续使用其真实合同，不借清理文字改变角色语义。

不能把所有业务 `data` 都清空来省 token。有业务数据时提供实际数据；仅有文字或媒体时不再增加 `data:null` 一类空包装。数据与文字分别表达不同事实时，二者都保留；同一份结果被上游重复放入两处时，在生产者处修正。

### 3.3 图片旁提供模型能用的信息

图片继续通过实际媒体内容传递。图片标签只承担识别与对应：用户标记中的图片编号、已有文件名、工具返回中的可读对象名或必要来源。

`OutputSource` 中的 Run、Operation、调用起点等原身份留在媒体记录中。图片对应的读取、转发与资源保留仍沿原媒体和短引用能力，不让模型凭一段执行链 JSON 猜怎么操作。

连续多张图片要保持顺序和文字对应关系。来自不同对象但内容相同的图片，也不能只按像素哈希合成一张；不同来源可能正是比较对象。用户主动重复引用如何呈现，按聊天引用方案处理。

同一公共规则同时接入 Responses、Chat Completions、Anthropic 及其他实际消费 `ProviderPart` 的适配器，不逐个复制一份提示词模板。图片不支持、类型限制和实际读取失败继续由现有媒体合同表达。

## 4. 接续与事件：一次到达，一份可读结果

### 4.1 进程与后台 Job

当前 `quoted_output` 同时加载存储形态与已解析形态，将完整存储形态嵌入 `facts`，又把已解析 `parts` 追加到正文。只要原结果带文本部分，同一文本就可能在一次输入中出现两遍；媒体还可能带出其存储描述。

改为沿同一个原结果生成可读输入：

- 接续入口提供安排的原意，以及这次真正发生的触发事实。
- 进程／Job 提供可识别名称、实际结果状态、必要的退出或错误信息。
- 原结果的业务数据进入数据部分，文本与图片进入内容部分，每部分仅出现一次。
- 完整结果较大时，沿现有结果预算与读取入口继续读取，不新增一套接续专用截断规则。

`receiptIdentity`、`receiptEpoch`、Job binding、内部 source Run 等仍保留在原执行记录。实际是否停止、写入是否发生、结果是否未知这些会影响下一步的事实要表达，但不把证明这些事实的全部内部材料搬给模型。

后台 Job 的受理结果与最终结果也要分别判断用途。最终回报只带当前有用内容；初始受理里确有尚未重复的业务材料时保留，不能机械地每次把完整 acceptance 和 terminal result 都重放一遍。

例如，模型可以收到“原安排：检查构建结果；构建已结束，退出码 1”，接着是原错误输出与可读取进程日志的入口。它不需要先读完执行器绑定、收据代次和两份相同输出才知道构建失败。

### 4.2 外部事件

事件仍由原安排与连接入口受理。模型侧围绕事件含义组织：是什么来源、发生了什么、与当前安排有什么关系，以及原业务内容。只有对时序判断有意义时才呈现发生时间或状态变化。

事件去重 ID、传输游标、路由记录、安排 generation 与重复计划的内部定义继续供 owner 使用。业务中需要回复的消息、操作的议题或读取的附件，提供已有工具能使用的对象入口；不把这些有操作用途的目标误删。

事件元数据的可读部分选择一个呈现位置。取消 `events[].source` 和 `External event: {metadata}` 对同一来源的双份输出，也不在外层再把 `registeredBy`、整个 trigger 与同义证据一遍遍铺开。模型需要查看完整安排时，沿既有查询能力取得。

现有事件批次规则保持：只有同一消费边界中、身份和顺序明确的重复或被替代状态才能合并。普通消息、不同安排的不同意图、没有可靠顺序的事件继续分别保留。不能因为文字相同或“看起来已经说过”就消掉另一个真实事件。

### 4.3 与交付和恢复的关系

可读结果从原触发、原输出与原事件生成，沿原输入受理并固定下来。生成模型视图不代表事件已消费；是否送达、是否完成与是否需要重试仍由原回执和执行状态决定。

取消、暂停、立即发送、排队和重启恢复保持现有语义。本案不改唤醒条件、接续频率或消息路由。源记录保留完整，模型输入减少的是重复呈现与内部包装。

## 5. 编辑器上下文：把实际工作材料说清楚

本节只处理编辑器上下文本身，不涉及聊天引用对象与输入标记的实现。

| 编辑器材料 | 模型应看到 | 留在程序里的信息 |
| --- | --- | --- |
| 已保存文件 | 文件路径或可读文件入口；名称不同于路径时保留名称 | 编辑器本地修订、没有实际用途的 `none` 修订行 |
| 未保存缓冲／选区 | 路径、所选范围、明确的“未保存内容”与实际文字 | Document 实例、缓冲版本、来源证明 |
| Diff | 对应文件、实际差异和理解改动所需的背景 | 为恢复和确认而保存的底层资源记录 |
| 诊断／测试失败 | 文件与位置、原错误、必要的上下文 | 编辑器对象身份及反复的能力免责声明 |
| 栈帧 | 文件、行号、函数或帧信息及相关内容 | 内部导航对象、UI 状态 |

未保存内容与磁盘内容的区别必须保留，这是实际语义。不同设备或来源下出现相同路径时，附可读的来源名称来消除歧义；实际文件定位继续由原资源关系承担。

`projectEditorContextAttachments` 不再为每个测试失败或栈帧追加“不会授予某种能力”的段落，也不为普通已保存文件固定附一组磁盘／编辑器修订。各类材料保留自己的内容，不为了排版一致凑齐所有字段。

行内评论当前已经以路径、行号、代码和用户评论为主，保留这一结构。只有发现同一上下文在相邻处理层重复附加时才去重，不因为文本较长而删掉用户写的说明。

接入原输入内容与资源关系，沿聊天引用方案正在建立的受理底座传递。已知版本用于原编辑／保存校验，仍由程序持有；模型后续编辑文件时沿统一文件引用合同取得实际需要的版本，不能把编辑器本地修订冒充文件写入版本。

## 6. 压缩模型：整理原材料，不整理内部序列化结构

### 6.1 只改输入呈现

本节保持现有后台准备、替换时机、整理模型选择、摘要输出、原文保留分组和回读能力。已搁置的增量摘要设计不在这里重启，也不增加必留栏目、强制检查清单或新的压缩算法。

当前 `quote_sources` 将原历史项整体序列化成文字，`context_retention` 再加保留成本信息；过长时，`source_item` 把 JSON 字符串片段再序列化一次。模型既要理解实际对话，也要阅读内部层级、长身份和大量转义。

改成按实际内容生成固定的整理材料：说话者或材料类型、原文，以及必要的保留组和成本信息。工具交换仍保留动作、参数和实际结果；图片仍提供实际媒体。角色关系保留，来源证明留在内部。

一种可读呈现可以是：

```text
用户 · 保留组 r1
保留原文预计占用：…… token
请沿用旧文件的编码，只修改这处逻辑。

工具 file_read · 保留组 r2
文件：src/parser.c
……原读取结果……
```

这是内容结构的说明，不规定所有整理材料必须套同一个长标题。已有 `r1` 等标识继续用于原文保留选择，同组只计一次成本。回读目标使用现有摘要读取与统一短引用能力，不新增一套永久摘要别名表。

### 6.2 结构归程序，原文给模型

原历史身份、内容部分关系、工具配对、保留组映射和资源持有保存在整理任务的固定来源中。预算与保留判断读取这些结构，不从模型可见的标题或 JSON 字符串反向解析来源。

一份工具结果包含业务数据、文字和媒体时，沿公共可读视图展开一次，并保持原顺序。原文保留仍指向完整原记录，不把瘦化后的说明误当作原始历史，也不把多个工具部分拆成可任意丢失配对的独立历史。

用户原文中本来就含 JSON、代码、路径或哈希时照常保留。省掉的是外层存储对象的序列化，不改写任务材料。

### 6.3 容量计算与切片

容量估算基于真正准备发送的文字、媒体和工具说明。压缩模型输入的成本，与后续主模型保留原记录的成本，是两个用途，继续分别计算；不能因为整理输入变短，就错误低估保留原工具交换所需的空间。

一份材料过长时沿已有容量机制分批。片段使用固定可读材料的有效文字边界，保留必要的连续读取信息；程序维护到原条目的对应关系，不能把新文本偏移当成旧 JSON 序列化后的字节偏移。

单纯减少包装不得触发更多整理轮次或新的辅助摘要调用。保留与回读的使用时机仍由整理模型自主判断。

## 7. 技能清单：保持发现与读取直接

模型选择技能需要名称、简介和直接可读的入口。技能来源名称在区分同名技能或理解适用范围时保留，适用目录和真正的用户指令仍按原规则表达。

从 `renderSkillMetadata` 的常驻清单移除版本哈希。普通 `resource_read kind:skill` 使用本次请求固定的目录；明确激活的历史技能已有 `activationId` 选择原版本。两条链继续由原资源 owner 处理，清单不要求模型再携带哈希校验一次。

资源引用的缩短与解析交给正在实施的统一引用方案。本案不发明以技能名称猜唯一对象的替代机制，不省掉读取入口，也不额外制造一轮“先兑换技能”的调用。

工作区指令的来源文件和适用范围有实际用途，继续保留可读信息。此次不删除用户的 AGENTS、系统提示词或技能正文，不把内容长度本身当成需要压缩的理由。

## 8. 记忆整理辅助模型：明确选择材料

### 8.1 收敛完整行序列化

`memory-maintenance.ts` 当前把完整 Knowledge 行及版本摘要放进初始输入，后续读取也直接序列化完整记录。改成同一份明确的整理材料投影，初始候选和后续读取共同使用。

保留模型判断所需的记忆 ID、正文、适用条件、信息性质、有效性，以及相关的补充／派生／替代关系。时间与出处在判断变化、冲突或依据时有意义，应以可读事实呈现；不能为了变短抹掉“这是谁说的、何时成立、后来怎样变了”。

内部来源 key、proposal key、执行身份组合、来源版本哈希、持久化修订摘要和维护回执留在 recipe 与 store。召回次数、上次召回时间属于运行统计，不默认塞给整理模型充当重要性或真实性依据。

已有整数记忆 ID 继续用于提出合并、替代和回读，不另做一套编号。关系中的目标仍能定位原记忆；原材料读取交给已有 `readSource` 路径，不把完整来源证明塞进每个候选。

### 8.2 一致性检查留在原 owner

维护运行已持有原输入记录，且 `assertCurrent` 使用 `memoryExpected` 判断内容是否变化。模型输出合同引用记忆 ID，并不回传 `memoryVersion` 哈希。因此版本校验继续在程序里完成，模型材料不再附一份哈希让它阅读。

程序比较的是实际被整理的那份记录。若期间用户修改或遗忘了记忆，继续使用原冲突／取消处理；不能悄悄换成最新行再应用旧提案。

来源不可用、只有节选、已经失效或历史被清理等状态继续准确表达。后续读取返回业务材料与连续读取信息；有结构化结果时直接表达其内容，避免把整份 JSON 再塞进字符串字段形成不必要的二次转义。

现有容量与分页机制保留，计算改用实际准备的输入。候选选择、维护触发、遗忘传播、整理自主性和输出动作不在本案重设，也不追加新的“必须先读／必须保留”提示词。

普通记忆注入与 Bot 增量召回不在此次改造范围内；它们已采用不同于完整存储行的投影，继续沿原机制工作。

## 9. 实现归属、衔接与稳定性

### 9.1 原 owner 提供材料，公共入口组合

领域逻辑留在对应模块，公共层不识别每种事件的业务字段。采用少量直接的呈现函数与现有类型，不新增上下文管理服务、投影规则 DSL、第二份权威数据库或全局字段黑名单。

需要让内部元数据与模型材料分开保存时，在原结果／输入元数据中表达其关系，复用 ContentStore 的内容与媒体引用。不为每个模型请求完整复制一份原日志、图片或历史，也不把同一材料分别建成“UI 版”和“模型版”的独立存储系统。

### 9.2 与前两份实施的接点

协作与短引用方案负责对象和原始结果的关联；本案消费其有效引用，处理公共包装及剩余领域内容。聊天引用方案负责用户选择和输入位置；本案提供精简的编辑器材料与通用媒体呈现。三者共享原输入受理、结果发布和模型编码入口。

共同涉及 `projection.ts`、`Content::Output` 或 provider 公共函数时，需要合并最终合同后修改，避免一个方案去掉来源 JSON，另一个方案又在下一层补回来。引用表示和内容呈现可以分别推进，不能用裸删关联字段临时绕过尚未接通的资源读取能力。

第三方 MCP／扩展返回的业务内容继续按原契约传递。只有明确由 Varin 生成的内部包装在本案范围内；不猜测第三方任意字段的性质，也不要求插件先升级才能使用现有能力。

### 9.3 请求稳定与历史

已准备的模型请求及不确定重试继续使用原固定内容，不能重试时重新取一份最新事件或重新解释旧回执。新的材料在原准备／发布边界确定可读视图，后续请求沿同一份历史接续。

按前案的新旧输入衔接规则处理历史，不批量重写旧对话中的来源文字或 ID。实际需要调整持久结构时，由原存储 owner 的升级路径完成；原收据、历史来源和用户资源仍然有效。

不会为了省略文字而失去回收依据。队列、历史、报告与辅助任务持有的原资源关系继续有效；重复展示被移除后，多余的呈现副本按既有生命周期释放，不建立永久去重账本。

## 10. 实施顺序与验收

先处理有直接重复证据的接续输出和事件，再接通公共外部输出／图片呈现；随后完成编辑器材料、技能清单及两个辅助模型的输入。每项都沿真实 consumer 验证，不通过测试字符串变短来证明行为正确。

| 关键场景 | 要保护的结果 |
| --- | --- |
| 进程／Job 返回结构化数据、文本及图片 | 各有效部分恰好呈现一次，完成状态和错误仍准确，日志继续可读 |
| 两个事件内容相同但身份不同；同一事件被多个安排选择 | 不按文字猜去重；仍遵循既有消费边界和不同意图规则 |
| 单图、多图、工具图片及混合文字 | 实际图片和顺序正确，内部执行来源不变成附加文本 |
| 数据为空、只有文本、只有图片、数据与文本分别有业务含义 | 不产生空包装，也不误删有效结构化数据 |
| 附加未保存文件、diff、诊断及栈帧 | 原内容与位置准确，未保存语义保留，内部编辑修订不再反复展示 |
| 压缩含工具配对、多部分输出和需分批的长材料 | 实际整理输入可读，原文保留组正确，输入成本与保留成本分别准确 |
| 技能普通读取和显式历史激活 | 清单不含无用途哈希，读取仍取得对应原版本 |
| 记忆维护初始候选、续读及期间用户修改 | 两种入口材料一致，原依据与语义完整，冲突仍由原 owner 正确处理 |
| 用户日志或第三方数据本来包含 ID、JSON、版本和 source 字段 | 内容原样保留，不能被通用清理逻辑误删 |
| 受理后重试、排队、恢复和回收 | 使用同一份已固定材料，不重复触发，不遗失原资源关系 |

优先复用 provider 序列化、接续受理、编辑器输入和辅助推理已有测试，在真正的边界补少量稳定用例。重复内容可以用确定的原输出核对次数；有效内容和媒体要同时核对，不能只设一个“token 必须下降”的阈值。

不为本案新增默认提示词抓取、全量日志、长期性能监控或常驻评测系统。源码与针对性输入输出证据足够时停止扩大验证。只交付本文时，检查本地文档链接及范围即可，不运行应用构建或真实模型请求。
