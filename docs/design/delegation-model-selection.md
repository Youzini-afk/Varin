# 自由派发与模型选择

状态：2026-11-02 设计确定，待实现。本文描述目标行为；当前派发机制见[Agent 协作](../collaboration.md)，长期总助手见[Bot](../bot.md)。

## 1. 要解决的问题

Varin 可以安排负责人，负责人也可以继续安排子任务。每次分工应由派发者结合任务决定，不要求任务先落进某个预制角色。

当前普通 `dispatch` 已允许不选预设、直接传任务，但执行配置主要继承派发者；改用其他模型和思考设置通常通过预设完成。接下来需要把模型配置选择从固定角色中独立出来：任务、执行模型和思考投入可以按本次工作组合，预设仍作为用户保存的常用搭配。

难点在于派发者未必了解用户配置的模型，尤其是新模型、自定义名称，以及不同渠道下的同一个模型。思考等级也不统一，有的模型支持等级，有的只支持开关或预算。仅靠模型名称不足以作出可靠选择。

本设计提供两种方式：派发者直接选择；或启用一个辅助模型，为每次派发选择执行配置。辅助岗位既可以使用普通 LLM，也可以使用专用决策模型。

## 2. 核心决定

- 派发以任务为中心。任务内容、必要背景、名字和具体分工由派发者决定。
- 每个渠道下的模型配置可以保存一份自由文本简介。模型特点、用户经验、渠道偏好和思考建议都写在这一份简介里。
- 启用「派发模型选择」后，派发者通常只需写好任务，不需要接收完整模型目录，也不需要额外撰写选择理由。
- 选择者使用短的近期对话、任务正文和候选目录，一次请求返回配置。普通 LLM 与专用决策模型采用同样的信息边界。
- 不引入用于选模型的 Agent 会话、工具循环、历史回读、额外摘要模型或逐级决策链。
- 已明确指定的配置优先，辅助选择只补齐仍需决定的部分。
- 原生任务受理、模型绑定、权限、执行、回报和用量继续由现有 owner 负责。

## 3. 模型简介

### 3.1 一份文本表达使用经验

在现有模型设置中增加可选的「简介」，例如：

> 响应快，我主要用来做检索和明确的执行任务。一般用中等思考，需要综合复杂约束时可以提高。这个渠道走套餐，日常优先考虑。

不再拆成能力介绍、用户说明、适用任务、渠道评价等多个编辑区域。也不要求用户按照模板填写。

平台已有可靠介绍时可以提供初始文本；用户编辑后保存其内容，目录更新不覆盖用户的修改。没有介绍时保留空值，不凭模型名称生成能力评价。模型元数据源是否提供简介，要以实际数据为准。

同一个模型在不同渠道中可以保存不同简介。基础资料可以共用已确认的模型匹配，但实际可选项仍是具体渠道中的配置；不能因名称相似就将两个配置合并成同一个执行目标。

### 3.2 复用已有事实

简介旁已有的上下文容量、输入类型、价格、思考控制等配置继续作为事实来源，不要求用户重复填写。模型选择使用当前有效值，明确保存的用户值优先于目录推断。

给选择者的候选包含可读名称、渠道名称、简介和影响执行的必要信息。连接地址、凭据和原始认证配置不进入选择上下文。

模型能力与执行环境分别表达。是否能浏览网页、编辑 Office 文件或运行终端取决于本次工具与环境；不把这些写成模型自身固有能力。本次任务明确需要的输入能力应当能与候选配置对照。

## 4. 如何选择

### 4.1 自由派发与预设

自由派发允许选定实际模型配置，并按需覆盖思考设置。调用方引用平台提供的稳定配置标识，不自行拼接请求模型名或渠道参数。

已有预设保留其模型、指令和工具组合。显式选择预设时沿用该组合，包括现有的继承语义；启用自动选择不暗中改写一个已经选定的预设。

普通自由派发的行为为：

| 本次情况 | 处理 |
| --- | --- |
| 未启用辅助选择，也未指定模型 | 沿用现有继承行为 |
| 已明确指定完整执行配置 | 直接准备该配置，不调用选择模型 |
| 已指定模型，思考未指定，且启用了辅助选择 | 在该模型实际支持的选项中决定思考设置 |
| 未指定模型，启用了辅助选择 | 选择具体渠道模型及其有效思考设置 |
| 只指定了思考要求 | 保留要求，在兼容的模型配置中选择；不修改要求来迁就候选 |

省略思考设置与明确选择“使用该配置默认值”应可区分。后者已经作出选择，不再交给辅助模型重选。
未启用辅助选择时，显式指定模型而省略思考设置，使用该模型配置的默认值；不把父模型不兼容的思考参数直接搬过去。

未启用辅助选择时，派发者可通过现有按需披露路径获取简短模型目录及简介，自行选择。启用后不把整份目录追加进派发者的每次请求；目录只进入实际的辅助选择请求。

### 4.2 辅助岗位

设置入口称为「派发模型选择」，配置启用状态、所用模型，以及该选择模型自身支持的思考设置。模型选择器允许普通对话模型和专用决策模型，按操作能力区分调用方式。

这个岗位自身的思考设置，与它为执行者选择的思考设置相互独立。启用和修改配置作用于之后受理的派发。初始实现保持未启用状态，已有安装沿用原派发方式，用户开启后采用辅助选择。

不新增一个“用户选择偏好”文本框。长期使用经验放在各模型简介中；当前任务的偏好由实际对话和派发正文表达。

Varin 派发负责人、负责人派发子任务共用同一机制。父任务使用了某模型和高思考，不自动表示它的所有子任务必须采用相同配置。

## 5. 选择上下文

### 5.1 选择任务需要的材料

选择者每次接收：

1. 简短的选择指令及本次已固定的配置。
2. 当前实际候选目录与简介。
3. 本次派发任务正文，以及派发已经声明的工具、输入类型等必要执行信息。
4. 派发位置之前，最近 3 轮交流中选出的用户和助手消息。

不单独追溯最初用户请求，不自动提取一组“质量优先”“时效等级”标签。长程任务的要求已融入持续交流，应让选择模型读有限的真实原文来理解。

不加入压缩摘要、长期记忆全文、完整工具流水、私有思考、文件正文或附件二进制。附件只保留已有的名称、类型等必要信息，不为模型选择重新读取或生成材料摘要。

选择上下文与执行者收到的任务背景分别准备。选择上下文的截断不改变实际派发任务、执行者继承的历史或原始聊天记录。

### 5.2 最近 3 轮与最近两条助手输出

以本次派发者的实际历史分支和派发位置为边界，选择最近 3 轮自然交流，包含当前尚未结束的一轮。

这里的轮次按用户输入和随后的助手交流识别，不按 provider 请求次数或工具调用次数计数。任务执行中的真实用户补充可以开启新的交流轮次；工具结果、子任务回报、日程事件和内部通知不伪装成用户消息。子 Agent 的初始上级交办可作为其本地交流起点，不递归收集整条父级链。

选择规则：

- 取这 3 轮中的用户消息。
- 每轮取最后一条助手文本。当前轮没有结束时取最新文本。
- 确保距离派发最近的 2 条助手文本被包含；它们可以都是当前轮的进展说明。
- 按原消息身份去重，最后按原时间顺序排列。
- 最近两条助手文本从这 3 轮的范围内选取，不额外扩大为另外两轮。
- 范围内不足 3 轮或不足两条助手文本时，就使用已有内容，不补造消息。

助手文本包括正常回复与面向用户的执行进展。流式增量先按原消息身份归并，只取派发边界前已经产生的正文；不把同一消息的多个增量算成多条输出。

长程任务中，最近一轮即使有大量工具调用，也只带入上述选出的消息。这样既保留近期用户交流，也能看到当前助手的发现和安排。

### 5.3 单条文本的初始长度

| 文本 | 初始保留量 |
| --- | --- |
| 每轮用户消息 | 最多约 1,000 个 Unicode 字符 |
| 最近 2 条助手文本 | 每条最多约 2,000 个 Unicode 字符 |
| 其余入选的助手文本 | 每条最多约 600 个 Unicode 字符 |

这些是辅助选择输入的初始产品默认，不是聊天、任务或模型输出的限制。先集中定义在上下文组装处，不为每个数字增加设置项；根据实际任务选择效果再调整。

超过长度时保留首尾，中间标记省略。最近助手文本初始采用约 30% 开头、70% 结尾，即 2,000 字符时约 600 + 1,400；用户和较早助手消息使用相同比例。未超过长度时保留完整原文。

截取按 Unicode 字符边界完成，省略标记计入最终输入。保持角色、消息顺序和截断事实，不添加模型生成的总结，不把省略部分伪装成完整证据。

### 5.4 总容量与预留阈值

先应用上述单条截取，再按选择模型实际输入容量和预留阈值组装请求。复用现有分词和请求预算能力，计入指令、候选、任务、消息标签、协议包装及输出预留。专用决策接口有单题容量时也按其真实约束核算。

输入分配优先级：

1. 选择指令、有效候选、已固定配置和本次任务。
2. 最近用户消息及最近两条助手文本。
3. 较早的入选对话。

达到预留阈值时截断剩余文本或停止加入更早消息。容量分配可以按上述优先级，最终对话仍按时间排序。模型上下文窗口不是每次请求要填满的目标，正常请求只包含这份有限材料。

本次任务本身特别长时，选择请求可以使用标明省略的首尾预览；完整任务仍交给执行者。候选简介也可以在真实容量不足时缩短，但实际配置身份和有效思考选项必须完整，不能静默丢弃部分模型让选择者误以为那就是全部候选。

连必要候选身份和选择协议都无法容纳时，返回具体的容量或接口能力问题。不得通过多次调用分组选优、增加历史读取或额外摘要来掩盖这个问题。

### 5.5 历史读取成本

从原历史索引定位消息元数据和正文引用，只读取入选消息需要的文本范围。不能为了凑出几条消息，先把几十轮的全部工具正文加载出来再过滤。

若最近交流涉及已经压缩的历史，沿原历史身份读取入选原消息，不把压缩摘要插进这份输入。来源读取沿现有授权与保留规则处理，不为选择请求新增一份长期历史副本。

候选和指令采用稳定顺序，当前任务与对话作为变化部分，尽量复用 provider 缓存。不同派发不能只因任务文字相同就复用旧的选择结果：近期上下文、简介和配置可能已经变化。

## 6. 单次选择协议

### 6.1 普通 LLM

沿现有辅助文本请求能力调用一次，只返回实际配置引用和有效思考选择。不提供工具，不创建对话循环，不要求输出分析报告、评分或解释。

选择指令可以采用以下方向，具体协议格式由适配器补充：

> 为这次派发选择合适的执行模型和思考设置。结合任务、近期交流、候选简介及实际可用参数判断，保留已经明确指定的配置。返回一个有效选择。

不规定“检索必须用小模型”“代码必须高思考”等固定分工；不要求写选择理由。候选简介是选择参考，不改变执行权限和请求协议。

### 6.2 专用决策模型

复用现有 typed-classifier 的选择能力。它接收与普通 LLM 相同的材料，不需要工具或后续读取。

初始适配采用一次选择有效执行组合：每个选项对应实际渠道模型及一种允许的思考设置。模型简介在共享材料中出现一次，组合选项引用对应配置和思考选择，避免重复长文本。

只生成真正有效的组合：固定思考不扩展出无效等级，开关与等级沿现有声明；预算型配置先使用用户已有的默认预算，不人为编造几档数字。显式指定的部分收窄组合，明确选择默认值时解析为该配置的实际默认。

适配器实际支持的候选数、文本容量等约束需要在发请求前检查。普通 LLM 与专用接口能力不同，但都只完成一次选择；不为绕过专用接口的候选限制偷偷串行调用多轮。

### 6.3 输出和失败

返回值只映射到这次请求中的候选及有效思考选项。未知标识、失效配置或不支持的等级保留具体错误，不猜测另一个渠道或静默换成继承模型。

网络类重试沿已有请求重试策略，继续使用同一次冻结输入；不增加专门的语义纠错对话或再请求一遍“请修正你的输出”。明确选择失败时由派发结果报告，调用方仍可通过已有显式派发能力决定下一步。

## 7. 受理、执行与延迟

辅助选择属于本次派发的准备阶段。先固定任务、历史边界、候选目录和选择模型配置，再执行选择；只有得到有效结果后，才准备所选执行模型及真正需要的执行资源。

读取候选目录不预先创建所有候选模型的执行者、保留所有渠道的凭据租约或准备全部工作区。选中后沿原模型 authority 绑定一个实际配置。

选择记录复用现有原生 Operation 和辅助推理回执，保存配置身份、输入引用、结果及用量。请求重试、Host 重启和取消继续遵循原回执：已完成的选择恢复原结果，不因前端重新观察再调用一次选择模型。

受理后的执行配置固定到本次任务。设置编辑只影响后续选择；当前实际配置不可用时按原绑定失败处理，不偷偷换渠道。取消派发同时传递给仍在进行的选择请求，取消后不能继续启动执行者。

选择等待应沿已有异步派发准备路径处理，不能占住全局执行锁或阻塞其他任务。对用户而言它是任务启动中的一个准备步骤；最终仍能查看实际执行模型和思考设置，无需为每次选择弹出确认或新增聊天气泡。

单次派发只需要一次模型选择请求。既有 transient retry 属于失败恢复，不作为正常选择流程的一部分。已明确选好配置时跳过选择请求。

## 8. 与外部 Harness、任务复用的关系

本设计首先完善 Varin 原生自由派发。Codex、Claude Code、Pi、ACP 等外部 Harness 的账户、会话和模型选择仍由其原适配器负责；不能把 Varin 的任意渠道模型直接塞入外部 Harness 的原生会话。

用户明确选择外部预设时沿原外部派发路径。后续若要将外部执行配置纳入自动选择，应使用它们实际暴露的选项，并另行明确配置映射。

向已有 Agent 发送补充或再次交办，继续沿原任务复用机制，不因开启辅助选择而自动换模型或重建会话。本次设计负责新派发的执行配置，已有会话的显式模型修改保留其独立语义。

## 10. 实施与验收

实现顺序以完整链路为单位：先让模型简介能保存和进入真实候选，再完成自由派发的显式模型／思考绑定，接入一次性的辅助选择和短上下文，最后贯通设置、重启恢复与任务展示。

优先复用既有测试，重点保护以下行为：

- 最近 3 轮、每轮最后一条助手文本与最近两条助手输出的并集正确，按身份去重；当前轮大量工具调用不扩张输入。
- 长文本保留首尾并标记省略，总输入遵守实际选择模型的预留阈值；工具正文、思考和压缩摘要不混入。
- 同一模型在不同渠道可携带不同简介，结果绑定到正确渠道；支持的思考选项与真实请求一致。
- 普通 LLM 和专用决策路径都只需要一次正常选择请求，显式配置与预设语义得到保留。
- 选择准备不阻塞其他派发，取消不启动子任务，重启复用已提交结果；实际选择费用进入原用量系统。
