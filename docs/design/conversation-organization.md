# 会话组织：项目与分组、Bot 访问和管理

状态：**设计方案，尚未实施**。整理于 2026-11-11，源码核对基线为 `a0631605e`。本文汇总会话分类、Bot 跨会话读取、项目与分组混合嵌套、派发来源头像的讨论，并明确数据归属与交互合同。

当前行为以[架构](../architecture.md)、[工作台](../workbench.md)、[Bot](../bot.md)、[协作](../collaboration.md)及源码为准。实现完成后，将稳定合同归入这些领域文档，设计过程保留在 Git。

## 1. 产品目标与确定的方向

用户和 Bot 使用同一套会话分类。Bot 创建的分组、放入分组的任务及后续整理，直接呈现在用户的导航中；用户的调整也能被 Bot 按需查询。

项目与分组组成一棵混合导航树。分组可以包含项目，项目可以包含分组，也可以经由分组继续包含其他项目。两者都能收纳会话；项目额外关联真实工作目录、文件能力和项目配置。

Bot 可以发现和读取同一用户可访问的其他 Bot 直接会话，包括自己的其他会话。开放范围仍沿实际 Host、认证主体和原内容权限，不通过同名 Bot、项目路径或导航层级推断跨用户访问。

Varin、工作台与 IDE 使用相同的分类记录，保留各自的布局、工作重点和视图偏好。Bot 派发的任务显示实际来源 Bot 的小头像。分组有默认图标，也可更换图标和颜色。

会话创建、派发、读取、归档和删除复用现有 owner。导航不持有另一份聊天历史、执行队列、凭据、文件副本或 Bot 记忆。提示词说明可用能力，由模型选择何时查询与整理，不要求先建组、每轮检查目录或填写固定工作摘要。

## 3. 混合导航树

### 3.1 容器与会话

项目和分组是容器，会话是内容入口。容器的子项可以是项目、分组或会话引用。

```text
工作〔分组〕
├─ Varin〔项目〕
│  ├─ 版本发布〔分组〕
│  │  ├─ 发布讨论〔与 Varin 的会话〕
│  │  └─ 准备新版发布〔Varin 派发的任务〕
│  │     └─ 回归验证〔该任务的子任务〕
│  ├─ 产品设计〔分组〕
│  └─ 配套产品〔分组〕
│     └─ 文档站〔项目〕
│        └─ 内容更新〔会话〕
└─ 长期调研〔分组〕
   └─ Agent 协作机制〔会话〕
生活〔分组〕
└─ 旅行安排〔与另一个 Bot 的会话〕
```

树中项目的父子位置表示组织关系。文档站可以使用另一目录或资源设备，其文件不会因此变成 Varin 目录下的子文件。

每个容器节点有一个稳定身份和一个导航父节点；根是隐式容器。项目节点引用原项目身份，项目名称、目录和配置继续由项目 owner 管理。分组保存自己的名称、图标和顺序。名称允许重复，路径负责显示位置，稳定引用负责定位。

同一项目在一棵树中保留一个正式入口；置顶、搜索、Bot 范围等视图可以引用该入口。会话也有一个有效分类位置，多个视图展示同一会话不会复制历史。这个约定使移动、排序和继承有明确含义。树提交检查自身包含、祖先环和悬空目标；不预设固定层数、分组数量或会话数量上限。

### 3.2 导航层级与执行层级

导航父节点回答“放在哪里”，`parent_thread_id` / 外部交办关系回答“谁派发了谁”。两种关系分别保存。

Bot 直接交办的一项工作在目标容器中作为主任务展示。它内部派发的子任务默认按原任务关系展开。把任务移入另一个组，不改变派发者、报告接收者、取消树或 Bot 生命周期归属。

子任务未指定分类位置时，继承其主任务的有效位置。明确移动某个子任务后，它出现在目标容器，并保留“来自哪个任务”的入口；原任务详情仍能查看完整分工。侧栏同一视图避免将它同时作为两个完整条目重复铺开。平铺和搜索可以展开所有命中项，并附原任务路径。

会话分支继续归原会话管理，分类移动作用于会话。独立建立的 fork 若已有独立 Thread，则作为该 Thread 的入口处理。

### 3.3 空容器与未分类内容

空分组可以保留，便于先组织再开展工作。根下未放进具体容器的会话进入“未分类”视图；这是根成员的呈现，不需要额外创建一个系统分组。现有“最近”可继续作为按时间查看的视图，不能同时承担另一份分类权威。

分组名称和图标无需包含任务说明、执行计划或角色要求。分类提供位置，工作内容仍由会话与任务自身表达。

## 4. 项目与工作环境

### 4.1 项目保留的职责

项目继续关联目录与附加目录、文件树和搜索、Git、项目指令与 Skills、项目设置及信任、编码选择、默认模型与工作侧重。分组本身没有目录要求，也不新增一层模型、工具或权限配置。

新建工作采用以下优先顺序：明确选择的执行来源优先；未选来源时，以目标容器最近一层项目提供默认环境；没有项目祖先时，沿现有会话身份的默认来源准备，例如 Bot 家目录或普通设备来源。进入内层项目后，采用内层项目自己的配置，不把多个项目的配置自动叠加。

项目提供适用的默认值，显式模型选择、Bot 专属模型及已有设置优先级继续由原配置 owner 解析。导航树不新增一套模型配置覆盖规则。

新 Bot 直接会话可以从项目分组中创建，保留所选 Bot 的身份、档案与记忆，项目只提供这次会话的默认工作环境。Bot 家目录仍保存其自身资产，不因分类移动而迁移。

### 4.2 移动和正在进行的工作

移动项目节点不移动磁盘目录。移动会话或其祖先容器，不更改已经选择的 Source、外部 Harness cwd、模型绑定、已受理输入或正在运行的任务。

新建草稿时固定已解析的默认项目/来源意图；整理目录不会在发送时悄悄重新选择另一环境。用户明确更换来源时，沿原准备与受理路径完成。列表和详情应能分别说明“分类位置”和“当前工作区”，两者不同是有效状态。

容器移动后，从该容器新创建的草稿使用新的最近项目默认值。删除分组使子项提升到上一层时，同样只影响之后的新建默认值。

### 4.3 分开部署

导航树属于当前协调 Host 的用户空间。会话、文件工作区和 Computer Use 设备继续保持各自身份。切换 Host 时读取该 Host 的目录，不把相同项目名、分组名或路径合并。

跨设备项目需要明确的项目来源绑定。实现时扩展原项目 DTO/设置与准入路径，引用现有 `SourceResourceOwner` 和 Documents 登记；当前项目缺省保持原本地含义。远端路径由目标 Host 解析，连接和凭据沿现有 managed-host owner。导航层只保存项目引用，不复制账号或自行访问远端文件系统。

当前 `ProjectEntry` 尚无这项远端绑定，Settings 项目路径校验也使用本机文件系统。跨设备项目接入必须同时覆盖这些真实消费者，不能只在树节点上补一个 Host 标签。设备暂时离线时保留已保存的项目节点，呈现不可用原因；分类浏览和已有会话读取不依赖启动该设备。

## 5. 创建与派发的分类规则

### 5.1 默认位置

原生会话、Bot 直接会话与外部 Harness 会话使用同一套导航位置选择：

1. 明确指定容器时，放入该容器。
2. 未指定容器但明确选择项目时，放入该项目节点。
3. 两者均未指定时，新派发工作沿发起会话/父任务的有效分类位置。
4. 没有可继承位置时，放在根下，由“未分类”视图呈现。

用户在树的某个容器中点击“新建”，该容器就是明确目标。Bot 工具接受可选容器引用；没有分类要求也可直接执行，不需要先查询整棵树。任务内部继续派发时，沿上一节的任务树规则组织。

Bot 直接交办的主任务在受理时固定解析出的容器，之后整理 Bot 的聊天不会顺带搬走所有已交办任务。任务内部的默认子任务则固定“继承父任务位置”这一意图，父任务移动时跟随；明确为子任务选择容器后，采用独立位置。同键重试保留原选择方式，回执中的当时位置与当前查询结果分别表达各自时间的事实。

分类位置与执行来源可以分别指定。例如在“跨项目调研”组中派发使用 Varin 项目文件的任务，分类仍放在该组，文件来源使用原项目准备结果。目录同时保留这两项事实。

### 5.2 新建会话与立即执行

创建空会话、创建同一 Bot 的新直接会话、派发并启动工作是不同意图。分别复用原 Thread 创建、Bot session 和 `dispatch` 受理入口；分类参数随各自命令传递，不通过事后猜测标题关联。

Bot 指定另一个 Bot 的会话入口时，沿原 BotService、真实用户身份和执行 gate 检查。休眠、归档或删除状态仍按原 owner 处理，不能通过创建普通 Thread 后填入 Bot 名称来绕开原生命周期。

同一创建/派发命令在首次受理时固定分类意图。重试读取原回执，不把已经创建的任务移到“此刻最新分组”，不重新派发。模型已选中的容器在受理前被删除或产生语义冲突时，返回具体错误，交由调用方重新选择；不用另一容器冒充成功。

原生 Thread 与分类记录由同一 Catalog 事务提交。外部会话的产品受理也在其原 Catalog 命令边界接入分类；外部程序准备仍沿原执行流程。后续模型、资源或 Harness 准备失败时，已受理会话保留原分类及实际失败状态。

## 6. Bot 的读取与管理范围

### 6.1 可读会话

Bot 直接会话可以发现和读取当前 Host 上、与其可信认证主体一致的产品会话：普通会话、自己的其他直接会话、其他 Bot 的直接会话、委派任务，以及原外部 Harness 适配器允许读取的会话。

隐藏的上下文整理、记忆维护和内部检索执行继续通过其原领域读取入口访问。删除后的会话遵守原 tombstone 与内容保留合同。归档会话仍可读取，只在默认目录浏览中收起。

普通执行 Agent 继续采用原任务关系和已有授权，新增工具是否可用沿原工具选择机制。Bot 读取范围的扩展不通过父子关系自动传递给每个子执行者。明确传给子任务的背景与附件，仍由现有固定引用和交付 owner 核验。

### 6.2 分别表达读取、消息与记忆

现有 `ordinary_conversation` 同时参与历史读取、背景引用和 `can_message`。实现应提取明确的读取判定，更新目录、正文、分页、媒体和背景引用消费者，避免只改目录 SQL 后出现“能看到但读不了”。读取开始与完成边界继续验证真实身份和访问条件。

本设计扩大读取及导航管理范围。消息发送继续走原 `send` 准入、原接收分支和 Bot gate；不能因共用判断被放宽而意外改变 Bot 之间的主动唤醒。读取其他 Bot 会话的内容保留原作者与来源，进入调用方上下文时作为材料呈现。长期记忆写入、明确关注和记忆关联使用各自原有操作，不由一次目录查询代替。

### 6.3 管理能力

模型可使用分组创建/改名/图标编辑、容器与会话移动、顺序调整，以及会话创建、改名、置顶、归档、恢复和删除。Bot 默认可发现这组能力，实际执行沿可信调用身份、所选工具和原权限 owner 验证。

用户与模型调用同一业务命令。模型不用自行填写用户 ID、内部 UUID、数据库 revision 或确认文案。Host/原生 invocation 固定调用主体；工具返回的稳定对象引用和读取版本用于后续解析与冲突检查。

管理权限不由所在分组名称、项目路径或“由某 Bot 创建”推断。项目注册和移除仍走原项目能力；项目 owner 当前按 Host 保存，不能因导航按用户分区就声称项目配置已经隔离到用户。

## 7. 目录查询和模型输入

### 7.1 查询合同

`threads` 继续承担会话/任务发现，`read_thread` 继续读取概况和原文。增加分类条件及容器发现能力，复用原模型短引用与分页机制。分组管理可以通过一个按操作披露的组织工具提供，避免在普通对话中常驻完整目录和全部管理参数。

| 条件 | 语义 |
| --- | --- |
| 容器 | 查询该项目/分组，支持明确选择仅直接成员或包含后代 |
| 项目 | 区分导航最近项目与实际工作来源项目，参数描述明确采用哪一种 |
| 来源 Bot | 按原直接绑定或派发祖先查询，支持仅直接交流或包含其工作 |
| 会话类型 | 普通直接会话、Bot 直接会话、委派任务；执行后端另列原生/外部 Harness |
| 归档 | 默认未归档，可包含归档或只查归档 |
| 执行范围 | 保留 `current/history/all` 的现有含义，与归档分别筛选 |
| 内容线索 | 名称、短引用、父任务、时间和成果文件条件继续复用原查询 |

树的子节点读取提供分页和继续读取引用。搜索返回命中项与必要祖先路径，不展开所有同级会话。计数明确所选用户、Bot、容器和归档范围；尚未读取的分支不伪装成零项。

导航分页绑定原查询条件与所读父容器的排序代际。移动或重排使续页失效时，返回明确的重新读取入口，避免跳项或重复项被误当成完整结果。客户端保留稳定对象的选择和草稿，重新读取不会重放管理动作。

### 7.2 结果呈现

目录结果保持精简，按实际用途提供：稳定短引用、名称、会话类型、分类路径、来源 Bot/父任务、执行状态、归档/置顶、最近更新时间。空的可选信息省略，详情由 `read_thread` 继续取得。

```text
准备新版发布 · 正在执行
位置：工作 / Varin / 版本发布
来源：Varin · 发布讨论
工作区：Varin
```

内部保存 typed target 和完整 owner 关系，模型看到可读名称与可直接操作的引用。名称或祖先改名不改变引用，重复组名也能准确区分。原生与外部会话保留真实执行身份，不为了共用列表伪造原生 Run。

现有模型投影会移除目录中的许多内部字段，新分类信息必须显式进入精简投影，不能只扩展原始 DTO。历史冻结工具声明按其原合同继续读取；不向旧调用回执临时添加它无法消费的参数要求。

### 7.3 上下文连续性

目录按需读取。创建或移动工具结果说明本次实际变化，不返回整棵树。分类变化通过 UI 的领域事件更新，不转换成逐请求的全局队友/目录概览。

已进入历史的目录结果保留当时内容，后续改名和移动不会回写旧提示；下一次查询再得到当前位置。Bot 的基础提示只说明可以发现、读取和整理工作，不规定整理频率、分类体系或必须完成的管理流程。

## 8. 三种模式的导航体验

### 8.1 共享目录与不同视角

工作台和 IDE 在现有会话侧栏接入混合树。项目与组使用相同的缩进、展开控制、行高和拖放规则，保留会话阅读和编辑器主体。

Varin 保留 Bot 身份选择、现有助手分组和当前聊天。会话导航可以选择“当前 Bot”与“全部会话”：前者从共享树筛选该 Bot 的直接会话和相关工作，保留必要分类路径；后者浏览完整可见树。切换范围不创建另一套分类。

每种 Shell 可以保留自己的折叠、宽度、排序显示和筛选偏好。名称、图标、父子关系、手工顺序、会话归属、归档与置顶由共享 owner 保存。同一用户在同一 Host 的桌面、Web 和移动端得到相同分类。

Bot 直接会话从工作台或 IDE 打开时，允许保留当前外壳，使用其真实 Bot 身份、发送偏好与原 Thread。进入完整 Bot 档案、记忆或工作面板有明确入口。Varin 中打开派发任务继续沿既有旁侧详情与完整工作台入口，保留返回位置。

### 8.2 选择、搜索与拖放

分组行主要承担展开、选择浏览范围和新建入口；项目行保留项目导航和文件工作区入口。切换浏览范围不重新准备当前会话的执行来源。会话行打开原身份，移动不会造成会话卸载、重建或丢失输入草稿。

拖到容器内部表示移入，拖到行间表示排序，落点提前显示实际动作。移动期间保持原行占位，提交成功后自然过渡到新位置；取消或冲突回到最新有效位置。键盘菜单提供同等的移动能力，触屏在长按成立前保留正常滚动与文本操作。

搜索暂时展开命中路径，清空后恢复原折叠选择。筛选视图中管理容器时，依据服务端完整范围解释操作，不把屏幕上部分可见成员当成整个分组。

### 8.3 图标、来源与视觉轻重

分组默认使用现有图标库中的集合类图标，支持更换用途图标及克制的强调色；不指定时使用随主题变化的中性色。项目继续使用原项目图标/自定义图片。图标和颜色属于共享元数据，用户与 Bot 均可编辑；Bot 可省略它们，不需要为建组额外查询图标或生成图片。

展开箭头、节点图标与名称位置固定，图标不承担展开状态。深层路径通过缩进、面包屑和可聚焦容器显示，窄屏可以进入单个容器查看，而不缩小文字或挤压任务标题。

任务的主头像表示执行者，右侧小头像表示发起 Bot。沿用现有 `AgentAvatar`、`BotFigure` 和 Bot 自定义形象资产；默认保持静态小头像，提示包含实际 Bot 名称，并提供回到发起会话的操作。直接 Bot 会话使用自己的主头像，不重复附一个相同来源头像。

任务列表的来源采用最初创建/派发关系。旧任务被其他 Bot 继续交办时，当前执行的请求者在详情中单独显示，单次消息不重写任务起源。来源 Bot 已删除或资料不可读时，保留可确认的原关系并显示实际缺失状态，不按相同名称寻找替代 Bot。

普通树、平铺、搜索、归档与工作详情使用同一个来源投影。外部 Harness 任务从原 `external_children` 关系取得来源，补齐当前外部列表缺少 `botId` 的接线。列表避免重复头像加载和逐行查询完整历史。

视觉沿用现有轻量行式侧栏：颜色主要落在图标与必要状态上，浅色/深色分别保持文字对比；选中、重排、展开收起沿现有可中断动效连续变化。窗口变窄或性能优化不以去除这些动效作为实现方式。

## 9. 数据与实现归属

### 9.1 原 owner 分工

| 内容 | 目标 owner |
| --- | --- |
| 会话组、混合容器父子关系、共享顺序、会话分类位置 | 原 Rust Catalog 内的会话组织领域 |
| 原生会话标题、归档、置顶、删除及执行关系 | 原 Catalog Thread / collaboration 领域 |
| 外部会话绑定、产品元数据与派发关系 | 原 Catalog external 领域，Host external service 协调真实程序 |
| 项目目录、图标、默认值及设置 | 原 Host Settings 与项目能力；Documents/资源 owner 核验实际来源 |
| Bot 档案、形象及助手分组 | 原 BotService / Storage 记录与形象资源 |
| 无框架依赖 DTO、失败类型和 HTTP 客户端 | `application-client` |
| 导航投影、行组件、拖放、视图偏好 | 共享 UI 与各 Shell 的现有接入层 |

组织领域放在现有 Catalog，便于原生/外部产品会话创建和分类受理在原事务中完成。它只保存轻量引用与组织信息。项目和 Bot 的正文配置继续由原 owner 保存，不复制到 Catalog 形成第二个 writer。

### 9.2 概念数据结构

以下描述职责，具体 wire 名称和格式版本在实现时由原 schema 生成链确定。

- **组织空间**：由协调 Host 与可信 principal 确定。调用方不能通过传入另一个 principal 来选择空间。
- **容器**：稳定 ID、`group/project` 类型、父容器、同级顺序和 revision。组拥有名称/图标/颜色；项目容器引用原项目身份。
- **会话位置**：引用 `native Thread` 或 `external conversation`，保存明确容器与必要顺序；未明确定位的子任务沿真实父任务解析有效位置。
- **对象来源**：从现有直接 Bot 绑定、派发关系、执行 requester 和项目来源投影，包含可确认的发起 Bot/会话。导航不另写可伪造的创建关系。
- **命令与事件**：稳定受理键、操作意图、实际结果、revision 和原 Catalog durable cursor，用于重试、观察与冲突处理。

原生与外部会话使用带类型的引用，避免同形 ID 混淆。内部隐藏执行不因有 Thread 记录就自动拥有公开导航入口。分组节点、项目引用和会话位置需要适配原模型短引用 owner；模型持有引用不会获得额外内容或文件权限。

归档、置顶和删除保持在原会话记录中，组织领域不镜像一套布尔状态。项目名称/图标从项目记录读取，Bot 形象从其原资产读取；分类路径是根据当前祖先生成的投影，不保存多份可相互矛盾的路径字符串。

### 9.3 API 与共享消费者

在 `RuntimeAPIs` 中提供框架无关的会话组织接口，负责容器读取、搜索、创建/更新/移动/解散，以及原会话分类位置。Host 接口做认证与项目/Bot/外部 owner 协调，Rust 验证树与事务不变量。

会话元数据命令继续调用 `ThreadsAPI` 与原外部接口；组织接口的便捷动作也必须返回这些原 owner 的结果。UI 与模型工具共享业务实现和失败分类，不各自维护组列表或排序算法。

导航事件进入原 Catalog 事件及 Host 分发机制。一个当前 Host 的 UI store 负责合并目录变化，已挂载节点读取该投影，不为每一行创建观察流。初始快照和断线补读使用原 cursor/epoch 思路，Host 切换使旧请求及其修改目标失效。

### 9.4 项目注册的跨 owner 边界

项目注册、文件准入与 Catalog 导航不在同一个数据库事务中。添加项目先由原项目 owner 注册稳定项目身份，再将该引用纳入导航；现有项目只需后一步。

命令固定原项目身份与导航意图。第二步失败时返回“项目已登记、分类尚未完成”的真实结果，重试核对原项目并继续分类；不再次建项目，也不删除已成功登记的资产来伪造回滚。需要扩展幂等受理时，在原项目命令/原操作回执中补齐，不另建安装、任务或重试服务。

移除项目同样区分原项目登记操作和导航整理。源记录暂时无法读取时保留项目引用与错误状态；真正移除后按明确操作处理其子项，不能用一次读取失败触发清空。

## 10. 并发、重试与批量整理

人、Bot 和多个客户端都可能同时改树。目录读取携带版本信息，移动/更新检查目标节点及受影响父节点的版本和当前关系。全局目录 revision 用于观察追平，不必让不相关分支的修改彼此冲突。

移动在一个 Catalog 事务中验证旧位置、新父节点、实际同级锚点和无环关系，再提交父子关系及顺序。目标已删除、锚点失效或对象已被别人移动时返回冲突和当前事实，调用方可以重新选择；不能把任意迟到请求当成对最新状态的确认。

同键同意图返回原结果，同键不同意图明确冲突。响应丢失或观察断连时，UI 保留原受理键核对回执；取消等待不声称已提交的移动撤回。用户明确撤销移动时，向原 owner 提交新的反向操作，先核对现有位置，不能覆盖别人之后的整理。

纯导航的多选移动可以在一个 Catalog 事务中原子提交。涉及不同 owner 的批量归档/删除，先固定选择的实际对象集合，再逐对象返回原结果；已成功、冲突、忙碌、失败和结果未知分别保留。重试只继续未确认项，不把部分成功显示成全部成功。

名称可以重复，UI 操作用稳定对象和容器路径消歧。模型按返回引用操作，重试不重新通过名字寻找可能已换人的目标。

## 11. 归档、删除与容器整理

### 11.1 会话归档

归档沿原元数据命令，保留分类位置、执行、来源和历史。归档只影响默认浏览，不停止已经受理的工作；归档中的活跃工作继续出现在原工作概览与必要 attention 中。

归档视图和普通视图使用同一目录、用户范围、来源头像与分类路径。恢复会话回到仍有效的位置；分组已解散时，采用解散事务已经提交的新位置。恢复不重放旧输入或自动唤醒休眠 Bot。

容器本身的移除与“归档其中会话”是不同动作。批量归档显式选择直接成员或整个后代范围，受理时固定对象集合，不让后来加入的会话被旧操作顺带归档。

### 11.2 会话删除

原生会话删除先保留 tombstone 与必要身份，原执行、回执和内容回收沿既有生命周期完成。导航可以立即移除公开入口，后台 owner 继续结算已受理工作。

外部 Harness 使用现有 external service：当前实现要求停止活跃 turn，并等待原交办结算后再删除。统一界面与工具需要返回这种真实差异，不能只在导航树隐藏条目就宣称原会话已删除。[原外部删除路径](../../packages/web/application-host/lib/external-agents/service.ts)与[Catalog 命令](../../kernel/crates/varin-runtime/src/catalog_external.rs)保持权威。

删除会话与停止任务提供各自明确动作。树状列表批量删除若包含子任务，提交前明确实际范围；删除一个导航父项不自动改写执行树的取消语义。Bot 的最后一个直接会话删除后，入口解析继续采用原 Bot entry 规则。

### 11.3 分组与项目移除

分组“解散”移除容器并把直接子项提升到它的父容器，保持相对顺序；项目、会话、文件及执行保留。解散在一个导航事务中提交，不遍历删除会话历史。它是默认的分组移除操作，菜单文案直接说明子项去向。

项目移除使用原项目 owner，导航子项提升到上层；移除登记与删除磁盘文件继续是不同操作。若用户要删除某些会话，通过明确的会话选择与原删除命令处理，不因项目或分组位于另一项目中就递归删除其资产。

## 12. 既有数据接入

### 12.1 保留资产与建立初始分类

Catalog 原升级 owner 增加组织结构和格式合同，转换与标记在同一原存储事务中完成。Thread、branch、原模型请求、执行回执、短引用及内容引用保持原身份。格式号在实施时按实际 main 版本分配，本文不预占。

Host 为初次目录准备提供已读到的项目身份、顺序与现有会话元数据。原 Settings 项目列表仍由其原 owner 管理；项目读取失败、格式损坏与有效空列表分别处理，失败不发布一棵虚假的空树。

初始接入规则：

- 已登记项目形成根下项目节点，沿 Host 已保存的项目顺序。设备本地的额外排序继续作为视图偏好保留；用户进行新的共享排序后，以该次提交为准。
- 普通会话与 Bot 直接交办任务依据已确认的项目关系接入，沿现有侧栏的项目解析规则保持尽可能一致的初始位置。历史 `observer_project_ids` 是读取投影，不直接改造成可编辑的唯一项目字段。
- 多项目或来源不明的记录保留原关联；无法确定正式位置时放在根下，并允许后续整理，不按相似标题猜组。
- 子任务沿原任务关系组织。Bot 直接会话保留原 Bot 绑定，已有助手分组不自动转换为会话分组。当前 Bot 视图仍能立即找到这些会话。
- 原生与外部会话归档、置顶和删除状态来自各自记录，已有档案、项目目录及外部原生历史不复制。

首次初始化只发布一次已核验代际，重复打开读取原初始化回执。旧客户端送来的 Settings 项目数组不包含会话分组，不能被解释为删除全部组。新旧工具声明和私有 wire 按原版本合同处理，不能静默丢弃未知分类字段后假装成功。

### 12.2 用户范围与部署

新组织记录按实际可信用户主体保存，同一用户的不同客户端共享。现有 Host 项目仍是原共享配置，导航引用它不改变项目配置的实际可见范围。

旧无主体记录按既有 Catalog 用户归属规则接入；启用认证后不因第一次访问或看到同名项目，就自动认领别人的会话和分类。独立 Host 保持独立目录；远端资源引用保持连接与资源 Host 身份，不按本机绝对路径导入。

数据升级不发起模型请求，不重放派发，不移动文件，也不自动停止运行任务。候选失败保留旧资产和可核对原因，恢复仍由原升级及受理 owner 完成。

4. 用已保存数据、并发操作和实际平台交互完成验收，将当前合同归回领域文档。每阶段都保留原有会话、来源与执行入口可用。

## 14. 关键验收场景

验证围绕真实 owner 与用户动作，优先扩展现有测试；文档和 DTO 枚举本身不作为行为证据。

- **混合树与来源**：组中项目、项目中组、组中另一个项目均可创建和移动；自身/祖先环在提交时被拒绝。最近项目决定新建默认值，移动已有会话及祖先后，原文件来源、外部 cwd 和活动 Run 保持原记录。
- **Bot 跨会话读取**：同一用户的 Bot 能发现并读取自己的其他会话、另一 Bot 会话及原外部会话；正文、媒体、分页和固定背景使用一致授权。另一个用户的目录与内容不进入结果，消息和记忆操作仍由原合同受理。
- **派发与分类原子性**：同一受理键在响应丢失、重开和容器变化后仍返回原任务与原分类；没有重复 Thread、外部 turn 或派发。明确失败、已受理但准备失败、结果未知分别呈现。
- **多人/多端整理**：UI 与 Bot 并发移动同一对象返回真实冲突，不同分支可独立修改。重命名祖先不使短引用指向其他对象，撤销不能覆盖别人之后的移动。
- **列表一致性**：同一任务在工作台、IDE、Bot、搜索和归档中可找到，来源小头像与真实发起会话一致；外部任务同样可识别。内层任务显式移出后，原任务详情仍保留执行关系。
- **生命周期**：解散组提升成员，移除项目入口不删文件；归档不停止任务。原生删除后的在途工作继续由原 owner 结算，外部活跃 turn 删除返回原忙碌状态；批量结果保留部分成功与未知。
- **旧数据与断连**：既有项目、Bot 助手分组、普通/归档会话、任务树和原始回执保持身份。格式损坏不被空目录覆盖；设备离线保留项目入口；切换 Host 后旧响应不能修改新 Host 的树。
- **呈现与性能**：实际组件核对浅深主题、长名称、深层导航、键盘与触屏拖放、输入法和可中断动效。目录读取只取所需元数据，不为每项加载历史正文或发起模型请求；未打开分支可按需加载。采用代表性的真实层级和会话量检查，不另设无依据的硬上限。

实现完成应能连续演示：用户在工作台创建“工作 → Varin → 版本发布”，Bot 将任务派发到该组；任务项显示 Bot 来源；IDE 能打开同一执行；另一 Bot 按路径发现并读取讨论；用户把任务归档后，各端及模型查询按明确归档范围得到一致结果。全过程沿原 Thread/外部会话、原资源和原回执运行。
