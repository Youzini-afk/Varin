# Varin：安排与关注、外部事件和模型唤醒

状态：2026-11-07 设计方案，待实施。本文在[长期总助手设计](bot-assistant.md)上细化长期安排、插件入站事件和模型触发的完整链路。现有实现见[Bot](../bot.md)、[运行时](../runtime.md#waitfollow-up-与后台工作)、[扩展](../extensions.md)；本文的新增行为不作为已实现能力介绍。

## 1. 要解决的问题

模型在一次推理结束后不会继续感知时间和外部世界。长期助手的连续性，需要平台保存工作与安排、接收变化，在需要处理时提供新的输入，并保留处理后的结果和后续安排。

Agent 经常需要“等测试结束后继续”“文件生成后读取”。Bot 还需要“留意这个仓库的反馈”“收到客户回复后继续”“每天早上汇总进展”。后一类关系可以持续跨越很多轮对话，来源可能位于邮件、GitHub、社媒、其他设备或已有任务中。

产品围绕以下问题组织：

- 正在等待或关注什么，为什么关注？
- 什么变化需要进入模型，什么时候进入？
- 交给哪个 Bot、哪个会话或已有任务？
- 这次处理后是否需要告诉用户、向外回复或继续安排工作？

Bot 保留直接处理小事、复用既有任务和新派发工作的自由。触发机制提供事实与交办背景，不规定固定的判断、派发、审查、汇报流程。

## 2. 现有基础与缺口

| 现有能力 | 实际职责 | 本次接续方向 |
| --- | --- | --- |
| 持久 Wait | 等待真实进程、子任务、回复、提问或上下文就绪 | 继续承载执行过程中的等待和观察 |
| `follow_up` | 保存指令与时间、文件、日志、指标、任务结果等条件；支持一次性和重复触发 | 增加长期归属和插件事件来源 |
| Calendar | 管理一次性、每日、每周、Cron、时区、错过执行和 occurrence | 继续计算时间和保存日程实际触发，不另建 Bot 计时器 |
| Catalog 输入与 activation | 保存输入、区分被动信息与激活请求，将输入交给运行中会话或续接空闲会话 | 作为事件处理的统一执行入口 |
| Bot 工作回报 | 将任务结果、用户介入和关联工作变化送回相关 Bot 会话 | 保留原交办关系与结果身份，参与事件汇集 |
| 插件服务、事件声明与凭据 | 描述能力，执行服务调用，管理连接和账号凭据 | 补齐长期入站事件的接收、恢复与投递桥接 |

当前 `follow_up` 定义要求 `source_run_id`，并保存当时来源和上下文范围，适合具体工作的接续。长期邮箱关注不应以那次 Run 继续存在、仍有执行环境为成立条件。

现有插件服务的 `events` 可以描述事件，但没有完成“长期监听 → 持久接收 → 指定会话输入”的通用闭环。MCP 资源通知已有被动输入路径，当前不会自行启动新的模型工作；这一语义应保留，明确建立的处理安排才赋予它触发用途。

实现继续由 Rust Catalog 拥有安排、触发、输入和执行事实，Host 负责外部服务适配与准备，ContentStore 保存正文与附件。UI 读取投影；插件不成为第二个会话执行器。

## 3. 产品对象与生命周期

### 3.1 安排与关注

“安排与关注”是用户管理持续工作意图的入口。一条定义表达：关注的来源或时间、可直接判断的条件、自然语言处理意图、接收位置及处理时机。模型和用户操作同一份定义。

归属分为：

- **当前工作的接续**：与原任务关联，文件来源、进程、结果和等待沿原对象保留。
- **Bot 的长期安排**：由 Bot 持有，指定接收会话或任务，跨越多次执行。

创建者、创建时的 Run 和原交办作为来源保留；长期安排的存续不依赖创建 Run 保持活动。UI 可以在 Bot 尚无首轮 Run 时建立安排，不先制造一轮用户输入。

已有 Calendar 资产继续是日程定义的来源；长期事件关注由扩展后的条件接续定义保存。产品页面聚合两类定义，不重复复制日程正文、执行状态或计时进度。时间驱动、事件驱动的输入最终进入同一执行入口。

### 3.2 连接、关注与每次处理

连接描述哪个账号或服务可用；关注描述用户希望处理什么；一次触发记录实际发生了什么；一次模型处理沿原 Run 保存。连接可以被多条关注共用，一条关注也可以触发多次处理。

关注不要求建立正式事项、Goal 或独立 Agent。与已有事项有关时保存原引用，实际运行状态仍由原任务拥有。

注册关注返回真实受理结果。Bot 可以自然地修改或撤销安排；“我会明天再看”“等对方回复后继续”需要通过实际安排能力落地，普通回复文字本身不创建定时器，也不通过扫描承诺句子自动执行。

### 3.3 暂停与结束的含义

| 操作 | 定义与接收 | 模型及任务 |
| --- | --- | --- |
| 关闭页面、切换会话 | Host 上的关注继续 | 不改变执行 |
| 停止当前答复／本轮任务 | 长期关注保留，未交付事件保留 | 停止本轮及已绑定批次的继续执行，不立即把同批内容重建为新一轮 |
| 暂停某条关注 | 保留定义、同步位置和已收待处理；暂停该关注的新接收与投递，共用连接按其他使用者需要继续 | 已启动工作保持可见，由用户单独停止 |
| 恢复关注 | 从保存位置恢复；支持历史补拉的来源补齐暂停期间变化，时间安排沿既有错过策略 | 按原处理方式汇集与投递 |
| 休眠 Bot | 保留定义与已收事件；仍运行的账号同步可保存后续事件 | 暂停该 Bot 的模型准入并按既有生命周期处理其执行 |
| 停用连接或插件 | 保存同步位置和未完成交付，显示来源不可用 | 独立运行的已有任务仍按自身状态管理 |
| 删除关注 | 撤销未来触发，取消尚未交付的对应输入，释放该关注的监听引用 | 已交付工作保留原身份与结果；不冒充已经停止 |

恢复关注若不能补拉，显示来源提供的实际覆盖范围；恢复时间不被当成此前没有发生变化。提供“仅从现在继续”的明确操作，供用户放弃积压，而不是静默丢弃。

停止一轮不撤销持续关注。之后实际发生的新事件仍可按开启的安排处理；用户另行暂停目标会话、关注或 Bot 时，才保持对应的暂停。实现需区分取消中的原批次和真正的新触发，避免用新触发名义自动重试刚被停止的工作。

Bot 休眠与账号同步分属不同生命周期。实现中要将共享连接监听从 Bot 的实际模型／任务 worker 中分离；暂停某个 Bot 不关闭其他关注正在使用的同一账号。Host 退出后本地监听停止，之后按第 10 节恢复。

## 4. 插件入站事件能力

### 4.1 责任分配

插件提供可关注的事件源及其参数说明，例如“某个邮箱的新消息”“仓库事件”“外部聊天消息”。核心使用可扩展的来源标识，不为 Gmail、GitHub 等服务商逐个增加固定触发枚举。

插件负责服务商协议、连接配置、凭据刷新、推送或增量拉取、远端内容解析和必要的远端注销。Host 提供后台生命周期、网络入口适配、持久接收和原凭据服务。账号配置继续在插件自己的页面维护；市场页面不承担邮箱登录状态等内部业务。

SDK 围绕以下实际动作提供接入：

1. 声明事件源、可选连接、支持的筛选条件和接收／恢复方式。
2. 从平台保存的位置启动或恢复监听，必要时执行一次增量读取。
3. 提交带实际来源身份的事件及其正文、附件或原文引用。
4. 在平台确认接收后推进同步位置；关闭监听时释放该使用者的资源。

服务事件声明可以复用已有契约；面向 UI 的短时通知不会自动成为可持久触发模型的事件源。长期来源需要实现实际接收和恢复合同。

### 4.2 运行方式

支持服务商推送、长连接和增量拉取。方式由服务能力和部署条件决定，不要求每个插件实现全部方式。

- 远端推送使用真实服务的回调协议。只在事件已持久接受后确认成功；服务商要求快速确认时，先完成接收，后续处理异步进行。
- 增量拉取使用服务商游标或修改位置。轮询频率根据接口能力、服务商限制和用户设置选择；没有变化的轮询不创建模型请求或永久触发日志。
- 同一连接的底层同步可共享；各关注保留自己的范围、处理意图与交付位置。
- 在 Host 的可取消 worker 中完成网络等待、解析和附件准备。Catalog 事务只提交短事实，不持锁等待第三方服务。

本机没有公网回调入口时，支持增量拉取的服务可正常使用拉取。必须依赖公网回调的来源，应在连接配置中说明实际要求；部署到服务器、使用用户配置的隧道或服务商中继按既有网络能力处理，不自动部署新的平台中转服务。

### 4.3 账号与来源身份

沿用现有连接与凭据命名空间。模型看到连接名称和非秘密身份，不取得密钥、令牌或 OAuth 原始材料。

关注引用原连接和实际账号。账号被替换时，原关注显示需要重新关联，避免将旧邮箱的关注无声转到新邮箱。插件提供外部消息的发送者、账号、会话或对象身份；核心保留这些事实用于显示、路由和去重。

## 5. 从事件接收到模型输入

```text
插件／原生事件来源
    ↓ 接收正文、附件与来源位置
Catalog 接受事件，ContentStore 保存内容
    ↓ 匹配关注、保留交付关系
按处理时机选取本次事件批次
    ↓ 固定实际接收会话和批次范围
原 input_queue / ingress / activation
    ↓ 当前执行接收，或空闲会话续接
模型处理 → 直接完成／联系已有任务／派发工作／调整关注
```

接收到事件、交给会话、会话处理、实际外部动作，是不同事实。界面据此显示“已收到”“待处理”“处理中”和实际结果。

### 5.1 接收与去重

同一外部事件用稳定来源身份识别，包括连接账号、来源对象、事件 ID 或服务商提供的修订。推送、补拉、重试交叉到达时，重复接收复用同一事实。

平台确认接收后才推进相应同步位置。正文保存与 Catalog 引用发布沿现有 ContentStore 机制完成；中途失败不能先推进游标使事件丢失。没有稳定事件 ID 的来源由插件按其协议生成可复现身份，不用接收时间充当每次都不同的新事件 ID。

去重不压掉同一对象的真正新修订。一个事件命中多条关注时，原事件正文共用，关注与交付关系分别保留；同一目标本次处理可合并相关意图，不因此遗漏另一个合法目标。

### 5.2 条件与处理意图

确定条件由代码匹配：连接、发件人、标签、仓库、事件类型、状态转换或已关联对象等。插件披露其真实支持的条件，平台不创造所有服务都必须支持的筛选字段。

语义要求保留自然语言，例如“明确的问题先调查”“可能影响周五发布的内容告诉我”。触发后由模型结合材料判断，不将这些意图硬编译为固定分数或流程。

需要从大量事件中做语义初筛时，可以选用辅助模型并沿现有用途模型、思考设置、预算和用量记录实现。默认不添加逐事件的双重模型判断。具体采用主 Bot 直接处理还是辅助筛选，作为实际负载下可配置的处理方式，而非所有关注的前置环节。

### 5.3 处理时机

| 方式 | 行为 |
| --- | --- |
| 到来即处理 | 有新输入时尽快进入目标会话的可接收边界；空闲目标可开始一轮 |
| 汇集后处理 | 按关注配置的窗口聚合相关变化，窗口截止后投递 |
| 到约定时间处理 | Calendar 到点选取尚未处理的来源变化，例如晨间汇总 |
| 留待下次处理 | 作为被动信息保存，不因此创建一次模型请求 |

普通外部聊天输入默认及时接收；报告汇总或高频状态变化可以选择汇集。用户和 Bot 可以根据交办调整，不硬编码全平台等待秒数、批次数或事件配额。

汇集窗口从第一条待处理变化开始计算，后续持续到达不无限推迟处理。界面显示本次预计处理时间。底层截止唤醒使用既有计时与调度能力；服务商请求频率与模型处理时机分别管理。

“到约定时间处理”需要区分有新内容才处理和即使没有新内容也执行交办。例如“汇总新增邮件”可以跳过空批次，“每日检查运行状态”则仍执行其原安排。保留用户意图，不把无新增统一判定为无事可做。

### 5.4 合并与固定批次

- 多条聊天消息保留原顺序、正文和附件；可以同批进入，不能用最后一句覆盖前文。
- 独立邮件、评论和工作请求保留各自身份。
- 可覆盖的状态通知，在尚未交付时突出当前状态及期间重要转换。例如 CI 先失败又恢复，报告该变化关系，而不是让模型误以为失败仍持续。
- 同一输入中的相关关注可共用原文，同时保留各自交办目的。

选择批次时固定实际事件集合和来源位置。新事件留在下一批；旧批次完成不把后来收到的事件一并标为已处理。已经进入请求的批次不被后续通知原地修改。

事件内容过多时沿已有材料分页、附件与请求容量处理，保留未处理位置。不能默默截断正文后把整批视为完成，也不要求先对所有事件调用一次模型生成摘要。

## 6. 路由、多会话与既有任务复用

### 6.1 接收位置

在某个会话内建立关注，默认选择该交办会话。在账号配置或全局页面创建关注时，需要选择具体 Bot 和接收位置。保存实际 Thread/branch 身份，不依赖“第一个 Bot”“最近打开的聊天”或当前 UI 外壳。

接收位置可以是 Bot 会话，也可以是已经明确关联的普通任务。不同 Bot、不同会话分别接收自己的交办事件；来源连接可以共享。

读取和复用范围仍为同一用户的普通工作台／IDE 会话与 Agent 任务，包括用户直接创建及其他 Bot 派发的任务。其他 Bot 的入口聊天继续排除在任务发现之外。事件路由不引入新的按 Bot 划分任务可见范围的限制。

### 6.2 外部聊天与外部对象

外部聊天可以在接入时明确映射到已有 Bot 会话，或选择首次接触时创建一个对应会话；映射一旦建立，后续沿同一会话继续。多个来源共享一个接收会话也可以由用户配置，不强制“一个账号一个聊天”。

普通邮件或 issue 事件默认先进入关注指定的位置，不因每个外部对象自动创建 Bot 会话。Bot 决定交给已有任务后，可以保存该来源对象与任务的明确关联，后续变化沿该关联续接；关联沿原任务引用保存，不建第二份任务池。

已有任务自己在等待维护者或客户回复时，可以由它继续处理，最终结果沿原交办关系送回 Bot，不需要每次经过 Bot 重新阅读再重新派发。

目标被归档、删除或不再可用时，定义显示具体接收问题并保留待办，提供重新选择入口。不能悄悄改投另一个 Bot 会话。重新指定目标影响尚未交付的事件；已经交付的输入和结果继续属于原会话。

### 6.3 运行中与空闲目标

| 目标状态 | 输入处理 |
| --- | --- |
| 模型或工具正在执行 | 保留原请求与操作；输入进入队列，在原可接收边界消费 |
| 等待可结束的观察 | 按现有 observation 机制结束等待，让相关新输入进入；不取消被观察工作 |
| 原会话空闲 | 以原 Thread/branch 接续，使用真实历史与当前有效配置 |
| 尚无首轮 Run 的 Bot 会话 | 沿原冷启动准备进入首轮，不伪造用户消息 |
| 用户明确暂停或 Bot 休眠 | 保存待处理事实，显示实际原因，不绕过暂停启动执行 |
| 外部 Harness 任务 | 使用其实际发送／resume 能力；不能续接时显示实际原因和可改选目标 |

同一分支沿原执行所有者顺序接收。不同会话、独立任务按现有运行能力并发，不为新事件创建覆盖原会话的平行 writer。

## 7. 上下文、提示词与记忆

### 7.1 唤醒输入

输入包含本次需要理解的四类内容：触发原因、相关原交办、实际新增材料、已有工作引用。它们按实际情况自然组织，不要求所有事件都填一套固定报告模板。

例如：

> 你此前安排关注这个仓库的新 issue，先调查明确的问题。自上次处理后收到两条新 issue。下面是新增内容及来源；其中一条关联正在跟进的任务。

邮件可直接提供本次邮件正文和附件引用；仓库事件提供新增评论或状态变化。来源时间与本次接收／触发时间保留在这次输入中，避免模型将补拉的旧消息误判为刚刚发生。

真实用户通过已连接聊天渠道发送的消息，在已建立的发送者对应关系下沿用户输入处理。任意邮件或评论内容作为外部材料保留来源，不因字符串像命令就取得用户身份。

### 7.2 缓存与材料选择

稳定系统指令保持稳定。连接目录、全部关注、全部积压和所有任务历史不在每轮重新注入；模型需要管理安排时按需查询。

本次事件只追加相关安排和变化。原会话历史、既有摘要和按需召回的记忆继续有效；处理完成不创建全新的“Bot 总上下文”副本。自然语言意图较长时沿原材料引用和容量管理处理，不为本功能新增固定 Token 硬切规则。

大量来源的语义筛选若使用辅助模型，只提供实际选定批次与处理目的。筛选结果保留原事件引用；任务判断所需材料仍可由接收模型读取。

### 7.3 提示词与能力披露

简洁说明 Bot 能建立、查看、修改和结束安排，能在事件后自行处理、复用任务或联系用户。不要要求每次回答都建立关注，不规定先分类、再评分、再派发的流程。

整理现有接续输入中的长段防御性说明。执行身份、重复触发、取消和权限的机械判断由运行时承担；输入着重表达原交办、来源事实和当前状态，必要的来源区别简短说明一次。

事件来源和参数沿已有工具目录按需披露。常驻说明让模型知道存在安排能力；完整服务商字段只在选择实际来源时读取，不将所有插件事件 schema 加进每轮请求。

沿 `follow_up` 扩展注册、读取、修改、暂停、恢复、取消和积压处理能力；日程继续调用既有 Calendar 操作。实际工具名和参数由原契约细化，模型不需要填写完整执行策略对象或猜测回执版本。

### 7.4 长期记忆

订阅定义与待处理事件归运行时，不写成记忆来充当计时或触发记录。处理后有长期价值的信息再进入现有主动／自动记忆链。无新语义内容的轮询、重复通知和内部交付不会不断提炼成新记忆。

## 8. 处理结果、对外回复与循环

模型处理事件后，可以直接完成小事、续接现有 Agent、另派工作、调整关注或结束这轮。保持现有静默处理能力：完成计算不必生成聊天气泡，后台活动仍可在动态里查看。

批次接收沿原输入消费回执，处理状态关联接收 Run 和实际产生的工作，不要求模型为每批事件再调用一个确认工具。若本轮将事情交给已有 Agent，界面展示该工作引用与当前状态；这轮事件已被处理，相关事情仍可以继续推进。

对外回复沿相应插件的发送工具，保留原邮件、聊天或 issue 的回复关系。接收事件与发送回复分别拥有真实回执，收到一条事件不会机械地对外回复一次。用户已交办的自动答复按交办执行，不为每条正常回复增加额外确认流程。

外部服务返回 Varin 自己发送的消息或更新时，保留其发送者和原动作回执关联。对同一变化的回显不再次触发同一处理；用户明确关注自己的提交等真实后续状态时仍可接收。不能用“忽略全部自己的事件”替代来源关联。

一批事件经模型读取后，处理结果沿原 Run 和工具回执保存。失败或取消保留已消费批次和已发生的操作。重试沿原执行恢复，不能把同一批事件重新包装成全新交办后重放已发邮件或评论；未知外部结果由其原操作查询和对账。

## 9. 界面与交互

### 9.1 入口

Agent 的“定时与接续”继续展示与当前工作有关的等待和安排。Varin 的对应管理入口升级为“安排与关注”，整合 Bot 日程、长期来源关注和相关任务等待；复用原页面与组件，不再增加一套独立的日程中心。

Bot 面板展示紧凑的相关安排，完整列表提供“本会话／该 Bot”范围及搜索。查看其他范围不改变接收目标，不把全部邮箱动态展开到主聊天。

### 9.2 列表与编辑

每条优先展示自然语言名称、来源、下一次时间或触发条件、当前状态。已积压、来源断开、暂停、目标不可用等情况给出具体原因和对应操作。未取得来源健康状态时不显示虚构的健康标记。

点击展开原位编辑：处理意图、来源条件、接收位置、处理时机和重复方式。采用已有可打断展开／收起动效，保存状态在当前条目内反馈；草稿不因来源状态刷新被覆盖。

创建时根据来源披露实际需要填写的内容。模型在对话里建立安排之后，聊天可以给出简洁的真实安排引用，点击查看或修改，不再让用户重复填写一遍同一表单。

账号认证和插件内部状态留在插件配置页。本页面显示影响该关注的连接状态并提供对应配置链接，不在市场卡片或每条关注里嵌套登录表单。

### 9.3 待处理与触发记录

展开能看到最近实际触发、接收时间、当前批次、关联的处理会话和结果。提供“现在处理”“暂停”“取消”及明确的积压清理操作，行为与原队列保持一致。

高频变化只更新条目的紧凑状态，不反复播放整条入场动画，不逐条增加全局通知。Bot 正在处理时显示本次原因，例如“处理客户回复”；完成后仅在有公开输出时进入用户聊天，后台结果留在动态中。

触发列表、队列和结果依照原记录投影。前端不拥有计时器、监听生命或重试调度；Web、桌面与移动端使用相同接口。
新增名称、状态与操作说明进入既有 i18n；来源自己的显示名称与平台状态文案分别处理。

## 10. 部署、离线与恢复

事件监听在配置连接的 Host 上运行，唤醒和会话执行由接收任务的实际运行时承担。前端、资源 Host 或电脑控制服务可以位于其他设备，插件事件不依赖聊天页面常驻。

跨 Host 接收沿既有认证连接和传输能力交付事件，发送方在接收端确认持久接受前保留待交付位置。断连后以原事件身份恢复，不通过创建假本地会话绕过远端不可用。

应用或服务器停止期间：

- 可查询历史的来源恢复时从已保存位置补拉。
- 只有实时推送且服务商不会补发的来源，显示实际中断区间。
- 已持久收到的事件重启后仍可投递，不重新读取所有账户历史。
- 定时沿原 `skip`／`coalesce_once` 策略处理错过的时间点；事件补拉与日程补执行分别保留含义。

补拉后按原处理意图汇集。例如停机期间的一组状态变化可以在恢复后一次处理，原聊天消息仍保留顺序。是否放弃积压由用户明确操作；不引入未经讨论的按天自动丢弃策略。

关闭某条关注只释放其监听使用关系。多条关注共用账号连接时，最后一个使用者结束后才释放不再需要的共享监听。停用插件沿原退役流程结束网络等待并保留已接收事实，重新安装恢复时重查实际来源能力。

## 11. 持久化与资源回收

在现有 Catalog 的定义、occurrence、事件、输入及交付事实中扩展所需关联。正文、附件放在 ContentStore／材料 owner；Host 不另建一份 Bot 待办数据库，插件缓存不成为执行是否完成的权威。

长期定义需要保存归属、来源、条件与意图、目标、处理方式和恢复位置。事件接收需要稳定来源身份和正文引用；交付需要关联原定义、原事件集合和实际输入。字段围绕这些用途确定，不为未来可能的策略预留大批空字段。

外部原文、同步暂存、批次材料和运行时回执分别按真实引用回收：

- 已被会话、产物或有效记忆来源引用的材料按原保留规则管理。
- 没有后续引用的下载临时文件、派生预览和已结算批次中间材料可以释放。
- 服务商提供可靠位置时，已结算接收进度可归并为水位，减少逐事件交付记录。
- 无法用水位表达去重的来源保留必要的紧凑事件身份；不能为了删除小记录导致旧推送再次执行。
- 未变化的轮询、相同状态重读不生成永久正文和大量空回执。

清理关注不删除用户已收到的会话历史；删除会话或明确清理事件历史时，沿原引用关系释放材料。保留范围和真实占用可解释，不承诺无限历史零增长，也不借这次设计强制设定保留天数或数量上限。

## 12. 工程落点与实施顺序

| 层 | 主要改动与复用 |
| --- | --- |
| `varin-runtime` Catalog | 扩展长期定义归属和插件事件来源；接收、匹配、汇集、交付与回收关联；接入原 ingress、activation、Wait 和 Bot 生命周期 |
| Calendar | 沿原定义、时区、到期与错过策略提供定时处理，不复制 scheduler |
| `protocol` / `application-client` | 统一来源发现、安排编辑、待处理、触发记录及控制 DTO/API |
| `extension-contract` / `extension-sdk` | 扩展实际事件源接收与恢复合同，复用服务声明、连接凭据和能力发现 |
| Application Host | 连接监听、推送接入或拉取准备、正文与附件处理、跨 Host 交付、插件生命周期 |
| UI | 在现有接续／日程与 Bot 面板中实现安排管理、状态、待处理和结果导航 |

按依赖顺序完成以下工作，交付覆盖完整链路：

1. **定义与生命周期**：区分任务接续和 Bot 长期归属，去掉长期定义对创建 Run 存续的依赖；保持原临时等待语义。
2. **插件来源与持久接收**：打通声明、账号选择、后台运行、事件接受、同步位置及恢复；复用原网络与凭据实现。
3. **匹配、汇集与路由**：实现四种处理时机、固定批次、实际接收目标、外部聊天映射和既有任务关联。
4. **输入与模型能力**：接入原会话激活、原工具操作和简明输入组织；处理回报、失败和静默结果。
5. **产品界面与配置**：补齐用户与模型共用的创建、编辑、暂停、恢复、立即处理和清理操作，覆盖移动和远端前端。
6. **升级与资源结算**：由 Catalog 原 owner 自动升级旧定义，保存原 ID、触发证据、已交付输入和取消状态；不重放历史发生记录。实施完成后将当前合同归入领域文档。

旧 `follow_up` 升级后保持原任务接续、一／多次触发及来源含义。不能仅凭创建者属于 Bot 就把一次性等待升级成永久监听；长期归属通过新的创建或明确修改建立。

具体邮件、社媒、GitHub 接收适配由相应插件交付。这份设计负责它们可接入的真实能力及产品闭环；不以一个示例插件页面代替平台事件来源、恢复和执行接线。

## 13. 有判别力的完成场景

实施验证围绕实际链路复用已有 Catalog、插件生命周期和 UI 行为测试；按变化风险选择，不以新增测试数量或全量巡检作为完成标准。

| 场景 | 应达到的结果 |
| --- | --- |
| 用户交办邮箱关注，原对话结束、压缩或切换模型 | 关注保留；事件进入指定会话，执行采用当前有效配置 |
| 同一事件由推送、补拉和重试到达 | 原正文只接收一份，同一关注的交付不重复；真正的新修订仍可处理 |
| 事件命中多条关注和多个目标 | 正文可共用，每个合法目标及处理意图仍被保留 |
| 固定批次已进入模型时又有新事件 | 新事件仍待处理，旧批次完成不越过其边界 |
| Bot 正在思考、执行工具或等子任务 | 沿原边界接收；等待可被唤醒，真实工具和子任务继续由原 owner 管理 |
| 多 Bot、多会话及用户创建的任务 | 交付给配置和交办所指的实际会话，可复用普通任务，不按 UI 当前视图改投 |
| 用户停止本轮、暂停关注或休眠 Bot | 三类行为各自生效；被停止的原批次不自动重开，后续新触发遵循持续安排及实际暂停状态 |
| 插件失联、账号替换、Host 重启或接收方离线 | 恢复原位置与未交付事件，来源问题可见，不换账号、不伪造接收成功 |
| 目标会话删除，或关注修改时已有在途批次 | 明确显示待重新关联；原已交付工作不被改写 |
| 一组 CI 变化、数条聊天和不同邮件同时到达 | 状态可汇集，独立消息与指令不被覆盖，下一次处理不无限延后 |
| 回复邮件成功后连接中断，并收到自身消息回显 | 恢复原回执，不重复发送，不被同一回显持续唤醒 |
| 长期运行后删除关注并清理不再保留的历史 | 无引用材料实际回收，必要接收位置保留，普通轮询不堆积无用账本 |

外部服务的真实回调、历史补拉和发送确认，在对应插件适配时依据具体协议验证；实际覆盖范围记录在该来源的能力说明中。
