# 插件中心、公开收录目录与作者发行来源

状态：目录、发行交付、插件中心及通用 Host 凭据接线已实现；生产站点部署与具体插件的生产 OAuth 交付另行验证。原设计日期：2026-11-06。源码基线：`d0d5f579d`。

本文整合插件界面、内置与外部插件管理、公开市场和发行包安装更新。连接类插件通过现有 Host 的授权与凭据机制接入。当前已实现的扩展机制见[扩展](../extensions.md)和[作者指南](../ops/varin-extension-authoring.md)。

需求背景见 [#288](https://github.com/Youzini-afk/Varin/issues/288)。[Gmail PR #285](https://github.com/Youzini-afk/Varin/pull/285)提供插件业务实现参考。

## 1. 核心决定

Varin 提供应用内插件中心和独立的公开插件市场。市场帮助用户找到插件，Application Host 管理安装与执行，作者自己的发行来源提供版本和安装包。

已经确定的职责如下：

1. **市场列表的名称、图标、简短介绍、作者和分类由我们的收录仓库维护。** 打开列表和搜索时不批量读取作者仓库、README 或 Releases。
2. **详细介绍、使用文档和源码通过链接打开作者仓库。** 市场不另建一份需要同步维护的长篇详情。
3. **安装与更新直接读取登记的作者发行来源。** 作者正常发布新版，不需要向我们的收录仓库提交版本 PR，也不需要等待我们的定时同步或网站重新部署。
4. **插件中心只呈现平台管理状态。** 账号连接、邮箱、授权失效及其他插件业务状态，由插件自己的配置页面负责。安装后的通用入口是“配置”，不是平台推断出的“连接 Gmail”。
5. **沿用现有扩展运行时与生命周期。** 补发现、发行来源解析、交付和公共连接能力，不再建立第二套安装目录、执行实例或插件权限系统。

本次自动化主要有两种：收录资料合并后自动发布市场网站；用户使用安装或更新功能时，Host 自动解析作者发行来源。市场没有持续监控所有作者仓库的中心版本同步服务。

## 3. 数据来源与请求路径

### 3.1 谁维护什么

| 数据 | 权威来源 | 读取时机 |
| --- | --- | --- |
| 收录身份、名称、短简介、图标、作者、分类、仓库链接 | 我们的收录仓库 | 进入发现页，或刷新目录 |
| 作者发行位置与选择规则 | 收录资料；安装后保存到该安装记录 | 首次安装时取得，后续更新使用已保存来源 |
| 详细说明、使用文档、问题反馈 | 作者仓库及其文档链接 | 用户点击链接 |
| 版本、兼容范围、目标平台、下载文件、摘要、更新说明 | 作者的发行来源与发行包 | 单个插件安装预览、安装或已安装插件更新检查 |
| 已安装版本、启停、候选版本、加载错误 | 当前 Host 的扩展 catalog 与实际 generation | 已有扩展观察链路 |
| 插件设置、账号和业务状态 | 插件的配置页面及其服务 | 用户打开配置页或插件执行所需业务 |

“公开收录目录”与“Host 的安装 catalog”是两个已有明确用途的数据集合。前者不记录用户装了什么，后者不因目录变化自行安装、删除或替换代码。

### 3.2 两条直接路径

```text
作者提交收录资料 PR → 我们合并 → Cloudflare 构建网站与目录
                                           ↓
                               网站 / 应用展示插件列表

用户点击安装 / 检查已安装插件更新
                  ↓
      当前 Host → 作者 Releases / npm / 明确的其他来源
                  ↓
          解析具体版本与发行包
                  ↓
       现有 artifact、候选与执行生命周期
```

浏览市场不访问所有作者仓库。安装和更新不向市场询问“最新版本”，也不由市场抓取后再转发一份版本信息。

市场网站本身主要提供浏览、外链和安装入口。具体版本选择与兼容性由接收安装请求的 Host 完成，网站不猜测用户要安装到哪台机器。

### 3.3 安装后的独立性

安装记录保存逻辑发行来源，以及当前实际安装的版本和内容身份。来源信息在 Host 保存，不只保存一个市场条目 ID。

因此，公开市场暂时离线、条目未收录或后来退出目录，不影响已安装插件运行及从原来源检查更新。下架改变发现结果，已有安装的启停与移除仍由用户控制。

市场修改某条目的仓库地址时，不静默改写已有安装的更新来源。更换维护仓库是一次明确的来源变化，用户可以在管理界面确认迁移；普通版本发布不需要这一步。

## 4. 应用内插件中心

### 4.1 信息结构

设置导航使用“插件”。主页面只有两个日常入口：**发现**和**已安装**。记住用户上次访问的页签、筛选和滚动位置；从市场安装链接进入时直接定位目标插件。

```text
插件                   当前 Host：……        从链接或本地安装  ⋯

发现   已安装
──────────────────────────────────────────────────────────
搜索插件……                              用途筛选 ▾

图标  名称                                  安装 / 管理
      简短介绍，最多按两行展示
      作者 · 用途                          查看仓库 ↗
```

这是排布关系示意。实际尺寸沿用设置页 typography、间距和容器断点，不再新增一套缩放规则。

“服务路由”“工作台组合”“目录来源”“诊断”放入高级管理入口。其中与单个插件有关的权限、依赖和加载错误，也能从该插件的管理操作直接进入。

### 4.2 发现页

列表使用紧凑条目，图标、名称和简介形成主阅读顺序。作者与分类降低一级，操作区域保持稳定。搜索同时覆盖收录资料中的名称、简介、关键词和作者。

目录中的图标随市场静态资源交付，不在浏览时回源每个作者的网站。长名称自然截断，简介最多显示两行，完整收录简介可按需展开；不设置未经依据的作者字符配额。详细文档始终通过仓库链接打开。

列表不展示依靠遍历所有上游才得到的“最新版本”、实时下载量或运行健康标记。已安装标记来自本地 Host 状态，安装按钮可以启动该插件的一次版本解析。

搜索无结果与目录加载失败分别呈现。读取失败时保留最近一次有效目录并显示更新时间和重试入口，不清空列表制造“没有插件”的假象。尚无缓存时正常显示加载或失败，不阻塞设置页其他功能。

### 4.3 已安装页与内置能力

已安装提供“全部 / 外部 / 内置”筛选。默认布局中外部插件先展示，内置能力单独成组；搜索能够同时命中两组，不因分组折叠隐藏搜索结果。

来源和维护者是两个维度：

- 内置表示随 Varin 发行，版本由应用发行管理。
- 外部表示用户另行安装，可由官方或社区维护。
- 官方 / 社区标记描述维护归属，不用“已收录”替代代码信任。

内置能力使用面向用户的名称和用途。用户仍可查看底层扩展记录、服务依赖与原始错误，相关事实进入诊断详情，避免把所有 service ID 和 generation 常驻铺满页面。既有可配置、可替换能力继续可达，不因简化界面移除功能。

内置条目没有独立卸载和作者 Release 更新按钮，沿用发行归属。外部条目提供启停、配置、检查更新、卸载和来源信息。普通启停后显示真实准备/加载结果；启用但按需等待的插件不显示为故障，也不伪装成已经运行。

已安装条目的市场名称和简介使用与其身份、来源相符的收录资料；未收录、离线或无匹配资料时，使用已安装 manifest 中的名称和简介。不会为补一行介绍去访问作者仓库，也不因为另一个目录出现同名 ID 就改用不同发布者的介绍。

### 4.4 配置入口与业务状态

安装后统一提供“配置”，打开该插件已经注册的 `settings-page` contribution。多个配置页面可由插件声明主要入口，并提供页面选择；优先复用既有设置页标题、导航和挂载合同。

账号状态、连接操作及业务信息由插件自己的配置页呈现。插件中心提供进入该页面的“配置”入口。

平台加载失败、包不兼容、缺少运行依赖等信息属于插件中心。插件调用某个外部 API 失败不自动把整个插件标成启动失败。

没有配置页时省略“配置”；当前 Surface 无法承载配置页时说明支持的入口。不能为了打开被禁用插件的配置页而偷偷启用它的业务执行。若作者需要在未启用业务前配置，沿现有 contribution 生命周期提供独立配置入口和真实可用状态。

### 4.5 视觉、交互与动效

- 使用现有浅色、深色主题和重点色。主要操作使用重点色，普通元数据依靠层级和间距，不为分类铺满彩色标签。
- 每行主要动作有限，低频操作放菜单。安装进度在原操作位呈现，错误靠近对应插件，不用连续弹窗驱动整个流程。
- 管理信息在页面内按需展开；展开、收起可打断，焦点和滚动位置连续。复用现有 motion primitive，避免给每个条目单独创建持续动画循环。
- 插件配置进入现有设置导航，返回能够恢复插件列表。窄屏改为单栏，不继续压缩多个并排区域。
- 搜索、菜单、开关和安装预览支持键盘与读屏。状态变化不抢走正在搜索或编辑配置的焦点。

## 5. 公开收录仓库与网站

### 5.1 仓库职责

插件市场使用已建立的 [Astrmira/Varin-plugins](https://github.com/Astrmira/Varin-plugins) 作为收录仓库。站点域名建议使用 `plugins.varin.dev`，待部署时确认。

仓库承载收录资料、静态图标、网站源码和校验脚本。插件源码与发行包保留在作者自己的项目中。

建议目录结构：

```text
entries/       每个插件一份收录资料
assets/        列表使用的图标
site/          市场网站
scripts/       目录校验与静态生成
CONTRIBUTING   收录与修改方式
```

每份收录资料包含稳定插件 ID、展示名称、短简介、图标、作者、分类/关键词、仓库/文档链接以及发行来源定位。这里不列每个版本的下载 URL、最新版本号或更新日志。

发行来源定位表达“到哪里找这个插件”，例如某个 GitHub 仓库中的指定发行系列，或某个 npm 包。它是稳定接入信息，不是逐版本登记表。单仓多插件时需明确对应的发行清单或系列，避免把仓库里任意新 Release 当成该插件。

### 5.2 收录与修改

作者先发布一个可安装版本，再使用模板提交收录 PR。CI 检查资料结构、ID 冲突、图标和链接、来源定位，并通过发行包检查确认实际 manifest 身份及入口。审核时查看维护归属、用途和交付情况。

收录检查下载和检查发行材料，不在有部署凭据的流程里运行投稿插件或作者安装脚本。来源检查失败应保留可读原因；不根据网络偶发失败自动删除已经收录的项目。

合并 PR 后，网站和应用目录出现该插件。之后：

| 作者的变化 | 是否修改收录资料 |
| --- | --- |
| 发布新版本、更新安装包或更新说明 | 不需要 |
| 修改仓库 README 和使用文档 | 不需要 |
| 修改市场列表中的名称、简介、图标或分类 | 需要 |
| 更换发行来源、仓库或维护归属 | 需要；已有安装另行确认来源迁移 |

网站提供“提交插件”“修改收录资料”和对应 GitHub 入口，直接复用 PR 讨论和维护者审阅，不额外建设投稿账号系统。收录只代表进入公共目录，实际代码信任沿用安装时的现有流程。

### 5.3 Cloudflare 部署

建议使用静态站点构建，可复用官网的 Astro 生态和视觉变量。Cloudflare Pages 连接收录仓库，`main` 的资料或网站变更触发构建，一次生成网页、目录 JSON 和图标资源。

目录和资源随同一部署发布，带内容版本和缓存验证信息，避免网页与目录使用两套手工维护的数据。应用按所支持的目录合同读取；目录格式确有不兼容变化时使用明确的协议版本入口，不能返回半个可解析目录。

本仓库分支可使用 Pages 预览部署；外部 fork PR 至少完成资料校验和静态构建，不承诺 Cloudflare 原生为所有 fork 自动提供预览。预览或投稿构建不取得生产部署秘密。

**作者发版不触发我们的市场站点重建。** 页面不需要同步展示每个插件的实时版本；下载按钮打开 Varin 的安装入口，详细说明链接到作者仓库。

站点主要提供搜索、分类、简短条目和外链。应用读取静态目录，无需为了本设计新增动态数据库、中心版本 API 或全市场定时爬取任务。

### 5.4 其他目录与直接安装

官方目录是默认发现来源。高级入口允许添加同合同的其他目录，并显示条目来自哪里。不同来源的同 ID 插件需要明确区分，不能依据加载顺序互相覆盖；多个目录指向同一身份及同一发行来源时，可以合并展示来源信息。

直接链接、Git、本地目录和发行包安装始终独立可用。市场收录决定是否出现在该市场，不成为可安装插件的白名单。

## 6. 作者发行与可安装包

### 6.1 逻辑来源和已解析版本

现有安装 source 继续表示用户选择的来源。新增发行来源解析时，区分：

- 逻辑来源：GitHub 仓库及发行系列、npm 包及所选发行渠道、本地文件或已有 Git/local 来源。
- 解析结果：这次选择的具体版本、对应资产、兼容范围、平台目标、下载地址和内容摘要。
- 安装事实：原安装 owner 核验并保存的不可变 artifact 与 selected/candidate 状态。

检查更新只获取元数据，不自动下载所有发行包、不提前启动插件。安装确认使用本次解析出的具体版本，不能在确认后重新解析浮动 `latest` 并悄悄换成另一份代码。

### 6.2 GitHub Releases

推荐为作者提供 CLI 打包与 GitHub Actions 示例。作者在自己的 Releases 上传已构建插件包及机器可读发行清单。可采用 `varin.release.json` 作为初始约定，精确 schema 在 `extension-contract` 中与 CLI、Host 共同定义。

发行清单只承担选择安装包所需的信息：插件身份、发行版本、兼容范围、不同目标对应的文件和校验摘要。插件的能力、入口及运行合同继续以包内 `varin.extension.json` 为准，两者相关身份必须一致。更新说明可直接使用 Release 文本。

Host 根据目标平台、架构、Varin 兼容范围和用户所选发行渠道选择合适版本。普通源码提交不是安装版本；没有可用包的新 Release 明确显示交付不完整，不能将它标为可安装更新。

稳定渠道默认选择适用的正式发行，预发行作为用户可选渠道；不能按字符串排序版本。较新的不兼容发行可说明要求，同时保留当前版本及可选兼容版本，不自动降级。

同版本被替换为不同内容时，现有内容身份检查仍然生效。重新发布不能覆盖正在执行的已选 artifact；若用户选择新内容，沿候选更新处理并明确显示其内容变化。

### 6.3 npm、Git 与本地来源

npm 市场安装可以直接解析 registry 元数据和已发布 tarball，核验 registry integrity，并将已构建内容送入原 artifact 管线。普通市场安装不应要求用户为了下载一个包先安装 npm CLI。现有 npm 开发来源保留可用路径，公共包要求作者发布完整运行材料。

Git 和本地目录保留当前开发体验。检查它们时说明真实来源状态，不将任意工作树修改显示为作者正式发行。本地导入发行包应支持直接选择文件；没有记录更新来源的本地包使用手动替换，不根据显示名称猜测远程项目。

私有或第三方来源继续走 Host 已有的网络、认证和来源机制。公开市场目录不包含访问令牌，本次不要求私人扩展必须公开或被市场收录。

### 6.4 包的内容与运行环境

扩展 CLI 在现有 `build/check/test` 上补发行打包能力，产出自包含入口、样式、静态资源、manifest 和必要运行材料。常规 JavaScript 依赖在作者构建时处理；原生模块或辅助程序由作者发布对应目标包。

发行包读取器只负责安全解包、校验和交付文件，再复用现有 `ExtensionArtifactStore`。包中真实需要系统程序或额外运行环境时，在安装预览说明；作者可随包交付合法可分发的运行材料。缺少实际依赖时给出具体解决入口，不用“已安装”掩盖不能运行。

包格式应采用标准归档和既有 manifest，不因插件市场另造可执行安装 DSL。解包继续防止路径越界写入，不运行包管理器生命周期脚本。校验摘要用于确认所选择的字节，作者提供的摘要本身不等同于独立代码审计。

## 7. 安装、升级、移除与来源变更

### 7.1 安装

1. 用户选择市场条目、粘贴来源链接或导入本地包。
2. 当前 Host 解析对应发行，下载并只读检查选定包，返回具体版本、安装目标、实际 manifest、能力请求和依赖信息。预览准备不加载插件入口。
3. 用户审阅现有代码信任及能力界面，确认这次安装。
4. Host 使用已经下载并核验的具体内容，沿原安装 owner 准备 artifact 和实际 generation；不再次解析浮动版本或重复下载相同包。
5. 列表原位显示安装结果，提供启停、配置和仓库入口。

下载与解析阶段不能执行投稿代码来生成介绍。实际代码可能在启用时获得其 OS 账户能力，继续使用现有代码信任说明。权限审查与插件自身账号授权由各自的入口负责。

已有安装从市场进入时定位到管理条目。相同 ID 但来源不同的直接安装不能静默接管原安装，按明确的来源替换处理。

### 7.2 更新检查与应用

已安装页提供“检查更新”和单项重查。进入该页先展示本地事实，再对有发行来源的外部插件检查更新；同一 Host 的重复请求合并，使用上游 ETag 等缓存机制。发现页不启动这批请求。

后台检查仅围绕已安装插件及用户的更新检查设置，不轮询全部市场。检查失败保留“上次检查时间/失败原因”，不能显示“已经最新”。服务端限流按实际响应处理，不另造任意插件数量上限。

用户选择更新后，沿现有 candidate 准备、权限差异审查和应用流程完成。新增权限、原生入口需要重启等情况使用现有真实状态。没有改变的账户或配置不因换包自动重建。

正在运行的调用继续持有原 generation；新版本准备失败保留旧版本，不能为刷新页面强制终止现有任务。取消观察与取消实际安装仍遵循原操作寿命。

### 7.3 卸载与数据

外部插件卸载沿现有先退役执行、再移除安装记录的流程。保留数据或删除该插件数据继续是明确选择，不能连带删除项目文件或其他服务的数据。

插件禁用、卸载、删除本地数据、撤销外部账号授权是不同操作。插件配置页可以提供账号撤销入口；平台不能把网络撤销失败冒充成功，也不为卸载悄悄调用任意第三方业务接口。卸载后凭据是否保留由统一数据选择及账号 owner 处理，不让插件更新或重装猜测别人的连接。

## 8. Host、Surface 与链接安装

### 8.1 多设备

插件安装位置沿用当前 Application Host。页面顶部显示人能识别的 Host 名称，避免用户在手机上安装时以为代码运行在手机本机。

Host 系统和架构决定执行包，当前 Surface 决定配置页和视觉 contribution 能否显示。插件的 Host 服务能够在 headless 服务端运行，不因手机无法显示某个桌面界面而停用其兼容部分。

切换 Host 后，列表、安装目标、更新状态和配置导航随对应 Host 重置或恢复。已发出的操作仍归原 Host，不能把迟到结果发布到新 Host 的界面，也不能把继续安装的确认发送给新目标。

### 8.2 网站到应用

在既有 `varin://` 深链接机制上补插件安装意图。链接携带公开的收录身份或来源引用，不携带凭据，不直接授予安装权限。

桌面端收到链接后打开插件安装预览，并使用当前连接的 Host。若目标需要用户选择，在预览处明确选择；不能默默改成网页所在电脑。

网页和移动端用户可复制安装链接，在 Varin 中打开；已有 Web 部署可以在其自身入口接收同样的安装意图。公共市场不扫描本机端口，也不索取用户服务器凭据。

## 9. 复用 Host 的授权与凭据机制

### 9.1 从现有实现接入

模型服务已经将渠道配置和凭据分开保存。它的 `CredentialService` 支持凭据引用、API Key、OAuth 刷新、并发刷新合并，以及在重连或替换后拒绝旧请求回写。Host 的 `AuthorizationFlows` 已管理授权地址、设备码、回调输入和取消。搜索及代理另有 Host 管理的 API Key 存储，MCP OAuth 由 MCP 连接管理。实现入口见[模型凭据](../../packages/web/application-host/lib/models/credentials.ts)、[Host 授权交互](../../packages/web/application-host/lib/authorization-flows.ts)和[服务凭据](../../packages/web/application-host/lib/service-credentials/store.ts)。

普通插件的接入点是现有扩展 Host capability。按插件调用需要，把凭据读写、替换、刷新协调和授权交互中与模型无关的逻辑提到 Host 公用代码。模型渠道继续通过自己的适配层使用这些机制，保留模型请求头、端点、模型配置与 Run 绑定的语义。搜索、代理和 MCP 可在各自的维护中复用通用部分，插件市场的交付无需先归并现有文件或迁移凭据。

### 9.2 插件定义连接，Host 持有凭据

插件自己组织邮箱、工作区、服务端点及配置界面。它可以把连接配置放在现有插件存储中，将秘密保存为 Host 凭据引用。插件 Host 端适配器处理服务商特有的授权参数、令牌交换、请求签名或撤销行为。Host 端按真实调用身份解析引用并用于目标请求，前端、工具参数与模型上下文只使用配置所需的非秘密信息。

普通扩展调用通过 Host capability `varin.credentials` 接通凭据归属。Surface service lease 的认证主体与 Rust Catalog 保存的 Thread/Run 主体分别进入 Host-only 调用 scope，插件参数不能替代它们。配置页授权和 Agent 工具执行都要由 Host 从各自的可信调用链解析同一用户身份，并将凭据范围绑定到插件与连接。一个用户可拥有同一插件的多条连接，同一 Host 上的不同可信主体各自管理自己的连接。当前登录入口仍为原单一 Host owner 的密码、passkey 与设备配对；多用户注册和邀请不在本次实现中。模型渠道、MCP 或其他插件的凭据仍按各自的归属解析。

上述归属约束作用于 Host 凭据 API。原生插件仍以其进程账户权限运行，代码信任沿用现有安装与执行边界。

### 9.3 授权交互与生命周期

授权尝试复用现有 Host 交互，绑定发起用户、插件与目标连接。具体回调由服务商和部署方式决定，例如本机桌面可用系统浏览器与本机回调，远程 Host 则使用该部署能接收且已登记的回调方式。发布者负责所需的 OAuth 应用配置与审核。配置页负责呈现授权结果、重连以及服务商支持的撤销操作。

## 10. Gmail 插件的接入职责

目标路径：用户在市场安装 Gmail，点击“配置”进入 Gmail 自己的页面，完成账号授权，然后在对话中搜索、读取、发送和回复邮件。账号可见范围与实际执行绑定一致。

按 #288 的明确需求，发送前展示实际收件人、抄送、主题和正文，单次确认只授权这次内容。取消不发送；已派发但结果不确定时，不自动重复发送。将这种操作预览和确认接进既有权限及回执机制，而不是让插件另建对话、审批和执行数据库。

收发邮件、在原邮件线程回复、附件处理属于 Gmail 插件自己的能力声明。新邮件通知或持续监听需由用户在插件中启用；它们不是安装插件的隐含效果，也不是市场的全局业务状态。

#285 已有实验实现可复用，但公共交付还需要验证普通安装包、Windows/macOS/Linux、本机和远程授权、可信账号归属及生产 OAuth 应用。文档中的实验说明不能替代这些真实交付。

Google 桌面应用属于公共客户端，应按原生 OAuth 与 PKCE 处理；不要把“必须有一个保密的桌面 client secret 分发服务”当作所有桌面接入的固定前提。Gmail 读取及发送涉及的 scope 审核要求依据发布时的官方规则落实。

## 11. 实现落点

| 模块 | 本次职责 |
| --- | --- |
| `extension-contract` | 演进公开目录合同；定义发行来源/解析结果与发行包清单；配置入口及通用连接合同按消费者补齐 |
| `extension-cli` | 在现有构建上产出发行包与清单，核对完整依赖，提供作者 Release 工作流示例 |
| `extension-host` | 来源解析、发行包读取、上游元数据缓存、具体版本准备；复用 catalog、artifact、候选与退役 |
| `application-host` | 可信网络请求、公开目录读取与目标 Host 协调；复用现有授权与凭据机制，接通扩展调用的用户归属 |
| `application-client` | 无框架的目录读取、发行查询、检查更新和安装意图接口；返回有意义的进度与失败 |
| `ui` | 发现/已安装页面、来源筛选、安装预览、配置导航与高级诊断；不在组件里访问 GitHub API 或写安装状态 |
| `electron` | 扩展现有深链接入口与原生授权交互，仍调用相同的 Host 服务 |
| 新收录仓库与站点 | 人工维护展示资料、静态目录构建、PR 校验、Cloudflare 发布 |

现有 `source.kind` 和 discovery parser 都需要同步演进；不能只在 UI 新加一个 GitHub 按钮后拼接 npm/Git 字符串。逻辑来源和已安装 artifact 分开持久化，新记录保存真实来源，旧本地/Git/npm 记录按已知信息继续使用，不猜测它来自哪个市场条目。

扩展安装状态仍由 `ApplicationExtensionRuntime`、`ExtensionPackageManager` 及其 catalog 负责；Rust 原生 Agent 历史、权限和工具执行归属保持原 owner。目录刷新不是原生会话配置变化，不重建已受理请求中的工具列表。

设置页拆分职责明确的小模块，避免继续把发现、账户、路由和所有调试状态塞进一个 `ExtensionsPage.tsx`。新文案进入 application-client 的设置本地化资源，构建产物按现有包依赖同步。

## 12. 完整交付与实施顺序

先把目录合同、发行来源和界面消费关系写通，再并行于真实插件完善账号连接。每一步有可用产物，但整体完成需要下列链路全部闭合。

1. **公开目录与站点**：独立仓库、提交模板、静态列表和图标、资料校验、Cloudflare 部署。来源数据职责与第 3 节一致。
2. **发行交付与安装更新**：CLI 发行包、GitHub/npm 直接来源解析、跨平台选择、明确版本安装、本地包导入、已安装检查更新和候选应用。
3. **插件中心**：发现/已安装、内置分组、配置入口、安装进度、升级和卸载、保留高级功能，接通网站安装链接。
4. **连接类插件接入**：扩展复用 Host 授权与凭据能力，补齐调用身份绑定。Gmail 自己提供配置、服务商授权和发信预览，完成 #288 的目标路径。
5. **开发者与用户文档**：从空项目到发行、一次收录后的后续发版、各部署下账号连接和失败处理；把落地机制合入当前扩展文档。

市场及普通插件安装可以先投入使用。Gmail 的生产 OAuth 审核按该插件的发布安排推进。

## 13. 验收依据

验证围绕真实行为和职责，不以新增大量字段形状测试替代交付。

| 场景 | 应观察到的结果 |
| --- | --- |
| 打开发现页、搜索和筛选 | 请求只涉及公开目录及其展示资源，没有按条目访问作者仓库 |
| 长名称、长简介、浅深主题与窄屏 | 排版稳定、内容可达、操作不被挤走；列表展开收起可打断 |
| 点击详情 | 打开登记的作者仓库/文档，市场不镜像长篇 README |
| 作者发布新版，但收录仓库不变 | 已安装插件能直接发现并安装该版本，网站无需重建 |
| 收录资料修改简介，但作者没有发版 | 市场展示更新，已安装代码不变 |
| 市场不可用 | 已安装插件运行与直接来源更新不依赖市场恢复 |
| 未收录插件或本地发行包 | 可以安装和管理；有明确来源才能检查相应远程更新 |
| 未装 npm/Git 的普通桌面环境 | 市场发行包路径能够安装完整插件，无需用户本地构建 |
| 最新发行不兼容、资产缺失或摘要不符 | 明确说明，旧安装保持可用，不发布错误 candidate |
| 更新发生在原工具调用进行期间 | 原调用继续持有原实现，新版本只在实际发布后供新绑定使用 |
| 用户切换 Host 时安装/更新仍在进行 | 操作保持原 Host 归属，迟到结果不污染另一个 Host |
| Gmail 安装后未授权 | 插件中心显示平台状态和“配置”，账号状态只出现在插件页面 |
| 不同用户共享 Host；同用户多端 | 前者连接及凭据隔离，后者按真实身份使用自己的连接 |
| 单次发信确认、取消和未知结果 | 原始内容展示正确，取消无发送，未知结果不自动重发 |
| 内置与外部插件管理 | 保留原有组合、权限、数据保留和生命周期能力，入口清楚可达 |

复用已有扩展 Host、UI 和 SDK 行为测试，围绕目录请求范围、直接上游更新、候选发布和账号归属补少量关键用例。文档和网站资料改动只做相应结构、链接与构建检查；不因写设计就触发安装包或真实账号操作。
