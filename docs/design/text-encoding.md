# 文件与终端编码设计

状态：核心链路与通用编码扩展已实现。2026-11-10。实现入口及当前边界见[原生编码](../../kernel/README.md#file-text-representation)与[资源文档](../resources.md)。

Varin 应直接读懂和修改 GBK／GB2312 老项目，同时保持 UTF-8 项目的速度与使用方式。用户不需要先设置编码，
Agent 不需要换一种工具，保存后原工具链仍能读懂文件。内部文本统一使用 Unicode；磁盘文件沿用自己的格式；
终端按真实进程和传输通道处理。正常路径不增加鉴权、弹窗、常驻编码控件或确认步骤。

本文确定文件表示、保存、搜索、草稿和进程 I/O 的共同语义，记录实现入口与取舍。它不改变现有文件访问权限，
不迁移整个 Documents 服务，不创建另一套文档数据库，也不承诺任意损坏或混合编码文件都能自动恢复原意。
当前行为仍以[架构](../architecture.md)、[资源](../resources.md)、[工作台](../workbench.md)及源码为准。

## 1 用户应得到什么

- 打开老项目里的中文源码，编辑器、Agent 和搜索看到一致的文字。改几行后，文件仍是原来的编码。
- UTF-8 与 GBK 文件可以存在于同一项目，不要求转换整个仓库，也不要求给每个文件声明编码。
- 自动识别产生一个可使用的解释，不要求用户审核检测结果。用户主动纠正时，所有入口遵循同一选择。
- 保存、批量修改、撤销、崩溃恢复与隔离工作区都保留格式，不在某个中间环节偷偷转成 UTF-8。
- 终端中文输入与输出能按程序需要工作；修复输出乱码不改变 Python 等程序读取项目文件的默认行为。
- 只有实际无法完成的那次保存需要处理，例如新增字符确实不能用原编码表示。草稿保留，错误就地呈现，
  不弹出全局模态窗口，不阻塞其他文件，不重复提醒。

编码是文件格式与进程 I/O 的细节，不成为新的用户工作流。手动选择是低频纠正出口，不是开始工作的前置条件。

## 3 选定架构

### 3.1 Rust 统一字节与文本之间的实现

在现有 Rust 文件和计算能力旁建立共同的文本 codec／serializer。它负责编码解析、BOM 处理、增量解码、
严格编码、坐标映射及必要的原字节片段复用。Storage、native 文件工具和 Compute 直接调用它；Host Documents
通过明确的内部接口使用同一实现。实际保存仍由原 Storage writer、版本检查和恢复记录完成。

| 状态或行为 | 继续负责的模块 |
| --- | --- |
| 文件原字节、revision、blob 引用、条件写入、before/after image | Rust Storage |
| bytes 与 Unicode 的解释、格式保持与编码结果 | 共同 Rust 文本模块 |
| 原项目设置、文档身份、Surface 协调、dirty barrier | 现有 Host 对应 owner 与 Documents |
| 活动 Unicode 缓冲、撤销、local edit revision、呈现 | 客户端 Document Registry 与编辑器适配器 |
| 产品 DTO 与有类型的失败 | application-client |
| 模型是否调整自己生成的文本、是否执行用户要求的转换 | Agent；实际读写仍使用上述文件能力 |

共享的是语义和实现，不是强制每个消费者创建完整文档对象。范围读取可以只持有窗口和解码状态，搜索可以逐文件
处理，编辑器可以持有全文；不要求同时保存全量 raw、Unicode 和逐字符映射。renderer 不增加任意 kernel RPC，
codec 也不建立新的权限服务、持久句柄体系或文件 writer。

### 3.2 不选择的两条路径

分别为 TS 与 Rust 补 GBK 最快能得到局部演示，但两端的识别顺序、编码别名、不可表示字符和分页行为迟早分叉。
文件、搜索与恢复本来就要一起改，保留双份生产实现没有长期收益。

把 Documents 全部搬进 Rust 可以减少语言边界，但编码问题不要求迁移 Host 工作区登记、Surface 协调和 Registry
生命周期。这会扩大验证面，也容易再造一份活动缓冲。只统一编解码与保存规则即可。

## 4 编码选择与解释生命周期

### 4.1 默认规则

一次读取先解析原项目与文件的有效规则，再从原字节得到实际 codec。优先级为：

1. 本次操作或当前文件的明确覆盖；冲突时采用范围更具体的选择。
2. 原项目明确声明的文件／路径规则。项目的“默认或偏好编码”只是后面的候选先验，不等同于强制规则。
3. Auto 模式下识别 BOM，再采用可识别的头部编码声明，然后验证 UTF-8。包含非 ASCII 字符且合法的 UTF-8 优先；无 BOM 的纯 ASCII 没有足够
   编码证据，在 ASCII 兼容候选之间采用项目默认编码，无默认时采用 UTF-8。这也决定首次加入非 ASCII 字符时的保存格式。
   非空 ASCII 不因 UTF-16 项目默认而两两组合成字符；空文件可使用 UTF-16 默认，新建文本默认带对应 BOM。
4. 对非 UTF-8 文本，优先使用有效的项目默认，再由 chardetng 选择通用编码候选；对选定表示验证完整字节流。

当前支持头部 XML 声明、前两行注释中的 coding 声明，以及 HTML meta 的标准 1024 字节预扫描；这是编码声明探测窗口，不限制文件大小。不会因任意正文里出现 `charset` 字样切换文件编码。
`.editorconfig` 与 Git `working-tree-encoding` 尚未接入。
接入这些来源时需明确路径作用域、优先级及工作树／Git 对象语义，不能悄悄套用另一套配置。

自动检测不需要用户确认。编码来源作为轻量元数据提供给 Agent 和必要的诊断；置信度不成为编辑或保存门槛。
不能因为 GBK 能解码很多字节，就把所有非 UTF-8 二进制都当成 GBK 文本。BOM、文件内容与二进制特征共同参与
分类；UTF-16 的 NUL 不能在识别其 BOM 前直接判为二进制。普通文件读写不新增硬性大小限制。

### 4.2 不可能从字节唯一判断的情况

`C2 A9` 既可以是 UTF-8 的 `©`，也可以是 GBK 的 `漏`，两种解释都能原样往返。纯 ASCII 更无法揭示原工具链
预期的编码。因此，UTF-8-first 是明确、稳定的默认，不是正确性证明；项目明确规则和用户覆盖能够替换它。

原文本可重新编码回相同字节，只说明可使用快速序列化路径，不能说明自动识别一定正确。不能用往返检查产生
“已确定原编码”的标记，也不能用检测置信度要求用户逐个批准文件。

### 4.3 固定一次读取的解释

对同一原始版本和同一有效规则，所有入口应得到相同结果。分页不重新猜编码；模型先读到的文件与随后编辑时
采用的解释保持一致。项目设置变化不重新解释正在编辑的 dirty buffer，也不改变已受理 mutation 的含义。

用户主动纠正文件编码时，在既有配置 owner 下记住该文件的明确选择；普通项目按原项目归属，隔离 native 分支
按稳定来源身份区分主动选择，不能因重开旧副本而改变原 live 文件的解释。Auto 的推断结果只作可失效缓存，
不写入仓库，不自动形成新的持久强制规则。文件外部变更后按有效规则重评估；有活动草稿时先沿原基准协调，
不把重评估当作可以覆盖草稿的理由。

显式转换保存也更新这份文件选择。例如用户先按 GBK 重开，再选择“转为 UTF-8 保存”，成功后不能残留一个
更高优先级的 GBK 覆盖，让下次打开再次乱码。新格式先随真实保存回执成为该文档的基准，再协调既有文件级
偏好；失败不提前修改偏好。若回执后偏好更新被中断，重读原 operation receipt 完成协调，不重做文件写入。
该文件的明确转换优先于原来的宽泛项目规则，不因此改写其他文件或仓库中的配置。单次临时读取覆盖则仍只
作用于那次读取，不等于用户选择永久转码。

隔离 WorkingState 捕获原项目的有效解释规则与必要的已选格式。物化到 Linux、远端 Host 或临时目录后，
不能改用执行机 locale 重新决定文件含义。文件编码与终端 code page 不共享一条全局 fallback。

## 5 格式与版本合同

沿用现有 raw revision／readVersion 的原始版本语义作为磁盘并发基准。文本读取补充实际 codec/profile、BOM、换行信息和
选择来源；底层如需重建原表示，持有现有原始对象引用或可再次核验的基准，不另造永久文档 ID。

读取的基准是“原 readVersion + 该次 resolved format”，后续文本 mutation 必须携带并沿用这一组合，可扩展
原 read receipt／参数表达，不依赖一个可能已逐出的进程内缓存。否则在 read 与 edit 之间改了项目设置，bytes
虽未变，edit 仍可能用另一 codec 定位和写出。实际 operation 记录保留已受理的读取解释与目标保存格式；它们
是操作含义，不是额外鉴权 token。原始字节 CAS 不变，源解释与显式转换的目标格式分别表达。

三种语义需要区分，但不必建立三套持久版本系统：

- **原始版本**用于文件冲突与恢复，仍由原字节决定。
- **解释身份**从原始版本、实际 codec/profile 和会改变解释结果的规则派生，用于缓存与分页。
- **缓冲版本**沿用 Registry 的 localEditRevision；跨进程校验需要时才计算原有 bufferHash。

仅改变规则来源而实际解释相同，不必使全部派生工作失效。相同 bytes 改成另一 codec 后，文本可能改变，
搜索与结构结果就不能只凭 raw revision 复用。当前 SyntaxRuntime 缓存的是 grammar/query，不存在可直接称作
“旧语法树复用 bug”的文本缓存；这里要求核对所有现有派生结果的身份，而不是新增一套大缓存。

文件格式与传输编码要分开。JSON 中的 Unicode 文本、base64 原始字节、磁盘 GBK 是三个概念；不能继续让
单个模糊的 `encoding` 字段同时代表它们。具体 DTO 名称在实现时随真实消费者收敛，不预先冻结空接口。

保存表达两类意图：普通保存沿用读取基准的格式；显式转换才改变 codec、BOM 或换行策略。保存回执返回实际
格式与新原始版本。格式变更参与 dirty、local revision 和 undo；旧保存回执不能清掉保存期间新发生的格式修改。
当前实现的本地格式撤销保留编码／BOM 历史。混合 EOL 统一在提交前可撤销，提交后其原逐行字节布局通过现有
Recovery 文件操作恢复，不用一个默认 EOL 枚举假装还原混合布局。

## 6 原格式保存与字节保持

### 6.1 单一 serializer 的三条路径

1. 文本和格式都未变，复用原始 bytes/blob。先完成原版本核验，不因 no-op 绕过外部变更检查。
2. 合法常规文本在原文往返一致、换行可完整还原时，使用严格整段编码快速路径。
3. 混合换行、非双射映射或其他需要保留来源的情况，按明确编辑范围复用未改原始片段，只编码改动部分。
   映射按需建立，可以使用流式扫描与稀疏 checkpoint，不要求每个字符常驻一条记录。

精确范围编辑与全文替换的保证不同。前者能明确指出哪些原始片段未修改；后者只有最终字符串，不能凭重复
文本中的某次匹配推断用户删除了哪一个原始片段。全文保存可以做确定性的差异计算来保留可证明未改的内容，
但计算出的 diff 不是原编辑事件的替代凭证。

当前 Registry 的 lastChanges 只保留上一笔，部分批量／恢复路径又用一个宽范围替换表示多处变化，不能据此
恢复相对磁盘基准的完整编辑来源。需要精确保留的文档采用轻量的 base-relative 片段映射，随现有缓冲编辑与
undo 更新；各入口有真实范围就传递范围。常规可逆路径不必维护逐字节映射。缺少来源的全文替换按替换语义
处理，不声称它没有改动字符串中恰好相同的那一段原字节。

### 6.2 BOM 与换行

BOM 是格式元数据，不作为编辑器正文的首字符，也不向原本无 BOM 的 GBK 文件添加标记。正常编辑保留原有
换行边界，新插入的换行使用该文档的默认 EOL；用户明确选择统一换行时才整体转换。

现有 [line-ending helper](../../packages/web/application-host/lib/documents/line-ending.ts) 将缓冲规范化为 LF，
再按单一枚举生成全文件换行，不能证明混合 EOL 原样保留。支持混合 EOL 时须让原始边界信息跟随基准；若某条
全文替换路径只能保持文档默认 EOL，应明确其替换语义，不把它写成“所有未改字节必定不变”。无需为每个混合
换行文件弹窗；实现应尽量由确定性序列化完成保留。

### 6.3 不可表示字符与异常原字节

写端使用无替换编码 API，并处理实际不可表示的字符。已有 `encoding_rs` 可复用；不能把普通编码 API 生成的
问号、字符实体或其他替代输出当作保存成功。新增字符无法保存时，原文件不变、草稿继续保留，结果包含字符
位置与可采取的动作，不只有“保存失败”。

codec registry 只将实际验收过的方向标为可用，不能假定库的 decode 与便捷 encode 对称。若纳入 UTF-16 写入，
需明确端序与真正的 UTF-16 writer；JS 未配对 surrogate 在进入严格编码前返回有位置的结果，不能被自动替换。
只在物理开头处理一次 BOM，正文 U+FEFF 保留；不做 NFC 等 Unicode 规范化，不改变组合字符和非 BMP 字符。

Agent 可以在不改变用户要求和代码语义的前提下改写自己生成的注释或文案，再用原格式保存；不能擅自删除用户
正文，也不能为通过编码器偷偷把整个项目升级为 UTF-8／GB18030。用户本已要求转换时直接完成，不再确认一次。

异常字节不自动变成可覆盖的 U+FFFD。原 bytes 仍可读取；当实际路径已能建立可靠原字节范围时，允许不触及
异常段的编辑并保留该段，不因别处有异常而增加整文件禁令。无法建立来源的整篇文本路径保留 raw／预览和
具体失败，不伪称已经可无损编辑或确认没有搜索命中。若完整 newText 已丢失异常段来源，就不能声称可还原
任意损坏文件。该次无法完成的写入保留草稿，其他文件工作照常。通用损坏文件编辑器或新的字节片段编辑 UI
不作为本提案的前置工程。

## 7 GBK 与 GB2312 的产品含义

Auto 默认采用现代 GBK 兼容解释，覆盖大部分通常称作 GB2312 的中文旧文件。不能仅凭当前字符都落在共同范围，
推断文件必须采用严格 GB2312 写入限制，也不能自动声称识别出了严格 GB2312。

严格 GB2312 与 GBK 不只字符范围不同，部分字节的 Unicode 映射也不同。常见 Encoding Standard 实现将
`gb2312` 标签作为 GBK 别名；接收这个标签不等于实现了严格标准。读取结果应报告实际 codec/profile。

同一原生目录提供独立的 `gb2312-strict`，不增加常态 UI 开关。它使用 CPython 固定版本分发的 Unicode
GB2312-80 完整映射，保留原始授权与来源；全部 7,445 个已分配字符通过双向验证。项目文件规则、单次操作与
文件菜单可明确选择该 profile；普通 `gb2312` 别名继续表示 GBK 兼容解释，不通过统计检测推断严格写入范围。

该机制同时覆盖 encoding_rs 的通用文件编码，而非持续增加中文特例。原生目录是别名与实际能力的唯一来源，
`text.encodings` 通过 Documents 到达本地或远端文件编辑器。统计检测由 chardetng 完成，选择与严格验证分离。
分页复用连续解码器的真实输出边界；Big5 多字符映射的编辑扩展到触及的完整编码单元，ISO-2022-JP 等状态编码
在修改后连续序列化并保留原换行。无修改仍原字节返回，不以重新编码代替 no-op。

## 8 Agent 编辑器与批量编辑

### 8.1 Native 文件工具

live source 与 fixed source 使用同一编码解析。file_read 返回可读 Unicode 与实际格式；raw 读取仍返回精确
字节。file_edit 使用同一解释定位原文本并保持原格式；file_write 对已有文件默认保留格式，新文件遵循明确
文件规则，其次项目默认编码，无默认时采用 UTF-8。本次格式选择随已受理操作固定，重试读取原回执，不换
codec 重做同一次写入。

byte offset 永远表示原始字节。文本分页要从已知字符边界推进，并返回真实消耗范围；不能把 UTF-8 的前后补
三字节及 continuation-byte 判断套到 GBK。GBK lead/trail 字节范围有重叠，应从已知边界顺序解码或利用稀疏
checkpoint。行读取、字节读取和 Unicode 列号各自保持原有清楚的单位。

### 8.2 Documents 与 Registry

Monaco 与 CodeMirror 继续消费同一 Registry。Documents 使用原生文本读取和序列化结果，不在 Host 重新猜码；
Registry 保存基准格式、当前格式意图及已有编辑版本。只改变编码、BOM 或 EOL 也能保存和撤销。

自动保存遇不可表示字符时停止该次文件保存并保留 dirty 状态，在已有文件区域提供一次简短提示和可执行动作；
不每 1.5 秒重弹错误，也不把全局自动保存关闭。正文或格式发生相关变化后再尝试，其他文件照常保存。

用户主动按另一编码重新打开 clean 文件时，直接重新读取，不触碰磁盘。dirty 文件优先保存原草稿到既有恢复
机制，再提供就地的新解释预览；采用新解释或回到草稿是用户主动发起动作的一部分。首期不自动重放或合并
任意 dirty 编辑，不要求用户先处理整批文件，也不在普通打开流程插入这一步。

### 8.3 批量与 Surface

Workspace edit 沿用已有计划、affected-path barrier、Surface receipt 与资源 writer。每个目标携带自己的
格式，批次可以混合 UTF-8 与 GBK，不借一个项目编码统一重写。纯 Registry 文本编辑仍是未保存的 Unicode
编辑，可以暂时含有原格式无法表示的字符，与用户手动输入相同；不能因编码预检拒绝整批缓冲修改。仅对本批
实际要落盘或物化的目标，在产生相关写入前预检可编码性，不写完部分文件后才发现其余只能有损保存。

Surface draft、Agent input capture 与隔离源 materialization 使用同一序列化语义，包含格式-only 变更。
快照固定原格式与原基准，不因后续编辑器选择或项目配置变化重新生成不同的字节。原有批次部分效果与恢复
合同保持不变，不因此承诺文件系统和多个编辑器缓冲具有新的全局原子性。

只捕获或阅读草稿时，可以保留 Unicode 正文及目标格式，不要求先成功保存；Agent 的普通讨论与分析仍能使用
该草稿。若真实执行必须把它物化成原格式文件，才处理实际不可编码的目标，不能伪装成已保存字节，也不能
悄悄丢掉该草稿改用磁盘旧版本。实际文件快照与尚未可序列化的缓冲快照需保留这个区别。

## 9 搜索与结构分析

Compute 的文本入口先得到同一解码表示，再执行现有正则、固定字符串搜索与语法分析。不用不同编码重跑多次
查询后合并命中，也不因非 UTF-8 静默跳过本应可读的中文文件。保留现有 ignore、分页、取消和输出预算语义。

`source.rs` 的 search_capture 在前缀读取阶段就按 NUL／UTF-8 排除文件，必须改为共同 probe 的分流；只替换
下游 `query.rs` 的 from_utf8 不够。采样可提前发现明确的二进制，却不能把尚未读到非 ASCII 字节的文件永久
认定为 UTF-8；最终解释与实际读取版本绑定。

搜索返回行号与 UTF-16 column，与编辑器一致；原始字节偏移、解码 UTF-8 内部偏移和 UTF-16 列号不得混用。
替换依据对应原始版本与解释定位，不能拿显示列号直接切 GBK 字节。

查询分页固定有效解释规则，延续同一次扫描；编码覆盖改变后重建相关文本结果，不复用另一解释下的命中或
结构信息。解析器接收 Unicode 的 UTF-8 表示，其内容身份与磁盘原始 hash 分开表达。只有真正需要反向定位
到原文件字节的消费者才建立映射，普通语法分析不需要完整逐字符 source map。

原始二进制仍不作为普通文本结果；实际无法解释的文件保留已有查询诊断／不完整结果语义，而不是伪装成
“确认没有匹配”。这些信息用于诊断，不每搜索一次就通知用户处理文件编码。

## 10 冲突恢复与历史字节

磁盘 before-image 保存原始 blob／bytes，不再从解码后的 String 重建 UTF-8。undo 恢复历史原字节，不按当前
项目偏好重新编码。草稿 journal 同时保存文本、格式意图和重建所需的原基准；纯文本 hash 相同不代表格式相同。

journal 正文仍用其自身的 Unicode／JSON 存储格式，不按目标文件的 GBK 编码。即使草稿含 emoji、暂时无法
保存到目标文件，也必须能持久恢复。当前 UTF-8 JSON journal 具备这个能力，统一文件 serializer 不应破坏它；
真正物化成工作文件时才按目标格式严格编码。

需要连带修正两个已核验的入口：

- Documents write 当前对 binary／unsupported-encoding 跳过用户 expectedRevision 比较。后续 writer 只比较
  刚读取的 current，不能补回用户基准检查。所有已存在文件都应比较原 revision，包括外部改成非文本的情况。
- Registry 当前恢复 journal 内容时没有装回 loaded.encoding／bom；加入多编码后必须恢复完整格式，格式-only
  草稿不能因正文等于 baseContent 而被清除。

这些是现有保存合同的一致性修正，不引入新的鉴权或确认。响应丢失、并发修改及不确定效果继续由原 operation
receipt、CAS 和恢复 owner 处理，不新增一套编码专用恢复日志。

## 11 终端与进程 I/O

### 11.1 文件格式不决定终端格式

| 通路 | 默认及明确合同 |
| --- | --- |
| Windows ConPTY 主机侧 | UTF-8；不因 GBK 文件或应用 ACP 改成 GBK |
| POSIX PTY | 保留环境与既有 UTF-8 默认；真实 legacy 会话可显式覆盖，没有 ConPTY 相同的系统保证 |
| 普通 pipe | 原始字节；输入与输出使用各自默认及逐次覆盖，未知输出允许自动推断 |
| LSP、DAP、JSON 等已知协议 | 遵循自身协议编码，不套用项目 GBK 规则 |

复用现有进程启动／任务配置表达 input encoding、output encoding 与 auto，不建立庞大的全局 profile 系统。
明确启动选择成为后续读写默认，单次操作仍可覆盖。Auto 本身也是一种默认，不能在看到第一行后偷偷变成
“整个进程永远只用这一种编码”。远端执行采用实际进程的环境／code-page 事实，不借观察端 locale 推断。

process_write 的文本入口目前固定转 UTF-8，需要按输入合同编码；明确的字节入口保持精确。输出编码不能
直接推导输入编码，Windows 控制台代码页也不是每个 pipe 子程序实际编码的保证。

### 11.2 已知编码与未知输出分别处理

明确 codec 的 stdout 与 stderr 分别维持增量状态。字符跨 OS read、spool chunk、分页或断线重读都不能丢字、
重字或与另一路拼成一个字符。保留原始 spool 与唯一字节游标；seek checkpoint 与解码状态是可重建投影，
不新增一套解码后存储权威。晚到字节可以补全同一路未完字符，即使中间已有另一通道输出。

nextCursor 仍是已消费的全局 raw 字节水位，可以越过某个通道尚未完成字符的前半段。续读或随机读取从稀疏
checkpoint 重放各通道状态，按字符最后一个原始 fragment 的全局结束位置决定本页归属；不按解码字符串长度
推进游标。文本投影附实际来源范围，stdout 半个字符不阻塞 stderr 的完整输出，也不伪造跨通道的因果顺序。
改变 codec 的重读使用对应投影的 checkpoint；原字节及其 cursor 不变。

这需要补齐内部数据帧，而不只是替换 decoder。当前 [worker](../../kernel/crates/varin-kernel/src/process/worker.rs)
在 reader EOF 后没有发送通道结束帧，[launch](../../kernel/crates/varin-kernel/src/process/launch.rs) 的数据入口只
接受 output。各通道的 EOF／读取失败应沿同一有序数据通路，在该通道最后数据之后发布并保留，不让控制侧
退出通知超越尚未消费的输出。尾部记录绑定 raw offset，不占原始字节长度；BOM 也按通道自己的开头处理。
旧记录没有通道结束证据时使用真实整体 outputComplete，而非猜测某一路已结束。现有页结构需能表达文本与
跨片段来源的关系，不能给每个原始 chunk 独立 decode 后宣称已解决。

未知 auto 保持低延迟 best-effort。`E4 B8` 既可以是一个完整 GBK 字，也可以是 UTF-8 字符的未完前缀；一律
等待后续字节会卡住无换行提示，一律按 GBK 输出又会误解异步 UTF-8。因此，不承诺自动识别所有混合输出，
也不为此新增强制等待或实时重投影协议。现有按行混合判断可以保留。

Auto 若在返回前已经消费完整文字，就当次作出低延迟解释；不能先让 raw cursor 跨过它，再无限等待换行补发。
真正未完成的码元按已选解释保留状态。每次返回保留本次采用的 codec／依据和原字节范围。原 spool 允许以另一
编码重读，但重读是另一种解释，不能撤回已经交给 Agent 的旧文本或静默改写历史结果。明确程序协议或用户
覆盖优先解决已知任务，不把猜测升级
为事实。只有相应通道的有序结束证据或真实整体 outputComplete 才能最终 flush，进程 exit 与输出排空仍是
不同事件。

### 11.3 Python 环境不顺带改文件语义

当前 Windows Agent 继承环境时补入 PYTHONIOENCODING=utf-8 与 PYTHONUTF8=1。前者针对 Python stdio，后者
还改变 open() 等默认文件编码，可能破坏未显式 encoding 的 GBK 项目。

保留用户已设置的环境；将需要的 UTF-8 stdio 与 Python 全局 UTF-8 mode 分开。Varin 管理且已知的协议进程
按其协议准备 stdio；普通项目命令沿真实环境，只有明确的任务配置才改变全局 Python mode。不统一执行 chcp，
不修改系统代码页、系统 locale 或用户永久环境。现代 Python 自身版本的默认行为仍由该解释器决定。

## 12 无感默认与现有 UI 出口

默认不新增编码弹窗、顶部编码标签、常驻警告或全工作台状态栏。自动识别成功就正常显示；识别来自推断也不
单独通知用户。项目／文件覆盖由主动操作或既有设置承载，不引导用户先完成编码配置。

实际入口落在已有布局：

- [ResourceEditorHost](../../packages/ui/src/components/workbench/ResourceEditorHost.tsx) 的文件路径工具栏右侧
  已有「…」，放“按编码重新打开…”与“以编码保存…”两个低频操作，复用一个选择器。
- IDE 布局底部已有 [IdeEditorStatus](../../packages/ui/src/workbenches/ide/IdeEditorStatus.tsx) 显示编码／BOM／EOL。
  可将现有编码文字接到同一菜单，不增加普通聊天布局的状态栏，也不要求切到 IDE。
- 真正无法预览文本时，在现有占位区域提供“选择编码打开”；只在需要时出现，不覆盖正常编辑区域。
- 独立移动文件页复用文件操作入口呈现同样动作，不挤进一条桌面式状态栏。图片、PDF 等非文本视图不显示
  不适用的编码保存操作。

“重新打开”只改变读取解释，“以编码保存”才转换磁盘格式。自动保存遇实际不可编码字符时，在当前文件的
已有状态／错误区域保留一条可操作信息，例如“此字符无法保存为 GBK · 转为 UTF-8 保存”，不会接管焦点。
用户主动展开时才展示字符位置、实际编码与其他选择。不使用置信度百分比或内部权限术语让用户判断底层状态。

## 13 跨平台与性能

文件编解码由同一 Rust 实现决定，Windows、Linux、macOS、远端 Host 和移动客户端看到相同结果。操作系统
区域设置只作为明确的进程事实使用，不决定仓库文件含义。文件名与路径的 OS 编码是另一问题，不在本提案中
借内容 GBK 支持一并改写。

UTF-8 保留借用／快速验证路径；不为普通 UTF-8 文件统一分配 GBK 转码副本。检测、hash 和实际读取尽可能
复用同一次扫描；缓存键绑定原始版本和实际解释，失效后按需重建，不为了编码再扫描整个项目。

范围读取保留当前窗口式驻留，不强制加载整文件到内存。搜索保留现有逐文件处理与可取消扫描；本设计不把
当前全文件 capture 自动描述成已实现的流式搜索。大型 UTF-8 文件、GBK 文件和混合项目分别测量首读、热读、
搜索、保存、范围读取的耗时与峰值内存，分清检测、解码、映射、传输与原有 hash 的成本。

索引与检测采样是性能策略，不是固定文件大小准入门槛。准确解码所需的字节边界必须满足；不能用截断样本的
结果假称整文件已经验证，或用后台扫描的文件顺序悄悄改变已经打开文件的解释。

## 14 实施顺序与验收

阶段按现有 owner 分工推进，不将整个系统重写作为开始使用 GBK 的条件；发布完整支持前需贯通所有必经路径。

1. 明确实际格式描述、raw 与文本坐标、严格编码结果及保存意图，补共同 Rust codec 和行为 fixture。
2. 接入 live／fixed 文件读取与 mutation、Documents、Registry、批量编辑、快照和恢复，去掉局部 UTF-8 假设。
3. 接通 Compute 搜索／结构与解释身份，验证跨 Host 和隔离来源一致；接入低频 UI 出口及格式-only 状态。
4. 独立补齐进程 input/output 默认、已知 codec 的跨块／跨通道投影与 Python 环境语义。

| 验收场景 | 要观察的结果 |
| --- | --- |
| 同一 GBK 文件经编辑器、Agent live/fixed、批量修改、草稿和隔离源 | 一致文本与实际格式，无中途 UTF-8 转换 |
| 纯 ASCII、UTF-8／GBK 双合法字节、混合编码项目 | 默认稳定；明确覆盖一致；不出现识别确认弹窗 |
| 零文本且零格式变更 | 原字节完全相同，外部版本变化仍被发现 |
| 精确局部编辑、CRLF、混合 EOL、非双射映射 | 明确未改片段保持，新增内容符合格式；全文替换不冒充原编辑来源 |
| 新增无法编码字符、异常原字节、批量中某个文件不适用 | 无替代字符落盘；草稿与原字节保留；错误只影响相关操作 |
| 只改编码／BOM／EOL，保存期间继续改格式，重启后恢复 | dirty、回执、undo 和 journal 一致，不清掉后来的修改 |
| 磁盘外部修改为 GBK、另一编码或 binary | 基于用户原 raw revision 产生冲突，不覆盖后来版本 |
| GBK 字符恰跨读取页，重复文本编辑 | 分页不漏字重字；坐标单位正确，不依赖 UTF-8 字节技巧 |
| 中文与 emoji 的搜索／替换，原 bytes 不变但改 codec | UTF-16 列正确；结果解释一致，不复用另一解释的派生数据 |
| 进程单字节切块、stdout/stderr 交错、EOF、断线和按 cursor 重读 | 已知 codec 连续正确；auto 不伪称确定；raw 可重读 |
| BOM 跨块／按通道出现、正文 U+FEFF、未配对 surrogate、组合字符 | 不误吞正文、不隐式规范化、不替换非法输入，错误有位置 |
| Windows ConPTY、legacy pipe、普通 Python 与协议进程 | 不混淆 wire／stdio／文件编码，不修改系统或用户永久环境 |
| 大型 UTF-8、GBK 和多编码目录 | 范围读取无新增整文件驻留；性能成本有同来源基线可比较 |

Rust 行为测试负责 codec、实际字节、版本和恢复；Host／UI 测试负责协调、格式状态、用户主动操作与低打扰呈现；
native suite 及 Windows 实机验证进程、ConPTY、真实代码页与 Python 行为。纯函数 fixture 不能代替目标平台
验收，能够显示一段中文也不能代替保存与恢复证据。

## 15 已收敛的实现选择与边界

文件 codec 使用现有 `encoding_rs`，范围探测与全文解码共享选择顺序和严格校验。没有增加另一个统计猜测库：
明确覆盖优先，其后是 BOM、严格 UTF-8 与可验证的 GBK；纯 ASCII 遵循 ASCII 兼容默认。BOM-less UTF-16
需要明确解释。UTF-8 与 GBK 双合法字节仍不能只靠字节确定原意，低频文件覆盖解决这个真实歧义。
`gb2312` 接受为 GBK 兼容别名，不宣称严格 GB2312 profile，也不把 GB18030 四字节扩展悄悄算成 GBK。

编辑来源由 Registry 的可组合 UTF-16 范围变化保留，Monaco、CodeMirror、批量编辑、undo、保存中继续编辑及
恢复均走同一表示。普通全文写入的常见可逆格式走快速路径；混合换行或非双射原片段需要推导局部变化时，使用
确定性 diff。该推导不是损坏文件编辑器，也不把重复文本的相似位置冒充编辑器提供的精确操作。

成功显式转换的实际格式和原始版本属于原 Storage 提交事实。当前路径投影只有小型格式元数据，不保留正文或
额外 blob 引用，不阻止旧 operation 正常释放。项目选择用既有配置写锁协调；手动重解释递增 choice revision，
旧转换回执不能覆盖后来的主动选择。隔离 native 分支的主动重解释保存到稳定来源对应的既有配置命名空间，
不修改原 live 文件选择；工作副本读取合并该主动选择与原冻结基线，不改写原固定版本。固定来源的解释随所选内容与来源捕获冻结，不回读已离线原目录，也不把
隔离执行副本的格式变化倒灌到原基线。

已知进程 codec 以 stdout／stderr 各自的连续解码状态工作，page 仍只有一个原始 cursor，通过来源范围描述跨块
文字；通道 EOF 进入同一有序 spool。Auto 保留低延迟 best-effort，不声称能消除异步混合输出的固有歧义。
采用旧代码页的 POSIX PTY 可使用同一 native 文本投影，正常 UTF-8 PTY 与 Windows ConPTY 不跟随项目文件编码。

当前 GBK 深页范围读取从原字节起点恢复必要解码状态，内存有界但耗时随 offset 增长；未增加稀疏状态检查点。
这是可继续优化的扫描成本，不以新文件大小上限掩盖。大型文件完整搜索仍沿现有逐文件 capture，而非声称已经
实现流式全文搜索。Windows ConPTY、真实系统代码页与各目标平台安装态仍应由对应平台测试验证。
