## 1. 要解决的问题

测试应帮助开发者判断产品是否仍然正确，并缩短定位错误的时间。当前维护成本已影响产品推进，需要重整整个验证体系，
而不是只修最近的红灯、调整超时或减少几个测试文件。目标包括反馈速度、证据可信度、正常重构成本和关键能力保护。

本阶段先回答一个问题：**某项检查失败时，用户的什么能力或哪项重要保证可能被破坏？**
回答可能是可观察功能，也可能是数据完整性、权限、资源释放或发行可用性。不能回答的检查，应重新判断是否保留。
测试数量、覆盖率和全绿状态都不能单独证明产品质量；减少数量也不是交付目标。

## 2. 全仓范围与边界

范围包括所有维护中的包：UI、Web/CLI/Application Host、Electron、Mobile、Pi host、broker/client、
protocol、settings、extension 系列，以及 Rust kernel、根脚本、测试辅助实现、构建和发行 workflows。
同时检查 `node:test`、Vitest、Cargo、独立进程/打包 smoke 的执行归属。源码树之外的依赖、缓存和构建副本不计入自有测试清单。

全仓覆盖意味着每个维护领域的测试家族和入口都得到判断，不要求每个正常小测试填写报告。发现问题的家族深入到断言与装配；
未修改且无异常的快测试可以保留，不能以一次抽查宣称全仓已经清理。

本阶段不重写业务架构、不重新打开 R0–R6，不为测试便利恢复旧后端或放宽用户权限、数据恢复与进程契约。
调查发现的真实产品错误，按实际故障单独修复并取得对应行为证据；范围大的产品改造另列，不把测试整理扩成无期限重构。
AI4S 的科学实验评估与软件回归测试职责不同，本阶段不预建科研评测平台或新的模型质量门禁。

## 3. 按责任保留证据

### 3.1 测试应放在哪一层

| 责任 | 主要验证方式 | 不应重复承担的责任 |
| --- | --- | --- |
| 纯计算、解析、业务决策 | 直接给输入，检查不同语义的输出 | 每个输入都启动 Pi、浏览器或 Rust 进程 |
| 协议与外部边界 | 编解码、运行时拒绝、实际消费者能接收 | 重复 TypeScript 已证明的静态形状，锁定私有函数名 |
| 持久化、权限、进程、文件 | 在对应真实权威上检查写入、重开、冲突、取消及相关故障后果 | 用旧 TS 存储或全 mock 声称生产 Rust 已验证 |
| UI 与状态消费 | 用户动作后的可观察状态、内容和必要交互 | CSS 类、组件函数措辞、无产品意义的快照布局 |
| 跨模块接线 | 代表性的公开入口到结果流程 | 将底层的全部输入组合在每一层复制一遍 |
| 打包与部署 | 从生成的产物启动并使用关键能力 | 把打包脚本包含某句话当作成品可用 |

这些是责任分工，不是每个功能必走的固定层级。一个简单改动可以由一个直接测试说明；只有跨层产生新的风险时才增加独立验证。
不同平台、运行器和产物可以提供不同证据，不能仅凭测试名称相似就删除。

### 3.2 删除、合并、替换与保留

- **删除**：无法对应现行需求的固定数量/字面写法断言、已结束迁移的临时检查、重复静态类型与 lint 的规则、只约束文档手写日期的门禁。
  无价值检查可以直接删，不要求为每一项另造替代测试。
- **合并**：同一语义被多个文件或层重复证明，或仅输入值不同且没有独立装配责任的用例。参数化服务于可读性，不把所有失败塞进一条巨大断言。
- **替换**：要求仍重要但证据方式错误。例如权限策略应检查实际允许/拒绝，CSP 应检查实际输出的策略，部署应观察新旧服务与恢复结果。
- **保留**：快速且清楚的规则测试、真实消费者接线、能发现文件丢失/权限越界/进程失控的具体反例，以及真实发行 smoke。

源码检查可以用于确有必要的依赖边界或生成产物完整性；优先复用编译器、lint、导入图或构建校验，不再各写一套正则扫描。
JSON/schema 的外部字段、协议版本和用户可见输出可以是稳定契约，内部语句顺序、实现类名和当前项目清单长度通常不是。
文档保留链接、页面路由和适用的状态信息校验；日期与 Git 历史不等于内容时效，不为它继续维护时区豁免或日期补丁。

删除唯一的真实风险保护之前，应确认该行为已有其他有效证据或在同一改动补到正确责任层；不要求逐条一换一。
已有历史决策不改写，把当前证据引用更新到保留的测试/消费者，不能留下删除文件仍作为 `proven` 依据。

## 4. 测试装配必须可信且轻量

### 4.1 模拟边界与共享夹具

模型、网络和外部服务通常使用可控制的响应；默认回归不依赖付费账户、公共服务可用性或开发者个人配置。
外部下载/兼容性现场测试按需运行并单独表达证据。测试包管理器等外部适配时，允许使用本地服务或 fixture 协议端点。

Host 策略测试可以注入窄接口 fake，但 fake 只表达输入与结局，不复制生产状态机。涉及 Rust 的持久化、授权、资源和恢复结论，
使用真实 Rust 边界。清理已退休 TS 实现及其专属测试时，先辨明哪些仍是合理的策略替身，哪些只是被测的旧产品。
必要契约统一后直接替换，不留双套兼容夹具。不要为维护旧测试重新引入生产 fallback。

共用有重复价值的 fixture 启动、隔离目录和释放逻辑；每个测试的关键安排、动作和断言仍可读。
不建设通过许多布尔开关拼出任意系统的通用测试框架，也不为这次清理更换全仓测试库。

### 4.2 完成、失败和资源释放

真实流程测试应知道自己如何结束。模拟响应耗尽、未预期工具调用、未捕获异步错误、子进程异常或提前退出不能被忽略后判成功。
不仅检查中间采样，还检查该场景声称的终态。失败场景显式断言预期错误和剩余状态，不能用 catch-all 隐藏其他故障。

局部时序用可控制的时钟、事件或 deferred 响应安排；实际进程/网络生命周期等待对应状态，超时仅兜住无法完成的测试并给出原因。
不以反复增加 sleep、加大超时、全仓串行或失败后自动重跑直到绿来解决抖动。确有资源竞争时隔离相应工作负载，依据实际限制设置并发。
全局禁止所有 timeout、sleep 或串行也不合理，应区分调度测试、真实 OS 行为与普通快速规则。

临时目录、端口、环境、全局 provider 注册和进程有明确所有者，成功/失败都释放。共享昂贵的不可变构建产物，避免跨用例共享可变会话和数据库。
测试环境故障与产品断言失败分别报告；受支持的 CI 环境缺少必需二进制不能静默 skip 后宣称已验证。

## 5. 执行入口与 CI 的目标形态

### 5.1 测试发现是一项可核对的事实

入口由已有 package scripts 和 runner 配置拥有。不同 shell 下应得到同样的公共测试集合，平台专属集合明确标注；
参数应能定向到文件/用例，不能让“跑一个文件”实际运行整包。检查孤立文件、错误 runner、收集到生成副本以及 native suite 重叠。
选择现有 runner 能力或简单 Node 文件发现即可，不新增全仓测试数据库、永久手工白名单或复杂调度服务。

验收时比较发现的文件集合及差异理由；不把当前文件数固化成新的断言。默认入口、平台入口、发行入口应可在本地复现。

### 5.2 三类反馈职责

| 场景 | 需要的反馈 |
| --- | --- |
| 日常改动 | 类型/lint、快速行为测试、相关模块的集成证据；共享底层变化扩到实际消费者 |
| 平台变化 | Windows/Linux 等平台的路径、权限、PTY、进程生命周期和原生模块行为 |
| 发行与部署 | 对应版本/平台/架构的实际产物启动、关键能力与必要的更新/回滚 |

这是职责而非固定 job 数。具体拆分根据现有脚本、依赖和运行数据决定；不再测试 workflow 必须有三个 job 或某命令必须出现两次。
平台无关的同一套检查不因矩阵方便就全量复制；平台相关行为继续在适用 runner 上运行。

同一套件在同一环境的一条流水线有一个执行归属。i18n、updater、kernel 专项与全包的重叠要消除，同时保证原有有效行为仍被执行。
构建依赖有明确顺序，测试直接消费已建产物，避免类型检查、smoke 和 dist 测试各自再构建同一依赖链。
产物复用绑定提交、lockfile、工具链、构建配置、目标平台/架构；不能把另一平台、另一版本或未包含本次源改动的缓存当本次产物。
缓存失效可重建，不能把缓存命中当验证成功。为缓存节省的时间应大于新增的传输和维护成本。

### 5.3 触发、发行与失败定位

文档变化不触发无关的全部原生构建与容器发行。按已有包和构建依赖选择相关检查；共享协议、kernel、lockfile、构建脚本和
workflow 的变化覆盖其消费者。影响范围不能确定时运行相关完整套件，不能靠过窄文件过滤制造成功。保留可直接运行完整适用验证的入口。

主线 CI、Docker、桌面发行可以复用同提交且适用环境的证据，但不能仅按分支最近一次绿灯跳过当前版本验证。
真实桌面/容器 smoke 不由源码测试替代。某条云部署检查失败需辨别是否影响桌面版本，不把互不相关的发布流程无条件绑死，也不隐瞒已知发行故障。
调整 workflow 时同步 required checks 的名称/聚合语义，避免 skipped 或改名让分支保护永久等待；只改实际需要的设置，不清空保护规则。

失败输出应让维护者直接看到失败的用例/步骤、子进程退出和相关 stderr/日志。只收集定位所需材料，避免泄露凭据、用户正文或完整环境。
区分产品失败、测试错误、环境缺失和外部平台故障；不要建立默认自动重试掩盖错误，也不为本阶段新增常驻监控、评分系统或测试费用看板。

## 6. 长期开发方式

新增或修改测试时，优先扩展保护同一责任的现有测试；一个缺陷不自动对应一个新文件、一条永久规则和全层复测。
修复后检查最直接的行为与实际受影响消费者，已有证据足够就交付。简单展示变化或编译器已覆盖的形状不强制新增运行测试。

正常重构不改变可观察行为时，测试应尽量继续成立。若大量测试必须跟着内部重命名和函数拆分修改，先检查它们是否锁错边界。
类型检查、lint、行为测试和产物验证各负其责；新的跨仓约束必须说明具体失败模式，不以“更安全”单独作为依据。
这些原则进入现有开发文档，不给每个测试添加强制元数据，也不引入新的审批流程。

## 7. 完成判据与 AI4S 顺序

阶段 Q 完成应有以下可核验结果：

- 全仓维护领域和测试入口已归类，已确认的重复/无价值约束、错误成功与跨平台发现问题完成处理，保留范围有简短理由；
- 关键数据、权限、线程、上下文和发行行为仍有有效证据，删除的旧证据引用已同步，没有用 skip/吞错或撤销关键 smoke 换取绿灯；
- CI 中同环境的重复执行/构建已按实际收益归并，失败能给出原因，required checks 与真实执行结果一致；
- 使用代表性的文档、UI、Host、kernel/协议及打包变化核对检查选择；有同等执行范围和环境下的前后数据，范围变化单列说明；
- 记录反馈墙钟、重复工作和定位成本的实际变化，不承诺固定分钟数、删减百分比、覆盖率或“永久零抖动”；
- 当前影响正常开发或目标产物使用的已知重大错误已解决，外部平台短暂故障和可选后续优化分别记录，不无限扩大阶段。

采用已有 CI 日志和少量针对性本地/平台运行取得上述证据，不为验收先建设持续性能评测平台，也不要求凑固定次数的全绿。
阶段 Q 收口后进入 AI4S 的 7A–7F；已有设计讨论可继续，既有修复和授权发行按各自产物证据推进，不等待全仓整理完毕。
